# ADR-202609110017-01: 開発方式の背骨を Spec-as-Code へ転換する

## Context

本リポジトリは Claude Code 向けのスキルライブラリであり、その開発は `dev-workflow` プラグインが定める工程（create-issue → refine-issue → plan-issue → implementation → code-reviewer → PR）で回してきた。この方式の前提は「自然言語の成果物を工程ごとに生成し、別コンテキストの LLM が読んで検証する」ことである。

目的（最小限の文書で合意を握りながら高品質なソフトウェアを継続開発する）に対し、この前提から次の症状が観測された。

- Issue 1件のクローズごとに約1.6件の Issue が生まれ、消化速度では収束しない（2026-08-06 実測）。
- 1本の PR でレビュー5周・指摘29件（PR #679）。指摘の多くは条文間の整合であり、製品の振る舞いではない。
- 規約文書を守る検査器、その検査器の変異検査、その適格性の監査、と統治対象が自己増殖している。
- 行番号固定の台帳が、テストへ1行挿入するだけで commit をブロックする。機械ゲートは増えたが、守っている対象が製品ではなく規約になっている。

構造的な原因は、読み手を人間から LLM へ置き換えても「人の目でしか検証できない形式」という問題が消えないことにある。読み手を増やすと読み手ごとに散文の指摘が生まれ、それを裁く工程がまた要る。

代替として Spec-as-Code 方式（ドメインの型と実行可能な例を仕様の正本とし、整合性の検査をコンパイラと CI に委ねる）を設計した。設計書は `docs/development/spec-as-code/design.md`。

射程の限定: 本 ADR は開発方式の背骨と本リポジトリ自身の統治について決める。新方式の内部設計（`期待` の型、並行性の扱い、格子による例の過不足検出など）は設計書が持ち、ここでは決めない。

## Decision

1. `dev-workflow` を開発の背骨から外し、Spec-as-Code 方式を新しい背骨として新プラグインに起こす。`dev-workflow` は残す価値のある部分を新方式へ移したのち退役させる。

2. 本リポジトリは新方式プラグインの置き場として維持し、統治機構を大幅に縮小する。縮小は個別裁定の積み上げではなく、以下の判定規則の機械適用として行う。個別に積み上げると、判定作業そのものが Context に挙げた症状を再生産するため。

3. 文書の判定規則。適用対象は `docs/` 配下の追跡下の資産とし、`.md` 以外（`docs/references/*.json` 等）を含む。gitignore 対象と未追跡のファイルは対象外。存続する配布物（growth / domain-design / dependency-insight / adr / writing（intent 執筆支援）/ 新方式プラグイン）に直接付随する文書を残す。紐づけを持たない横断規約は、次の3カテゴリに当たるものだけ残す。

   - 適用時点の main のリポジトリルート `CLAUDE.md`（縮小着手前の版）が単一出典として参照する文書。参照は推移閉包で取り、残す文書が「条文の受け持ち先」として名指した文書も残す。名指しの1段で切ると、`coding-agent-plugin-design-principles.md` が受け持ち先とした `distribution-boundary.md` / `autonomy-rubric.md` / `cross-host-plugin-conformance.md` が落ち、残る側の原則が条文の置き場を失う
   - 存続する検査器が読む文書。検査器が入力として読み込むものに加え、検査器が符号化している規範の正本を含む。`cross-host-compatibility.json` のように検査器の入力だけが残り、その意味を定める文書が落ちる状態を作らない
   - 自分で実測しないと得られない外部の事実を記録した文書

   3つめは `docs/references/document-permanence.md` §3（恒久的価値のある事実は独立した記録として配置せず、それを要するストック文書の中へ引用する）の例外である。実測の再取得コストが記録の維持コストを上回るため。例外は同文書へも書く。書かなければ、縮小後に同じ判定をやり直したときに逆の結論が出る。

   退役する配布物（`dev-workflow`）を参照している存続文書は、参照を落とすか、参照先の規範を存続資産へ移す。参照を残したまま配布物を消さない。

4. 検査器の判定規則。次の2つだけ残す。

   - 検査の主題がプラグイン共通の構造であるもの（配布物の manifest 形式、host 適合、配布物と配布元の境界）
   - 存続配布物の契約検査

   走査面が複数プラグインに跨ることは「プラグイン共通」の条件にしない。規約文書の条文を配布物の本文へ逐語で当てる検査は、走査面が全プラグインに跨っていても主題は規約の遵守であり、落とす側に入る。

5. 転換期間中、統治機構の縮小作業と新方式プラグインの立ち上げは、`dev-workflow` の工程（Issue・プラン・レビュー契約）を通さず直接コミットで回す。縮小作業は Issue 化しない。存続配布物（growth / domain-design / dependency-insight / adr / writing）の機能変更はこの射程に含めず、従来どおりレビュー契約を通す。利用者へ配る資産の変更が無レビューで入ることを避けるためであり、退行検知は契約レビューの代替にならない。転換期間は、新方式プラグインが本リポジトリ自身の開発を回せるようになった時点で終える。commit ゲート（`scripts/hooks/pre-commit-gate.sh`。`scripts/run-tests.sh` はそこから呼ばれる runner）は退行検知として最後まで残す。

6. ADR 運用は起票・発番・front-matter のスキーマ検査・識別子の一意性とファイル名の検査に縮める。縮めるのは人手の運用であり、機械検査は縮めない。`manage-adr` スキルの遷移操作（承認・上書き・廃止・分割の手順）を本リポジトリでは使わず、縮退した起票と発番の手順をローカルスキルで先行運用する。index 生成・ADR 間参照の双方向性検査・related 参照の妥当性検査は現行のまま回し続け、`index.md` も生成し続ける。`lint-adr.sh` はレイヤ選択の引数を持たず、commit hook が `git commit` のたびに全レイヤを無条件で実行するため、配布物へ手を入れずにレイヤを選ぶ手段が無い。止めるには配布物を編集するか、プラグインごと無効化して残すと定めたスキーマ検査・一意性検査も失うかの二択になり、どちらも割に合わない。

   ローカルスキルの先行運用は、決定5 の転換期間の終わりに、縮退形を配布物へ反映するかローカルスキルを捨てるかを決めて畳む。二重管理を避けるため、ローカルスキルは配布物の手順を複製せず、使う手順だけを持つ。

7. 既存 ADR は群単位で退役させる。退役の表現は `validity: 廃止済み` への変更とし、`docs/adr/archive/` への移動はしない。`lint-adr.sh` / `gen-adr-index.sh` / `next-adr-id.sh` はいずれも `ADR-*.md` のフラット glob でサブディレクトリを走査しないため、移動すると決定6 が残すと定めた検査と発番の対象から外れる（75本の大半が0件照合になり、発番は移動先の識別子との衝突を見なくなる）。`廃止済み` は `gen-adr-index.sh` の索引対象外であり、`lint-adr.sh` レイヤ4 の参照先退役違反が対象とする語彙（`上書き済み` のみ）にも入らないため、残存 ADR からの `Related:` 参照も赤にならない。1件ずつの退役判別は、いずれの群にも属さない7件に限る。

8. OPEN Issue は、存続資産を指すものを機械判定で除いたうえで一括して not planned でクローズする。判定の入力は Issue の title と body に現れるパス文字列とし、決定3・決定4 が確定させた存続資産の一覧と照合する。1件でも一致すれば存続側として残す。ラベルは付与の一貫性がないため入力にしない。クローズ時に、判定に使った入力と照合結果をコメントで残す。残さなければ再オープンの前提が「後で誰かが気づくこと」になり、救済が名目化する。逐語の欠陥確認を全件に課さない代わりに、判定を誤ったものは再オープンで戻す。

### 却下した代替

`dev-workflow` を intent.md 形成の上流工程として縮退させ、以降を新方式へ渡す案。要求の正本が GitHub Issue と intent.md の2か所になり、散文の統治機構が上流に生き残るため、症状の発生源が消えない。

決定2 について、本リポジトリを凍結して新方式プラグインを新リポジトリに起こす案。統治機構が新規開発に一切掛からない利点はあるが、存続配布物5件（growth / domain-design / dependency-insight / adr / writing）の移設と marketplace の二重化を伴い、利用者側の登録先が増える。得られる隔離に見合わない。

決定8 について、148件を1件ずつ検査してクローズする案。1件のクローズごとに約1.6件の Issue が生まれるという実測は、新規起票を伴う個別判定について成立する。クローズ判定それ自体が起票を生むわけではないが、148件の本文を1件ずつ読めば存続資産に残る欠陥の発見がそこで起き、起票の誘因が働く。実測の再生産率はその誘因が働いた結果である。Issue のクローズは再オープンで戻せるため、文書の削除より安全側の操作でもある。

## Consequences

受容したコスト:

- `docs/behavior-invariants.md` は残るが、それを守る検査器（`scripts/tests/behavior-invariants.bats`）は決定4 により落ちる。文書は残り検査だけ消える。同検査は `dev-workflow` 配下のパスを期待値として列挙しているため、決定1 の退役でいずれにせよ成立しなくなる。
- `dev-workflow` の hooks が注入していた完了判定原則が全セッションから消える。原則1〜3 に対応する規定はユーザースコープの `CLAUDE.md` にあるが、`inquiry` 層の4値決着値（解いた / 推移的に決定済み / 前提消滅 / 未決）は対応物を持たず、ここで失われる。
- プロジェクト `CLAUDE.md`「振る舞いの不変条件」節が持つ除外規定（完了判定における全項目の列挙は削減しない）の参照先が消える。決定3 の最終項に従い、参照元の側を直す。
- intent 執筆支援の対象を intent.md に絞るため、配布物の README・SKILL.md・設計書は文章品質の検査を受けなくなる。
- 一括クローズにより、存続資産へ残る欠陥を指していた Issue が閉じられうる。

得られる利益:

- 統治文書と検査器の総量が減り、「規約を守る検査器 → その検査器の検査」の再生産経路が塞がれる。
- 仕様と実装の整合、テストの実効性、完了判定が、散文の読み合わせから機械のゲートへ移る。

適用順序の制約:

- 検査器が、落とす対象の文書を読んでいる箇所がある。切り落としは検査器 → 文書 → ADR の退役の順に行う。
- 制約の対象は「落とす対象を入力として読む箇所」に限らない。落とす対象のパスを期待値として列挙している箇所（`behavior-invariants.bats` が `dev-workflow` 配下のファイルの実在を確かめる形）を含める。
- 配布プラグインが工場側の文書を参照している箇所がある。切り落とし時に例示か実参照かを確かめる。
- 決定3 の3つめのカテゴリを `document-permanence.md` の例外として同文書へ書く作業は、文書の切り落としと同じ回で行う。後回しにすると追跡先を持たない残作業になる。

将来再検討する条件:

- 新方式がプロダクトで回らなかった場合、決定1 が反転する。その場合も決定2〜4 の縮小は独立に成立する（統治総量の削減は方式の成否に依存しない）。
