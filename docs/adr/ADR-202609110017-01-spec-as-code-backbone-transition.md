# ADR-202609110017-01: 開発方式の背骨を Spec-as-Code へ転換する

## Context

本リポジトリは Claude Code 向けのスキルライブラリであり、その開発は `dev-workflow` プラグインが定める工程（create-issue → refine-issue → plan-issue → implementation → code-reviewer → PR）で回してきた。この方式の前提は「自然言語の成果物を工程ごとに生成し、別コンテキストの LLM が読んで検証する」ことである。

目的（最小限の文書で合意を握りながら高品質なソフトウェアを継続開発する）に対し、この前提から次の症状が観測された。

- Issue 1件のクローズごとに約1.6件の Issue が生まれ、消化速度では収束しない（2026-08-06 実測）。
- 1本の PR でレビュー5周・指摘29件（PR #679）。指摘の多くは条文間の整合であり、製品の振る舞いではない。
- 規約文書を守る検査器、その検査器の変異検査、その適格性の監査、と統治対象が自己増殖している。
- 行番号固定の台帳が、テストへ1行挿入するだけで commit をブロックする。機械ゲートは増えたが、守っている対象が製品ではなく規約になっている。

構造的な原因は、読み手を人間から LLM へ置き換えても「人の目でしか検証できない形式」という問題が消えないことにある。読み手を増やすと読み手ごとに散文の指摘が生まれ、それを裁く工程がまた要る。

代替として Spec-as-Code 方式（ドメインの型と実行可能な例を仕様の正本とし、整合性の検査をコンパイラと CI に委ねる）を設計した。設計書は `docs/development/spec-as-code/design.md`。

射程の限定: 本 ADR は開発方式の背骨と本リポジトリ自身の統治について決める。新方式の内部設計（`期待` の型、並行性の扱い、格子による例の過不足検出など）は設計書が持ち、ここでは決めない。

## Decision

1. `dev-workflow` を開発の背骨から外し、Spec-as-Code 方式を新しい背骨として新プラグインに起こす。`dev-workflow` は残す価値のある部分を新方式へ移したのち退役させる。

2. 本リポジトリは新方式プラグインの置き場として維持し、統治機構を大幅に縮小する。縮小は個別裁定の積み上げではなく、以下の判定規則の機械適用として行う。個別に積み上げると、判定作業そのものが Context に挙げた症状を再生産するため。

3. 文書の判定規則。存続する配布物（growth / domain-design / dependency-insight / adr / 新方式プラグイン / intent 執筆支援プラグイン）に直接付随する文書を残す。紐づけを持たない横断規約は、次の3カテゴリに当たるものだけ残す。

   - `CLAUDE.md` が単一出典として参照する文書
   - 存続する検査器が読む文書
   - 自分で実測しないと得られない外部の事実を記録した文書

4. 検査器の判定規則。プラグイン共通の検査と、存続配布物の契約検査だけ残す。

5. 転換期間中、本リポジトリ自身の開発は `dev-workflow` の工程（Issue・プラン・レビュー契約）を通さず直接コミットで回す。縮小作業は Issue 化しない。commit ゲート（`scripts/run-tests.sh`）は退行検知として最後まで残す。

6. ADR 運用は front-matter のスキーマ検査、識別子の一意性とファイル名の検査、および発番のみに縮める。index 生成・ADR 間参照の双方向性検査・related 参照の妥当性検査・`manage-adr` スキルの遷移操作は本リポジトリでは使わない。配布物である `adr` プラグイン本体には手を入れず、縮退形をローカルスキルで先行運用し、運用が成り立った時点でプラグインを置き換える。

7. 既存 ADR は群単位で `docs/adr/archive/` へ移す。1件ずつの退役判別は、いずれの群にも属さない7件に限る。

8. OPEN Issue は、存続資産を指すものを機械判定で除いたうえで一括して not planned でクローズする。逐語の欠陥確認を全件に課さない代わりに、判定を誤ったものは再オープンで戻す。

### 却下した代替

`dev-workflow` を intent.md 形成の上流工程として縮退させ、以降を新方式へ渡す案。要求の正本が GitHub Issue と intent.md の2か所になり、散文の統治機構が上流に生き残るため、症状の発生源が消えない。

決定2 について、本リポジトリを凍結して新方式プラグインを新リポジトリに起こす案。統治機構が新規開発に一切掛からない利点はあるが、存続配布物3件の移設と marketplace の二重化を伴い、利用者側の登録先が増える。得られる隔離に見合わない。

決定8 について、148件を1件ずつ検査してクローズする案。1件のクローズごとに約1.6件の Issue が生まれるという実測がある以上、個別判定の作業そのものが再生産の経路になる。Issue のクローズは再オープンで戻せるため、文書の削除より安全側の操作である。

## Consequences

受容したコスト:

- `docs/behavior-invariants.md` は残るが、それを守る検査器は落ちる。文書は残り検査だけ消える。
- `dev-workflow` の hooks が注入していた完了判定原則が全セッションから消える。同等の規定はユーザースコープの `CLAUDE.md` にある。
- intent 執筆支援の対象を intent.md に絞るため、配布物の README・SKILL.md・設計書は文章品質の検査を受けなくなる。
- 一括クローズにより、存続資産へ残る欠陥を指していた Issue が閉じられうる。

得られる利益:

- 統治文書と検査器の総量が減り、「規約を守る検査器 → その検査器の検査」の再生産経路が塞がれる。
- 仕様と実装の整合、テストの実効性、完了判定が、散文の読み合わせから機械のゲートへ移る。

適用順序の制約:

- 検査器が、落とす対象の文書を読んでいる箇所がある。切り落としは検査器 → 文書 → ADR archive の順に行う。
- 配布プラグインが工場側の文書を参照している箇所がある。切り落とし時に例示か実参照かを確かめる。

将来再検討する条件:

- 新方式がプロダクトで回らなかった場合、決定1 が反転する。その場合も決定2〜4 の縮小は独立に成立する（統治総量の削減は方式の成否に依存しない）。
