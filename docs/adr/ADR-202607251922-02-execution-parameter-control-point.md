# ADR-202607251922-02: 実行パラメータの統制点をサブエージェント定義に集約する

## Context

起票時点の Claude Code では、SKILL.md の front-matter も `model` と `effort` を受け付ける。したがって実行パラメータの統制点をスキル側に置く選択肢が存在する。

本 ADR は実行パラメータをどこで宣言するかに射程を限る。`context: fork`（スキル本文をサブエージェントの指示として実行し、メイン側の文脈消費を抑える機構）は実行パラメータではなく文脈設計の論点であるため、本 ADR では決めない。S3 規律再設定層が引き取るか、独立した課題として起票する。

ただしスキル側の指定が実効値を動かすかどうかは、起動経路によって分かれる。2026-08-06 時点の実測では、対話経路で `model` は実効モデルを変えなかった。スキル本文は展開されるものの、`--model` の明示指定の有無にかかわらず起動時のモデルのまま推移する。一方ヘッドレス（`-p`）経路では宣言値へ切り替わり、以降のターンでも復帰せず、別のスキルを起動するとその宣言値へ上書きされた。この切替はセッションを跨がず、`settings.json` へも書き込まれない。`effort` は 2026-08-05 時点の実測（ヘッドレス経路）で、効果がそのターンに限られ次のプロンプトでセッション値へ戻った。

## Decision

実行パラメータは `agents/{name}.md` の front-matter にのみ置く。SKILL.md の front-matter には `model` と `effort` を置かない。

## Consequences

対話や承認の待ち合わせで複数のターンにまたがるスキルでも、統制が一貫する。スキル側に置かない理由は経路によって異なる。対話経路では `model` が実効モデルを変えないため、統制として成立しない（同経路の `effort` は未確認）。ヘッドレス経路では `effort` が最初のターンにしか効かない一方、`model` は効いた上で持続し、スキルの起動がセッションのモデルを書き換えて残る。効かないことと、意図しない範囲まで効き続けることは、いずれもスキル側を統制点にしない理由になる。

起票時点でサブエージェント側を明示している以上、スキル front-matter の `model` 指定はサブエージェントの実行には届かない。起票時点の解決順は環境変数 → Agent tool の `model` 引数 → サブエージェント定義の front-matter → 親セッションであり、スキル front-matter の指定は、それが効く経路においても、主ループのモデルを差し替える形で最後尾の「親セッション」の位置に入るにとどまる。サブエージェント定義が `model` を明示している限り、この項は参照されない（サブエージェントの実行へ届かない点は `effort` も同じである。実効値を動かすかどうかは上記のとおり経路と対象で分かれる）。

一方で、呼び出し側からの明示指定は定義側の固定値より優先される（起票時点では Agent tool の `model` 引数がこれにあたり、サブエージェント定義の front-matter を上書きした）。このため本 ADR の統制は、呼び出し側で `model` 引数を指定しないことを前提に成立する。スキル本文には「モデルと effort は定義の frontmatter に従い、呼び出し側では指定しない」と明記する。

この前提が掛かるのは、front-matter による固定を選んだ役割である。2026-08-24 時点で、規約の正本に例外が1つ設けられた。水準を呼び出しごとに与える形を採った役割に限り、水準を与える側を統制点とし、その形を採ることを定義の側で明示することを条件とする、というものである。同一の内容を異なる水準で動かす必要が生じても、水準別の定義を複数枚置く形を採った場合は各定義の front-matter が統制点のままであり、この例外には当たらない。この例外は front-matter による固定を配布サブエージェント定義の既定とする本決定を反転させず、統制の前提が掛かる範囲を明示するにとどまる。同時点で例外に当たる配布サブエージェント定義は0件であった。

統制点を2箇所に分散させれば、どちらが効いているかの追跡が難しくなる。

本決定の下では、スキルのメイン側処理（バッチ分割・結果集約・整形）は親セッションの設定で動く。スキル front-matter の `model` でこの部分を下げることは、対話経路では手段として成立せず、ヘッドレス経路では可能だがその効果が当該スキルの処理にとどまらず以降のセッション全体へ波及する。いずれの経路でも採らない。削減の対象はサブエージェントに委譲された処理に限られる。

配布物としての制約も伴う。2026-08-06 時点の実測では、front-matter に存在しないモデル ID を書いた場合フォールバックは起きず、スキル本体が実行されなかった。エラー文言は存在しないモデルとアクセス権のないモデルを区別しないため、利用者のプランで使えないモデルを宣言した場合も同様になる公算が高い（この同一視は未実証）。
