# ADR-202607262019-01: ADR の識別子に時刻部を導入し、並行起票による重複を構造的に防ぐ

## Context

ADR-202607261504-01 が定めた識別子は `ADR-YYYYMMDD-NN-<slug>` であり、採番衝突時の解消手順は「対象日のファイルを配置ディレクトリから列挙し、既存ファイルの最大番号 + 1 を発番する」だった。この手順は、配置ディレクトリについて**単一の直列化されたビュー**が存在することを前提とする。並行ブランチではこの前提が成立しない。

### 実測された重複

2026-07-26、2本の PR がそれぞれ自分の base に対してこの手順を正しく実行し、双方が `-01` / `-02` / `-03` を発番した。結果として同一識別子が2組ずつ corpus に存在する状態になった。drift-lint は識別子の重複を検査しないため exit 0 で通過し、検出しない。手順の欠陥であって運用の逸脱ではない。

同種の重複は旧規約下でも2回発生しており（2026-06-21、2026-06-29）、いずれも1か月以上検出されないまま残っていた。参照側も既に曖昧化しており、同一の識別子文字列が別々の ADR を指す箇所が corpus 内に生じている。

### 時刻だけでも連番だけでも足りない

一方、同一コミットで複数の ADR を起票するバースト（多決定 ADR の分割による後継 N 本など）は、時刻では一意化できない。上記2本の PR ではいずれも3本の ADR が同一秒に作成されている。かつ分割後継が持つ順序は決定クラスタ順であって時間順ではないため、バースト内の順序づけには連番が要る。

したがって識別子には、**ブランチ間の一意性を担う時刻部**と、**バースト内の順序を担う連番部**の両方が要る。

### 発番の実行主体

時刻部を導入すると、起票時に分粒度の時刻が必要になる。ADR-202607261503-01 が定めたライフサイクル操作の tooling 委譲のもとで、採番日は「外部コマンドを実行せず、実行時コンテキストの現在日付から取得する」と規定されていたが、実行時コンテキストが与えるのは日付までであり分粒度の時刻を含まない。操作スキルに生シェルを開く選択は、時刻取得のためだけに権限面を広げる。

## Decision

### 1. ADR のファイル名・識別子は時刻部を含む単一形式とする

```
ADR-YYYYMMDDHHMM-NN-<slug>.md
```

- `YYYYMMDDHHMM`: 起票時刻（分粒度）。**作業者のローカル時刻**から取る。日付部の意味（起票日）を UTC 変換で動かさないため
- `-NN`: 同一時刻部内の連番。`01` 始まりの2桁ゼロ埋めとし、1件目にも `-01` を付与する。同一時刻部99件を上限とする
- `<slug>`: 内容を表す短い英数字ハイフン区切りの文字列

時刻部・連番部の双方を常に必須とし、いずれかを省略した形を作らない。識別子は番号部（`ADR-YYYYMMDDHHMM-NN`）を指し、full slug（ファイル名から `.md` を除いた文字列）とは区別する。相互参照が保持するのは full slug の方である。

### 2. 採番衝突の解消は同一時刻部の内側でのみ最大 + 1 を取る

発番時に列挙するのは、**同一の時刻部を持つ既存ファイルに限る**。配置ディレクトリ全体・同日全体を列挙して最大 + 1 を取る手順は採らない。日単位の最大 + 1 は、並行するブランチがそれぞれ自分の base に対して正しく実行しても同一識別子を生む（上記の実測がその帰結である）。

### 3. 時刻の取得と発番は同梱スクリプトへ委ねる

発番は同梱スクリプト（`next-adr-id.sh`）が担い、時刻部の取得と同一時刻部内の連番決定をスクリプト側へ閉じる。操作スキルは発番手順を自ら組み立てず、スクリプトの出力を識別子として受け取る。ADR-202607261503-01 の tooling 委譲を発番へ及ぼす形であり、許可するコマンドは drift-lint・index 生成と同じ「同梱スクリプトのみ」の枠に収まる。

既存 ADR を遡及的に新形式へ移行する場合、各 ADR の時刻部は git の初回コミット時刻から取る。移行の適用手段（一括スクリプトによるか、操作スキル経由か）は本 ADR では決めず、移行を行う側に委ねる。

## Consequences

**得られる利益**:

- 並行するブランチが互いを見ずに発番しても識別子が衝突しない。マージ時に振り直しを行う必要がなく、ブランチ間の調整も要らない。
- ファイル名の辞書順整列だけで起票順が再現される性質は、corpus 全体が新形式になった時点で維持される。時刻部・連番部とも固定長ゼロ埋めであり、`LC_ALL=C sort` の照合順が時系列と一致する（新旧が混在する期間の例外は下記トレードオフを参照）。
- 発番が機械実行されるため、手順の解釈差が入らない。同一時刻部の内側だけを見るという本 ADR の中核が、実行のたびに再現される。

**受容したトレードオフ**:

- 複数のタイムゾーンにまたがる利用者の間では、辞書順整列と起票順が一致しなくなる。単独利用者による運用を前提として受容する。
- 識別子が長くなる（日付8桁から時刻込み12桁へ）。
- 同一分に別ブランチで起票し、かつ双方が同じ連番を取った場合の重複は残る。時刻部が分粒度である以上これは構造的に消えず、検出は drift-lint 側の検査に委ねる。
- 本 ADR の承認時点では、既存 ADR のファイル名が旧形式のまま残るため、新形式と旧形式が corpus 内で混在する。この期間は同日内で辞書順と起票順が逆転する。`LC_ALL=C` では `-`（0x2D）が数字より前に照合されるため、同じ日付の旧形式が新形式より必ず先に並び、朝に起票された新形式のファイルが夕方に起票された旧形式より後ろへ回る。破れは混在期に限られ、遡及移行の完了とともに解消する。

**将来の留保事項（本 ADR のスコープ外＝ downstream）**:

- 既存 ADR の遡及リネームと、それに伴う full slug 参照・H1 見出しの書き替え、および既に発生している識別子重複の解消は #567 に委ねる。上記の混在はその完了により解消する。
- ファイル名形式の検査と識別子重複の検査を drift-lint へ加えることは、別途扱う。
