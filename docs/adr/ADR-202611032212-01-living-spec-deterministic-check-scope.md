# ADR-202611032212-01: living-spec の検査器が決定的に止める規則の範囲

## Context

living-spec は、仕様の正本（RDRA の表・要求票・例）を2つの担い手で保つ。検査器（`tools/living-spec`）は決定的に判定し、違反を終了コード 1 で返す。PostToolUse フックが、編集のたびにこの検査器を走らせる。突き合わせ（`rule-crosschecker` エージェント）は意味を読み、判定は揺れうる。どの性質をどちらに担わせるかの基準は、定めていなかった。

別リポジトリでの試用の報告（#918 の 1-6）で、この欠落が表に出た。規則 `requirement-name-absent` は、要求票の RDRA 欄に挙げた要素の名前が、同じ行の要求文に部分文字列として現れることを求める。条件名が「〜できる役割である」のとき、要求文は「〜できる役割である条件を満たさないならば」の形でしか通らず、「〜できる役割でなければ」とは書けなかった。

この規則が守りたい性質は「要求文が、欄に挙げた要素を意味の上で扱っていること」である。名前が文字列として現れるかは、その代わりの性質にすぎない。要求文の名前照合を扱う Issue（#920）は当初、照合を緩める（語幹・別名）方向で設計されたが、どの緩め方も代わりの性質の精度を上げるにとどまった。

射程の外: 突き合わせへ足す観点の文面、名前照合の Issue（#920）の受入条件の書き直し、判断の知識（ドメインごとに要るアーキテクチャ特性など）の置き場は、本 ADR では決めない。

## Decision

1. 検査器の違反（赤）に置く規則は、赤が出たら正本に直すべき欠陥（書式の欠け・参照の切れ・層間の追跡の切れ）が必ずあるものに限る。守りたい性質を、代わりの性質で判定する規則は置かない。この基準は、判定に要る情報がファイルの中で閉じることを含む
2. `requirement-name-absent` を撤去する。要求文が欄の要素を扱っているかは、突き合わせの観点として見る
3. 違反とは別の、注意（終了コード 0 のまま出す提示）の段は設けない

却下した案と理由:

- 照合の精度を上げて赤に残す（語幹の一致など）: 正しく書いた略称（「経費申請」を指す「申請」）を赤にする。名前は文にあるが指すものが違う欠陥は見逃す。たとえば欄に「承認者」、文に「承認者の上長が承認する」とある場合である。誤検出と見逃しの両方が残る。
- 書き手が誤検出を打ち消せる形で赤に残す（表の別名キー・要求文中の印）: 検査を通すためだけの記述が正本に入り、業務の事実は増えない。指すものの違いも見逃す。
- 注意として出す: 得るのは「欄に挙げたが文が触れていない」ことの手がかりだけで、それも正しい文への注意に混ざる。それに対して CLI の出力の形式と終了コードの意味が1段増える。
- 突き合わせへ照合の結果を手がかりとして渡す: 突き合わせのエージェントはもともと全文を読むので、得るものが受け渡しの経路の費用に見合わない。

## Consequences

- 正しく書いた要求文が赤になることは無くなる。書式の「名前を活用させずに使う」という指示は、規則の撤去に合わせて書き直す
- 受け入れた不利益: 欄に挙げた要素に要求文が触れていない欠陥は、編集の直後ではなく突き合わせの時点で見つかる。スキルを通さずに直接編集した場合は、突き合わせを起動するまで見つからない
- 名前は文にあるが指すものが違う欠陥は、突き合わせで拾える。照合の規則では、この欠陥を拾えなかった
- 可視化で要求文中の要素を強調する処理は、検査ではないので本決定の外にある。名前がそのまま現れたときだけ囲む表示として残せる
- 以後、検査器へ規則を足すときは決定1 の基準を当てる。「必須キーの有無」のように判定がファイルの中で閉じ、欠ければ必ず欠陥になるものは赤に置ける。「レコードがいつ書かれたか」のようにファイルの外の情報を要るものは置けない
- 再検討の条件: 欄と文の対応の欠陥を、突き合わせが繰り返し取りこぼす事例が出たとき

兄弟の方式である Spec-as-Code の設計（`docs/development/spec-as-code/design.md`）も、2026-11-03 時点で同じ向きの判断を持っていた。辞書と要求本文の突き合わせのうち、規則で正解が決まるものだけを赤にし、精度が測られていない照合は提示に留めていた。本 ADR が提示の段も採らないのは、living-spec の検査結果を受け取るのが主に書き手の AI であり、人が PR で読み流す提示とは前提が違うためである。
