# ADR-202611040903-01: ポリシーとアクターを、実行手段に依存しない業務上の役割で定義する

## Context

本 ADR 起票時点の domain-design は、ポリシーを「自動の反応」と定義し、アクターを実装の状態で分類していた。

- event-storming の Design Level の手順は、ポリシーを「〜したとき自動的に〜する」自動化ルールと定義していた。アクターの種別も「人間／外部システム／ポリシー／時間トリガー」で分けていた。
- domain-modeling の手順は、ポリシーを「自動発火するコマンド」として問うていた。記法ガイドは、ポリシーから参照されないコマンドを「外部指示由来」と消去法で判定していた。

この定義には2つの欠陥があった。

1. イベントを契機に人が判断して操作する反応を書けない。例は「PR がマージされたら、リリースノートを更新する」である。人の業務を含むドメインをモデル化すると、この反応は自動のポリシーへ押し込まれるか、モデルの外へ落ちる。
2. モデルが実装の状態を抱え込む。同じ業務の規則でも、自動化したりシステム化したりすると、ポリシーの有無やアクターの種別が変わる。ドメインモデルは業務の規則を表すもので、誰がどの手段で実行しているかに左右されるべきではない。

本リポジトリ自身の開発コンテキストのモデル（#909 で削除）は、独立した「運用ルール」の節を設けて1の欠陥を凌いでいた。

**前例**: ADR-202605131437-05 は、開発コンテキストのモデルについて次を定めた。人間アクターとエージェントアクターは同じコマンド・同じドメインイベントを共有し、エージェント固有の挙動はアクター内部実装として扱う。本 ADR は、担い手をモデルの外に置くこの原則を、domain-design の記法の一般規則へ広げる。新しい定義では、同 ADR の「人間アクター／エージェントアクター」は役割ではなく担い手にあたり、モデルの外の割り当てとして読み替える。同 ADR の決定は本 ADR と矛盾しないため、上書きしない。

**4決定を1本に束ねる根拠**は2つある。

1. 本 ADR 起票時点の #912 の受入条件 AC6 は、同 Issue の方針節の全決定と、却下した選択肢の全項目を、1本の新規 ADR に記録することを求めていた。
2. 4決定は互いの語を参照し合う。ポリシーの実行者・アクター表・ワークフローの公開先は、どれも役割を参照する。記法ガイドと両スキルの手順も、1回の改訂で同時に書き換える。

**独立に反転しうる下位決定**: 決定1（ポリシー）のうち次の3つは、「担い手をモデルの外に置く」原則から導かれず、他の決定と独立に反転しうる。

- きっかけは1つに限る。
- 時刻を、イベントとは別種のきっかけにする。
- `実行するコマンド:` にワークフロー名も書ける。

本 ADR 起票時点の雛形は、独立に反転しうる決定を別 ADR へ分けるとしていた。この3つはその条件に当たるが、上の2つの根拠により本 ADR に束ねた。

**射程の限定**: 本 ADR は次を決めない。

- 記法ガイドの他の規定（共通値の判定基準、ワークフローの粒度、失敗の扱い）の見直し。ただし、これらの節の中でも、本 ADR の定義と矛盾する文面の言い換えは行う。
- データとしての `開発者` 等の型の扱いの変更。
- 利用者が既に書いたモデル文書の移行手段（移行スクリプト・移行ガイド）の提供。
- 役割と担い手の対応を管理する仕組み。
- 業務上の意味を持つ時刻（締め日等）を名前で定義する仕組み。

## Decision

### 決定1: ポリシー

- ポリシーは「契機に対して、どの役割がどのコマンドを発行するかを定める業務上の規則」とする。定義から「自動」を外す。
- 全てのポリシーに `実行者:` 欄を必須で書く。値は役割の名前とする。
- 実行者は複数書ける。意味は「いずれかが実行する」（OR）に限り、`実行者: リリース担当 OR 開発担当` と書く。1回のきっかけについて実行するのは、いずれか1つの役割である。これは本 ADR 起票時点の記法ガイドの `OR` と同じ排他選択である。
- 結合演算子の `OR` の結果型に「単一の役割」を足し、適用文脈にポリシーの実行者の用法を足す。複数の役割が分担する共同作業は、発行するコマンドが別なので、ポリシーやイベントの連鎖を分けて書く。
- `きっかけ:` には、内部イベント、`外部_` イベント、時刻のいずれかを書く。時刻はイベントとは別の種類のきっかけとし、`きっかけ: 時刻 毎月末日の0時` の形で書く。
- 時刻は定義を要しない。どの集約の状態変化からも生まれず、発火元の集約を持たないためである。
- 1つのポリシーのきっかけは1つに限る。「A と B が両方そろったら」という観測は、集約が状態として持ち、そろった時点で1つのイベント（例: `承認がそろった`）を発火する。ポリシーはそのイベントをきっかけにする。
- 「A または B で同じことをする」は、ポリシーを分けて書く。本 ADR 起票時点の定義にあった「複数イベントの観測 → 1コマンド発行の集約点」は、集約の側へ移る。ポリシーは観測の状態を持たない反応とする。
- 欄名は `実行するコマンド:` のまま変えず、この欄にはコマンド名のほかワークフロー名も書けるとする。例は「月末になったら、経理担当が月次締めを行う」である。欄名を変えないのは、既存のモデルのポリシーの欄名を書き換えずに済むためである。
- ワークフローを実行するポリシーは集約に属さないため、ワークフローの節に置く。
- 名前の形（「〜ポリシー」接尾辞）は変えない。

```
リリースノート更新ポリシー:
    きっかけ: PRがマージされた
    実行者: リリース担当
    実行するコマンド: リリースノートを更新する

在庫引当ポリシー:
    きっかけ: 注文が確定した
    実行者: 在庫管理担当
    実行するコマンド: 在庫を引き当てる
```

却下した選択肢:

- **`実行者:` を人間が実行するポリシーにだけ書き、欄が無ければ自動とする**: 自動化すると欄の有無が変わり、モデルの構造が実装の状態に依存する。書き忘れも、黙って自動として読まれる。
- **`実行者:` を任意とし、省略時はそのコンテキスト（作るシステム）自身が実行するとみなす**: システムが存在することを前提にした読み方へ戻る。
- **独立した種別（「〜運用ルール」等）を新設する**: 新しい語と種別が要る。Event Storming の語彙からも外れる。
- **複数の実行者を配列で書く**: 本 ADR 起票時点の記法ガイドでは、イベント発火の配列は全てを発火する意味であり、OR と読ませるとその読みと衝突する。
- **1つのポリシーに複数のきっかけ（`きっかけ: A AND B` / `A OR B`）を許す**: どこまで観測したかという状態をポリシーが暗黙に抱え、モデルに現れない。「そろった」は業務の事実なので、名前のあるイベントとして集約に置く。
- **複数のきっかけの書式を定めず、「集約点・条件分岐」の説明文を補足として残す**: 定義と書式が食い違ったまま残る。
- **ポリシーが実行できるのをコマンドに限り、時刻起点の集約横断処理を単一コマンドの連鎖に分解する**: 業務上ひとまとまりの処理（月次締め等）が、記法の都合でイベントの連鎖に崩れて見えなくなる。
- **時刻もイベントとして定義させる**: 本 ADR 起票時点の記法ガイドが定める「イベントは発火元の集約に1か所だけ定義する」規則の例外を作る。
- **時刻を過去形（「毎日0時になった」）のまま書き、定義の要求からだけ外す**: 名前からイベントか時刻か判別できず、イベントの定義漏れと区別できない。

### 決定2: 役割

- アクターは業務上の役割とする（例: リリース担当・倉庫担当・顧客）。役割を人・AI エージェント・システムのどれが担うかは、モデルの外の割り当てとする。担当者が変わっても、自動化しても、モデルは変わらない。
- 役割と担い手の対応表は、モデルに置かない。担い手の割り当ては、運用文書やエージェント定義など、配置を管理する側が持つ。
- 役割は、ドメインモデル文書の独立した節 `役割` で定義する。この節は共通値と同じ階層に置き、役割名と責務を1行ずつ書く。入力や属性の型として現れるデータとしての `開発者` 等とは、別の名前空間とする。
- `実行者:` の値は、同じ文書で定義した役割に限る。未定義の名前は、イベント・コマンドと同じく文書の不備として扱う。
- 役割名は名詞句のままでよく、名前の形による種別の判別の対象外とする。役割は `役割` 節と `実行者:` 欄にだけ現れ、型の位置（入力・属性・状態）には現れないため、置き場所で種別が決まる。データとしての `顧客` と役割としての `顧客` が同名でも、現れる位置が重ならない。
- 役割と外部の相手の線は、コンテキスト境界で引く。こちらのコンテキストでコマンドを発行する者は、組織の外の者（例: 顧客）でも役割とする。
- 別のコンテキストで起きた出来事だけが届く相手（例: 決済代行）は役割にしない。その出来事を `外部_` イベントとして、こちらのポリシーの `きっかけ:` に書く。event-storming の成果物のポリシー表でも、そのきっかけのイベント名に `外部_` を前置きする。
- 記法ガイドの中でデータを「アクター」と呼んでいる文面は、人物のデータを指す語へ言い換え、「アクター」は役割の意味でだけ使う。同じく、一般語として「役割」を使っている文面も言い換え、「役割」は定義した用語の意味でだけ使う。

却下した選択肢:

- **実行者の値を人・AI エージェント・外部システム等の担い手にする**: 担い手は運用上の配置で、変わることが前提である。モデルに書くと、自動化のたびにモデルが変わる。
- **外部の相手（例: 決済代行）を役割として定義し、実行者に書けるようにする**: 外部の相手が何をするかは、こちらの業務の責務ではない。こちらに見えるのは、外部で起きた出来事だけである。
- **役割と外部の線を組織の内外で引く（顧客も外部とし、`外部_注文が申し込まれた` 等で受ける）**: 組織図がモデルに入る。顧客が直接行う操作が全てイベントの受け取りに置き換わり、業務の規則と無関係な区別を持ち込む。
- **役割を共通値・集約固有の型として置く**: データとしての人物と、業務上の責務が同じ名前に重なる。本 ADR 起票時点の共通値の配置規則（2集約以上で参照）が役割にも掛かり、役割の集合が集約の中に散る。
- **event-storming のポリシー表に、きっかけの出どころを示す列を足す**: 表の列が増え、テンプレートと domain-modeling の読み込みにも追随が要る。ドメインモデルの記法が既に持つ `外部_` の前置きで足りる。
- **event-storming では区別せず、domain-modeling に任せる**: event-storming の成果物だけでは、きっかけの出来事の出どころを判別できない。
- **データを「アクター」と呼ぶ既存の文面を残し、既知の不整合として記録する**: 新しく決めた用語の規律を、それを書いた文書自身が破る。
- **役割名に固有の名前の形（「〜担当」「〜者」等の接尾辞）を必須にする**: 「顧客」を「購入者」等へ言い換えさせることになり、利用者が業務で使う語から離れる。

### 決定3: アクター表とコマンド

- event-storming のアクター表から、種別列（人間／外部システム／ポリシー／時間トリガー）を廃止する。各値はどれも実装の状態の分類で、決定2 の役割の定義と矛盾する。ポリシーはアクター表の行にせず、ポリシー表に書く。
- 記法ガイドから、ポリシーから参照されないコマンドを「外部指示由来」と消去法で判定する規定を削る。本 ADR 起票時点の domain-design には、この区別を入力に取る手順や検査は無かった。「ポリシー由来コマンドの駆動経路は `実行するコマンド` から逆引きできる」旨は残す。
- event-storming と domain-modeling の問いでは、「人の操作か、自動の処理か」「誰が（何が）」を問わない。代わりに「何をきっかけに発行されるか（イベント・時刻・担い手の自発）」と「どの役割が担うか」を問う。
- event-storming のアクター表は役割の一覧とし、「責務」の列を持つ。アクターを洗い出すときに責務も問う。ポリシー表の実行者は、アクター表に挙がった役割に限る。
- domain-modeling は、event-storming のアクター表を読み、役割名と責務を `役割` 節へ引き継ぐ。
- 記法ガイドの中で、データとしての `開発者` 等を呼び出す者の意味で使っている文面は、役割の意味と混ざらないよう言い換える。

却下した選択肢:

- **アクター表の種別から「ポリシー」だけを外し、他の種別を残す**: 残る「人間／外部システム」も、自動化やシステム化で値が変わる実装の分類である。
- **役割の責務を domain-modeling の段階で聞き取る（Auto モードでは推定する）**: 役割の定義が業務を発見する段階より後へずれ、Auto モードでは推測が入る。

### 決定4: ワークフロー

- ワークフローの公開先は「他コンテキスト・役割」とする。本 ADR 起票時点の記法ガイドが挙げていた公開先「他コンテキスト・UI・スケジューラ等」のうち、UI とスケジューラは担い手（実装）の名前で、決定2 の役割の定義と矛盾する。
- 時刻で動く振る舞いは、時刻をきっかけにしたポリシーとして書く。
- ワークフローの粒度（集約横断のものだけを書く等）は変えない。

却下した選択肢:

- **ワークフローの公開先の列挙（UI・スケジューラ等）を OUT として残す**: 担い手をモデルの外に置く規律と食い違う文面が、同じ文書に残る。

### 適用範囲と追随の判定（4決定に共通）

- 4決定は、domain-design 配下の全体に及ぶ。記法ガイド・両スキルの手順・テンプレートのうち、ポリシー・役割・きっかけ・ワークフローの定義と矛盾する記述は、節を問わず追随させる。
- 追随の要否は、語の検索ではなく意味で判定する。定義と矛盾するかを文ごとに読み、改めた箇所と、検討して残した箇所を理由とともに挙げる。

却下した選択肢:

- **行単位の追随を、語の検索の網で受入条件に列挙する**: 中核概念の再定義の波及は語を変えて現れ（「発火」「API」「日次バッチ」等）、網から漏れる。追随は意味で判定する。

## Consequences

得られる利益:

- 人が判断して行う反応と自動で動く反応を、同じ欄の同じ記法で書ける。人の業務を含むドメインでも、反応がモデルの外へ落ちない。
- 自動化・システム化・担当者の交代で、モデルの構造が変わらない。変わるのはモデルの外にある担い手の割り当てだけである。

受け入れた不利益:

- 本 ADR 起票時点の自動のポリシーの例（記法ガイド・Design Level の手順・テンプレート）は、全て `実行者:` を書き足す必要がある。利用者が既に書いたモデルも、次に更新するときに `実行者:` 欄と `役割` 節を足す必要がある。
- アクター表から種別の手がかりが消える。アクターの洗い出しは、きっかけと役割の問いで補う。
