# ADR-202611140016-01: 共有の記憶を扱う機能を、growth の拡張ではなく独立プラグイン shared-memory として起こす

## Context

人間と AI が開発で得た知識・経験・判断基準を、利用者が所有する Git リポジトリへ蓄積し、次の作業で再利用する仕組み（Shared Memory）を作ることになった。

本リポジトリには、学びを扱う配布物として growth が既に在った。起票時点（2026-11-14）の growth は、Shared Memory と重なる面を2つ持っていた。

- 規範へ畳めない一回性の判断は、決定の記録として残す。配る先は ADR である。
- 学びの置き場には、プラグインで配る空間のほかに、チームやプロジェクト向けの閉じた空間がある。閉じた空間の実体は、利用者が管理するリポジトリやストレージに置く。

したがって「決定を残す」「利用者のリポジトリへ置く」という点では、両者は対立しない。対立するのは、置き場の形と、そこへ至る経路である。起票時点の growth は次を定めていた。

- 学びの置き場は、どちらの空間でも1つのファイルである。各エントリは見出しと本文だけを持ち、メタデータを持たない。
- 効かなくなった学びは、ファイルから物理的に除去する。置き換え済みのような中間の状態を残さない。経緯は git の履歴で辿る。
- 空間をまたぐ参照を持たない。除去のたびに、リポジトリ内の知識を1つの変更で整理し直せるようにするためである。
- 規範にも決定の記録にもならない気付きは捨てる。事実としての知識や、作業の経験そのものは残さない。
- 未検証の観測は、利用者の端末の `~/.claude/` 配下へ置く。
- 検証を通った仮説は Issue として起票し、人間が Issue 上で裁定する。

これらは、足場を太らせないという growth の設計原理から導かれていた。Shared Memory が求めるものは、このそれぞれと両立しない。

- 記録は1件ずつ、識別子・出典・検証状況・確信度・適用条件を持つ。
- 古い考えは消さずに残し、何がなぜ変わったかを追える形にする。
- プロジェクトは、別のリポジトリに在る記録を、版を固定して指す。昇格した記録は、元の層の記録を出典として指す。
- 知識と経験を、規範へ畳まずに残す。
- クラウドのセッションで使う。端末の領域は、セッションが終わると消える。
- 追加と修正は PR として出す。

**射程の限定**: 本 ADR は、機能をどの配布単位へ置くかだけを決める。記録の形式、索引の構造、参照と更新の手順は決めない。growth を将来どう扱うか（存続・統合・退役）も決めない。開発をどの工程で回すかも決めない。

## Decision

共有の記憶を扱う機能を、growth へ足さず、独立したプラグイン `shared-memory` として起こす。

growth からは、コードも保存形式も引き継がない。引き継ぐのは次の考え方に限る。

- 観測した事実と、その解釈を分けて記録する。
- 未検証のものを、長く残す記憶へ入れない。
- 機械で強制できる知識は lint やテストへ移し、文章の記憶から外す。

**却下した代替**:

- **growth を拡張する**: growth の置き場は、メタデータを持たないこと・物理的に除去すること・空間をまたぐ参照を持たないことを前提にしている。Shared Memory の記録は、この3つのいずれとも逆の形を要する。同じ置き場の上では両立しない。別の置き場を growth へ足すと、growth の中に、設計原理の異なる2つの置き場が並ぶ。
- **growth を置き換える**: growth は、検証を経た規範を、プラグインの配布の経路で他の利用者へ配る役割を持つ。Shared Memory は、この役割を担わない。置き換えると、その役割の担い手が無くなる。
- **growth の観測の段だけを共用する**: growth の観測は、端末の `~/.claude/` 配下へ書く。クラウドのセッションでは残らない。置き場を変えて共用するにも、配布物は他の配布物を参照できない。観測の段を第三のプラグインへ切り出すか、写しを持つことになる。前者は配布単位を増やし、後者は正本を2つにする。

## Consequences

- 学びを扱う配布物が2つになる。利用者は、どちらが何を担うかを知る必要がある。growth は検証を経た規範と決定の記録を配り、shared-memory は記録を1件ずつ蓄積して参照させる。
- 決定の記録は、どちらの配布物からも ADR へ向かう。shared-memory は ADR を指すだけにし、決定を重ねて持たない。
- growth の設計原理に縛られずに、記録の形式を決められる。
- 観測と仮説形成の考え方が、2つの配布物に別々に実装される。片方の改善は、もう片方へ自動では届かない。
- shared-memory が動き出したのち、growth の役割が実際に使われているかを見て、growth の扱いを判断する。
