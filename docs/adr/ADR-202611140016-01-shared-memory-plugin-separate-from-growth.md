# ADR-202611140016-01: 共有の記憶を扱う機能を、growth の拡張ではなく独立プラグイン shared-memory として起こす

## Context

人間と AI が開発で得た知識・経験・判断基準を、利用者が所有する Git リポジトリへ蓄積し、次の作業で再利用する仕組み（Shared Memory）を作ることになった。

本リポジトリには、学びを扱う配布物として growth が既に在った。起票時点（2026-11-14）の growth は、次の設計を採っていた。

- 保存するのは「次回どう違う行動を取るか」という規範だけである。記述的な知識は保存しない。当時の設計文書は、保存中心のナレッジ管理は形骸化すると述べていた。
- 配布する学びはメタデータを持たない。1つの見出しと本文だけで表す。
- 効かなくなった学びは、ファイルから物理的に除去する。経緯は git の履歴で辿る。
- 学びを配る先は、プラグインの全利用者である。配布の経路はプラグインそのものである。
- 未検証の観測は、利用者の端末の `~/.claude/` 配下へ置く。
- 検証を通った仮説は Issue として起票し、人間が Issue 上で裁定する。

Shared Memory が求めるものは、このそれぞれと逆を向いていた。

- 規範だけでなく、知識・経験・決定・考え方の変遷を保存する。
- 記録は、識別子・出典・検証状況・確信度・適用条件を持つ。
- 古い考えは消さずに残し、何がなぜ変わったかを追える形にする。
- 蓄積する先は、利用者が所有する別のリポジトリである。プラグインの利用者へ配らない。
- クラウドのセッションで使う。端末の領域は、セッションが終わると消える。
- 追加と修正は PR として出し、人間が PR で承認する。

**射程の限定**: 本 ADR は、機能をどの配布単位へ置くかだけを決める。記録の形式、索引の構造、参照と更新の手順は決めない。growth を将来どう扱うか（存続・統合・退役）も決めない。

## Decision

共有の記憶を扱う機能を、growth へ足さず、独立したプラグイン `shared-memory` として起こす。

growth からは、コードも保存形式も引き継がない。引き継ぐのは次の考え方に限る。

- 観測した事実と、その解釈を分けて記録する。
- 未検証のものを、長く残す記憶へ入れない。
- 機械で強制できる知識は lint やテストへ移し、文章の記憶から外す。

**却下した代替**:

- **growth を拡張する**: growth の保存形式（メタデータなし・物理除去）と、Shared Memory の保存形式（メタデータあり・変遷を残す）は、同じ成果物の上で両立しない。両立させるには growth の設計原理を外すことになり、growth の既存の契約を壊す。growth は存続する配布物であり、機能変更にはレビュー契約が要る。新しい機能の試行錯誤が、その工程を毎回通ることにもなる。
- **growth を置き換える**: growth が担う「プラグインの全利用者へ規範を配る」という役割を、Shared Memory は担わない。置き換えると、その役割の担い手が無くなる。
- **growth の観測の段だけを共用する**: 配布物は他の配布物を参照できない。共用するには、観測の段を第三のプラグインへ切り出すか、写しを持つことになる。前者は配布単位を増やし、後者は正本を2つにする。

## Consequences

- 学びを扱う配布物が2つになる。利用者は、どちらが何を担うかを知る必要がある。growth は全利用者へ配る振る舞いの規範を担い、shared-memory は利用者が所有する記憶を担う。
- growth の設計原理に縛られずに、記録の形式を決められる。
- 観測と仮説形成の考え方が、2つの配布物に別々に実装される。片方の改善は、もう片方へ自動では届かない。
- shared-memory が動き出したのち、growth の役割が実際に使われているかを見て、growth の扱いを判断する。
