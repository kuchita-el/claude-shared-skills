# ADR-202611141115-01: 命名規約に固有の ADR 化の振り分けを持たず、一般則で判定する

## Context

ADR-202608011354-01 決定2 は、命名規約を構造的か書式的かで振り分け、書式的なものを ADR の外に置くと定めた。判断に迷う場合のタイブレーカーは「ツールで自動強制できる規約は ADR 外」である。

この振り分けを運用する `manage-adr` の参照ファイルでは、規定が次の形になっていた。

- 書式的の特徴は「表記に閉じる・原理的にツール強制可能」であり、ADR の「局所・ツール強制可能」から述語が変わっていた
- タイブレーカーは、原理的に強制できるかを問う形で読まれていた。構造的の例（ファイル配置規約・集約名・ドメイン用語統一）は、いずれも原理的には強制できる。字義どおり適用すると、構造的の例が書式的へ移る
- 射程と適用順を整えた結果、一般則に無い規範として残ったのは1点だけだった。書式的な命名規約は、強制が未実装で粒度判定の合計が3点に届いても ADR 外とする、という例外である
- この例外の理由は「強制が未実装であることは、記録すべき設計判断ではなく実装の欠落である」だった。この理由は命名規約に固有でなく、どの規範にも等しく当たる

理由の射程が規定の射程より広く、規定を命名規約に閉じて残す根拠が無い。

## Decision

1. 命名規約に固有の ADR 化の振り分け（構造的／書式的の表と、書式的なら強制が未実装でも ADR 外とする例外）を持たない。命名規約も他の規範と同じく、却下代替の必要条件・粒度判定基準・判定結果の行き先の一般則で判定する。

**却下した代替**:

- **節を残し、タイブレーカーの時制だけを直す**: 現在時制へ揃えると、タイブレーカーは粒度判定の項目4（阻止の状態）と同じ問いになる。残る固有の規範は上記の例外1点であり、その理由は命名規約に固有でない。命名規約に閉じた節として残す根拠が無い。
- **例外をすべての規範へ広げる（原理的にツールで強制できる規範は、強制が未実装でも ADR 外とする）**: 「原理的に強制できるか」は、判定者によって結論が割れる。旧表の構造的の例もこの述語を満たし、振り分けが表の例と食い違った。一般則は阻止の状態を現在時制の3語で問い（項目4）、規範を担う資産が在れば「ADR 化しない」の第1分岐へ置く。強制を実装すれば規範の置き場所が実装になる経路は、一般則がすでに持つ。

## Consequences

- 強制が未実装の書式的な命名規約は、粒度判定の合計が3点に届けば ADR 化の側へ進む（起票の時点の判定を含む）。旧規定では表が ADR 外に固定していた。強制を実装すれば項目4は0点になり、規範を担う資産が在れば第1分岐に置かれる。
- 旧規定を根拠に ADR を起こさなかった判断は、根拠を失う。本リポジトリでは、`docs/development/adr-plugin-design-guideline.md` の同梱スクリプトの実行形の節がこれに当たり、一般則で判定し直した。
- 旧表の構造的の例に当たる既存 ADR（ADR-202607261503-03 など）は、本決定で状態を変えない。粒度判定は起票の前段の判定であり、既存 ADR の退役は格下げ判定が扱う。
- ADR-202608011354-01 の扱い: 決定2 を反転するので、本来は同 ADR を分割し、本 ADR を反転側に置く。ADR-202609110017-01 決定6 が転換期間中の遷移操作を止めている。そのため同 ADR の状態は変えず、本 ADR から `Related:` で指すにとどめる。転換期間の間、同 ADR 決定2 は `有効` のまま運用ルールと食い違う。分割は、転換期間の終わりに遷移操作をどう扱うかと併せて決める。
