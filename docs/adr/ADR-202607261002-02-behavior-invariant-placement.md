# ADR-202607261002-02: 振る舞いの規律を共有 references の単一出典に置き、配布物からポインタ参照する

## Context

本 ADR の起票時点（2026-07-26）で、実行時規約である `context-budget.md`（ADR-202606270040-01）を参照していたのは CLAUDE.md のみで、SKILL.md からもサブエージェント定義からも参照されていなかった。CLAUDE.md は配布物に同梱されないため、**第三者がプラグインを導入した環境にはこの規約が届いていない**。

S2（プロンプト適応層）の規律は、配布先の実行環境で効かなければ目的を達しない。したがって配置層を決める必要がある。候補は、各 SKILL.md 本文への直接埋め込み（確実に届くが12スキルへ重複記述となり drift 源になる）、サブエージェント定義のみ（S1 と統制点は揃うがメインループの挙動に届かない）、共有 references の単一出典＋ポインタ参照、の3つであった。

あわせて、成果物の分量をどこで縛るかの責務も定める必要がある。出力形式テンプレートは「どの節が、どの順で、どの型で並ぶか」を定義するものであり、散文の分量は内容側の性質である。両者を同一ファイルへ混ぜると、形式を変えるたびに分量規定が巻き添えになる。

## Decision

1. 振る舞いの規律は `plugins/dev-workflow/references/behavior-invariants.md` を**単一出典**とし、各 SKILL.md とサブエージェント定義からは1行のポインタで参照する。規約本文を参照側へ転記しない。
2. 責務を分離する。**どの節が存在するか**は各出力形式テンプレートが定義し（定義外の節を追加しない旨をテンプレート側に明記する）、**節の中身の分量**は本規約が扱う。
3. 実行時の規律は2軸に分ける。データフロー軸（メイン context に何を載せるか）は `context-budget.md`、生成・範囲軸（どれだけ書くか・どこまでやるか）は `behavior-invariants.md`。内容を重複させない。
4. 読者で置き場所を分ける。実行主体が実行中に読む規律は `behavior-invariants.md` に置き、スキル作者がスキル定義を書く際の規律（同一文脈での再確認を新たに指示しない等）は作成時軸の CLAUDE.md 側に置く。`behavior-invariants.md` は実行主体向けに純化する。

## Consequences

- CLAUDE.md 経由のみだった従来の参照経路の欠落を塞ぎ、配布環境へ届く経路が確立する。
- ポインタ挿入により SKILL.md 本文が各1行増える。適用後の最大は当時の計測で `dependency-check` の158行であり、170行規律の範囲内に収まっていた。
- 実効性は「スキルが実行時にポインタ先を Read する」ことに依存する。Read されなければ規約は効かない。この依存は既存の共有参照（DoR デフォルト等）と同じ構造であり、本決定が新たに導入するリスクではない。
- サブエージェント定義から共有 references へ到達する経路は、当時 `issue-refiner` / `issue-refiner-batch` の2本にしか整備されていなかった。`plan` / `plan-reviewer` は経路の新設が必要であり、`code-reviewer` / `test-designer` / `test-spec-validator` / `refactorer` は dev-workflow のスキルが起動しないため呼び出し側が存在しない（S1 で判明した統制外経路と同じ範囲）。これらは本決定の射程外とし、follow-up で扱う（#578 / #579）。
- 既存の `context-budget.md` も当時は配布物からの参照経路を持たなかった。同ファイルの読者が実行主体かスキル作者かの判定自体が未決であるため、本決定ではポインタを張らない。読者が作者であれば参照経路の欠落ではなく文書の性質ということになるが、その場合は作者向け規約が配布プラグイン配下に置かれている点が配置として不自然になる。判定と配置は follow-up で扱う（#580）。ADR-202606270040-01 は同ファイルを `dor-default.md` / `completion-judgment.md` と同型の分割と位置づけており、判定次第では同 ADR の上書き手続きを要する。
- 対象は dev-workflow プラグインに限る。`adr` / `growth` は独立配布であり、`growth` は当時 dev-workflow との疎結合を設計として明記しており、単一出典を跨いで参照できない。横展開は実害が観測されてから follow-up で扱う（#581）。
