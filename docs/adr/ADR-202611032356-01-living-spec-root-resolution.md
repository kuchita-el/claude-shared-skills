# ADR-202611032356-01: living-spec の正本の根を、ファイルから上へ辿って最も近い目印で決め、置き場をその根に属させる

## Context

living-spec の根は、`.living-spec.json` と、表・要求票・例の置き場を解決する基点である。2026-11-03 時点で、根は経路ごとに別の決め方をしていた。

- CLI の `check [根]`・`render [根]` は、引数のパスを根にしていた。引数が無ければ作業ディレクトリを根にしていた
- PostToolUse フックは、`CLAUDE_PROJECT_DIR` を根にしていた。それが無ければフック入力の `cwd` を根にしていた。根に表の置き場が無ければ、何もせず終了コード 0 で終わっていた
- スキル（`structure`・`crosscheck`・`view`）は、根の引数を付けずに中継（`scripts/run.mjs`）経由で `check`・`render` を実行していた。検査器は作業ディレクトリを根にしていた。Bash ツールの環境では `CLAUDE_PROJECT_DIR` は空だった
- 書式は、`.living-spec.json` を「根（リポジトリのルート）」に置くと定めていた

別リポジトリでの試用（#918 の 2-2）では、領域のディレクトリを根として CLI に渡し、そこに `.living-spec.json` を置く形で検査と描画が動いた。試用者は、この形を「1 リポジトリに複数の正本を持つ使い方」として書式に書き足すよう求めた。しかしこの形では、フックは `CLAUDE_PROJECT_DIR` に表の置き場を見つけられず、何も検査しない。利用者は編集のたびに検査されていると信じたまま、検査されない状態になる。作業ディレクトリが領域へ移っているときは、スキルとフックが別の根を見る。

要求「根はリポジトリのルートでなくてよい」を満たすには、フックを含む全ての経路が同じ規則で根を決める必要がある。さらに、ある根の検査が読むファイルを編集したとき、フックがその根を検査しなければならない。そうでなければ、CLI は読むのにフックは黙るファイルが残る。

射程の外: 複数の根をまたぐ一括の検査・描画と、根をまたぐ参照（別の根の UC を遷移 UC にする等）は、本 ADR では決めない。置き場のキーの値域を狭める（決定1）ほかは、`.living-spec.json` の既存キーの意味を変えない。

## Decision

1. 正本の根は、起点から上へ辿って最も近い目印のディレクトリとする。根の置き場は、その根に属さなければならない
   - 目印: `.living-spec.json` を持つディレクトリと、既定の表の置き場（`docs/rdra`）をディレクトリとして直下に持つディレクトリを、根の目印とする。後者は、中身が `{}` の `.living-spec.json` を持つものとみなす。両方を持つディレクトリでは、`.living-spec.json` が置き場を決める。ただし `docs` か `docs/rdra` が自身の `.living-spec.json` を持つときは、その `docs/rdra` を親の目印に数えない。設定を持つ側が根になり、誰も設定していない親が根になることを防ぐ。親を根にすると、親の既定の表の置き場が設定を持つ根の中に入り、親から実行した CLI が設定の誤りで止まる。`docs/rdra` を目印に含めるのは、設定を置かない正本が、書式の認める既存の形だからである（全てのキーは省略できる）
   - 起点: フックでは編集したファイル、CLI では引数のパスとする。CLI で引数が無ければ作業ディレクトリとする。ルートと領域の両方に目印があるとき（入れ子）は、起点に最も近い目印が根になる。境界まで目印が無ければ、正本は無い
   - 境界: 起点から上へ辿って最初に見つかる、submodule でない `.git` を持つディレクトリを境界とし、そこより上へは辿らない。境界のディレクトリ自身は目印になりうる。submodule の `.git` は境界にしない。submodule は親の作業ツリーの一部であり、親はそれを gitlink として記録するからである。worktree の `.git` は境界にする。既定のチェックアウトの下に置いた worktree の中の編集が、外側のチェックアウトの設定を根にしないためである。git の外では境界を設けない
   - 根を決めるのに `CLAUDE_PROJECT_DIR` は使わない。フックが相対の `file_path` を絶対パスにするときの基点にだけ使う。スキルが Bash から呼ぶ CLI の環境では同変数が空になるため、根に使うと、同じ起点でフックとスキルが別の根を見うる
   - 置き場はその根に属する: 根の置き場（表・要求票・例。`.living-spec.json` の値か既定）のそれぞれについて、置き場から同じ規則で上へ辿って最も近い目印が、その根自身でなければならない。外れる設定は設定の誤りとする。外れる形は3つある。置き場が `..` で根の外へ出る形と、別の根の中に入る形と、根と置き場の間に境界がある形である。別の根の中に入る例は、`tables` を、`docs/rdra` を直下に持つ `<X>` の `<X>/docs/rdra` に向ける設定である。置き場の値の先頭以外に `docs/rdra` の並びがある設定は、作ればその上のディレクトリが目印になるので、置き場がまだ無くても別の根の中に入る形の誤りとする。この検証により、根の検査が読むどのファイル（根の置き場の直下のファイルと根の `.living-spec.json`）でも、そのファイルから上へ辿って見つかる根は、その根自身になる。パスは字面のまま比べ、シンボリックリンクは解かない
   - 経路: フックも CLI も、起点から根を決め、根の置き場がその根に属することを確かめてから根を検査する。設定の誤りは、フックと CLI が同じ文面を出して終了コード 2 で終わる。両者の差は、起動のされ方から来る次の3点だけとする。1つは範囲で、フックは、編集したファイルが根の置き場のどれかの直下のファイルか根の `.living-spec.json` のときだけ検査と描き直しを行い、それ以外の編集では何もしない。ただし根の `.living-spec.json` を読めないときは、範囲を決められないので、フックは根が決まる全ての編集で止まる。2つ目は正本が無いとき（目印が見つからないか、根に表の置き場が無い）で、フックは何もせず終了コード 0 で終わり、CLI は終了コード 2 で終わる。3つ目は根が決まる前の探索でファイルを読めないときで、フックは何もせず終了コード 0 で終わり、CLI は終了コード 2 で終わる。根が決まる前は、編集がどの正本に関わるかが分からず、living-spec を使わない木の編集まで止めることになるためである。根が決まった後の探索で読めないときは、フックも CLI と同じ文面で終了コード 2 で終わる。根の `.living-spec.json` が `hook` を偽にしていれば、フックは従来どおり何もしない
   - 範囲を置き場の直下で定めるのは、検査器が置き場の直下だけを読むからである（表は `<tables>/<id>.yaml`、要求票・例は置き場の直下の `*.md`・`*.feature`）。置き場の下の全てを範囲に入れると、検査器が読まない深い階層のファイルまで読まれると扱い、根の置き場が別の領域の祖先を指す構成で、誰も読まない正本を検査済みと誤認させる
   - 範囲の判定: 範囲の判定と、範囲外の対象を独立した正本にする扱いの判定は、起動した場所 L と対象 T の組で行う。L は、フックでは `CLAUDE_PROJECT_DIR`（無ければフック入力の `cwd`）、CLI では作業ディレクトリとする。T は、フックでは編集したファイル、CLI では引数とする。T が無ければ T = L とする。根は T から決め、L は根を変えない。T が範囲内（根の置き場の直下のファイル、根の `.living-spec.json`、根の置き場そのものか、それを含むディレクトリ）なら、どの経路も、L と根の位置の関係によらず根を検査する。T が範囲外で対象を明示したときは、フックは何もせず、CLI は根を検査して標準エラーに注記を出す。注記は、T が根の置き場の外にあることと、扱い2つ（T を根の置き場へ移す／T の領域を独立した正本にする）を示し、終了コードは検査の結果のままとする。独立させる根の候補は、次の条件を全て満たすときだけ L とし、そうでなければ候補を示さない。L が今の根より下にあって T を含むこと、今の根の置き場がどれも L の中に無いこと（L 自身も置き場でない）、L がどの置き場の中にも無いことである。T が無いときは、根を検査し、注記は出さない
   - 出力: `check` は標準出力の1行目に `根: <絶対パス>` を出す。`render` の標準出力は書き出した場所のまま変えない。`render` が止まるときは標準出力を空にし、根は標準エラーの文面に含める
2. 根の探索・置き場の検証・範囲の判定は検査器だけが持ち、フック・CLI・スキルはそれを共用する。範囲の判定は検査器の1つの関数に置く。スキルは探索もパスの比較も自前で行わず、扱っているファイルを起点として `check`・`render` に渡し、CLI の注記を利用者へ伝えて扱いを尋ねる
3. 1 リポジトリに根を複数持てる。各根は独立した正本であり、可視化の書き出し先 `output` は根からの相対のままとする

却下した案と理由:

- 文書で「根はリポジトリのルートに限る」と宣言する: 要求の側を狭める。試用で動いていた、領域ごとに正本を持つ使い方を書式の外へ追い出す（2026-11-03 判断）
- 文書で「フックの根はプロジェクトルート」と境界を宣言する: 領域に根を置いた利用者は、フックが働かないことを知らないまま使い続ける。要求を満たさない
- ルートの `.living-spec.json` に根の一覧を列挙する: 設定を一覧と各根の 2 か所に持つことになり、片方だけ直したときに食い違う。ファイルの位置から導ける情報を、人に書かせることにもなる
- 根を決めるのに `CLAUDE_PROJECT_DIR` を使う: 探索の上限を `CLAUDE_PROJECT_DIR` 優先にする案と、`.git` が無いときに起点を含む `CLAUDE_PROJECT_DIR` を上限にする案がある。どちらも、スキルが Bash から呼ぶ CLI の環境では同変数が空になり、同じ起点でフックとスキルの上限が食い違う。`CLAUDE_PROJECT_DIR` は既定のチェックアウトを指すので、その下に置いた worktree での編集は、外側のチェックアウトの設定を根にしうる。CLI に `CLAUDE_PROJECT_DIR` の外のパスを渡すと根がずれ、引数のパスに目印があれば根は従来と同じ、という性質も崩れる
- 設定が見つからないときだけ `CLAUDE_PROJECT_DIR` を根にする: フックの退行は消えるが、スキルが呼ぶ CLI の環境では同変数が空なので、その構成でフックとスキルが別の根を見る
- submodule の `.git` も境界にする: ルートの `docs` が submodule の構成で、ルートの表の編集から上へ辿る道が submodule の境で切れ、ルートの正本の編集でフックが黙る。現行（`CLAUDE_PROJECT_DIR` を根にする）からの退行である
- 根の目印を `.living-spec.json` だけにする: 設定を置かない正本（ルートの既定の置き場も含む）には目印が無くなる。根を与えるには「境界を根にする」等の別の決め方を足すことになり、設定を置かない領域の正本がその根に吸われ、フックが黙る。設定を置くよう文書で案内しても、読まない利用者の環境では黙ったまま残る
- 2段の探索（`.living-spec.json` を優先し、どこにも無いときだけ `docs/rdra` を目印にする）: 設定のある根の下に、設定の無い `docs/rdra` を置いた領域が根にならない。その領域の正本は誰も読まないのに、編集したファイルの根は上の根になり、黙るか、止めて案内する仕組みが要る。優先順を置いた理由は、設定が表の置き場を `<X>/docs/rdra` に向けた構成で、X を根と誤認しないことだった。決定1 の置き場の検証がこの設定を誤りにするので、優先順が守るものは無くなった
- 根にならない `docs/rdra`（設定の無い領域）の置き場で、フックと CLI を止めて案内する: 止める対象・案内の2通り・案内を妨げるものの定義を、構成ごとに足すことになった。2周の独立レビューで、submodule の `docs`、`..` で根の外を指す置き場、置き場の種類をまたぐ一致、案内に従うと別の根が生まれる構成のように、黙る構成と、案内に従うと重なりへ導く構成が出続けた。原因は、上へ辿って見つかる根と、ファイルを読む根の食い違いを、止めの側で個別に埋めていたことにある。目印を1段にして置き場を検証すれば、根にならない `docs/rdra` が存在しなくなり、止める仕組み自体が要らない
- 2段の探索と止めの仕組みを保ち、置き場の外れを設定の誤りにして止めの規則を単純にする（2026-11-05 の案）: 止めの仕組みと、根にならない `docs/rdra` を見つけて案内する判定が残る。決定1 の置き場の検証は、この案の外れの条件を引き継いだものである
- `docs` か `docs/rdra` の設定によらず、その `docs/rdra` を親の目印に数える: 親の既定の表の置き場が別の根の中に入る。誰も設定していない親が根になり、親から実行した CLI が設定の誤りで止まる。避けるには、利用者が下の根の表の置き場の名前を変えるか、親から実行するときも起点に下の根を渡す必要がある。目印の側で数えなければ、この状態そのものが生まれない
- 値の先頭以外に `docs/rdra` の並びを含む置き場を、置き場がまだ無いうちは誤りにしない: 設定を書いた時点では通り、最初のファイルを作った時点で初めて止まる。`tables` では、作る前は表の置き場が無いと扱われ、誤りが見えない。作ればその上のディレクトリが目印になることは値だけで決まるので、作る前から誤りにできる
- 範囲の判定をスキル側で行う（スキルが起点と `check` の示す根を比べる）: 判定が検査器と SKILL.md の2か所に立つ。手でパスを比べる手順には、読み違えが残る
- 範囲外の明示の対象で、CLI を終了コード 2 で止める: コードのディレクトリ等からスキルを使うたびに止まる。目印を1段にした規則では、範囲外の対象を検査しても黙る正本は生まれず、止める理由が無い
- パスを、シンボリックリンクを解いた実体で比べる: 根の外を指すリンクの置き場も設定の誤りにでき、根の中のリンクを通した置き場も、どちらの名前で編集しても範囲に入る。しかし置き場をリンクにする構成はまれで、現行のフックも字面で比べているので退行ではない。全てのパスの解決、まだ無いパスの扱い、表示するパスの選び方を足す費用に見合わない。ハードリンクや綴りの違いは、実体で比べても解けない

## Consequences

- 正本を領域のディレクトリに置いても、編集のたびの検査と描き直しが掛かる。置き場がその根に属する根では、置き場の名前どおりのパスで編集する限り、CLI が読むどのファイルの編集でも、フックが同じ根を検査する
- ルートに `.living-spec.json` を置く形と、置かずに既定の置き場を使う形は、根が変わらないので検査の結果も変わらない
- 受け入れた変化: CLI の引数のパスは、根そのものではなく起点として扱われる。目印を持たないディレクトリを引数に渡すと、上へ辿って見つかった根が根になる。そのディレクトリに目印があれば、根は従来と同じになる。CLI はファイルも起点として受ける
- 受け入れた変化: フックの根は、`CLAUDE_PROJECT_DIR` ではなく編集したファイルから決まる。`CLAUDE_PROJECT_DIR` の外（別の worktree・別のリポジトリ）の正本の編集も、その正本の根で検査される
- 受け入れた変化: フックの範囲は、根の置き場の下の全てから、置き場の直下のファイルと根の `.living-spec.json` へ狭まる。置き場の下の深い階層のファイルを編集しても、描き直さない。検査器はそのファイルを読まないので、検査の結果は変わらない
- 受け入れた変化: `check` の標準出力の1行目に根が出る。どの正本が検査されたかが利用者に見え、`crosscheck` は `rule-crosschecker` へ渡す根をそこから取れる
- 受け入れた変化: `.living-spec.json` の `hook` は、その根の編集にだけ効く。従来はフックの根が `CLAUDE_PROJECT_DIR` だったので、ルートに `hook: false` を置けば、セッションの全ての編集でフックが止まっていた。設定の無い領域や別の根の編集では、既定の `hook: true` が効く
- 受け入れた費用: 置き場のキーの値域が狭まる。`..` で根の外を指す置き場、値の先頭以外に `docs/rdra` の並びを含む置き場（`<X>/docs/rdra` 等。作れば X が根になる）、submodule でない別の作業ツリーの中の置き場は、従来は CLI で読めたが、設定の誤りになる。値の先頭以外に `docs/rdra` の並びを含む置き場は、まだ作っていなくても誤りになる
- 受け入れた費用: 設定のある根の下の、設定の無い領域の正本は、その領域を根として新たに検査される。これまで検査されていなかった違反が出うる
- 受け入れた費用: フックだけが黙る構成が2つ残る。1つ目は、根が決まる前の探索でファイルを読めない構成（読めない `.gitmodules` 等）の中の編集である。living-spec を使わない木の編集を、祖先の読み取りの失敗で止めないための費用である。その木を起点にした CLI は終了コード 2 で止まるので、誤りは CLI で見える。2つ目は、根に属さない置き場の中のファイルの編集である。そのファイルから上へ辿って見つかる根は、設定を書いた根ではないためである。従来のフックは、`CLAUDE_PROJECT_DIR` の根から置き場の下を前方一致で見ていたので、この編集も検査していた。その根を起点にした CLI は、設定の誤りで止まる。その根の範囲内に境界の手前で編集できるファイル（根の `.living-spec.json` 等）があれば、その編集でのフックも止まる。そうしたファイルが無い構成（設定の無い根の置き場が全て境界の向こうにある等）では、誤りを示すのは CLI だけである
- 受け入れた費用: パスは字面で比べるので、同じファイルを別の名前で指せる構成（シンボリックリンク、ハードリンク、大文字小文字や Unicode の正規化の違う綴り）で、置き場の名前と違うパスで編集すると、フックは黙る。根の外を指すリンクの置き場も、設定の誤りにならない。現行のフックも字面で比べていたので、退行ではない
- 受け入れた費用: git の外では境界が無いので、無関係な祖先ディレクトリの目印を根に拾いうる。`check` の1行目に根が出るので、黙ってはいない
- 再検討の条件: 根をまたぐ参照や一括の検査が要る事例が出たときは、根を独立とする決定3 を見直す。根の外に置き場を共有したい事例が出たときは、決定1 の置き場の値域を見直す
