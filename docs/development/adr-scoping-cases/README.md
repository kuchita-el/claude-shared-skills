# 固定題材集合の実行手順書

`plugins/adr/skills/manage-adr/references/adr-scoping.md`（以下「対象文書」）を被テスト対象とする固定題材集合について、何のためのものか・何が置かれているか・どう通すか・結果をどう読むかを定める。

## 1. この題材集合の位置づけ

対象文書の判定手続きは、改訂すると帰結が動く。動いたことに気付けるのは、同じ入力を改訂の前後で通し、出てきた帰結を突き合わせたときだけである。本題材集合は、その「同じ入力」を固定して保持するためのものであり、**対象文書を改訂する編集の時点で帰結の差を見る**ことを目的とする。改訂の是非を決めるものではなく、改訂が何を動かしたかを見えるようにするものである。

本題材集合は Issue #604 が挙げた分割案1（判定仕様の退行検出）の成果物である。同じ Issue の分割案2（対象文書が満たすべき不変条件の点検）とは別系統であり、互いを代替しない。不変条件の点検は文書の記述そのものを検査するのに対し、本題材集合は文書を読んだ判定者が出す帰結を検査する。

## 2. 成果物一覧と各ファイルの責務

### 2.1 ファイルと配布物内／外の別

| ファイル | 責務 | 配布物との関係 |
|---|---|---|
| `docs/development/adr-scoping-cases/cases.md` | 題材文層。判定側へ渡る唯一の入力（`### 題材文` 見出しの下の本文ブロック）を持つ | 配布物外 |
| `docs/development/adr-scoping-cases/expectations.tsv` | 期待帰結層。題材ごとの導出すべきもの・期待値・由来・対の相手ID・出所・備考を持つ。**判定側へは渡らない** | 配布物外 |
| `docs/development/adr-scoping-cases/prompt-template.md` | 判定プロンプトの雛形。入力の限定・参照禁止対象・返却形式を定める | 配布物外 |
| `docs/development/adr-scoping-cases/sources.md` | 題材の出所台帳。各題材が PR #603 のどの巡のどの入力に由来するかを持つ | 配布物外 |
| `docs/development/adr-scoping-cases/README.md`（本書） | 実行手順書 | 配布物外 |
| `docs/development/adr-scoping-cases/runs/<実行日>-judgments.tsv` | 判定記録。題材 × 試行 × 項目の粒度で判定を残す | 配布物外 |
| `docs/development/adr-scoping-cases/runs/<実行日>-report.md` | 集計レポート。試行間一致・期待帰結との差・差の帰属を残す | 配布物外 |
| `docs/development/adr-scoping-cases/runs/<実行日>-raw-returns.md` | 判定側の返却全文。`judgments.tsv` の根拠列・行き先列はこれを人手で符号化した派生物であり、符号化の妥当性を後から確かめるための原文 | 配布物外 |
| `docs/development/adr-scoping-cases/<実行日>-<主題>.md` | 判別記録。対象文書の特定の規定について、判定を分けているかを判別した単発の調査の結論と根拠。`runs/` 配下（題材 × 試行の判定記録）とは別系統であり、独立2試行の手順に乗らない調査を置く | 配布物外 |
| `plugins/adr/scripts/adr-scoping-cases.sh` | 実行支援スクリプト。`prompt` / `validate` / `report` の3サブコマンドを持つ | **配布物内** |
| `scripts/tests/adr-scoping-cases-basic.bats` | 上記スクリプトのテスト（基本系。サブコマンドと fixture の組み合わせ） | 配布物外 |
| `scripts/tests/adr-scoping-cases-edge.bats` | 上記スクリプトのテスト（特殊系。環境操作を伴うもの） | 配布物外 |
| `scripts/fixtures/adr-scoping-cases/` | 上記テストが使う fixture（正常系・異常系の最小の題材集合。本リポジトリのデータを含まない当て馬） | 配布物外 |

実行支援スクリプトだけが配布物内に在る。これは検査器であり、**題材集合ディレクトリと対象文書パスをすべて引数で受けて既定値を持たない**ため、本リポジトリ固有のデータ（ディレクトリ構成・対象文書名・題材の中身）を一切持たない。逆に、題材集合・記録・レポートは本リポジトリ固有のデータであるため配布物外に置く。

**テストと fixture を配布物外へ置く境界は `docs/distribution-boundary.md` が定める。** その根拠は本書に置かない（前段の配布物内／外の別も同文書 §2 の判断軸に従う）。本題材集合に固有の事実として、この一方向性はアサーション42（配布元リポジトリ固有の名前が検査器のコードパスへ現れないことの走査）で機械検査している。

なお検査器は**引数の取り方**において汎用だが、スキーマまで可変という意味ではない。題材集合のスキーマ側は固定値として持っている（規範の担い方の3値、由来の2値、`expectations.tsv` の12列、項目1〜4 の4項目）。別の判定手続き文書へ持ち込む場合、パスは引数で差し替えられるが、これらの語彙・列構成は検査器の改修を要する。

このうち**規範の担い方の3値は、配布物内のコード（`adr-scoping-cases.sh` の `case` 文）が事実上の唯一の定義**になっている。値の意味は次のとおり。

| 値 | 意味 |
|---|---|
| `体現・強制` | 資産が規範そのものを体現している（実装本体・スキーマ・雛形・fixture 等）。散文で述べるのではなく、その資産の内容自体が規範になっている |
| `散文のみ` | 資産が規範を文章で述べているだけで、体現も強制もしていない |
| `なし` | 規範を担う資産が現に存在しない（実行者の記憶にのみ在る） |

由来の2値の定義は §10「由来の付け方」と `expectations.tsv` の注記行にある。

判定を担うサブエージェントが読むのは、組み立て済みのプロンプトファイルと対象文書だけである。`expectations.tsv` が別ファイルへ分離されているのはこのためであり、期待帰結が題材文と同居すると、判定側が対象文書を読まずに答えを再生できてしまい退行検出力が失われる。

### 2.2 題材を足すときの契約（題材文の必須要素）

`cases.md` へ題材を足す場合、題材文は次の (a)〜(i) をすべて備えること。いずれも対象文書が判定の入力として名指しする**事実**であり、対象文書が結論として述べる述語（値域を満たす／段1で確定する／条件Nに当たる／○点、およびその言い換え）は書かない。

- (a) 決定の内容
- (b) 規範が現に置かれている資産とその種別
- (c) その資産が規範を体現・強制しているか、散文で述べているだけか
- (d) 採用理由が現に書かれている場所と、その内容を確かめられるかどうか
- (e) 却下した選択肢・受け入れた不利益の有無とその中身
- (f) 反転時に直す必要のあるファイルと、影響が及ぶ単位
- (g) 反転が「配置・分割・命名の規約変更」「スキーマ・データ形式の変更」「既に配布された成果物の利用者側への影響」「蓄積済みデータの移行」のいずれを伴うか（いずれも伴わないならその旨）
- (h) 決定を知らない作業者が独立に別の選択をする箇所が現にいくつあるか（無いならその旨）
- (i) その規範に従う作業者が単独か複数か

(f)(g) を欠くと項目1・項目2 の期待値が確定しない。対象文書の項目1 は本数の条件に加えて OR 条件（非本数条件4種）を持つため、本数だけを書いた題材文からは OR が成立しないことを言えないからである。項目2 は本数条件のみで決まるため、(f) が述べる「影響が及ぶ単位」だけで確定する。

**(h) はどの項目の点数にも効かない distractor である。** 対象文書の項目2 はかつて非本数条件（決定を知らない作業者が独立に別の選択をする箇所が現に複数あれば1点）を OR で持っており、(h) はその入力として立てられた要素だった。Issue #641 が同条件を削除したため入力としての役割は失われている。それでも必須要素から外さないのは、判定側がこの事実を数えて項目2 を1点にしていないかを測るためである。**(h) を根拠に項目2 が1点になっている判定記録が現れたら、それは退行の徴候として読む。**

(i) は判定結果の行き先の分岐が入力として名指しする事実であり（「複数の作業者・複数の箇所へ効かせたい規範」の分岐）、これを欠くと行き先の期待値が一意に決まらない。**作業者の人数は項目2 の入力ではない**（対象文書の項目2 がそう明示している）。(i) は行き先だけに効く。

### 2.3 期待値の導出が割れた場合の扱い

`expectations.tsv` の期待値を人手で導出する際、値が一意に決まらないことがある。扱いは割れの原因で分ける。

- **割れの原因が題材文の事実の不足に帰属できる場合**: (a)〜(i) の欠落として `cases.md` へ事実を足し、一意に決まる状態にしてから導出し直す。
- **題材文が (a)〜(i) を備えているのに、規範本文の読みが分かれて割れる場合**: いずれか一方を暫定の期待値として置き、割れた候補値・割れた理由・どちらを採ったかを `expectations.tsv` の備考へ記録したうえで、集計レポートの帰属分析（規範側の一意性の欠陥か、題材文の記述密度の不足か）へ回す。

いずれの場合も、**題材を初期集合から外すことはしない。** また、規範側の欠陥と判断したものは記録に留め、対象文書は改訂しない。

### 2.4 据え置いた題材文の記述（次に `cases.md` を触る担い手向け）

判定へ影響していないと確かめたうえで、記述としては改善余地を残したまま据え置いた箇所がある。同じ指摘が繰り返されるのを避けるため、判断とその根拠をここへ残す。

- **CASE-13・CASE-18・CASE-20 の「この規範に関係する資産は2つある。」（`cases.md:161` / `:221` / `:245`）**
  - 経緯: 3巡目まで `この規範を書くとすれば、置き場所の候補になるのは…` と書いていたが、`書くとすれば` が対象文書の条件3 の判定枠組みを名指しする語であるため落とし、現在の文へ置き換えた。
  - 残る問題: 直前の「規範を体現・強制する資産も、規範を散文で述べた記述も、現に存在しない」と読み合わせにくい。**「現に2資産に置かれている」とも読めてしまう**。CASE-17 / CASE-18 は出所欄が明記するとおり「規範の現在の所在を書き分けた対」なので、読みが所在側へ倒れると対の設計意図が弱まる。
  - 判断: **据え置いた。** 判定結果には表れていない（3題材×独立2試行＝6試行とも項目3=1。`runs/2026-07-29-raw-returns.md` の該当6行——CASE-13 は `:392` / `:408`、CASE-18 は `:536` / `:552`、CASE-20 は `:608` / `:624`——はいずれも置き場所ではなく「分かれざるを得なさ」として読んでいる）。一方 `cases.md` の改訂は記録済みの判定を無効化し、この6試行の再実行を要する。観測できる改善が無いまま再実行コストを払う判断を PR #616 では採らなかった。
  - 次に触るとき: `書くとすれば` を含まずに「関係の種類」（所在ではなく、規範が効く先の構成）を明示する書き方へ直す余地がある。#619・#620・#624 で当該題材を再実行する機会があれば、そこへ相乗りするのが最も安い。

## 3. 実行手順

コマンドは題材集合ディレクトリを毎回明示して書く。スクリプトは既定値を持たないため、省略形は使えない。

### 手順1: 題材集合の内部整合を検査する

```bash
bash plugins/adr/scripts/adr-scoping-cases.sh validate docs/development/adr-scoping-cases
```

exit 0（「題材集合の検査に通った」）を確認する。落ちた場合は `[NG]` 行が指す欠落・不整合を直してから先へ進む。**この検査に通らないまま判定を始めない。** 期待帰結が欠けたまま通すと、判定は得られても差の突き合わせができない。

### 手順2: 記録ファイルを用意する

`docs/development/adr-scoping-cases/runs/<実行日>-judgments.tsv` を作り、先頭へ `#` 始まりの注記行を置く。注記には、対象文書のパス、実行日、担い手、および**この2試行が測っているのは同一入力に対する判定の再現性であること**を書く。対象文書と題材集合の commit は行ごとに異なりうるため注記へは書かず、列で持つ（下記14列目・15列目）。続けて列見出し行を置く。列は次の15列（タブ区切り）。

`題材ID` / `試行番号` / `項目1` / `項目2` / `項目3` / `項目4` / `合計` / `行き先` / `根拠_項目1` / `根拠_項目2` / `根拠_項目3` / `根拠_項目4` / `参照ファイル一覧` / `対象文書commit` / `題材集合commit`

`対象文書commit` に入れるのは、判定を実行した時点の対象文書の commit（短縮ハッシュ）である。試行の途中で対象文書が動かないことを、この列で後から確かめられるようにする。

`題材集合commit` に入れるのは、判定を実行した時点の `cases.md` の commit（短縮ハッシュ）である。改訂前後の2レポートを突き合わせる前提は題材文が同一であることなので、この列が無いと、帰結の差が対象文書の改訂によるものか題材文の変更によるものかを行単位で切り分けられない。題材文を直して一部の題材だけをやり直した場合、その行だけが別の値を持つことになる。**行ごとに実際の値を入れる。実行全体で1つの値を注記行へ書いて済ませない。**

### 手順3: 題材1件分のプロンプトを組み立てる

題材ID と試行番号の組ごとに1回実行する。

```bash
bash plugins/adr/scripts/adr-scoping-cases.sh prompt \
  plugins/adr/skills/manage-adr/references/adr-scoping.md \
  CASE-01 \
  docs/development/adr-scoping-cases
```

標準出力へ返るのは、組み立て済みプロンプトを書き出した一時ファイルのパス1行だけである。プロンプト本文は標準出力へ流れない。呼び出し側は本文を読まず、返ったパスだけを次の手順へ渡す。

### 手順4: 判定サブエージェントを起動する

手順3 が返したパスを渡し、そのファイルを読んで判定するよう指示する。返却は雛形が定める構造化サマリ（項目1〜4 の点数・合計・行き先・各項目の根拠1行・参照ファイル一覧）のみを受け取る。

### 手順5: 事後検査を行い、通った返却だけを記録へ書く

§7 の事後検査を行う。返却の全文を `runs/<実行日>-raw-returns.md` へ転記したうえで（§7.2）、通った返却を1行として手順2 の記録ファイルへ追記する。落ちた試行は無効として破棄し、破棄の事実を記録の注記行へ残したうえで、その題材・その試行をやり直す。ただし実行基盤の自動注入による逸脱は破棄しない（§7.1）。

### 手順6: 一時ファイルを削除する

`prompt` は呼ぶたびに新しい一時ファイルを作る。使い終えたファイルは削除する。放置すると題材数 × 試行数だけ溜まる。

### 手順7: 全題材 × 2試行が揃ったら集計する

```bash
bash plugins/adr/scripts/adr-scoping-cases.sh report \
  docs/development/adr-scoping-cases/runs/<実行日>-judgments.tsv \
  docs/development/adr-scoping-cases
```

出力は4区画（カバレッジ／試行間一致／各項目の1点率／期待帰結との差）である。カバレッジ検査に落ちる（未カバーの題材・題材集合に無い題材ID・重複行のいずれかがある）と非0で終わる。exit 0 を確認したうえで、出力を集計レポート `runs/<実行日>-report.md` へ貼り、§9 に従って読む。

## 4. 実行主体

起動するのは人間である。判定は、題材1件につき1つの**汎用サブエージェント**が行う。本題材集合のために新規のサブエージェント定義は作らない。判定の内容は対象文書の現行本文とプロンプト雛形だけで決まるべきものであり、エージェント定義側に判定の作法を持たせると、対象文書を改訂しても帰結が動かない余地が生まれるためである。

スクリプトが担うのは入力の組み立て・題材集合の内部整合の検査・判定記録の集計の3つだけであり、判定の真偽をシェルで決めることはしない。

## 5. 入力の限定と参照禁止対象

判定側が読んでよいのは次の2つだけである。

1. 組み立て済みのプロンプトファイル（題材文1件分と対象文書パスを含む）
2. 対象文書

**判定の入力は、題材文に書かれた事実と対象文書の現行本文に限る。改訂の経緯・レビュー履歴は入力に含めない。** これらを読めば、判定者は対象文書の現行本文が導く帰結ではなく、過去にそう判定された結果を再生できてしまい、対象文書を改訂しても帰結が動かなくなる。

参照禁止対象は次のとおり（雛形が判定側へ提示するものと同一）。

- 対象文書の変更履歴、過去のコミット、差分
- Pull Request や Issue の本文・コメント・レビュー記録
- 過去の判定記録、集計レポート、期待帰結を記した資料（`expectations.tsv` を含む）
- プロンプトファイルが置かれているディレクトリの他のファイル
- リポジトリ内の他の文書（対象文書が明示的に参照するファイルを除く）

題材文に必要な事実が書かれていないと判定側が感じた場合も、事実を推測で補わせない。対象文書が定める同点処理に従わせ、補えなかった事実を根拠欄へ書かせる。

## 6. 独立2試行の作り方

題材は**1件ずつ**渡す。試行ごとに**新規コンテキストのサブエージェントを起動し、前試行の判定・記録・他題材の判定を一切引き継がせない**。独立性の根拠はこの点だけに置く。

**この設計で測っているのは、同一入力に対する判定の再現性である。隣接題材の文脈効果は測っていない。** 1件渡しでは判定側の入力に他の題材が現れないため、文脈効果は最初から発生せず、測定の対象にもならない。集計レポートと判定記録の注記行にも同じ射程を明記する。

先例（`docs/development/adr-scope-observation.md` §1.3）は2回目の試行でバッチの切り方を変えているが、これはバッチ内の隣接文脈を消すための操作である。1件渡しではバッチが存在せず、投入順は判定側の入力に一切影響しないため、投入順を変えても2つの試行は同一入力の再実行にしかならない。したがって本手順では投入順の変更を独立性の根拠に用いない。

担い手（モデル・エージェント種別・プロンプト）を変えた試行を追加することはできるが、それが測るのは**判定者間信頼性**であり、同一入力に対する再現性とは別の量である。追加しても本手順の2試行には数えない。追加する場合は、担い手が異なる旨を記録の注記行へ明記して区別する。

## 7. 事後検査

各試行の返却について、`参照ファイル` 欄を検査する。**対象文書とプロンプトファイル以外のパスが挙がっていないこと**を確かめる。挙がっていた場合、その試行は入力の限定に違反しているため**無効として破棄**し、破棄した事実（題材ID・試行番号・読まれてしまったファイル）を判定記録の注記行へ残したうえで、当該題材・当該試行をやり直す。

この検査は入力の限定が守られたかを事後に確かめる唯一の手段であり、省略すると、参照禁止対象を読んだ判定が記録へ紛れ込んだまま集計へ入る。

### 7.1 破棄では解消しない逸脱（実行基盤による自動注入）

判定側が**自分で開いていないのに入力へ混入するファイル**がある。Claude Code は判定サブエージェントの起動時に、リポジトリルートおよびユーザースコープの `CLAUDE.md` を自動でコンテキストへ載せる。これは判定側の操作ではないため、試行をやり直しても同じことが起きる。**この種の逸脱は破棄・再実行では解消しない。**

したがって事後検査の扱いを2つに分ける。

- **判定側が能動的に開いたファイル**が対象文書とプロンプトファイル以外に挙がった場合 — 従来どおり破棄してやり直す。
- **実行基盤が自動注入したファイル**が挙がった場合 — 破棄しない。事実をレポートの「入力の限定に関する限界」へ記し、混入した文書が当該判定へ効きうるかを別途評価する。

`参照ファイル` 欄には、自動注入されたものも含めて挙げさせる（プロンプト雛形は「読んでしまった場合も隠さず挙げること」と指示している）。自動注入か能動的な参照かの区別は、判定側の申告と `参照ファイル` 欄の記述で行う。

### 7.2 返却全文の保全

事後検査に用いた**返却の全文**を `runs/<実行日>-raw-returns.md` へそのまま残す。`judgments.tsv` の根拠列・行き先列は全文を人手で符号化した派生物であり、原文が無いと符号化の妥当性を後から独立に確かめられない。符号化する者は試行1 の値と期待値を見た状態で試行2 を符号化しうるため、この経路は原文が残っていない限り閉じない。

## 8. メイン context へ題材集合本文を載せない運用

題材集合の本文（`cases.md` の題材文）は、呼び出し側のセッションへ載せない。

- **判定を実行する作業**では、呼び出し側が扱うのは題材ID・ファイルパス・サブエージェントが返す構造化サマリだけである。`prompt` がプロンプト本文をファイルへ書き出してパスだけを返す設計は、この規律を満たすためのものである。題材文を読んで確認したくなっても、呼び出し側で `cases.md` を開かない。
- **題材集合を作成・改訂する作業**では、本文の読み書きをサブエージェントへ委譲する。呼び出し側へ返させるのは、変更したファイルのパスと構造化サマリ（何をどう変えたかの要約・件数・検査の実行結果）だけであり、本文そのものは返させない。

委譲する際は、プロンプトへ次の2点を必ず含める。

1. ユーザースコープとプロジェクトルートの CLAUDE.md を読み、そのルールに従うこと
2. 実行した全ての Bash コマンドとツール呼び出しを、実行順に「実行ログ」セクションとして最終出力に含めること

## 9. 記録の見方

`report` の出力は4区画に分かれる。読む順序と見るべき点は次のとおり。

1. **カバレッジ** — 題材数に対して記録が覆う件数。全題材 × 2試行が揃っていない状態で一致率を読まない。
2. **試行間一致** — セル単位（項目1〜4 を1セルと数える）の一致件数と、項目別・合計・行き先の一致率。
3. **各項目の1点率（周辺分布）** — 試行ごとに、その項目が1点となった割合。
4. **期待帰結との差** — 題材 × 試行 × 項目の粒度で、期待値と判定が食い違った箇所の一覧。

**κ と該当率（1点率）は両方を見る。生の一致率は単独では使わない。** `adr-scope-observation.md` §4.3 が示すとおり、両者は別の失敗モードを検出する。該当率が高い項目は「安定しているが無情報」（常時点灯して判定を分けていない）であり、処方は項目の削除・統合・条件の細分化である。κ が低い項目は「解釈が試行ごとに割れる」であり、処方は操作的定義の付与である。κ だけを見ると前者を最良の項目として見逃し、生の一致率だけを見ると該当率の偏りによる上振れを一致と読み違える。

**κ はスクリプトが算出しない。** `report` が出す周辺分布（各項目の1点率）から手計算して併記する。二値の項目については、試行1 の1点率を p1、試行2 の1点率を p2 として、偶然一致率 Pe = p1 × p2 + (1 − p1) × (1 − p2)、実測一致率を Po として κ =（Po − Pe）/（1 − Pe）で求める。

**期待帰結との差には、人が帰属を付ける。** 差1件ごとに、規範側（対象文書）の一意性の欠陥か、題材文の記述密度の不足かの見立てを書く。この帰属は機械的には決まらない。題材文の記述密度が原因と判断した題材は、題材文を修正したうえで当該題材のみ独立2試行で再実行し、修正の事実と前後の帰結を記録する。規範側の欠陥と判断したものは記録に留め、対象文書は改訂しない。

**標本が小さいことは限界として注記する。** 題材数が数十件の水準では、κ も一致率も単独では読めない。数値は差の在処を指す手掛かりとして扱い、結論は差の内容と帰属で述べる。

## 10. 対象文書を改訂するときの使い方

1. **改訂前に1度通す。** 現行本文に対して §3 の手順を最後まで実行し、判定記録と集計レポートを残す。これが基準（改訂前の帰結）になる。
2. **改訂する。**
3. **改訂後に同じ手順で通す。** 題材集合を変えず、同じ題材ID・同じ雛形で §3 を再実行する。
4. **2つの集計レポートを突き合わせる。** 帰結が動いた題材を列挙し、動いたことが改訂の意図どおりかを1件ずつ判断する。意図しない箇所で動いていれば、それが退行である。

### 由来の付け方

`expectations.tsv` の由来列は `改訂前から在る` / `改訂の結果として追加` の2値であり、割り当て基準は次のとおり（`expectations.tsv` の注記行と同じ基準）。

- **`改訂前から在る`** — 初期集合、すなわち Issue #605 完了時点で `cases.md` に在った題材。
- **`改訂の結果として追加`** — Issue #605 の完了後に対象文書を改訂し、その改訂に伴って新たに足した題材。

ここでいう「改訂」は**今後行う対象文書の改訂**を指す。PR #603 による改訂を指すのではない。

したがって **Issue #605 完了時点では由来が `改訂前から在る` 側へ縮退し、`改訂の結果として追加` の行は0件だった。これは記入の欠落ではなく、上記基準による設計上の帰結である。** 0件であることを不足と読んで埋めない、というのがこの基準の趣旨である。2値が実際に分かれたのは、対象文書を1度改訂し、その改訂に伴って題材を足した時点からである。
