# 固定題材集合（題材文層）

このファイルは、`plugins/adr/skills/manage-adr/references/adr-scoping.md` を被テスト対象とする固定題材集合のうち、**題材文の層**だけを持つ。各題材が導くべき帰結（期待値）は同じディレクトリの `expectations.tsv` へ分離してあり、このファイルには一切書かない。判定を担うサブエージェントへ渡るのは `### 題材文` 見出しの下にある本文ブロックだけであり、題材IDの見出し・出所のメタ行・この前書きは渡らない。題材文には、被テスト対象が判定の入力として名指しする事実だけを書き、被テスト対象が結論として述べる述語（採点結果・経路・判定の語）は書かない。事実と結論を混ぜると、被テスト対象を読まずに題材文だけから帰結を再生できてしまい、被テスト対象を改訂したときに帰結が変わるかどうかを検出できなくなるためである。

題材IDは `CASE-NN` で安定させ、`sources.md` の通し番号および PR #603 最終巡の題材番号と1対1で対応させる。対応は各題材の見出し直下の「出所」行に置く。

---

サブエージェント定義には、実行に用いるモデルと思考量を必ず明示するという慣行が現に守られている。この慣行を述べた記述はどの文書にも無く、規範は実行者の記憶にのみ在る。したがって規範を体現・強制する資産も、規範を散文で述べた記述も、現に存在しない。明示の有無を機械的に検出する検査も無く、欠けていても作業は止まらない。この規範を書くとすれば、新規のエージェント定義を作るための雛形ファイルと、front-matter の必須キーを定めるスキーマ定義ファイルの双方で言明する必要がある。雛形にだけ書くと既に在る定義が検査を通ってしまい、スキーマ定義にだけ書くと新規作成時に雛形から漏れるため、どちらか一方の記載では規範が成立しない。当該決定の採用理由はどこにも書かれておらず、決定を採った者は既に離任していて到達する手段も記録も残っていないため、なぜこの慣行を採ったのか、比較して却下した選択肢があったのか、受け入れた不利益があったのかは、いずれも内容を知りようがない。慣行を反転しても、既に明示している定義の記述はそのまま残せ、表記が混在するだけで動作も整合も損なわれず、規範を書いた記述が現に無いため、直す必要のあるファイルは無い。影響が及ぶのは、サブエージェント定義を持つ2つのプラグインである。反転してもファイルの置き場所も分割の仕方も名前も変わらず、形式を変えるデータも、移し替えの要る蓄積データも無く、既に配布した成果物の利用者側へ及ぶ影響も無い。この慣行を知らない作業者が明示を省く選択をしうる箇所は、現にこの2つのプラグインに在る。

### 題材文

ADR の識別子をどの形式で採番するかを定めた。識別子は文書の front-matter に書かれるものであり、ファイル名には現れない。この規範は ADR の雛形ファイルの中に「識別子はこの形式で採番する」という散文のコメントとして書かれているだけであり、雛形ファイル自体は採番を体現も強制もしていない（雛形を写して作った文書の識別子が形式に合っているかは、雛形によって検査されない）。違反を機械的に検出する検査は現に無く、形式に合わない識別子を付けても作業は止まらない。当該決定の採用理由はその雛形にも他のどの文書にも書かれていないが、決定を採った者は在籍しており、採用理由として「時刻を含めると採番の衝突を避けられるため」と現に説明している。却下した選択肢は無く、受け入れた不利益・犠牲も無い。規範は書くとすればこの雛形1本に書き切れる。規範を反転しても、既に採番済みの識別子はそのまま残せ、表記が混在するだけで動作も整合も損なわれないため、直す必要があるのは雛形ファイル1本である。影響が及ぶのは、ADR を新規に起こす手順1つである。反転してもファイルの置き場所も分割の仕方も名前も変わらず、形式を変えるデータも、移し替えの要る蓄積データも無く、既に配布した成果物の利用者側へ及ぶ影響も無い。この規範を知らない作業者が別の形式を選びうる箇所は、現時点でこの1つだけである。
