# adr プラグイン 設計ガイドライン

## 位置づけ

- **対象**: `plugins/adr/`（ADR 運用機構の配布プラグイン）の設計・改修。機能を足す、消す、実装を置き換えるときに着手前に読む。
- **権威関係**: 本書は ADR の上位に立たない。`docs/adr/` の決定や配布物側の spec が改訂されれば、本書が追随して正しくなる側である。本書と ADR が食い違って見える場合は ADR が正であり、本書を直す。
- **由来**: adr プラグインの簡素化トラック（2026-08 に完了）の設計 spec とレビューで確立した原則のうち、その回限りでなく次の改修にも掛かるものを恒久化した。一時文書は役目を終えて削除済みであり、以後は本書がこれらの原則の出典である。
- **定めること**: プラグインが何を持ち続け、何を持たないか、削除と置き換えの進め方、参照面と検査資産の保ち方。
- **定めないこと**: 資産を配布物（`plugins/`）と配布元（リポジトリルートの `scripts/`・`docs/`）のどちらへ置くかは `docs/distribution-boundary.md`（配置の判断軸を3点で定める文書）が定める。スキル定義の分量・`allowed-tools` の最小化・実行時のコンテキスト規律はリポジトリ共通の規約（`CLAUDE.md` と、そこが指す `docs/references/context-budget.md`）が掛かる。いずれも本書へ転記せず、そのまま従う。ADR 運用そのものの手順・判定基準は `plugins/adr/skills/manage-adr/references/` 配下の条文が持つ。

## 1. 中核と周辺

**中核**（配布価値の本体）は、導入先リポジトリの ADR 群（蓄積された全 ADR ファイルと有効性 index の総体）に対して直接働く資産である。

- ADR 群の不変条件を守る機構: drift-lint（front-matter スキーマ、有効性 index との同期、上書き関係の双方向性、参照先の生存性・実在性、ファイル名・識別子規約の5レイヤ）、有効性 index の生成、識別子の発番、commit 前ゲート
- `manage-adr` スキルの条文群: 利用者の依頼を判断へ振り分ける `SKILL.md` と、判断ごとの参照ファイル

**周辺**は、中核を作る・保守するための装置である。**ADR 化要否の判定**（ある設計判断を ADR として起こすかの判断。以下、本書で単に「判定」と書くときはこれを指す。drift-lint が行う ADR 群の機械検査とは別物）を機械実行する検査器、固定題材集合とその期待値、走行記録を残す開発専用台帳、判定結果の直列化契約、上位の検証層などが該当する。周辺は利用者へ届かず、中核が正しいことを作り手が確かめるためだけに在る。

この区別に対する規律は3点。

- 周辺を足すときは、それが守る中核の不変条件を1つ名指せること。名指せない装置は足さない。
- 周辺の規模は、中核との比で見る。周辺が中核を上回った時点で、規模比そのものを存廃を問う根拠として扱い、上回ったまま放置しない。判定を機械実行する装置一式が中核を数倍上回った状態で廃止された実例が ADR-202608280911-01 にある。
- 中核の検査内容は実障害由来の不変条件として積まれている。整理・書き直しの名目で検査を減らさない。実装の構造を変える場合も、検査内容の不変を制約として先に置く。

## 2. 判定と条文をめぐる規律

### 2.1 判定の品質は条文の質で支え、判定を機械実行する装置を持たない

ADR 化要否の判定は、条文を読む判定主体が散文で結論と根拠を返す形のみを採る。判定結果を機械可読に直列化する契約、固定題材集合との突き合わせによる退行検出、条文の外に置く閾値の設定ファイルは持たない。この決定は ADR-202608280911-01（ADR 化要否判定の品質を条文の質だけで支え、判定を機械実行する検証装置を持たないと定めた決定。射程は判定の品質担保手段に限られ、中核機構の要否は対象外）が持つ。

設計上の含意は2つ。判定に用いる閾値・値域は判定手続きを述べる条文が単独で保持し、別ファイルへ外出ししない。判定のぶれが懸念されたときの既定の対処は「条文を直す」であり、「検査を足す」ではない。ぶれが実害として観測された場合に限り、その実障害を根拠に必要最小の検証を設計する。旧装置の復活を既定の選択肢にしない。

### 2.2 参照面は正本が一意に決まる状態に保つ

`manage-adr` の参照面（`SKILL.md` ＋ `references/`）は、**ある規範を改訂するときに触る文書が一意に決まる**状態に保つ。同じ規範が2箇所に載る状態を作らない。これが参照面の組織原理であり、以下はその帰結である。

- 判断の単位でファイルを分けることを既定の向きとする。ただし「1判断=1ファイル」を閉じた規則にはしない。結び付きの強い規範を1本が束ねる形（ドメインモデルの正本が状態の型・配置・採番方式・検査項目と正本の対応を併せ持つ等）は、正本が一意である限り許す。分けるか束ねるかで迷ったら、改訂時に触る文書が一意になる側を採る。
- 参照ファイル間の直接参照を許し、参照の深さの上限を2段とする。すべてのポインタを `SKILL.md` へ集約しない。集約すると `SKILL.md` が第二の列挙面になり、正本の一意性と衝突する。
- 例示は正本の重複を作る経路になる。他文書に規範として既述の内容を、例として再掲しない。

### 2.3 判定条文自体を書き換える改修は、判定に使う版を先に固定する

**適用条件**: 改修が判定を述べる条文そのもの（`adr-scoping.md`・`adr-destination.md`・`adr-demotion.md`）を書き換える場合に限る。検査器の実装だけを変える改修には掛からない。

この場合、改修は自分が書き換える条文によって ADR 化要否を判定されることになる。判定に用いる条文の版（commit）を着手前に固定し、判定記録へ明記する。固定しないと、改訂後の自分に都合の良い基準で自分を判定できてしまう。

## 3. 機能を削るときの規律

### 3.1 廃止の根拠に保守摩擦を混ぜない

保守摩擦（commit がブロックされる、更新の付随作業が煩わしい等）を廃止の根拠に挙げない。摩擦の発生源が廃止対象の外にもある場合、廃止しても摩擦は残り、「廃止は効かなかった」という誤った評価を生む。簡素化トラックでは、行番号を固定した台帳による commit ブロックが廃止対象由来の行だけでは起きなくなる保証がないことが実測で判明し、根拠から外して別の作業へ切り出した。摩擦を解くなら、その発生源そのものを対象とする作業として立てる。

廃止の根拠として実際に足りた例は「配布価値の本体（§1 の中核）でないこと」と「中核機構との規模比」の2つである。これは代表的な根拠の提示であって、根拠をこの2つに閉じるものではない。

### 3.2 削除の前に、存続側が削除対象へ実体を外出ししていないかを洗う

削除に着手する前に、存続させる側がその資産へ依存していないかを洗う。依存には通常の参照だけでなく、**存続側の条文が判定や手順の実体（閾値の数値、値域の定義、数え方）を削除対象のファイルへ外出ししている形**が含まれる。後者は参照の文面からは「詳細は別紙」としか読めないため見落としやすく、そのまま削除すると存続側が指示先を失った空文になる。

実体の外出しが見つかった場合は、実体を存続側へ取り込んでから削除する。取り込みを後続の工程へ回す順序は採らない。条文が指示先を失う期間が生じ、その間に判定を求められた主体が値域も閾値も参照できない条文だけを渡されるため、この順序は ADR-202608280911-01 が却下代替として退けている。

### 3.3 走査・追随の対象はパス列挙で固定する

削除・改名・参照の張り替えで対象集合を書くときは、「〜系」「〜一式」のような包含語ではなく、パスの列挙で固定する。受入条件も同じ形で書く。系統名をファイル名に含まない資産は語彙による走査を素通りし、依存元が消えたあとも孤児として残るが、検査は緑のままになる。簡素化トラックでは、廃止対象へ全面依存しながら名前に系統語を持たないスクリプトが取りこぼされた。

### 3.4 凍結記録・歴史記録は追随の対象から外す

過去の時点の観測・判定・移行を記録した文書は、参照先が消えても書き換えない。参照掃きの受入条件を書くときは、これらを除外集合としてパスで明示する。明示しないと「参照が残っている」と判定され、記録を改竄しなければ緑にできない状態に追い込まれる。現在真であり続ける義務を負う規約文書の側は逆で、例示が陳腐化したら注記を置いて追随させる。どちらに当たるかは、その文書が時点の事実を述べているか、現在の規範を述べているかで判別する。

### 3.5 前提が消える OPEN Issue は、廃止する PR の中で処理する

機能を廃止すると前提を失う Issue は、その廃止 PR の作業として棚卸しし、1件ずつ処遇を決める。「別途対応」と書いた残作業は追跡から落ちる。

処遇の振り分けは、**指摘された欠陥そのものが存続資産に残るか**で決める。

- 残らない（指摘の対象が機構ごと消える）→ 廃止 Issue へのリンクを添えてクローズする
- 残る（条文の欠陥として存続側に残る）→ 受入条件から廃止対象の機構への依存を外し、欠陥の是正だけを射程として再スコープする
- そもそも本文が廃止対象へ依存していない → 変更不要で存続させる

## 4. 検査資産と追随の規律

### 4.1 実装を置き換えたときの同値性は負例で確かめる

検査器の実装を書き直すとき、正常な ADR 群に新旧を当てて緑同士が一致しても、検査内容が同一である証拠にはならない。検査対象の ADR 群は commit ゲートを通っている以上、どちらの実装でも緑になるからである。レイヤごとに違反を含む ADR 群（負例）を用意し、新旧が同じ違反を同じレイヤで検出することを確かめてから旧実装を落とす。

### 4.2 検査資産へ持ち込まない形式

- **行番号を固定した台帳・版を据え置いて突き合わせる常設ゲートを新設しない**。参照面へ1行入れるだけで、無関係の変更まで commit がブロックされる。
- **変異検査・契約検査といった上位の検証層を、常設のゲートとして再導入しない**（§2.1 と同じ理由。装置を守るための装置を積まない）。改修時に一度行う変異の確認——分岐を消して赤になるかを手で確かめる——は作業手順であり、この禁止に当たらない。
- **実障害由来の回帰ケースには、どの障害に由来するかをテスト内のコメントで残す**。由来を失った回帰ケースは、後の改修で「何を守っているか分からない検査」として消される。

### 4.3 固定列挙は glob の増減に追随しない

参照面やテストスイートを増減させる改修は、次の3系統の固定列挙への追随を伴う。いずれも glob の結果を自動で反映しない。

- `scripts/run-tests.sh` の `EXPECTED_BATS` — 実行対象 bats の固定リスト。glob 結果との双方向照合を持つため、追随漏れは赤で現れる
- `scripts/tests/manage-adr-surface.bats` の `AC5_SURFACE_FILES` — 旧記述の除去を検査する対象面の固定列挙。同じく glob との双方向照合を持つ
- `docs/development/plugin-path-reference-ledger.md` — 配布物のパスを行番号で固定した参照台帳。行の挿入・削除でずれるため、行数を動かす編集で追随が要る

改修の締めに、この3系統を1つずつ確認する。

### 4.4 受入条件は、現行の検査経路が観測できる事象で書く

受入条件は、いま在る検査経路が実際に観測できる事象で書く。書いた時点で誰も観測できない条件は、充足も違反も判定できないまま緑を返す（「skip で緑になるテストが無いこと」は、skip を数える処理が無い限り観測できない）。観測できない条件を書きたくなったら、条件の側を現行の経路が実際に検出する事象へ書き換える。検査を新設して観測可能にする方向は、§2.1・§4.2 の制約により既定では採らない。

## 5. 本書に持ち込まないもの

- **一時的な定量値**（各資産の行数、ファイル数、棚卸しの集計）。時点の測定は測定した時点の文書（spec・PR・作業記録）が持つ。§1 の規模比は、値ではなく見方として書く
- **個別の Issue / PR 番号と、その処遇表**。在庫の状態は GitHub を単一の出典とする
- **完了した工程の実施記録**（削除対象の一覧、工程分割、実施順序、着手時の実測値）。廃止時の ADR 化要否判定・既存 ADR の遷移要否・検証の証跡は `docs/development/adr-judgment-pipeline-removal-2026-08-27.md` が持つ。削除対象の一覧と工程分割を持っていたのは当時の設計 spec であり、同 spec は削除済みで git 履歴からのみ取り出せる

本書へ書くのは、次の改修でも同じ判断を迫られる規範だけである。上記に当たる記述が本書へ混ざったら、時点の文書へ戻して本書からは落とす。
