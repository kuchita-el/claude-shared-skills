## 2. レイヤ1 の規範の値を再掲する箇所（決着後・`plugins/adr/` 配下の全列挙）

AC2 の列挙である。「レイヤ1 の規範の値」とは `status` / `validity` / `superseded-by` の**合法な組み合わせ**を指す。軸ごとの値域（`status` は3値、`validity` は3値と空）はこれとは別の粒度であるため、区別して併記する。

### 2.1 走査手順

`plugins/adr/` 配下の全ファイルに対して次を実行し、当たった行を1件ずつ目視で分類した。

**除外規則**: 構成子の全体像を与えない**部分的な言及**は個別に列挙しない。ここでいう部分的な言及とは、1つの遷移や1つの軸だけを取り上げ、合法な状態の集合がどう構成されるかを読み取れない記述を指す。値の個数では切らない（初版は「単一の値を使うだけの行」と書いていたが、実際には2キー・2値を述べる行も列挙外に置いており、文言が実態と噛み合っていなかった）。

```sh
# (a) 3キーのうち2つ以上を1行で名指す箇所（＝1行に収まる値組）
grep -rn 'superseded-by' plugins/adr/ --include='*.md' --include='*.sh' | grep 'validity'
# (b) 軸の値域を列挙する箇所
grep -rn '有効 / 上書き済み\|提案中 / 承認済み\|提案中 かつ\|上書き済み, \|validity=（空）' plugins/adr/
# (c) 値組が複数行へまたがる箇所（front-matter ブロック・雛形・骨組み）
grep -rn '^status:\|^validity:\|^superseded-by:\|status: 提案中\|status: 承認済み\|validity: 有効' plugins/adr/
# (d) 値の語彙が現れる全ファイル（取りこぼし確認）
grep -rln '上書き済み' plugins/adr/
```

**(c) は初版の走査手順に無く、レビューで指摘されて追加した。** 初版は (a)(b)(d) だけで組んでおり、値組が**行をまたいで**書かれる箇所へ構造的に届かなかった。`template.md` の front-matter は3キーが3行に分かれ、`上書き済み` の語も持たないため、(a) にも (b) にも (d) にも当たらない。「1行に収まる形」を暗黙の前提にした走査は、同じ内容の縦書きを見落とす。

`scripts/tests/lint-adr-surface.bats` へ面⑦「lint-adr.sh ヘッダがレイヤ1 の合法な状態集合を再定義しない」を追加した。

### 3.1 設計

**ブロックの切り出しは行番号によらない。** レイヤ宣言行（`# レイヤ1` の宣言行から `# レイヤ2` の宣言行の直前まで）で範囲を決める。行番号で固定すると、ヘッダへ1行足すだけで検査が別の範囲を見る（#787 と同型）。ブロックは一度閉じたら再び開かない（`# レイヤ1` を前方一致で見るため、レイヤが10個目に達すると `# レイヤ10` が再び開く）。境界判定は1関数だけが持つ。同じ状態機械を2箇所に置くと、片方だけ直したときに Tier B の射程と fail-closed のブロック抽出がずれる。

**走査面を2段に分ける。** レイヤ1 の写しは、削除したときと同じ体裁で戻るとは限らない。ブロックの外へずらす／表の体裁を外す／ラベルを言い換える、のいずれでも規範の写しは復活する。一方で「無いこと」の検査をヘッダ全域へ無条件に掛けると、レイヤ2〜5 の正当な散文まで落ちる。レイヤ2〜5 のヘッダ記述は本 Issue の OUT であり、その将来の編集を検査で縛ってはならない。

| 段 | 走査面 | 見るもの |
|---|---|---|
| Tier A | ヘッダ全域 | 値組の構造（区切りの反復・キーの共起・空欄マーカーの反復）を持ち、**かつ状態の値を伴う**行。値域そのものの再宣言もここで受ける |
| Tier B | レイヤ1 ブロック | 値の共起、構成子の書き下し、合法な組を導くラベル。レイヤ2〜5 は同じ語を別の意味で使うため、これらはブロックの外へ掛けない |

**体裁ではなく値組そのものの形を見る。** 7本の走査規則を持つ。

| 規則 | 段 | 検出対象 | 条件式の免除 | 現ヘッダでの当たり |
|---|---|---|---|---|
| R1 | A | 状態の値を伴い、区切り（`\|` / `｜`）を1行に `LINT_TABLE_SEPARATOR_MIN` 個以上含む行 | — | 0件 |
| R2 | A | 状態の値を伴い、3キーを1行で名指す行 | — | 0件 |
| R3 | A | 状態の値を伴い、空欄マーカー（「（無し）」「（空）」）を1行に2回以上使う行 | — | 0件 |
| R4 | B | 本文が「合法」を含み `:` で終わるラベル行 | — | 0件 |
| R5 | B | 状態の値が1行に2つ以上現れる行 | あり | 0件 |
| R6 | A | 状態の値が1行に `LINT_VALUE_DOMAIN_MIN` 個以上現れる行 | **なし** | 0件 |
| R7 | B | 状態の値を伴い、値を除いた残りに遷移名（起票／承認／上書き／廃止／却下）を含む行 | あり | 0件 |

R2 は「キー名を伴う値組」、R3 は「キー名を伴わず値だけを並べる値組」を受け持つ対である。R7 は「1構成子を1行へ割った書き下し」を受け持つ。値の語を先に落としてから遷移名を探すのは、`承認` が `承認済み` の、`上書き` が `上書き済み` の、`廃止` が `廃止済み` の部分文字列であり、落とさないと値の出現を遷移名と誤認するためである。

**条件式の免除は「範囲」ではなく「行の形」で持つ。** 違反種別の条件式（本文が「`<数字>. `」で始まる行）は決定2 の「持つ」側であり、値を2〜3語含むため R5・R7 に当たる。これを範囲（ラベル行から次の空コメント行まで）で免除すると、**免除領域そのものが無検査の書き込み先になる**。実測では、条件式の列挙の直後へ6値・5構成子を含む1行を足すと緑で通り（E1）、範囲の終端である空コメント行を1本消すと免除が採用理由の段落まで広がって同じ行が通った（E6）。行の形で免除すれば、免除は条件式1行に閉じる。番号を付けて値組を書いても（E1n）、免除の掛からない R6 が受ける。

R6 に免除を置かないのは、違反種別の条件式が1行あたり値3語までで書けるためである（値域を列挙する種別4・5 が最大）。閾値 `LINT_VALUE_DOMAIN_MIN` に届かないため、免除なしで共存できる。

**Tier A の3規則に「状態の値を伴う」条件を掛けているのは、掛けないと OUT 領域を縛るためである。** 条件なしでは、3キーを集合として名指す説明文（「レイヤ1 が読むキーは status / validity / superseded-by の3つである」）、`|` を選択肢の区切りに使う文、「（空）」を2回使う文がいずれも落ちる。これらは規範の再定義ではなく、`SKILL.md` が現に使っている自然な言い回しである。§3.2 の FP1〜FP3 がこの方向の正例である。

**閾値2件はいずれも実測で決めた。** `LINT_TABLE_SEPARATOR_MIN`（区切り）は3。2に下げると、選択肢を `|` で区切って列挙し `validity: 有効` に触れるレイヤ4 の散文が落ちる（FP6）。`LINT_VALUE_DOMAIN_MIN`（値域の再宣言）は5。4に下げると、検査対象を値で限定するレイヤ4 の散文（「source は 提案中・却下・廃止済み を含まない（有効 のみ）」＝4語）が落ちる（FP4）。いずれも偽陽性が出る境界の1つ手前に置いている。定数はコメント・失敗メッセージの双方から参照し、数値を直書きしない（閾値を4→5 へ上げた際、設計コメントだけが4のまま取り残された。本 PR が畳もうとしている「写しの静かな乖離」と同型である）。

**値の照合は別語を落としてから行う。** `有効性` は `有効` を部分文字列に持つため、有効性軸に触れる採用理由の文が値を1語含むものとして数えられる。決定2 が保持を定めた記述であり、落としてはならない（FP5）。

**fail-closed を4点持つ。** 「無いこと」を確かめる検査は、走査対象が空になった瞬間に何も照合しないまま緑になる。抽出の非空・抽出の下端（`set -euo pipefail` で閉じていること）・上端（`# レイヤ2` 宣言の存在）・ブロックの非空をそれぞれ落とす。下端を見るのは、終端の目印が変わると `sed` が一致せず本文末尾まで出し、ヘッダを見ているつもりで実装本体まで見ることになるためである（範囲が無言で広がる形の空振り）。

**正の錨を3点持つ。** ブロックが違反種別の列挙を持つこと（決定2 の「持つ」側）、正本ポインタを持つこと（決定1 の置換先）、そのポインタが指す見出し `## 状態の型` が `adr-model.md` に実在すること。`.sh` 内の節名参照は面⑤ の走査面（manage-adr スキル面）に入らないため、指し先の実在はここで見る。

ヘッダは1回だけ走査し、7規則の判定を同一ループ内で行う。ヘッダの抽出（`sed -n '1,/^set -euo pipefail/p'`）は面⑥ と共有する。抽出式を2箇所に持つと、終端の目印が変わったときに片方だけが無言で全文を走査する。多バイト文字の照合は bash のリテラル部分文字列操作だけで行い、awk の文字クラスを使わない（mawk はバイト単位に分解して誤判定する）。

### 3.3 ガードが取り逃していたもの（4周分）

面⑦ は4周かけて現在の形になった。各周で取り逃していたものを記録する。1周目から3周目までの穴はいずれも独立レビューの実測で判明したものであり、自分の変異の網では見つけられなかった。

**1周目（初版）が緑で通したもの**

1. **抽出範囲が無言で広がる方向（M3）**: fail-closed は「抽出0行」だけを見ており、終端の目印が外れて範囲が本文末尾まで伸びる側を見ていなかった。空振りは0行だけでなく、過剰な範囲でも起こる。
2. **置き場所を1つ隣へずらす方向（M11）**: 表検査だけをヘッダ全域へ掛け、合法列挙のラベル検査はブロック限定のままだった。設計原則を片方の規則にしか適用していなかった。
3. **体裁を外す方向（M10・M12・M13）**: 表検出が「本文が `|` で始まる」に依存し、行頭の区切りを外しただけの同一内容が素通りした。

**2周目が緑で通したもの**

4. **構造的な目印を一切使わない書き方（N1・N2・N3 とそのブロック外版）**: 走査は「値組が取りがちな表記の癖」（半角パイプ・キー名・特定の空欄記法）を見ており、癖を外せば抜けた。
5. **癖を無害に使うだけで落ちる（FP1〜FP3）**: 同じ根の裏返しである。本 Issue が OUT としたレイヤ2〜5 のヘッダ記述に対して、将来の編集を実質的に禁じる検査になっていた。

**3周目が緑で通したもの**

6. **免除領域への書き戻し（E1・E6）**: 3周目は 4・5 を同時に是正するため、値の共起（R5・R6）を軸に据えた。その代償として違反種別の列挙を**範囲**で免除したところ、免除領域そのものが無検査の書き込み先になった。列挙の直後へ値組の1行を足せば通り、範囲の終端である空コメント行を1本消せば免除が隣の段落まで広がった。§3.1 に書いた「免除は安全側へ倒れる」はラベルが失われる方向にしか成立しておらず、この2方向を見ていなかった。
7. **1行1値へ割る書き方（E4）**: R5 の閾値が2値であるため、ブロック内でも1行1値×5行に割れば踏まない。§3.4 に書いた既知の限界は「ブロックの外へ置く」を条件に含めており、**実際の穴より狭い記述になっていた**。限界の記述が実測と食い違うのは、その記録を根拠に射程を判断する側を誤らせる。
8. **R1・R4 の偽陽性（FP6・FP7）**: Tier A へ掛けた「値を伴う」AND は、`validity: 有効` のように値を1語含むだけで満たされるため R1 の免罪符として働かなかった。R4 には AND 自体が掛かっておらず、レイヤ5 の「合法とする識別子形式:」というラベルが落ちた。
9. **`有効性` による採用理由の巻き添え（FP5）**: `有効` が `有効性` の部分文字列であるため、有効性軸に触れる採用理由の文が値を1語余分に含むものとして数えられた。決定2 が保持を定めた記述である。

**2周目の設計判断を3周目で反転させた経緯**: 2周目の記録は「免除領域は設けていない。違反種別の列挙を免除領域にすると、そこへ値組を書き戻す経路が残る」と書いて免除を拒否していた。3周目に値の共起（R5・R6）を導入した際、条件式が値を2〜3語含むため免除なしでは条件式自体が落ちることになり、範囲による免除を採った。**このとき、2周目に自分で書いた拒否理由がそのまま現実になった。** 4周目では免除を範囲から行の形へ移し、かつ免除を持たない規則（R6）を残すことで、免除を必要としつつ免除領域が抜け道にならない形にした。

**規則を足しただけでは効いていないことがある。** 2周目で追加した R1・R3 は、追加直後は実装の欠陥で無効だった。`lint_count_occurrences` の先頭で `local haystack="$1" needle="$2" rest="$haystack"` と1文で書いていたため、同一 `local` 文の右辺が builtin の実行前に展開され、`rest` に外側スコープの値（空）が入って数え上げが常に0を返していた。M1 が別の規則単独で赤になっていたために「規則が効いている」ように見えた。**変異が赤であること自体は、赤にした規則を特定しない。** どの規則が落ちたかまで見て初めて、追加した規則が働いているかが分かる。§3.2 の「落ちた規則」欄はその確認のために置いており、検査項目のラベルへ規則名（`[R1]` 等）を入れているのも同じ理由である。

### 3.4 既知の限界

- 構成子の書き下しを**レイヤ1 ブロックの外**へ置き、どの行も Tier A の構造規則を踏まず、遷移名を使わず、1行あたりの値を4語以下に抑える経路は落ちない。Tier B（R5・R7）はブロックの中しか見ず、Tier C にあたる R6 の閾値は偽陽性を避けるために5語に置いている。ここから先は語彙と閾値の追いかけっこになり、規則を足すほどレイヤ2〜5 の正当な記述を巻き添えにする側の risk が上がる。**再混入の想定は「削除したものが戻る」であり、意図的な回避ではない**という前提で、この位置に線を引いた
- ヘッダは行単位のコメントであり、行をまたぐ構造の解析は行っていない
- 面番号はファイル内で一意であり、ファイル横断では一意でない（`lint-adr-layers.bats` にも面⑦ がある）。変異の再実測時は `bats --filter` だけに頼らず、対象ファイルを指定する（本記録の実測はいずれも `mise exec -- bats -f '面⑦' scripts/tests/lint-adr-surface.bats` の形で行った）
