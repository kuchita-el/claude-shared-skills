## 1. 観測方法

### 1.1 定量値の取得

参照件数・状態分布・寿命は以下の方法で取得した。

**参照件数**は git 追跡ファイルを基準とし、`git grep` で取得した。

```sh
PAT='ADR-[0-9]{8,12}(-[0-9]{1,2})?'
# 外部参照（docs/adr 以外の追跡ファイル。fixtures を除外）
git grep -hoE "$PAT" HEAD -- . ':!docs/adr' ':!plugins/adr/scripts/fixtures' | sort | uniq -c
# 内部参照（コーパス内の相互参照。自動生成の index.md を除外）
git grep -hoE "$PAT" HEAD -- 'docs/adr' ':!docs/adr/index.md' | sort | uniq -c
```

追跡外の作業成果物（`docs/plans/`、`.superpowers/`）は別枠で集計した。ここは `/usr/bin/grep -r` を用いる。

**測定上の注意（再現時に必要）**: 対話セッションの `grep` はユーザープロファイル由来のシェル関数（ugrep）へ解決される場合があり、これは `.gitignore` を尊重するためスクリプト内の `/usr/bin/grep` と走査範囲が一致しない。参照件数の集計は上記のとおり `git grep` で追跡ファイルへ範囲を固定する。

**状態分布**は front-matter の `status` / `validity` を先頭6行から読み取って集計した。

**寿命**（起票から退役までの日数）は、対象ファイルを変更した各コミットについて blob の front-matter を直読みし、`validity` が退役値になった最初のコミット日を退役日とした。

```sh
git log --follow --format=%ad --date=short --diff-filter=A -- "$f" | tail -1   # 起票日
git show "$sha:$path" | sed -n '1,6p' | grep -m1 '^validity:'                 # 各時点の状態
```

diff に対する `git log -S'validity: 上書き済み'` は使わない。状態モデルを説明する ADR が本文中に同じ文字列を引用しているため、front-matter の変更でないものを退役として誤検出する。

### 1.2 判定ルーブリック（問い2用）

ADR-20260719 決定1 の4項目を既存 ADR へ遡及適用するため、以下を調査開始時に固定し、以後変更しなかった。判定は各項目 0 点または 1 点。判定対象は当該 ADR の `## Decision` に書かれた決定内容であり、ADR の書きぶり・分量ではない。

判定は「その ADR を今この基準で新規に起票するかどうか」を問う。ADR として既に存在するという事実自体は判定材料にしない。

**項目1: 後戻りコストが高い**

- 1点: 決定を反転すると既存の成果物の書き換え・移行が必要になる。対象は、ファイル群の構造変更、スキーマ・データ形式の変更、既に配布されたプラグインの利用者側への影響、蓄積済みデータの移行のいずれか
- 0点: 反転しても書き換えは局所（おおむね1〜2ファイルの文言修正）で済み、移行対象のデータや配布物への影響がない

**項目2: 複数モジュール・複数開発者に波及する**

- 1点: 影響が2つ以上のプラグイン／スキル／スクリプト／成果物種別に及ぶ。または、決定を知らない第三者が独立に別の選択をしうる箇所が複数ある
- 0点: 影響が単一ファイル・単一スキル・単一スクリプトの内部に閉じる

**項目3: 採用理由が時間経過で揮発しやすい**

- 1点: 採用理由が実装・テスト・fixture・コード内コメント・型定義のいずれにも残らず、ADR を消すと理由が復元できない
- 0点: 採用理由が実装側の資産（コード、テスト、fixture、スクリプトのヘッダコメント、テンプレート）に保持されており、ADR がなくても現物から読み取れる

**項目4: ツールで自動強制できない**

- 1点: 決定への違反を機械検出できない。lint・hook・スキーマ検査・フォーマッタ・テストのいずれでも違反を検出する手段が、現状も将来も取れない
- 0点: 違反を機械検出できる。現に検出している場合は必ず0点。検出機構を作ることが現実的に可能な場合も0点

**合計と判定**: 3点以上は今の基準でも ADR 化に該当、2点以下は今の基準なら ADR 化しない。

**同点処理**: 各項目の判定に迷った場合は0点へ倒す。ADR-20260719 決定1 の「判断に迷ったら ADR 化しない」に合わせた向きである。この向きは「今の基準なら ADR 化しない」の本数を過大に数える方向へ働くため、集計値は上限として読む。

**レイヤ4同型フラグ**: 項目3が0点かつ項目4が0点であること。`lint-adr.sh` レイヤ4 と同じ性質（ツールで自動強制されており、採用理由は実装側が保持している）を指す。

**型分類**: 各 ADR を `構造モデル` / `運用手続き` / `ツール挙動` / `用語定義` / `配置命名` / `方針宣言` のいずれか1つへ主型として割り当て、複数該当する場合は `## Decision` の分量が最も多いものを主型、他を副型とした。

### 1.3 判定の実施と再現性の検証

上記ルーブリックを唯一の入力とし、59本を全数判定した。判定はサブエージェントへ分担し、結論のみを返させた。

再現性を測るため、同一のルーブリックで**独立に2回**判定した。2回目はバッチの切り方を変えた（1回目はファイル名の連番順に12本ずつ、2回目は5本刻みのストライドで割り当て）。同一バッチに入る ADR の組み合わせが変わるため、隣接する ADR の文脈に引かれる効果を排除できる。

判定結果は2回分を全件 `docs/development/adr-scope-observation-judgments.tsv` に記録した。本文の集計値はすべて同ファイルから導出できる。

#### 再現しない原因

判定を担った複数の担当が、独立に同じ曖昧点を報告した。

1. `references/` 配下の共有規約ファイル（`behavior-invariants.md`、`subagent-execution-parameters.md` 等）が項目3の「実装側の資産」に含まれるかが、字義的に確定しない
2. `CLAUDE.md` を実装側の資産とみなすかどうかで項目3が反転する
3. 項目4の「ツールで自動強制できない」が、「現に強制していない」と「原理的に強制できない」の二義で読める。ルーブリックが「検出機構を作ることが現実的に可能な場合も0点」と将来可能性を含めたため、見積もりの幅がそのまま判定の幅になった

いずれも各項目の**操作的定義が存在しない**ことに由来する。ADR-20260719 決定1 は4項目の名称とスコア境界を定めるが、各項目を何によって判定するかは定めていない。

#### 4項目の上位2項目は判定に寄与していない

## 3. 追加観測: 手続きコストの非対称

#589 の5問いには含まれないが、本調査の起点は「既存 ADR で決定したことを保全しようとすることが、結果的に意思決定を歪めかねない」という問題提起であった。5問いは総量とスコープを測るものであり、歪みそのものは測らない。判断材料として不足するため、並行して観測した結果を記録する。

観測できた事実は3点である。

**1. 手続きコストが変更方向にのみ発生する。** 既存決定を維持する場合のコストは0である。変更する場合は、`edit-decision.md` の分類（core／非core／些末）で core と判定されると、新規 ADR の起票・旧 ADR の `validity` 更新・双方向相互参照の書き込み・index 再生成・lint 通過が必要になる。編集対象は2ファイル、書き込み箇所は3箇所である。

**2. 既定が重い側へ倒れている。** `edit-decision.md` は分類を利用者へ問う際、既定選択肢を core とし「迷ったら core」を安全則として明示する。同ファイルはこの向きの根拠を可逆性の非対称に置く（core を非core と誤ると不可逆な不整合が残るが、逆は過剰なだけで可逆）。この評価は ADR ファイルの整合性を対象としており、**議論の場で結論が既存 ADR へ寄る効果は計上されていない。** ファイル上は可逆でも、寄った結論は可逆ではない。

**3. スコープが手続きコストで線引きされた実例がある。** #574 は OUT に「粒度判定基準の4項目・スコア境界・『判断に迷ったら ADR 化しない』の変更（ADR-20260719 決定1 由来のため、変更は core 反転にあたる）」を挙げている。変更しない理由として挙げられているのは、内容の妥当性ではなく core 反転であるという手続き上の分類である。

**4. ADR 運用自身の改善が最も高い摩擦に置かれている。** ADR 運用を主題とする ADR は12本（20%）あり、両方の判定で非該当とされた13本のうち6本がここに属する。ADR 運用の改善は、その都度 ADR 手続きを駆動する。

## 4. 精緻化提案

### 4.1 判断: 4項目・スコア境界・「迷ったら書かない」は変更しない

ADR-20260719 決定1 の4項目、スコア境界（3点以上／2点以下）、「判断に迷ったら ADR 化しない」は変更しない。したがって core 反転にはあたらず、同 ADR の上書き手続きは不要である。

根拠は問い2の観測にある。判定が再現しない主因は4項目の**構成**ではなく、各項目の**操作的定義の不在**である（§2.2）。項目を組み替えても、判定手続きが定まらない限り再現性は改善しない。上位2項目が判定に寄与していない事実（§2.2）も、項目の削除ではなく判定手続きの厳格化によって解消しうる。

ただし操作的定義を入れても再現性が改善しない場合、4項目の構成そのものを疑う必要がある。その判断を先送りにしないため、§4.3 の発火条件を併せて定める。

### 4.2 提案A: 各項目へ操作的定義を与える

4項目の名称・スコア境界・同点処理の向きを保ったまま、各項目に判定手続きを与える。項目・境界を変更しないため追加に留まり、#574 が OUT とした範囲にも触れない。配置先は #574 と同一ファイル（`adr-scoping.md`）であり、統合して実装できる。

| 項目 | 与える操作的定義 |
|---|---|
| 項目1 後戻りコスト | 反転時に書き換えが必要なファイルを列挙して**数える**。閾値を本数で置く |
| 項目2 波及 | 影響が及ぶプラグイン／スキル／スクリプトを**列挙する** |
| 項目3 理由の揮発 | 「採用理由の保持先」として認める資産の**値域を閉じた列挙で固定する**。共有規約ファイル（`references/` 配下）と `CLAUDE.md` を含めるか否かを明示的に決める |
| 項目4 ツール強制 | **現在時制へ一意化する**（現に機械検査されているか）。将来の実装可能性を判定に混ぜない |

項目3の値域と項目4の時制は、§2.2 で判定が反転した原因に直接対応する。この2点を決めない限り、判定は再現しない。

なお項目4を現在時制へ一意化すると、「機械検査を作れるが未実装」の決定は1点（ADR 化寄り）へ倒れる。ADR 化してから検査を実装した場合に非該当へ移ることになるため、§4.3 の発火条件で退役の検討対象として扱う。

### 4.3 提案B: 4項目を見直す発火条件

4項目の構成そのものを見直すべき状況を、観測可能な指標で定義する。いずれも本調査で実際に取得できたものであり、取得コストは低い。

| 発火条件 | 意味 | 本調査での実測 |
|---|---|---|
| ある項目の該当率が一定を超える | その項目が常時点灯し、判定を分ける働きをしていない | 項目2が93%、項目1・2の同時点灯が80% |
| 独立2回判定の二値一致率が一定を下回る | 判定が判定者に依存し、基準として機能していない | 71%（項目3は41%） |
| 起票から N 日以内の上書き率が一定を超える | 決定が固まる前に記録している（早期結晶化） | 退役8本中4本が15日以内、3本が2日以内 |
| ADR 運用自身を主題とする ADR の比率が一定を超える | 運用の改善が運用の手続きを駆動する自己言及の摩擦が増している | 59本中12本（20%） |
| 外部参照0件の比率が一定を超える | 記録が配布物・規約へ接続していない | 14本（24%） |

閾値の具体値は本文書では定めない。定めるには複数時点の観測が必要であり、本調査は1時点のみである。上記の実測値は最初の観測点として使える。

### 4.4 #574 との関係

#574 は `adr-scoping.md` に「発見型の入口」と「ADR 化しないと判定した対象の受け皿の一般則」を追加する。本調査の成果物は次の2点で #574 の根拠になる。

1. **受け皿の一般則が必要な事例は1件ではない。** レイヤ4同型は、両方の判定で該当したものだけでも6本ある（§2.2）。一般則の射程はメタ層（ADR 運用自身）に集中しており、`lint-adr.sh` レイヤ4 はその1例にすぎない
2. **入口の判定が再現しないため、受け皿だけでは足りない。** #574 が受け皿を整えても、判定が判定者に依存する限り、同じ対象が回によって ADR へ入る。提案A（操作的定義）を同一ファイルで併せて入れる必要がある

## 6. 測定限界

1. **識別子の重複により、5組の参照件数を個別に帰属できない。** `ADR-20260621` / `ADR-20260629` / `ADR-20260726-01` / `ADR-20260726-02` / `ADR-20260726-03` はそれぞれ2本のファイルが同一の識別子を持つ。参照トークンからはどちらを指すか判別できないため、これらの外部・内部参照件数は2本の合計である。#588 が扱う検知漏れの実例にあたる
2. **型分類は `## Decision` の分量の目視比較による。** 行数の機械計測はしていない
3. **問い2の判定は上限寄りに偏る。** 同点処理を0点（ADR 化しない）へ倒しているため、「今の基準なら ADR 化しない」の本数は過大に出る
4. **観測は1時点のみである。** §4.3 の閾値を定めるには複数時点の観測が必要である
5. **問い4の型ごとの偏りは、退役8本という小さな標本に基づく。** 傾向として読む以上の強度はない
