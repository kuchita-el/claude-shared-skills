## 1. 観測方法

### 1.1 定量値の取得

参照件数・状態分布・寿命は以下の方法で取得した。

**参照件数**は git 追跡ファイルを基準とし、`git grep` で取得した。抽出したトークンは**実在する ADR 識別子へ絞り込む**。この絞り込みがないと、テストスクリプトや `manage-adr` の例示が持つ架空の識別子を数えてしまう。

```sh
PAT='ADR-[0-9]{8,12}(-[0-9]{1,2})?'
REF=682e144   # 観測時点の commit へ固定する（HEAD を使うと後続の変更を巻き込む）
# 実在する ADR 識別子の一覧（ファイル名から採る。本観測時点では54個）
git ls-tree -r --name-only "$REF" -- docs/adr \
  | grep -oE 'ADR-[0-9]{8,12}(-[0-9]{1,2})?' | sort -u > /tmp/realids.txt
# 外部参照（docs/adr 以外の追跡ファイル。fixtures を除外し、実在識別子へ絞り込む）
git grep -hoE "$PAT" "$REF" -- . ':!docs/adr' ':!plugins/adr/scripts/fixtures' \
  | grep -Fxf /tmp/realids.txt | sort | uniq -c
# 内部参照（コーパス内の相互参照。自動生成の index.md を除外）
git grep -hoE "$PAT" "$REF" -- 'docs/adr' ':!docs/adr/index.md' \
  | grep -Fxf /tmp/realids.txt | sort | uniq -c
```

`REF` を `HEAD` に替えると値が変わる。本文書自身が ADR 識別子を大量に含むため、本文書を含むコミットで実行すると外部参照は334件から446件へ増える（寄与112件）。継続的に測る場合は §4.3 の除外規則に従う。

絞り込みの有無で値が変わるのは外部参照だけである。外部は絞り込みなしで380件、絞り込みありで334件（差分46件）。内部は653件で変わらない。差分46件の出どころは次のとおりで、いずれも架空の識別子を含む資産である。

| 件数 | ファイル |
|---|---|
| 21 | `plugins/adr/scripts/test-lint-adr.sh` |
| 14 | `plugins/adr/skills/manage-adr/references/io-examples.md` |
| 4 | `plugins/adr/skills/manage-adr/references/transitions.md` |
| 4 | `plugins/adr/scripts/test-next-adr-id.sh` |
| 3 | `plugins/adr/skills/manage-adr/references/adr-model.md` |

`':!plugins/adr/scripts/fixtures'` は fixture ディレクトリを除くだけで、テストスクリプト本体は除かない。本文書で外部参照といえば**絞り込みあり（334件）**を指す。

追跡外の作業成果物（`docs/plans/`、`.superpowers/`）は別枠で集計した。ここは `/usr/bin/grep -r` を用いる。

**測定上の注意（再現時に必要）**: 対話セッションの `grep` はユーザープロファイル由来のシェル関数（ugrep）へ解決される場合があり、これは `.gitignore` を尊重するためスクリプト内の `/usr/bin/grep` と走査範囲が一致しない。参照件数の集計は上記のとおり `git grep` で追跡ファイルへ範囲を固定する。

**状態分布**は front-matter の `status` / `validity` を先頭6行から読み取って集計した。

**寿命**（起票から退役までの日数）は、対象ファイルを変更した各コミットについて blob の front-matter を直読みし、`validity` が退役値になった最初のコミット日を退役日とした。

```sh
git log --follow --format=%ad --date=short --diff-filter=A -- "$f" | tail -1   # 起票日
git show "$sha:$path" | sed -n '1,6p' | grep -m1 '^validity:'                 # 各時点の状態
```

diff に対する `git log -S'validity: 上書き済み'` は使わない。状態モデルを説明する ADR が本文中に同じ文字列を引用しているため、front-matter の変更でないものを退役として誤検出する。

### 1.2 判定ルーブリック（問い2用）

ADR-202607191825-01 決定1 の4項目を既存 ADR へ遡及適用するため、以下を調査開始時に固定し、以後変更しなかった。判定は各項目 0 点または 1 点。判定対象は当該 ADR の `## Decision` に書かれた決定内容であり、ADR の書きぶり・分量ではない。

判定は「その ADR を今この基準で新規に起票するかどうか」を問う。ADR として既に存在するという事実自体は判定材料にしない。

**項目1: 後戻りコストが高い**

- 1点: 決定を反転すると既存の成果物の書き換え・移行が必要になる。対象は、ファイル群の構造変更、スキーマ・データ形式の変更、既に配布されたプラグインの利用者側への影響、蓄積済みデータの移行のいずれか
- 0点: 反転しても書き換えは局所（おおむね1〜2ファイルの文言修正）で済み、移行対象のデータや配布物への影響がない

**項目2: 複数モジュール・複数開発者に波及する**

- 1点: 影響が2つ以上のプラグイン／スキル／スクリプト／成果物種別に及ぶ。または、決定を知らない第三者が独立に別の選択をしうる箇所が複数ある
- 0点: 影響が単一ファイル・単一スキル・単一スクリプトの内部に閉じる

**項目3: 採用理由が時間経過で揮発しやすい**

- 1点: 採用理由が実装・テスト・fixture・コード内コメント・型定義のいずれにも残らず、ADR を消すと理由が復元できない
- 0点: 採用理由が実装側の資産（コード、テスト、fixture、スクリプトのヘッダコメント、テンプレート）に保持されており、ADR がなくても現物から読み取れる

**項目4: ツールで自動強制できない**

- 1点: 決定への違反を機械検出できない。lint・hook・スキーマ検査・フォーマッタ・テストのいずれでも違反を検出する手段が、現状も将来も取れない
- 0点: 違反を機械検出できる。現に検出している場合は必ず0点。検出機構を作ることが現実的に可能な場合も0点

**合計と判定**: 3点以上は今の基準でも ADR 化に該当、2点以下は今の基準なら ADR 化しない。

**同点処理**: 各項目の判定に迷った場合は0点へ倒す。ADR-202607191825-01 決定1 の「判断に迷ったら ADR 化しない」に合わせた向きである。この向きは「今の基準なら ADR 化しない」の本数を過大に数える方向へ働くため、集計値は上限として読む。

**レイヤ4同型フラグ**: 項目3が0点かつ項目4が0点であること。`lint-adr.sh` レイヤ4 と同じ性質（ツールで自動強制されており、採用理由は実装側が保持している）を指す。

**型分類**: 各 ADR を `構造モデル` / `運用手続き` / `ツール挙動` / `用語定義` / `配置命名` / `方針宣言` のいずれか1つへ主型として割り当て、複数該当する場合は `## Decision` の分量が最も多いものを主型、他を副型とした。

### 1.3 判定の実施と再現性の検証

上記ルーブリックを唯一の入力とし、59本を全数判定した。判定はサブエージェントへ分担し、結論のみを返させた。

再現性を測るため、同一のルーブリックで**独立に2回試行**した。2回目はバッチの切り方を変えた（1回目はファイル名の連番順に12本ずつ、2回目は5本刻みのストライドで割り当て）。同一バッチに入る ADR の組み合わせが変わるため、隣接する ADR の文脈に引かれる効果を排除できる。

この設計で測れるのは**同一手続きの試行間再現性**である。判定の担い手（モデル・エージェント種別・プロンプト）は2回で同一であり、担い手を替えた場合の一致（判定者間信頼性）は測っていない（§6-6）。

判定結果は2回分を全件 `docs/development/adr-scope-observation-judgments.tsv` に記録した。本文の集計値はすべて同ファイルから導出できる。同ファイルの先頭にある `#` で始まる行は注記であり、TSV パーサはこれを解釈しない。機械処理する場合は読み飛ばす。

### 2.2 問い2: 4項目の遡及適用

#### 判定が再現しない

同一ルーブリックによる独立2回の試行を突き合わせた結果である。生の一致率は偶然一致の寄与を含むため、Cohen の κ を併記する（κ =（実測一致率 − 偶然一致率）/（1 − 偶然一致率）。偶然一致率は各回の周辺分布から算出する）。

| 比較対象 | 1回目の1点率 | 2回目の1点率 | 実測一致率 | 偶然一致率 | κ |
|---|---|---|---|---|---|
| 二値分類（3点以上／2点以下） | 該当 39/59（66%） | 該当 36/59（61%） | 71.2%（42/59。17本が反転） | 53.5% | **0.38** |
| 項目1 後戻りコストが高い | 48/59（81%） | 48/59（81%） | 89.8% | 69.7% | 0.66 |
| 項目2 複数モジュールに波及する | 53/59（90%） | 51/59（86%） | 93.2% | 79.0% | 0.68 |
| **項目3 採用理由が揮発しやすい** | 40/59（68%） | 11/59（19%） | 40.7% | 38.8% | **0.03** |
| 項目4 ツールで自動強制できない | 29/59（49%） | 44/59（75%） | 71.2% | 49.6% | 0.43 |

**項目3は偶然を超える一致がほぼない（κ=0.03）。** 実測一致率40.7%は偶然一致率38.8%をわずかに上回るだけであり、この項目は判定の基準として機能していない。

κ で見ると二値分類（0.38）が項目4（0.43）を下回る。生の一致率では両者がともに71.2%で並ぶが、周辺分布の偏りを除くと二値分類の方が一致していない。

#### 不一致は系統的な方向シフトである

項目ごとの1点率を2回で比べると、項目3と項目4に逆方向の大きなシフトが出ている。項目3は68%から19%へ3分の1以下に減り、項目4は49%から75%へ1.5倍に増えた。項目1・項目2の周辺分布は安定している（81%→81%、90%→86%）。

これは個々の ADR で判定が独立に振れているのではなく、**2回の試行が項目3・項目4 の判定線を系統的に別の場所へ置いた**ことを意味する。原因は次項に挙げる定義の曖昧点であり、解釈が2通りに分かれた結果である。

2つのシフトは逆方向であるため、合計点では相殺される。**生の一致率71.2%は、二値判定の安定性を過大に見せている。** 合計点の一致が構成項目の一致より高く出るのは、逆方向の系統シフトが打ち消し合った結果であり、判定線が同方向へ動けば同じ相殺は起こらない。

ただし二値分類の κ=0.38 は周辺分布の偏りを補正した後の値であり、相殺の効果はその算出過程に織り込まれている。そこからさらに項目3のκ=0.03 側へ引き下げる根拠はない。

非該当の本数は次の区間に留まる。

- **下限13本**（両方の判定で2点以下）
- **上限30本**（いずれか一方の判定で2点以下）
- 全59本に対して22〜51%

1回目単独では20本（34%）、2回目単独では23本（39%）であった。いずれも一つの確定値として扱えない。

#### 再現しない原因

判定を担った複数の担当が、独立に同じ曖昧点を報告した。

1. `references/` 配下の共有規約ファイル（`behavior-invariants.md`、`subagent-execution-parameters.md` 等）が項目3の「実装側の資産」に含まれるかが、字義的に確定しない
2. `CLAUDE.md` を実装側の資産とみなすかどうかで項目3が反転する
3. 項目4の「ツールで自動強制できない」が、「現に強制していない」と「原理的に強制できない」の二義で読める。ルーブリックが「検出機構を作ることが現実的に可能な場合も0点」と将来可能性を含めたため、見積もりの幅がそのまま判定の幅になった

いずれも各項目の**操作的定義が存在しない**ことに由来する。ADR-202607191825-01 決定1 は4項目の名称とスコア境界を定めるが、各項目を何によって判定するかは定めていない。

#### 4項目の上位2項目は判定に寄与していない

項目1・項目2 がともに1点である ADR は、1回目48/59、2回目47/59（いずれも80%）であった。2回の試行を跨いで再現する。

このリポジトリの成果物はスキル定義や共有規約そのものであり、決定はほぼ必ず複数のスキル・プラグインへ波及し、反転には複数ファイルの書き換えを要する。したがって上位2項目は常時点灯し、判定を分ける働きをしない。

結果として、**3点という境界は「項目3か項目4のどちらかが1点か」という実質的な二値判定へ縮退している。** 4項目のうち2項目しか判定に寄与しておらず、しかもその2項目が上記のとおり最も再現しない。

## 3. 追加観測: 手続きコストの非対称

#589 の5問いには含まれないが、本調査の起点は「既存 ADR で決定したことを保全しようとすることが、結果的に意思決定を歪めかねない」という問題提起であった。5問いは総量とスコープを測るものであり、歪みそのものは測らない。判断材料として不足するため、並行して観測した結果を記録する。

観測できた事実は4点である。

**1. 手続きコストが変更方向にのみ発生する。** 既存決定を維持する場合のコストは0である。変更する場合は、`edit-decision.md` の分類（core／非core／些末）で core と判定されると、新規 ADR の起票・旧 ADR の `validity` 更新・双方向相互参照の書き込み・index 再生成・lint 通過が必要になる。編集対象は2ファイル、書き込み箇所は3箇所である。

**2. 既定が重い側へ倒れている。** `edit-decision.md` は分類を利用者へ問う際、既定選択肢を core とし「迷ったら core」を安全則として明示する。同ファイルはこの向きの根拠を可逆性の非対称に置く（core を非core と誤ると不可逆な不整合が残るが、逆は過剰なだけで可逆）。この評価は ADR ファイルの整合性を対象としており、**議論の場で結論が既存 ADR へ寄る効果は計上されていない。** ファイル上は可逆でも、寄った結論は可逆ではない。

**3. スコープが手続きコストで線引きされた実例がある。** #574 は OUT に「粒度判定基準の4項目・スコア境界・『判断に迷ったら ADR 化しない』の変更（ADR-202607191825-01 決定1 由来のため、変更は core 反転にあたる）」を挙げている。変更しない理由として挙げられているのは、内容の妥当性ではなく core 反転であるという手続き上の分類である。

**4. ADR 運用自身の改善が最も高い摩擦に置かれている。** ADR 運用を主題とする ADR は12本（20%）あり、両方の判定で非該当とされた13本のうち6本がここに属する。ADR 運用の改善は、その都度 ADR 手続きを駆動する。

## 4. 精緻化提案

### 4.1 判断: 4項目・スコア境界・「迷ったら書かない」は変更しない

ADR-202607191825-01 決定1 の4項目、スコア境界（3点以上／2点以下）、「判断に迷ったら ADR 化しない」は変更しない。したがって core 反転にはあたらず、同 ADR の上書き手続きは不要である。

ただし操作的定義を入れても再現性が改善しない場合、4項目の構成そのものを疑う必要がある。その判断を先送りにしないため、§4.3 の発火条件を併せて定める。

| 項目2 波及 | 影響が及ぶプラグイン／スキル／スクリプトを**列挙する** |
| 項目3 理由の揮発 | 「採用理由の保持先」として認める資産の**値域を閉じた列挙で固定する**。共有規約ファイル（`references/` 配下）と `CLAUDE.md` を含めるか否かを明示的に決める |
| 項目4 ツール強制 | **現在時制へ一意化する**（現に機械検査されているか）。将来の実装可能性を判定に混ぜない |

項目3の値域と項目4の時制は、§2.2 で判定が反転した原因に直接対応する。この2点を決めない限り、判定は再現しない。

**申し送り: 項目4の現在時制化は、文言上は追加でも判定結果を体系的に動かす。** 現在時制へ一意化すると「機械検査を作れるが未実装」の決定は1点（ADR 化寄り）へ倒れる。2回目の試行で項目4の1点率が75%と高かったことはこの向きと整合するが、どの試行がどちらの解釈を採ったかは記録していないため、現在時制解釈での実測とは断定できない。したがって ADR-202607191825-01 決定1 の core 反転にはあたらないが、**既存 ADR の判定結果は変わりうる**。この性質を #574 へ明示的に渡す必要がある（§4.4）。

また、ADR 化してから検査を実装した決定は事後的に非該当へ移る。これは §4.3 の発火条件で退役の検討対象として扱う。

### 4.3 提案B: 4項目を見直す発火条件

4項目の構成そのものを見直すべき状況を、観測可能な指標で定義する。いずれも本調査で実際に取得できたものであり、取得コストは低い。

| 発火条件 | 意味 | 本調査での実測 |
|---|---|---|
| **独立2回試行の κ が一定を下回る** | 判定が試行に依存し、基準として機能していない | 二値分類 κ=0.38、項目3 κ=0.03 |
| ある項目の該当率が一定を超える | その項目が常時点灯し、判定を分ける働きをしていない | 項目2が90%、項目1・2の同時点灯が80% |
| 起票から N 日以内の上書き率が一定を超える | 決定が固まる前に記録している（早期結晶化） | 退役8本中4本が15日以内、3本が2日以内 |
| ADR 運用自身を主題とする ADR の比率が一定を超える | 運用の改善が運用の手続きを駆動する自己言及の摩擦が増している | 59本中12本（20%） |
| 外部参照0件の比率が一定を超える | 記録が配布物・規約へ接続していない | 14/54（26%） |

**κ は該当率を代替しない。両方を見る。** κ は該当率（周辺分布）の偏りが生の一致率を押し上げる分を補正するが、「その項目が常時点灯して判定を分けていない」ことは検出しない。本調査の実測がそれを示している。

| | 該当率（1回目 / 2回目） | κ |
|---|---|---|
| 項目1 | 81% / 81% | **0.66** |
| 項目2 | 90% / 86% | **0.68** |
| 項目3 | 68% / 19% | 0.03 |
| 項目4 | 49% / 75% | 0.43 |

§2.2 が「判定に寄与していない」と結論した項目1・項目2 は、κ では表中で最も高い。κ だけで監視すると、この2項目は最良の項目として通過する。

2つは別の失敗モードであり、処方も異なる。

- **該当率が高い** = 安定しているが無情報。処方は項目の削除・統合・条件の細分化
- **κ が低い** = 解釈が試行ごとに割れる。処方は操作的定義の付与（提案A）

なお生の一致率は単独では使わない。該当率が偏るほど自動的に上振れするためである（本調査では二値分類と項目4がともに71.2%で並ぶが、κ では 0.38 対 0.43 と順序が入れ替わる。§2.2）。

**参照系の指標では、観測成果物自身を測定範囲から除く。** 本文書と判定 TSV は ADR 識別子を大量に含むため、これらを測定範囲に入れると外部参照は334件から446件へ増え（寄与112件）、TSV が全59識別子を列挙しているせいで**外部参照0件の識別子（観測時点で14）は0へ落ちる。** 除外しなければ、上表の最終行は本文書がマージされた時点から恒久的に0を返し、閾値を後から定めても発火しない。

```sh
# 参照系の指標を測る際に除外するパススペック
':!docs/development/adr-scope-observation*'
```

閾値の具体値は本文書では定めない。定めるには複数時点の観測が必要であり、本調査は1時点のみである。上記の実測値は最初の観測点として使える。

### 4.4 #574 との関係

#574 は `adr-scoping.md` に「発見型の入口」と「ADR 化しないと判定した対象の受け皿の一般則」を追加する。本調査の成果物は次の2点で #574 の根拠になる。

1. **受け皿の一般則が必要な事例は1件ではない。** レイヤ4同型は、両方の判定で該当したものだけでも6本ある（§2.2）。一般則の射程はメタ層（ADR 運用自身）に集中しており、`lint-adr.sh` レイヤ4 はその1例にすぎない
2. **入口の判定が再現しないため、受け皿だけでは足りない。** #574 が受け皿を整えても、判定が試行ごとに振れる限り、同じ対象が回によって ADR へ入る。提案A（操作的定義）を同一ファイルで併せて入れる必要がある
3. **提案Aは core 反転ではないが、既存 ADR の判定結果を動かす。** とくに項目4の現在時制化がこれにあたる（§4.2）。#574 は「4項目・スコア境界を変更しない」ことと「既存 ADR の判定結果が変わらない」ことを同一視しない。なお既存 ADR の棚卸しは #574 も本調査も OUT としており、判定結果が変わることと既存 ADR を是正することは別の問題である
4. **入口は「ADR 化するか否か」だけでは足りない。** 退役していない ADR による分散11件のうち6件は、既存の枠組みへ別の面を追加する段階的拡張である（§2.5）。そのうち `ADR-202606061159-01` は、当時 in-place 改訂が禁じられていたために別 ADR になったもので、現行の非core 改訂規定なら新規 ADR にならない。したがって発見型の入口は、ADR 化要否の手前に「既存 ADR への非core 改訂で済むか」の分岐を持たないと、同型の分散を再生産する
5. **分割は主題内の分散より主題の数を増やす。** 分割後継は同一主題へ揃って落ちない（§2.5）。「ADR 化しない」対象の受け皿を設計する際、総量の指標として主題数を使うなら、分割機構の副作用が乗ることを織り込む

1. **識別子の重複により、5組の参照件数を個別に帰属できなかった。** 観測時点（`682e144`）では、`ADR-202606211417-01` と `ADR-202606211859-01`、`ADR-202606291631-01` と `ADR-202606291949-01`、`ADR-202607261002-01` と `ADR-202607261459-01`、`ADR-202607261002-02` と `ADR-202607261501-01`、`ADR-202607261002-03` と `ADR-202607261503-01` の5組が、それぞれ2本で同一の識別子を共有していた（#567 の移行で解消済み）。参照トークンからはどちらを指すか判別できなかったため、本文書が記録するこれらの外部・内部参照件数は2本の合計である。#588 が扱う検知漏れの実例にあたる。なお本項を新識別子のペアで書き直した際（#593）に本文書が持つ識別子トークンは5件増えており、§1.1・§4.3 の自己参照の寄与112件はその増加を反映した値である
2. **型分類は `## Decision` の分量の目視比較による。** 行数の機械計測はしていない
3. **問い2の判定は上限寄りに偏る。** 同点処理を0点（ADR 化しない）へ倒しているため、「今の基準なら ADR 化しない」の本数は過大に出る
4. **追跡外の参照件数は観測時点固有であり、再現できない。** `docs/plans/` と `.superpowers/` は git 追跡外で作業のたびに増える。観測時点で総数2189件・`ADR-202607112231-01` が380件・`docs/plans/` が65ファイルであったが、これらは後から同じ値にならない（本文書の作成翌日には総数2382件・387件・113ファイルへ増えた）。§2.3 の定性的な結論（追跡外の参照密度が最も高い）は影響を受けないが、定量値を後続の根拠に使う場合は追跡下の値（外部334・内部653）に限る
5. **観測は1時点のみである。** §4.3 の閾値を定めるには複数時点の観測が必要である
6. **判定者間信頼性は測っていない。** §1.3 の設計は同一ルーブリック・同一の担い手（モデル・エージェント種別・プロンプト）でバッチの切り方だけを変えた2回試行であり、測れているのは試行間再現性である。担い手を替えた場合の一致は未観測であり、本文書の κ を判定者間信頼性として読むことはできない
7. **問い4の型ごとの偏りは、退役8本という小さな標本に基づく。** 傾向として読む以上の強度はない
8. **問い5の帰属は主題タグを単位とするため、タグの粒度に依存する。** 段階的拡張と判定した6件はいずれも「同一主題の別の面」であり（配置に対する内容、ドメイン層に対する Explanation 層、傘規約に対する個別適用、パークの充足）、タグを面の粒度まで細かくすれば分散として数えられなくなる。主題タグは問い5のために設けたものではなく、1回目の判定時に型分類と併せて付与したものである
9. **問い5のルーブリックのうち順7（段階的拡張）は消去法で決まる。** front-matter に前後継関係が記録されていない関係は捕捉できない。本調査では該当6件すべてについて本文の記述で先行への言及と非上書きの明示を確認したが、記録のない関係が他に存在しないことは示せない
