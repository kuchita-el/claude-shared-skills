# Shared Memory 設計

## 位置づけ

本書は、人間と AI が共有する記憶の仕組み（Shared Memory）の設計と、その根拠を持つ。対象は、記憶のデータの形と置き場、および `shared-memory` プラグインと検査器の役割分担である。

本書はストックであり、現在真であり続ける義務を負う。実装が本書と食い違ったら、どちらかを直す。記録と採用の台帳の項目ごとの定義、採用した記録の変化の判定、検査器が違反とするものは、配布物の `references/format.md` が正本であり、本書は再掲しない。

独立プラグインとして起こした判断と、却下した代替は ADR-202611140016-01 が持つ。立ち上げをどの工程で回すかは ADR-202611140053-01 が持つ。

## 1. 目的と、設計が守ること

目的は、開発で得た知識・経験・判断基準を、次の作業で再利用できる形で蓄積することにある。AI モデルを再学習させるのではない。モデルの外に置いた記憶を更新し、次の作業で参照する。対象はソフトウェア開発に限る。

設計は次を守る。以降の節の判断は、いずれかに根拠を持つ。

| 守ること | 内容 |
|---|---|
| 所有 | 記憶の原本は、利用者が所有する Git リポジトリの Markdown である。特定の AI サービスが無くても読める |
| ホスト非依存 | Claude Code と Codex、クラウドとローカルのどれからでも、同じ記憶を同じ規則で使える |
| 未検証の区別 | 検証していない仮説は、検証状況で検証済みの事実と区別して記録する。事実として引用しない |
| 出所の区別 | AI が推測した判断基準を、人間が明示したものとして記録しない。AI は自分の提案を、検証済みの事実として記録しない |
| 根拠の追跡 | AI が提案に使った記憶を、識別子と版で特定できる |
| 採用の固定 | プロジェクトが採用した判断の根拠は、後から記憶が更新されても変わらない |

追跡できるのは、AI が実際に取得した記録と、明示した判断の根拠である。モデル内部の思考過程は対象にしない。

## 2. growth との役割の違い

学びを扱う配布物は2つある。どちらも、利用者が管理するリポジトリへ学びを置ける。決定の記録を ADR へ向ける点も同じである。異なるのは、何を残すかと、置き場の形である。

| 観点 | growth | shared-memory |
|---|---|---|
| 残すもの | 検証を経た規範と、規範へ畳めない一回性の決定。それ以外の気付きは捨てる | 規範へ畳まない知識と経験も残す |
| 置き場の形 | 1つのファイル。エントリはメタデータを持たない | 1記録1ファイル。記録ごとにメタデータを持つ |
| 効かなくなったもの | 物理的に除去する | 置き換え済みとして残す |
| リポジトリをまたぐ参照 | 持たない | 持つ。採用と昇格が、別のリポジトリの記録を指す |
| 他の利用者への配布 | プラグインの配布の経路で配る | 配らない |

growth から引き継ぐのは考え方だけである。観測と解釈を分けること、未検証のものを検証済みのものと区別して扱うこと、機械で強制できる知識を lint やテストへ移すことの3つを引き継ぐ。

## 3. 構成

資産は、データと機構に分かれる。データは利用者のリポジトリに在り、機構は本リポジトリから配る。配布物へ実データを載せない。

```
[データ] Global Memory のリポジトリ（利用者が所有する。private）
  records/                    記録。1記録1ファイル。人間がマージか直接の編集で入れたもの
  candidates/                 選別の前の候補。プロジェクトが送り出しを承認したもの
  inbox/                      人間の未整理のメモ。索引の対象にしない
  index.md                    索引。記録と候補を分けて載せる。検査器が生成する
  policies/memory-policy.md   記憶の使い方の規則
  AGENTS.md / CLAUDE.md       規則の在り処を指す
  .github/workflows/          検査、索引の再生成、候補の取り込み

[データ] 各プロジェクトのリポジトリ
  docs/memory/records/        Project Memory。Global と同じ形式
  docs/memory/index.md        索引。検査器が生成する。記録を足す変更に含める
  docs/memory/outbox/         Global へ送り出す下書き。既定のブランチに在るものは、送り出しを承認済み
  docs/memory/adopted/        採用した Global の記録の台帳。1つの記録につき1ファイル
  docs/memory/tasks/          Task Memory。作業中のブランチにだけ在る
  AGENTS.md / CLAUDE.md       Project Memory の置き場と、Global Memory の利用規則の在り処を指す
  .github/workflows/          形式の検査と、Task Memory の残留の検出
  docs/adr/                   決定の記録。adr プラグインが扱う

[機構] 本リポジトリ
  plugins/shared-memory/
    .claude-plugin/plugin.json      Claude Code 用の manifest
    references/format.md            記録・索引・採用の台帳の形式
    references/matching.md          既存の記録との照合の手順
    references/confidentiality.md   記録がリポジトリの境界を越えるときの、機密の確認
    references/replacement.md       置き換えの手順
    references/carrying.md          承認済みの下書きを、Global の候補へ運ぶ手順
    scripts/memory.mjs              検査器
    agents/                         照合と突き合わせのサブエージェント
    skills/                         スキル
```

検査器は、ビルドを持たない単一のファイルとしてプラグインへ置く。依存は Node の組み込みだけにする。writing プラグインの検査器と同じ形である。記憶のリポジトリの CI は、プラグインを導入せずに、本リポジトリを clone して検査器を実行できる。

記録の版を返すコマンド、採用した記録の変化を報告するコマンド、下書きを候補へ写すコマンドだけは、git を呼ぶ。版はコミットであり、採用した版の内容と、運び済みかどうかは、git の履歴にしか無いためである。形式の検査と索引の生成は、git を要さない。記憶のリポジトリの CI が使うのは、この2つだけである。git のオブジェクトを検査器が自前で読む形は採らない。pack の形式を読む実装が要り、検査器の大半がそれになるためである。

検査器を配布物の外に置いて Release で配る形は採らない。形式を定める文書と検査器の版が別々になり、形式を変えたプラグインを古い検査器で動かせてしまうためである。

どのリポジトリを Global Memory にするかは、利用者が選ぶ。ADR の置き場は adr プラグインの設定に従う。

プロジェクト側の置き場（`docs/memory/`）は既定であり、利用先が変えられる。変えた置き場は、プロジェクトの指示ファイル（`AGENTS.md`。無ければ `CLAUDE.md`）に書く。プラグインを読み込まないセッションで AI に届くのは、指示ファイルだけだからである（4節）。CI は、ワークフローが検査器へ渡す引数として置き場を持つ。検査器は、根を引数で受け取り、既定を持たない。置き場を変えた利用先は、指示ファイルと CI の引数の2か所を直す。

採らなかった形は3つある。

- **設定ファイルを足す**: 指示ファイルの記述は要るままなので、置き場を書く箇所が3つに増える。プラグインの無いホストの AI は、設定ファイルを読む手順を持たない。
- **検査器に既定の `docs/memory/` を持たせる**: Global Memory の根はリポジトリの直下なので、既定が外れる。層によって、引数の要否が変わる。
- **目印で探す**（`records/` と `index.md` を持つディレクトリを探す）: 探す範囲が試行ごとに変わる。

記憶の根の中の配置と、記録の形式は、検査器の入力の契約として配布物が定める。記録は、検査器と複数のホストが読む交換の形式であり、形が揃わなければ索引と参照が成り立たない。設計原則 C05 は、入力の契約を配布物が持ち、格納先を利用先が選ぶと定める。本設計はこの分担に従う。

成果物ごとの維持の方針は次のとおりとする。

| 成果物 | 分類 | 手での編集 | 生成元 |
|---|---|---|---|
| 記録 | 権威あるストック | する | なし |
| 利用規則（`memory-policy.md`） | 権威あるストック | する | 初期化のときだけ、プラグインの雛形から作る |
| 採用の台帳（`adopted/`） | 権威あるストック | する | なし |
| 送り出しの下書き（`outbox/`） | 権威あるストック。送り出しの承認の正本 | 承認の前は書き換える。承認の後は、運ぶ前に消して取り下げることだけをする | なし。運んだ後に残すか消すかは、利用先が決める |
| 送り出しの報告（`outbox/` の下の階層） | 権威あるストック。送り出しの承認の材料 | 承認の前だけする | なし。下書きと一緒に残すか消すかは、利用先が決める |
| 選別の前の候補（`candidates/`） | 権威あるストック。選別までの間だけ在る | 選別でだけする | 送り出しの下書き。手を加えずに写す |
| 索引（`index.md`） | 再生成可能な派生物 | しない | 記録と候補の front-matter |
| Task Memory（`tasks/`） | 一時的なフロー | する | なし。レビューへ出す前に消す。既定のブランチへ入れない |

利用規則は、初期化したあとは利用者の資産である。プラグインの更新で上書きしない。

索引は、既定のブランチへコミットする。プラグインも検査器も無いホストから、索引を読めるようにするためである。検査器は、索引が記録と一致しないことを違反とする。

Global Memory の索引を保つのは、記憶のリポジトリの CI である。記録と候補を足す変更には、索引を含めない。既定のブランチへ入った後に、CI が索引を作り直してコミットする。人間が直接編集した場合も、運ばれた候補を CI が取り込んだ場合も、同じく索引が追随する（7.3節）。変更のたびに書き手が索引を直す形は採らない。並行する変更が索引の同じ箇所を書き換えて衝突するためである。手で保った索引が、同じ変更の中で記録の主張とずれた例もあった。

Project Memory では、記録を足す変更と直す変更に、索引を含める。索引は手で書かず、検査器で作り直す。索引が記録と一致しないことは、プロジェクトの CI が赤にする。CI は索引をコミットしない。理由は次のとおりである。

- Project Memory の書き込みは、その PR の中で起きる（5.1節）。書き手は checkout を持ち、検査器を実行できる。人間が端末の外から直接編集する、という Global Memory の事情が無い。
- CI が索引をコミットする形は、既定のブランチへ書く権限を CI に要る。既定のブランチを保護したリポジトリでは、採りにくい。
- 既定のブランチの上で、索引と記録が常に一致する。CI が保つ形では、マージから CI のコミットまでの間、索引が古い。
- 手元の検査と CI が、同じ `check` の1コマンドで済む。CI が保つ形では、検査の前に作業ツリーの索引を書き換える必要がある。
- 手で書いた索引が、生成した索引と一致しなかった例が在る。本リポジトリの Project Memory の `MEM-202611211012-01` が、この観測を持つ。

受け入れた不利益は、並行する変更が記録を足すと、索引が衝突することである。取り込んだ後に、検査器で作り直す。これは既定であり、利用先は Global Memory と同じ形を選んでもよい。検査器は、どちらの形でも同じコマンドで足りる。索引をコミットしない形（都度生成する）は採らない。プラグインも検査器も無いホストから、索引を読めなくなるためである。

## 4. 土台を、プラグインではなくリポジトリへ置く

記憶を参照する・提案に引用する・記録の追加を提案する、の3つの基本操作は、プラグインが無くても成立させる。必要なのは、利用規則の文章と git、PR を出す手段だけである。Global Memory への追加の提案は、プロジェクトの変更に下書きを載せることと、承認された下書きを運ぶことから成る（7.2節・7.3節）。運ぶのに要るのは、git と検査器と、Global のリポジトリへブランチを push する手段である。検査器は、プラグインを導入しなくても、公開のリポジトリから git で取得できる（3節）。

プラグインのスキルは、基本操作に取って代わらない。記録の追加の提案では、前段だけを担う。候補を挙げ、既存の記録と照らし、下書きを検査するところまでである。出し方は、利用規則に従う（7.1節）。

根拠は、クラウドのセッションがプラグインを読み込むとは限らないことにある。2026年11月の時点で、Claude Code on the web の公式文書は次のように述べていた。実機では確かめていない。

- リポジトリの設定でプラグインを有効にしても、クラウドのセッションは読み込まない。
- 複数のリポジトリを付けたセッションでは、リポジトリ側のフックを実行しない。
- リポジトリ内の `.claude/skills/` は読み込む。

次は、2026年11月に Claude Code on the web の1つのセッションで実測した。

- 開発対象のリポジトリ1つで始めたセッションへ、途中で2つ目の private リポジトリを追加できた。2つ目のリポジトリで、clone・push・PR の作成が通った。2つのリポジトリは、同じ階層に置かれた。
- 2つ目のリポジトリの `CLAUDE.md` と、そこから取り込んだ利用規則は、セッションを再開した時点で指示として読み込まれた。追加した直後には読み込まれなかった。

途中で追加したセッションでは、再開するまで利用規則が届かない。その間は、AI が利用規則を自分で読む。

次は、2026年11月に Codex のクラウドの1つのタスクで実測した。環境には、開発対象と Global Memory の2つのリポジトリを選んであった。

- 2つのリポジトリを、1つのタスクから読めた。
- 2つ目のリポジトリへ push し、PR を作れた。
- 2つ目のリポジトリの `AGENTS.md` は、タスクの開始の時点では AI へ示されなかった。AI がファイルを自分で読んで、初めて内容を得た。
- 既定のブランチのリモート追跡参照が無く、記録の版を得るコマンドが失敗した。既定のブランチを fetch した後に通った。

Global Memory のリポジトリの指示ファイルが届くかは、ホストによって異なる。届かないホストでも利用規則へ辿り着けるよう、開発対象のリポジトリの指示ファイルからも利用規則を指す。

人間の編集もプラグインを通らない。Obsidian から直接コミットする経路があるためである。

ここから、役割を次のように分ける。

| 担い手 | 役割 |
|---|---|
| 利用規則 | 基本操作の手順。どのホストの AI も、これを読めば操作できる |
| Global Memory のリポジトリの `AGENTS.md` / `CLAUDE.md` | 利用規則の在り処を指す。この指示ファイルを読み込むホストでは、これだけで届く |
| 開発対象のリポジトリの `AGENTS.md` / `CLAUDE.md` | Project Memory の置き場と、見る順を定める。記録を使うのに要る最小の手順を持つ。作業環境に在る Global Memory のリポジトリを、名前ではなく置き場の約束で指す。利用規則の本文は写さない |
| 記憶のリポジトリの CI | 形式の検査と、索引の再生成。人間の直接の編集も、ここで受ける。候補を足すだけのブランチを、既定のブランチへ取り込む（7.3節） |
| プロジェクトのリポジトリの CI | Project Memory の形式と、索引の一致の検査。送り出しの下書きの形式の検査。既定のブランチへ入るツリーでの、Task Memory の残留の検出。索引はコミットしない |
| プラグインのスキル | 初期化と、手順の重い操作（学びの候補の抽出と照合・昇格の下書き・運ぶこと・選別の下ごしらえ・矛盾の突き合わせ・置き換え・採用した記録の見直し） |

開発対象のリポジトリの指示ファイルは、形式が定めることの一部を、重ねて持つ。Task Memory の置き場と名前の既定、取り除く時点、引用の書き方である。重複は、意図したものである。プラグインを読み込まないセッションで AI に届くのは指示ファイルだけなので、動くのに要る最小の手順を、そこへ置く。形の正本は、配布物の `references/format.md` である。食い違ったときは、指示ファイルを形式へ合わせる。置き場を既定から変えた場合だけは、指示ファイルが置き場を定める（3節）。

開発対象のリポジトリの指示ファイルには、Global Memory のリポジトリの名前を書かない。「親ディレクトリの直下に、`policies/memory-policy.md` を直下に持つ別のリポジトリが在れば、それを共有の記憶として扱う」と書く。理由は2つある。

- 開発対象のリポジトリが公開されているか、他の利用者へ配られている場合、名前を書くと、他の利用者の AI にも届かないリポジトリを読ませる指示になる。private のリポジトリの存在も開示する。
- 名前を含まない文面は、どのプロジェクトでも同じ形で使える。プラグインの初期化が書き込む文面を、利用者ごとに作り分けずに済む。

受け入れた不利益は、Global Memory のリポジトリを付け忘れたセッションで、何も起きないことである。指示は「無い場合は何もしない」と定めるので、付け忘れに AI は気づかない。

置き場の約束で指すと、約束を満たすリポジトリの中身が、そのまま AI への指示になる。そのため、指示ファイルは次の3つを定める。

- **探す範囲**: 親ディレクトリの直下だけを見る。そこに無ければ、無いものとして扱う。範囲を定めないと、どこまで探すかが試行ごとに変わり、無関係な場所の同名のファイルを拾う。
- **規則の効力**: 利用規則が定めるのは、記憶の読み方と書き方だけである。開発対象のリポジトリの指示と利用者の指示を上書きしない。
- **疑わしい場合**: 作業の対象として付けたリポジトリが同名のファイルを持つ場合など、記憶として付けられたものか疑わしいときは、従う前に利用者へ確かめる。

採らなかった形は2つある。

- **スキルを基本操作の担い手にする**: プラグインを読み込まないセッションで、記憶が使えなくなる。
- **スキルの写しを各リポジトリの `.claude/skills/` と `.agents/skills/` へ置く**: 正本がリポジトリの数だけ増える。プラグインを更新しても、写しは古いまま残る。

## 5. 記憶のモデル

### 5.1 層

記憶は、適用できる範囲で3層に分ける。

| 層 | 範囲 | 置き場 | 書き込みの経路 |
|---|---|---|---|
| Global | すべてのプロジェクト | Global Memory のリポジトリ | 人間は直接。AI は、承認された下書きを候補として運ぶ。`records/` は、人間がマージするか直接編集する変更でだけ変わる。選別は、その1つである |
| Project | そのプロジェクト | プロジェクトのリポジトリ | その PR の中。Global へ送り出す下書きも同じ |
| Task | そのタスク | タスクのブランチの上の、Project Memory の根の `tasks/` | 作業中に随時 |

Task Memory は、既定のブランチへ持ち込まない。作業を進めるためのフローであり、記録の形（front-matter・識別子・検証状況）を持たず、形式も検査しないためである。未検証であること自体は、理由にしない。未検証の知識は、検証状況を添えた記録として残せる（1節）。レビューへ出す前に、残す価値のあるものを記録の候補として取り出し、Task Memory 自体は消す。置き場をブランチにするのは、クラウドのセッションでは push したものしか残らないためである。

候補を取り出す段では、プラグインのスキルが、Task Memory を材料として読める（7.1節）。必須の経路ではない。スキルは、Task Memory を消さない。消すのは、タスクを進めている持ち主である。

Task Memory は、Project Memory の根の `tasks/` に、タスクごとに1ファイルで置く。ファイル名の既定は、ブランチの名前から作る。名前を1つに固定する形は採らない。スタックしたブランチで、子が親のファイルへ追記するためである。親が消しても、子のファイルに親の内容が混ざったまま残る。並行するセッションも、同じファイルを取り合う。Issue の番号を名前にする形も採らない。配布物は、Issue の仕組みを前提にしない。根の外に置く形は採らない。AI と CI が知るべき場所が、2つになるためである。

取り除く時点は、レビューへ出す前とする。レビューを待つ間じゅう検出が赤い、という状態を作らないためである。レビューの指摘で作業が続く場合は、作り直してよい。

残留は、プロジェクトの CI が検出する。判定は、検査器の `check` の `--no-task-memory` が持つ。見るのは、既定のブランチへ入るツリーである。時点は2つある。既定のブランチを base にする PR と、既定のブランチへの push である。前者はマージの前に止め、後者はすり抜けたものを拾う。手元の検査と、base が既定のブランチでない PR では見ない。作業中のブランチには、Task Memory が在ってよいためである。既定のブランチへの push だけで見る形は採らない。入った後にしか分からないためである。

既定のブランチを base にする PR は、draft の間も見る。Task Memory を持ったまま PR を開くと、取り除くまで検出は赤い。スタックしていない普通のタスクが、これに当たる。この赤は、まだレビューへ出せないことを表す。draft の間は見ない形は採らない。レビューへ出す前に取り除くと決めたので、見ない期間を作る必要が無い。draft の有無に判定を掛けると、ホストの機能への依存も増える。

スタックしたブランチでは、親の Task Memory が子に残ることがある。2026年11月に git 2.43 で確かめた。親がファイルを消してから squash でマージされた場合、子が既定のブランチを merge で取り込むと、親のファイルが子に残った。親の旧い先端を起点に `rebase --onto` で載せ替えると、残らなかった。残ったファイルは、子が既定のブランチへ出す前に消す。

次は、2026年11月に Claude Code on the web の1つのタスクで確かめた。タスクのブランチは、既定のブランチではない別のブランチを base にしていた。

- Task Memory を commit して push し、別の文脈のエージェントが、ブランチから読んで検証に使い、追記できた。
- 申し送りとしては働いた。ただし、追跡していない計画の記号に頼る文は、そのファイルだけでは解けなかった。本リポジトリの Project Memory の `MEM-202611211045-01` が、この観測を持つ。
- レビューへ出す前に、残すものを取り出して、ファイルを消せた。
- 検査器の残留の検出は、ファイルが在るツリーで違反を返し、消したツリーで通った。手元で実行した。
- base が既定のブランチでない PR では、残留の検出のジョブは飛ばされた。

### 5.2 種類

層とは独立に、記録を5種類に分ける。

| 種類 | 内容 |
|---|---|
| Knowledge | 学んだ知識・事実 |
| Experience | 実際の作業・検証から得た経験 |
| Belief | 現在の判断基準・設計思想 |
| Decision | 意思決定と、その理由 |
| Evolution | 判断基準や知識が、何からなぜ変わったか |

Evolution は、旧い記録と新しい記録を結ぶ遷移の記録である。置き換えられた記録と、置き換えた記録を、それぞれ1件以上指す。片方しか指さない Evolution は作らない。記録を別の記録で置き換えるときは、必ず Evolution を作る。

プロジェクトの Decision は ADR を正本とする。Project Memory へ同じ決定を書かず、ADR の識別子で指す。決定を2か所に持つと、片方だけが更新されて食い違うためである。

ADR を正本とする方針は、検査器の規則にしない。検査器は、根がどの層かを知らない。ADR を使うかは、利用先が決める。ADR を使わないプロジェクトは、決定を Project Memory へ `decision` として書いてよい。ADR を使うプロジェクトは、指示ファイルで `decision` を使わないと定める。

### 5.3 記録の形

| 方針 | 理由 |
|---|---|
| 記録を種類ごとのディレクトリへ分けず、`records/` へ平置きする | 種類を直すたびにパスが変わると、記録を指す参照が切れる |
| 識別子は起票の時刻から作る | 複数のセッションが並行して記録を作っても、衝突しない |
| 層を識別子で区別しない。層は置き場が表し、引用と出典が層の名前を添える | 検査器は、根がどの層かを知らないまま、同じ形式を検査できる。記録の中にも層を書くと、置き場と記録の2か所が層を持つ |
| 種類・適用条件・出所・検証状況・確信度は front-matter に持つ | 索引を機械で作れる。Obsidian のプロパティとしても読める |
| 承認の状態を front-matter に持たず、置き場で表す | 既定のブランチの置き場が、承認の状態を表す。Project の `records/` と `outbox/` は、プロジェクトが承認したもの。Global の `candidates/` は、送り出しが承認され、受け入れが決まっていないもの。この約束は、利用規則と写すコマンドが保ち、Global の CI は確かめない（7.3節）。Global の `records/` は、人間がマージか直接の編集で入れたもの。未承認のものは PR と `inbox/` にだけ在る。承認の正本を2つにしない |
| Belief は、人間が明示したものか、AI が推測したものかを出所として持つ。この区別は利用規則で外せない | 推測した判断基準を、本人の判断基準として扱わないため |
| 置き換えた記録は消さず、置き換え済みとして残す。置き換え済みの記録は、置き換えた先を必ず持つ | 変遷を辿れる。置き換え済みの記録は、既定の索引から外す |

承認と検証は別のものである。既定のブランチの `records/` に在る記録は「残してよいと認められたもの」であり、「正しいと確かめたもの」とは限らない。後者は検証状況が表す。選別の前の候補も、検証状況を持つ。選別の状態を検証状況で表さない。`verified` の候補は、確かめたが、受け入れが決まっていないものである。

### 5.4 記憶の出口

記憶は、参照される根拠の置き場である。次に当たるものは、記憶に留めず移す。

- 機械で強制できるものは、lint・テスト・型へ移す。
- 毎回守る規範は、`CLAUDE.md` / `AGENTS.md` へ移す。

移した記録は置き換え済みとし、移した先を記録自身が指す。移した先は記録ではないため、この場合は Evolution を作らない。出口を持たないと記憶は増える一方になり、索引が読み切れなくなる。

## 6. 参照

AI は、索引を先に読み、関連する記録の本文だけを取得する。全文を読み込まない。

- **順序**: Project Memory を先に、Global Memory を後に見る。プロジェクト固有の制約は、一般の知識より優先するためである。食い違う場合は、Project Memory を優先し、食い違いを示す。
- **採用済みの優先**: プロジェクトが採用した記録は、台帳が固定した版で読む。最新の版と食い違う場合は、両方を示す。
- **索引の1行**: 識別子・種類・主張の要約・適用条件・検証状況を持つ。本文を取るかどうかを、この1行で判断できるようにする。
- **選別の前の候補**: Global の索引は、記録の表と候補の表を分けて持つ。候補は、検証状況にかかわらず、確かめていない仮説として扱う。事実として引用しない。引用するときは、識別子と版に「候補」と添える。候補は採用しない。採用の台帳が指せるのは、`records/` の記録だけである（8節）。
- **送り出しの下書き**: Project の `outbox/` は、プロジェクトの知識として読まない。索引に載せない。中身は Global の候補として読む。

候補を索引から外さないのは、承認を待つ間も、ほかのプロジェクトから読めるようにするためである（7節）。候補を記録と同じ表に混ぜない。読み手が、受け入れたものと、まだ選別していないものを、1行で見分けられるようにするためである。

記録の候補を足す前の、既存の記録との照合も、同じ順序と2段で行う。索引で選び、本文で確かめる。照合の相手には、Global の候補と、プロジェクトの `outbox/` の下書きも含める。同じ学びを、運ぶ前や選別の前に重ねて送らないためである。候補か下書きと重なり、補うものが無ければ、送らない。補うものが在れば、補う相手を本文に書いた下書きとして送り、選別でまとめる。手順の正本は、配布物の `references/matching.md` である。

AI は、設計や方式に関わる提案に、次を添える。

- 参照した記録の層の名前・識別子・版（`Project MEM-…@…`、`Global MEM-…@…`）
- 判断に使った前提
- 既存の記録との矛盾
- 確かめていない事項

記録の版は、その記録が在るリポジトリの既定のブランチで、その記録を最後に変えたコミットである。候補の版も、同じく数える。マージの前のブランチにあるコミットは、版として使わない。マージの方式によっては、そのコミットが既定のブランチに残らないためである。まだ既定のブランチに無い記録は、版の代わりに「未マージ」と書く。同じ変更で足した記録を引用する場合が、これに当たる。版を得る前に、既定のブランチの履歴を取り直す。クラウドの checkout は、履歴を一部しか持たないことがある。履歴が足りないまま git で版を数えると、エラーにならず、誤ったコミットが返る。履歴を1件だけ持つ clone で、記録を最後に変えたコミットではなく先頭のコミットが返ることを、2026年11月に git 2.43 で確かめた。

そのため、検査器の版を返すコマンドは、履歴が浅い checkout では版を返さずに止まり、取り直し方を示す。取り直すのは呼び出す側であり、検査器は、ネットワークへ出る git のコマンドを呼ばない。この約束の射程は、`references/format.md` が定める。採らなかった形は3つある。

- **浅くても、求めたコミットが履歴の切れた地点でなければ返す**: 正しさが、git が履歴を辿る順序の細部に掛かる。
- **検査器が自分で履歴を取り直す**: 認証と失敗の扱いが、検査器へ入る。
- **警告だけ出して版を返す**: 誤った版が標準出力に出て、呼び出す側がそれを引用する。

版を数える起点の ref は、呼び出す側が指す。省いたときは、clone のときに git が記録した remote の既定のブランチを使う。それも無ければ止まる。作業中の HEAD へは落とさない。記憶のリポジトリで PR 用のブランチに居ると、マージの前のコミットが版として出るためである。既定のブランチの名前を推測する形（`main`・`master` を順に試す）も採らない。名前の違うリポジトリで、存在しないブランチや別の用途のブランチを起点にするためである。remote へ尋ねる形も採らない。検査器がネットワークを使うことになる。既定のブランチの名前を知っているのは利用規則であり、起点を決める責任をそこへ置く。

起点が remote 追跡の ref のとき、ref が古いと、検査器は誤った版を正常終了で返す。記録が古い ref に無ければ「無い」と答え、下書きの手順はそれを「未マージ」と書く。浅い履歴と同じく、エラーにならない誤りである。そこで検査器は、起点が remote 追跡の ref か `FETCH_HEAD` のとき、その worktree の `FETCH_HEAD`（最後に取り直した結果）と照合する。食い違えば止まる。省いたときの既定も、解決した先の remote 追跡の ref で照合する。照合する行は、同じ枝を、その remote の URL から取り直した行に限る。枝の名前だけで照合すると、remote が複数ある checkout で、別の remote から同じ名前の枝を取り直した行と一致し、古い ref が通る。URL は、insteadOf を解いた remote の URL と、認証情報と末尾の `/`・`.git` を除いて比べる。git は、`FETCH_HEAD` へ書く URL をこの形に整える。クラウドの checkout でも、`FETCH_HEAD` の URL が remote の URL と一致することを、2026年11月に2つのリポジトリで確かめた。ローカルのブランチ・タグ・コミットは照合しない。それが既定のブランチを指すかは検査器には分からず、渡す側が責任を持つ。写すコマンドの、プロジェクトの起点だけは、渡す側に任せない（7.3節）。

枝が remote の fetch の refspec の外にあると、取り直しても remote 追跡の ref は作られないか、進まない（`--single-branch` の clone など）。そのとき検査器は、取り直しではなく `FETCH_HEAD` を起点にするよう案内する。取り直しを案内すると、従っても通らないためである。

照合で防げるのは、最後に取り直した結果と食い違う起点までである。取り直した後に上流が進み、ref と `FETCH_HEAD` が揃って古くなった状態は、ネットワークへ出ずには見分けられない。この残りは、版を求める直前に取り直す手順で塞ぐ。手順の正本は `references/format.md` である。採らなかった形は5つある。

- **remote へ尋ねて最新かを確かめる（`git ls-remote` など）**: 検査器がネットワークを使うことになり、認証と失敗の扱いが入る。検査器が自分で履歴を取り直す形を退けた理由と同じである。
- **起点に `FETCH_HEAD` だけを受ける**: `FETCH_HEAD` は、どの枝を取り直したかを起点として名指さない。別の枝だけを取り直した後でも、その枝を指したまま通る。remote 追跡の ref なら、同じ枝の行と突き合わせられる。
- **枝の名前だけで照合し、URL を比べない**: 別の remote から同じ名前の枝を取り直した行で、古い ref が通る。
- **URL が一致する行が無ければ、枝の名前だけの照合に落とす**: 同じ経路が残る。一致しない checkout では止まり、`FETCH_HEAD` を起点にする経路がある。
- **取り直してからの経過時間で判定する**: 上流が進む速さはリポジトリごとに違い、閾値を決める根拠が無い。同じ checkout でも、判定が時刻で変わる。

版は、コミットの省略形（7桁以上）で書く。利用規則と既存の記録が、この形を既に使っているためである。完全な形だけにする案は採らない。提案に添える引用が長くなり、既存の書き方と割れる。台帳の版は、文字列のまま比べない。コミットへ解決してから、その版での記録の内容を読む（8節）。省略形の長さが違っても、結論は変わらない。

AI が読むのは作業ツリーの記録であり、版は取り直した ref から数える。作業ツリーが古いと、読んでいない内容の版を引用する。そこで検査器は、作業ツリーの記録がその版と内容が違うとき、止めずに知らせる。止めないのは、作業用のブランチで記録を直している最中には、食い違って当然のためである。

利用規則は、版を得る手順として検査器のコマンドを指す。あわせて、検査器を入手できないホスト向けに、git だけの手順を予備として残す。基本操作を、利用規則と git だけで成り立たせるためである（4節）。

## 7. 更新

更新に人間の承認を置くかは、利用規則が定める。配布物は、承認を一律には求めない（設計原則 C06）。外せないのは、記録がリポジトリの境界を越えるときの機密の確認だけである（7.2節）。雛形の利用規則は、次のとおり承認を置く。

- **AI の更新**: AI は、Global の `records/` を直接変えない。Global へ足すものは、プロジェクトで送り出しを承認された下書きであり、候補として運ぶ（7.2節・7.3節）。`records/` を変えるのは、人間がマージするか、人間が直接編集する変更だけである。AI は、その変更をブランチに用意できる。候補を扱う変更が選別であり（7.4節）、ほかに、主張を変えない修正と、記憶の外へ移す変更がある。人間の判断基準を変える提案は、本人が承認するまで確定しない。
- **人間の更新**: 人間は直接編集してよい。形式の誤りは CI が検出する。走り書きは `inbox/` へ置き、後から記録へ整える。
- **昇格**: Task から Project へ、Project から Global へ昇格できる。上の層の記録は写しではなく、一般化した新しい記録である。Global への昇格は、送り出しの下書きを経る（7.2節）。
- **修正**: 新しい経験で既存の記録を直すときは、旧い記録を置き換え済みにし、Evolution に理由を残す。主張を変えない修正は、記録を直接直す。どちらも、Global では人間がマージする変更で行う。新しい経験による Global の修正は、候補として届き、選別で行う（7.4節）。

Global へ記録を入れるときの判断は、2つある。プロジェクトから送り出してよいかと、Global として受け入れる価値があるかである。2つは、観点も、判断できる人も、取り返せるかも違う。

| | 送り出してよいか | 受け入れるか |
|---|---|---|
| 観点 | 機密（固有名、認証情報、個人の情報、公開していない事情） | 正しさ、ほかのプロジェクトに当てはまるか、重なり、食い違い |
| 判断できる人 | 元のプロジェクトを知る人。何が機密かは、プロジェクトの中でしか分からない | Global を使う人。ほかの記録との関係が見える人 |
| 判断する場 | プロジェクトの PR（7.2節） | Global の選別（7.4節） |
| 誤りを取り返せるか | 取り返せない。Global へ push した文字列は、直しても履歴に残る | 取り返せる |

そこで、2つを別の場で行う。流れは次のとおりである。

1. タスクのセッションが、一般化した下書きを、プロジェクトの `outbox/` へ書く。機密の確認の結果を、送り出しの報告として同じ変更に入れる。
2. 人間が、プロジェクトの PR をレビューしてマージする。これが、送り出しの承認である。
3. 2つのリポジトリが在るセッションの AI か人間が、承認済みの下書きを、手を加えずに Global の `candidates/` へ写す。Global の CI が、候補を足すだけの変更を、既定のブランチへ取り込む。
4. 候補は、索引の候補の表に載り、ほかのプロジェクトから仮説として読める。
5. 人間が、都合のよいときに候補を選別する。AI は下ごしらえをする。

人間の操作は、2と5だけである。3と4には、人間の操作を置かない。置くと、承認を待つ列がそこへ移るだけだからである。

1つの場で2つを判断する形は採らない。Global への PR の中で、機密と受け入れを、人間が同時に承認する形である。この形には、次の不都合がある。

- 人間の機密の判断が、push の後にしか入らない。Global が公開のリポジトリなら、承認の前に漏れている。
- Global の承認者は、機密の確認を検証できない。照合した語を知るのは、元のプロジェクトだけである。
- 承認を待つ間、知識はほかのプロジェクトへ届かない。人間の居ないところで、PR が溜まる。
- 非対話の実行と、PR を出せないホストに、例外の道が要る。
- 昇格した記録の `Project` の出典は、元のリポジトリへのアクセスを持つ人にしか辿れない。出典で2度の昇格を防ぐ検索は、別のプロジェクトの同じ識別子にも一致する。識別子が、根ごとにしか一意でないためである。

採らなかった形は、ほかに2つある。

- **送り出しだけをプロジェクトへ移し、Global の PR の承認は残す**: 機密の判断の時点は直る。承認を待つ列と、PR を出せないホストのための例外の道が残る。
- **送り出しの承認を置かず、機械の確認と別の文脈の読みだけで送る**: 何が機密かは、プロジェクトの中でしか分からない。取り返せない判断を、プロジェクトを知る人間が見ないことになる。

受け入れた不利益は2つある。選別が、欠かせない工程になる。選別の前の候補が増えると、読む量が増える。

送り出しの下書き・運ぶこと・選別の下ごしらえ・突き合わせ・置き換えは、別々に起動できるスキルにする（設計原則 C03）。起動の契機・入力・書き先が違うためである。運ぶことは、候補の提案と昇格の終わりにも、同じ手順で行う（7.3節）。突き合わせを単独のスキルにするのは、プラグインを通らない書き込みを、後から確かめる入口が要るためである。1つのスキルにまとめる形と、突き合わせをサブエージェントだけにする形は採らない。

置き換えは、同じ根の中でそろえる。旧い記録の `superseded-by` と Evolution の記録は、同じコミットに入れる。片方だけの状態は、検査器が違反にするためである。新しい記録は、それより前か同じコミットに入れる。順序と確かめ方の正本は、配布物の `references/replacement.md` である。

置き換えの3つは、同じ変更（同じ PR）に入れる。新しい記録に使えるのは、その変更で `records/` へ足す記録だけである。既定のブランチの `records/` に入った記録を、後の変更で新しい記録にする形は採らない。3つを同じ変更で行うという形式の定めと、記憶の利用規則に反するためである。Global では、選別の変更の中で置き換える。選別で `candidates/` から移す候補は、その変更で `records/` へ足す記録である。どちらも既に既定のブランチの `records/` に在る2件の記録の食い違いは、置き換えのスキルの対象の外である。`records/` に在るかは、検査器が、起点の ref の `records/` にその記録を見つけるかで決める。通信はしない。判定は、手元の ref の時点のものである。

### 7.1 候補の提案

タスクで得た学びを記録の候補にし、既存の記録と照らして、下書きにして検査する。ここまでを、プラグインのスキルが受け持つ。手順の正本は、配布物のスキルと参照である。本節は、決めた形と理由を持つ。

**起動。** 人間か AI が、明示して起動する。配布物は、自動の起動を持たない。指示ファイルへ、促しの文面も書き込まない。候補を確かめる時点を促すかは、利用規則が決める。理由は3つある。クラウドのセッションは、プラグインもフックも読み込むとは限らない（4節）。候補を挙げる時点は、利用先の工程である。設計は、レビューへ出す前に残すものを取り出す、という時点を既に持つ（5.1節）。採らなかった形は3つある。

- **配布物が、指示ファイルへ促しを書き込む**: プラグインを読み込まないセッションで、存在しないスキルを指す指示が残る。
- **定期的にまとめて行う**: 材料である会話が、セッションの外に残らない。人間の居ないところで、PR が溜まる。
- **フックで起動する**: プラグイン単位のフックを持たないホストで動かず、ホストで挙動が割れる。

**層。** 候補は、Project Memory へ置く。次の3つを全て満たす候補だけを、Project の記録を経ずに、Global へ送り出す下書きにする。下書きは、Project の `outbox/` へ置く（7.2節）。迷えば、Project へ置く。

- Global Memory の根と、Project Memory の根が、どちらも在る。
- 主張と当てはまる条件が、プロジェクトのコード・構成・規約・決定を条件に含まない。
- 機密の情報を含めずに書ける。

理由は3つある。

- 層は、適用できる範囲で決まる（5.1節）。範囲がプロジェクトを越える記録を Project に置くと、他のプロジェクトから見えない。
- 昇格は、一般化した新しい記録を作る。既に一般的な主張には、一般化の余地が無い。Project の記録を経由させると、同じ主張の記録が2件残る。
- Global へ送り出すことは、利用規則が定める基本操作である（4節）。スキルだけが禁じても、基本操作では起きる。

Project Memory の根を求めるのは、送り出しの下書きの置き場が、その根の `outbox/` だからである。根が無いプロジェクトでは、Global 向きの候補も、見送りとする。Global Memory の根を求めるのは、送り出しに効く利用規則と照合の相手を、その根が持つためである（7.2節）。

Global の既存の記録と食い違う候補や、既存の記録に足せる候補も、置き換えや追記にしない。食い違いか、補うものを本文に書いた下書きとして、送り出す。直すかどうかは、選別で決める（7.4節）。

検証状況は、層を分ける条件にしない。確かめていない候補は、`unverified` と書いて、決まった層へ置く。未検証の仮説は、置き場ではなく検証状況で区別するためである（1節）。別の文脈が観測し、スキルを実行する文脈が確かめていないものも、`unverified` とする。出典に、誰が観測したかを書く。AI は、自分で確かめていないことを、検証済みの事実として記録しないためである（1節）。既存の記録と食い違う未検証の候補は、置き換えにしない。食い違いを本文に書いた仮説として足す。置き換えは、確かめた候補に限る。採らなかった形は4つある。

- **常に Project を経由する**: 上の誤配置と重複が残る。
- **条件を定めず、AI の判断に任せる**: 判定の入力が決まらず、試行ごとに層が割れる。
- **種類で決める**: 種類と層は独立である（5.2節）。プロジェクトに固有の経験も在る。
- **検証済みの候補だけを Global へ送り出す**: 未検証の仮説を、層で隔てることになる。区別は、検証状況が受け持つ。

**件数。** 候補は、単位と関門で絞る。そのうえで、下書きにする数に目安を置く。

- 単位は、1つの主張である。同じ1回の試行や、同じ対象から出た複数の観測は、それぞれが別々に次の行動を変えるときだけ分ける。
- 関門は、次を確かめる。このタスクでの観測が在る。次の作業で行動が変わる。記憶の出口（5.4節）と、決定の正本（5.2節）へ送るものでない。
- 下書きにする候補が、置く先の層ごとに目安の数を超えるときは、次の行動の変化が大きい順に並べ、上位だけを下書きにする。残りは、見送りとして、理由つきで表に残す。捨てた候補も、同じく表に残す。

目安は上限ではない。超えるときに絞る手順の起点である。数と並べる基準は、配布物のスキルが持つ。利用規則が別の数を定めれば、それに従う。目安を置くのは、単位と関門だけでは絞り切れないためである。1つのタスクの材料から、関門を通る候補が、人間が1件ずつ承認できる量を大きく超えて出たことが在る。どれも観測を伴い、行動が変わると言えるものだった。数を置く先の層ごとに数えるのは、層ごとに承認の観点が違うためである。Project の記録は残してよいかを、送り出しの下書きは外へ出してよいかを、人間が1件ずつ見る。採らなかった形は4つある。

- **目安を置かず、単位と関門だけで絞る**: 関門を通る候補が多いタスクで、承認が形だけになる量の下書きが出る。
- **固定の上限を置き、超えた分を落とす**: 長いタスクの正当な学びを、数を理由に黙って落とす。見送りとして表に残せば、人間が名指して戻せる。
- **多いときに、読み直して減らすよう促す**: 書いたものを、同じ文脈で読み直す手順になる。同じ文脈は、同じ見落としを繰り返す。並べる基準を先に定めておけば、読み直しに頼らずに絞れる。
- **下書きの前に、人間の承認を挟む**: 利用規則が置く承認と、二重になる。

**照合の文脈。** 照合は、候補を書いた文脈とは別の文脈で行う。ホストの機構に合わせて、3段で落とす。定義済みのサブエージェントを起動できれば、起動する。できなければ、汎用のサブエージェントへ定義のファイルを渡す。それもできなければ、同じ文脈で同じ手順どおりに照合し、出力にそう書く。別の文脈を必須にしないのは、照合の誤りを取り返せるためである。下書きは、プロジェクトの PR で人間が見る。Global へ送り出した下書きは、選別でも見る。採らなかった形は3つある。

- **別のセッションで照合する**: スキルが途中で止まり、人間が結果を運ぶ工程を課す。
- **照合を省く**: 重なる候補を、足す側へ入れてしまう。
- **どのホストでも、同じ文脈で行う**: 索引と本文が、候補を書いた文脈に載る。独立の利点も捨てる。

**出し方。** スキルは、下書きと検査までを自分の道具で行う。Project の記録も、送り出しの下書きも、作業中のブランチの変更として残す。commit・push・PR の作成は、プロジェクトの工程に従う。スキルの終わりに運ぶとき（7.3節）だけ、Global のリポジトリへ push する。commit・push・PR の作成を、スキルは事前に許可しない。了承は、ホストの許可の確認が受け持つ。応答で尋ねて止まらない。許可されない・確かめられないときは、運ばずに止まる。承認済みの下書きは `outbox/` に残り、次に運ぶ者が運ぶ。Global の利用規則を読めないときは、送り出しの下書きを書かない（7.2節）。Project の規則を読めないときは、Project の記録の下書きで止まり、出していないと報告する。理由は2つある。PR を出す手段と push の可否は、ホストで違う（4節）。push と PR を事前に許可すると、利用者の許可の設定を、配布物が飛び越える。採らなかった形は4つある。

- **スキルが PR まで出す**: 特定の道具を前提にすると、動かないホストが出る。承認を置くかを、配布物が決めることにもなる。
- **下書きで必ず止める**: 利用規則が在る根でも、起動した人が、続きを自分で指示することになる。
- **文で尋ね、答えを待つ**: 非対話の実行では、答えが来ないまま了承待ちで止まる。未回答をいつ見切るかを、スキルが決めることにもなる。ホストの許可の確認なら、対話では答えを待ち、非対話では拒むので、未回答が残らない。
- **`AskUserQuestion` を許可に足す**: 対話の経路が無い実行では尋ねられず、未回答の扱いが残る。対話の経路が在っても、ホストの許可の確認と二重に尋ねる。

**索引。** 下書きを置いた根の規則に従う。Project Memory の既定では、作り直した索引を同じ変更に含める（3節）。送り出しの下書きは、索引に載らない（6節）。検査の合否は、検査器の違反の行で決める。

**機密。** 送り出しの下書きの機密の確認は、7.2節が定める。

### 7.2 送り出し

**置き場と形。** 送り出しの下書きは、Project Memory の根の `outbox/` に、1件1ファイルで置く。形は、記録と同じである。Global の `candidates/` へ、手を加えずに置ける形で書く。

- 識別子は、新しく発番する。元の記録の写しではなく、一般化した新しい文書だからである。
- 出典には、誰でも辿れるものだけを書く。公開の文書の URL と、「いつ、どの環境で実測したか」の形の記述である。`Project` の出典は書かない。Global の記録を指すときは、識別子だけを書く。置かれる先の根の記録になるためである。
- 置き換えの項目（`superseded-by`・`moved-to`）を持たず、`evolution` にしない。Global の置き換えは、選別で行う（7.4節）。
- 未検証の記録も、`unverified` のまま送り出せる。下書きの本文と送り出しの報告に、未検証であることを書く。利用規則が認めないと定めていれば、送り出さない。

検査器は、`outbox/` と Project の `records/` を合わせて、識別子の重複を見る。元の記録と同じ識別子を下書きに付ける誤りは、ここで止まる。上の出典と置き換えの定めも、検査器が見る。形式の定義は、配布物の `references/format.md` が持つ。

**送り出す時点。** 送り出しの下書きは、Global Memory の根と Project Memory の根が、どちらも在るセッションで書く。送り出しに効く利用規則（機密として照合する語、未検証の記録を送ってよいか、件数の目安）は、Global の根が持つためである。Global の根が無いセッションでは、送り出しの下書きを書かない。Global の根の利用規則が在るのに読めないときも、書かない。Project の記録は書ける。Global の根が無いまま書く形は採らない。利用規則が挙げる語を照合しないまま、承認されて運ばれる経路が残るためである。運ぶ時点で照合し直す形も採らない。承認の後に止まると、直すには新しい下書きと承認がもう一度要り、送り出しの前に照合するより手間が大きい。

**承認。** プロジェクトの既定のブランチの `outbox/` に在ることが、送り出しの承認を表す。下書きは、タスクの PR に載せる。既に在るレビューの中で判断でき、承認だけの列を別に作らずに済む。承認した後に、下書きを書き換えない。

**取り下げ。** 運ぶ前に誤りが分かったら、下書きを `outbox/` から消して取り下げる。直すときは、新しい下書きを足す。取り下げは、消す変更が既定のブランチへ入った時点で効く。それまでに運ばれた下書きは、取り下げられない。運んだ後に誤りが分かったら、選別で候補を除く。機密の誤りは、除いても Global の履歴に残る（7節）。

この承認は、プロジェクトの既定のブランチへ入る変更を、人間が見ることに依る。AI が人間を経ずに既定のブランチへ書けるプロジェクトでは、`outbox/` に在ることは承認を表さない。そのプロジェクトは、指示ファイルで、`outbox/` を変える変更を人間のレビューに通すと定める。配布物は、これを検査しない。誰がマージしたかは、ツリーからは分からないためである。

**元の記録との対応。** 元の記録との対応は、プロジェクト側に持つ。Global の記録には書かない。ほかのプロジェクトの読み手には、辿れない識別子だからである。

- 昇格の下書きを書くときは、元の記録に `sent-as` を書き、下書きの識別子を並べる。下書きと同じ変更で書く。主張は変えないので、置き換えにはしない。
- `sent-as` を持つ記録を昇格しようとしたら、送った下書きを示して止める。送り直すと、起動した人が明示したとき（`promote-record` の `--resend`）だけ進む。内容の重なりの判定は、Global の選別が受け持つ。
- 下書きを取り下げたら、消す変更と同じ変更で、元の記録の `sent-as` からその識別子を外す。取り下げた下書きのために、送り直しが止まらないようにするためである。
- 元の記録は、同じ変更で足すものでもよい。昇格の元を既定のブランチの記録に限っていたのは、既定のブランチに在ることが、承認済みであることを表すためだった（5.3節）。元の記録と下書きを同じ変更に入れれば、その変更のレビューが、両方の承認を兼ねる。そのため、限る理由が無い。

採らなかった形は3つある。

- **Global の記録に `Project` の出典を書く**: ほかのプロジェクトの読み手には、意味が取れない。出典で2度の昇格を防ぐ検索は、別のプロジェクトの同じ識別子にも一致する。
- **対応を下書きの front-matter に持ち、運ぶときに除く**: 運ぶものと承認したものが、バイトの単位で一致しなくなる。運び済みかを、内容の一致で判定できなくなる（7.3節）。
- **対応の台帳を、別の置き場に作る**: 元の記録に書けば、昇格の手順が既に読むファイルで足りる。置き場と形式を増やさずに済む。

**機密の確認。** 機密の確認は、利用規則で外せない。記録が、元のプロジェクトを知らない読み手へ届くためである。確認は、下書きを `outbox/` へ書いた後、プロジェクトの PR をレビューへ出す前に行う。下書きは、まだプロジェクトの中に在る。境界を越えるのは、運ぶとき（7.3節）である。そのため、下書きを作業ツリーの外の一時の置き場に置く必要は無い。

確認は2段で行う。1段目は語の照合である。元のプロジェクトのリポジトリの名前と所有者の名前などを、下書きから機械で探す。2段目は読みである。認証情報、個人の情報、語に載らない固有名を、下書きを書いた文脈とは別の文脈が読んで探す。書いた文脈は、プロジェクトの名前を普通の語として読むので、混入に気づきにくい。対象と手順の正本は、配布物の `references/confidentiality.md` である。

結果は、送り出しの報告として、下書きと同じ変更にファイルで入れる。人間が、承認の判断に使う材料だからである。書くのは、下書きを書いたスキルである。プラグインの無いホストでは、下書きを書いた者が書く。報告は PR の差分に載るので、誰が PR を作っても、承認する人間は報告を見る。報告は `outbox/` の下の階層の `reports/<下書きの識別子>.md` に、下書き1件につき1ファイルで置く。取り下げと運ぶことが、下書きの単位だからである。写すコマンドは、報告を写さない。報告は、下書き・元の記録・語の照合・読み・重なりの照合の5つの節を持つ。形の正本は、配布物の `references/outbox-report.md` である。照合した語のうち、元のプロジェクトのリポジトリから得た語は、報告に書いてよい。報告の読み手は、そのリポジトリを読める。利用規則と利用者が挙げた語は、件数だけを書く。プロジェクトのリポジトリに無いことがある語であり、公開のプロジェクトでは、報告に書くと漏れる。

報告の置き場で採らなかった形は2つある。

- **スキルの出力に載せ、PR を作る者が説明へ写す**: スキルを実行したセッションと PR を作る者が別のとき、承認する人間に届かない。人間が PR を作るときも同じである。
- **Task Memory に置く**: レビューへ出す前に消すので、承認する人間に届かない。

別の文脈を作れないホストでは、読みを同じ文脈で代えない。報告に `未実施` と書き、送り出しを止めない。最後の門は、PR を承認する人間である。語の照合は、どのホストでも必ず行う。採らなかった形は2つある。

- **別の文脈を作れないホストでは送り出さない**: 人間がプロジェクトの中で文面を見る門が無い場合の定めである。門を置くので、ホストの機構で送り出しを止める理由は弱い。
- **語の照合も任意にする**: 照合する語は、元のプロジェクトのセッションでしか集められない。機械で確かめられるものを、人間の目だけに頼ることになる。

受け入れた不利益は、PR を承認する人間も、プロジェクトの名前を普通の語として読むことである。読みが `未実施` の下書きでは、書いた文脈と同じ見落としが残りうる。照合した語と一致の箇所を報告に示して、補う。

機密の確認で採らなかった形は、ほかに2つある。

- **検査器に秘密の走査を持たせる**: 認証情報の型の一覧は、保守の対象が増える。プロジェクトの名前は、記録の内容だけからは決まらない。
- **書いた文脈の読み直しだけにする**: 同じ文脈の再確認であり、足しても見落としは減らない。

**送り出しで、受け入れの判断はしない。** 昇格で確かめることは5つある。元の経験は検証済みか、他のプロジェクトにも当てはまるか、適用条件と例外は何か、機密の情報を含まないか、既存の記録と矛盾しないか、である。送り出しで確かめるのは、機密である。ほかに、重なりの照合だけを、送るかを決めるために行う。Global の記録と候補との突き合わせを行い、重なって補うものが無ければ、送らない。結果は報告に添える。残りの4つ（検証済みか、他のプロジェクトにも当てはまるか、適用条件と例外、既存の記録との矛盾）は受け入れの観点であり、選別で確かめる（7.4節）。材料は、下書き自身が持つ。検証状況・確信度・当てはまる条件は front-matter に在り、当てはまらない場合は本文に在る。

### 7.3 運ぶ

**運ぶもの。** 運ぶのは、プロジェクトの既定のブランチの `outbox/` に在る下書きだけである。作業ツリーと、作業中のブランチからは運ばない。承認されていないものを、運ばないためである。既定のブランチの起点の決め方と、取り直した結果との照合は、記録の版と同じである（6節）。ただし、記録の版と違い、写すコマンドは、渡された起点が既定のブランチを指すことを自ら確かめる。確かめられない起点（ローカルのブランチ・タグ・コミットなど）は、渡す側の責任に任せず、拒む。ただし、この確かめは渡し間違いを防ぐもので、ローカルの `refs/remotes/origin/HEAD` を意図して付け替える者は防げない。承認の保証は、プロジェクトのレビューに在る。

**運ぶ者と時点。** 2つのリポジトリが在るセッションの AI か、人間が、明示して運ぶ。運ぶ手順は、単独で起動できる。候補の提案と昇格の終わりにも、まだ運んでいない下書きを、同じ手順で運ぶ。そのプロジェクトで作業が続く限り、承認から運ぶまでの遅れは小さい。手順の正本は、配布物の `references/carrying.md` である。採らなかった形は2つある。

- **プロジェクトの CI が、マージの後に運ぶ**: Global へ書ける鍵を、プロジェクトごとに置くことになる。既定のブランチを保護していなければ、その鍵で既定のブランチも書き換えられる。採用した記録の変化の検出で、リポジトリをまたぐ認証情報を CI に置く形を退けた理由と同じである（8節）。運ぶのは同じコマンドなので、後から CI を呼ぶ側として足せる。
- **人間が運ぶか、取り込む**: 承認を待つ列が、運ぶ段へ移るだけである。

受け入れた不利益は、誰かが運ぶまで、承認済みの下書きが Global へ届かないことである。

**写し方。** 検査器の写すコマンド（`carry`）が、起点の `outbox/` の下書きを、手を加えずに Global の `candidates/` へ写す。AI は中身に触れない。承認したものと運ぶものを、バイトの単位で一致させるためである。

写す前に、運び済みかを判定する。判定が見るのは、Global の起点の ref から辿れる履歴の、`candidates/` と `records/` である。今のツリーだけでは見ない。次を上から当て、最初に当たったものにする。

1. 同じ内容のファイルが、一度でも在れば、写さない。内容は、git の blob の識別子で比べる。選別で捨てた候補を、運び直さないためである。運んだ後に `outbox/` に残っている下書きも、これで飛ばす。選別で言い回しを直して採った候補の下書きも、運んだときの内容が履歴に在るので、これで飛ばす。
2. 同じ識別子のファイル（名前が `<識別子>-` で始まるもの）が、一度でも在れば、写さずに止まり、示す。別のプロジェクトの記録と識別子が重なったか、承認した後に下書きを書き換えたかである。どちらも、人間が決める。
3. どちらにも当たらなければ、写す。

判定には、Global の既定のブランチの履歴が要る。履歴が浅いときは、記録の版と同じく、写さずに止まる（6節）。

運んだ下書きを `outbox/` に残すか消すかは、利用先が決める。運び済みの判定が Global の履歴を見るので、どちらでも2度は運ばない。

検査器を入手できないホストのために、git だけで運ぶ予備の手順は置かない。運び済みの判定を手順の文で再現すると、判定の誤りが、運び直しか取りこぼしになる。取りこぼしは、誰にも気づかれない。版の予備の手順（6節）と違い、運ぶことは急がない。運べないホストでは運ばずに止まり、下書きは次に運ぶ者が運ぶ。

**Global への入れ方。** 運ぶ者は、写すコマンドが書いたファイルを git でコミットし、`candidates/` へファイルを足すだけのブランチを、Global のリポジトリへ push する。API を介してファイルの中身を渡すコミット（GitHub の MCP の道具など）では運ばない。中身が AI の手を通り、バイトの単位で一致することを保てないためである。Global の CI が、次の2つを確かめて、既定のブランチへ取り込む。索引は、取り込むコミットの中で作り直す。

- ブランチが既定のブランチから分かれた点（merge-base）からの変更が、`candidates/` の直下への `.md` の追加だけである。
- その変更を既定のブランチの先端へ合わせたツリーが、形式の検査を通る。

差分は、分かれた点から数える。既定のブランチの先端とのツリーどうしでは比べない。取り込みのたびに CI が索引をコミットするので、ツリーで比べると、前の取り込みより前に切ったブランチが、全て取り込めなくなるためである。運ぶ者は、ブランチを、運び済みの判定に使った Global の起点から切る。同じパスを並行して足したブランチは、合わせられずに取り込めない。取り込みのジョブは、push されたコミットに在るワークフローの定義で走る。既定のブランチから切るので、既定のブランチの定義で走る。この起動と取り込みは、実機で確かめた。クラウドのセッションから git で push すると、push のイベントで取り込みのジョブが起動する。CI は、GitHub Actions の既定のトークンで既定のブランチへ取り込みを push でき、取り込んだブランチを消せる。

**取り込みの形。** 既定のブランチの先端から、ブランチが足した `candidates/` のファイルだけを取り出し、作り直した索引と合わせて、1つのコミットにする。コミットの author は、ブランチの先端のコミットの author を引き継ぐ。先端にもう同じパスが在れば、取り込まずにジョブを失敗させる。merge のコミットも早送りも使わない。理由は3つある。

- 取り込むものが、判定した「足したファイル」と構造の上で一致する。
- 先端に同じパスが在る場合だけが衝突であり、判定が単純になる。
- CI の push は既定のトークンで行うので、別のワークフローの起動を生まない。索引のジョブは走らないので、索引を同じコミットで作り直す。

**直列にする。** 取り込みのジョブは、1つの並行の組（`concurrency` の `group`）に入れ、走っている実行を取り消さない。先端へ push して競合したら、取り直して1回だけやり直す。それでも競合すれば、ジョブを失敗させる。GitHub は、組ごとに待ちの実行を1つしか持たない。3つ以上が重なると、間の実行が取り消される。取り消されたブランチの候補は、既定のブランチの履歴に入らないので、運び済みの判定に当たらず、次に運ぶ者が運び直す。

**取り込んだブランチ。** 取り込んだ後に、CI がブランチを消す。候補を足すだけのブランチは、取り込めば役目を終えるためである。取り込めなかったブランチは残し、人間が見られるようにする。

ほかの変更を含むブランチは取り込まず、人間のマージを待つ。CI は、そのブランチでは何もしない。選別の変更を用意したブランチが、これに当たる。こうして、2つを両立させる。候補は、人間の操作なしで入る。`records/` は、人間がマージするか直接編集する変更でしか変わらない。

**取り込みの結果。** 候補を足すだけのブランチを取り込めなかったとき、CI はジョブを失敗させる。検査を通らないとき、先端に同じパスが在るとき、やり直しても push が競合したときである。運ぶ者は、push の後に Global の既定のブランチを取り直し、候補が入ったかを確かめて報告する。CI が終わる前なら、push までを報告し、取り込みは確かめていないと書く。push の成功を、運んだ結果として報告しない。取り込まれなかった下書きは、運び済みの判定に当たらないので、次に運ぶ者が運び直す。

push は、ホストの許可の確認に任せる。許可されない・非対話で拒まれる・手段が無いときは、運ばずに止まる。push するのは、写す前に名前が空いていると確かめた、新しい `carry/*` のブランチだけである。名前が、手元か remote（`ls-remote` で問い合わせる）に在れば、写さずに止まる。写した後に `switch -c` が失敗すると、写したファイルが作業ツリーに残り、次に運ぶ者が止まるためである。クラウドのセッションのように、Global の根が作業用のブランチに居て、ホストがそこへの push しか許さないときは、運ばない。取り込む CI は、取り込んだブランチを消すので、作業用のブランチを取り込み元にできない。運ぶには、新しい `carry/*` のブランチを push する許可が要る。運ぶ手順の前提には、Global の利用規則が `candidates/` と運ぶことを定めていることも置く。判定は、利用規則の本文に `candidates/` と `carry` の2つの文字列が在るかで行う。無ければ、取り直しも写しもせずに止まる。下書きは `outbox/` に残り、次に運ぶ者が運ぶ。PR を出せないホストのための別の道は、置かない。送り出しは、どのホストでもプロジェクトの変更の中で済み、運ぶのに要るのは検査器と push だけだからである。採らなかった形は4つある。

- **候補の PR を、GitHub の自動マージで取り込む**: 自動マージは、ブランチ保護の必須の検査を要する。private のリポジトリでブランチ保護を使うには、有料のプランが要る（10節）。クラウドの AI は PR を draft で出すので、ready にする手間も要る。PR を出す道具の無いホストでは使えない。
- **AI に、既定のブランチへの直接の push を認める**: 取り込む前の検査が無い。クラウドのセッションは、作業用のブランチのほかへ push しないよう指示されている。
- **候補の PR を、人間がマージする**: 承認を待つ列が残る。
- **PR を出せないホストでは、記録と PR の本文を、プロジェクトの `tasks/` に置いて運ぶ**: 例外の道が、通常の道と別の手順を持つ。運ぶまでの間、プロジェクトの PR の残留の検出が赤い。

受け入れた不利益は4つある。

- Global に、既定のブランチへ書く自動化が1つ増える。書き込みの範囲は、CI の判定だけが絞る。
- 運ぶことが3つ以上重なると、間の取り込みが取り消され、その候補は次に運ばれるまで届かない。
- 候補を足すだけのブランチなら、誰が push したものでも取り込む。private のリポジトリでは、push できるのは、利用者が招いた者に限られる。
- CI は、ブランチがプロジェクトの承認を経たかを確かめない。Global は、どのプロジェクトのどの既定のブランチから写したかを知らず、確かめる手段が無い。`candidates/` が承認済みを表す約束（5.3節）は、利用規則と写すコマンドだけが保つ。写すコマンドは、プロジェクトの既定のブランチからしか読まない。それでも、利用規則を読み違えた AI が、承認を経ない下書きを候補のブランチへ push すると、CI は取り込む。push しただけでも、文字列は Global の履歴に残る。取り込みは、届く範囲を、索引を通じて全てのプロジェクトのセッションへ広げる。

取り込みの条件に承認の印を求める形は採らない。Global はプロジェクトのリポジトリを読めないので、印を確かめられない。印は、承認を経ない者も書ける。

### 7.4 選別

**受け入れ。** 人間が、候補を `candidates/` から `records/` へ移して確定する。移すことが、受け入れの承認になる。選別の結果は、次の5つである。

| 結果 | すること |
|---|---|
| 採る | 候補を `records/` へ移す。言い回しを直してよい |
| まとめる | 複数の候補や既存の記録から、新しい記録を書く。まとめた候補を `candidates/` から除く |
| 捨てる | 候補を `candidates/` から除く |
| 補う | 既存の記録に、主張を変えずに候補の中身を足し、候補を `candidates/` から除く |
| 置き換える | 採った候補か、まとめた記録で、既存の記録を置き換える |

- 置き換えの3つは、選別の変更に入れる（7節）。
- まとめた記録と補った記録の出典には、その候補の識別子を書く。候補を除いた後も、プロジェクト側の `sent-as` から、Global の記録まで辿れるようにするためである。候補の本文は、Global の履歴に残る。
- 「補う」を置くのは、主張を変えない追記のたびに置き換えると、新しい識別子と Evolution が積み上がるためである。採用しているプロジェクトには、置き換えではなく内容の変化として届く（8節）。
- 選別の結果を、候補の検証状況や確信度で表さない（5.3節）。

**下ごしらえ。** AI は、選別の下ごしらえをする。候補ごとに、既存の記録やほかの候補と突き合わせ、5つの結果のどれにするかの案を、根拠つきで出す。突き合わせは、候補を書いた文脈とは別の文脈で行う（9節）。人間に頼まれれば、選別の変更をブランチに用意してよい。そのブランチは候補を除くか移すので、CI は取り込まない。既定のブランチへ入れるのは、人間のマージか、人間の直接の編集である。

選別で確かめるのは、送り出しで確かめなかった4つの観点である（7.2節）。元の経験は検証済みか、他のプロジェクトにも当てはまるか、適用条件と例外は何か、既存の記録と矛盾しないか、である。誰が確かめるかは、利用規則が定める。定めが無ければ、AI が下ごしらえで確かめ、人間が裁定する。

**合図。** いつ選別するかは、人間が決める。配布物は、自動の起動も、定期の実行も持たない。人間の居ないところで、案が溜まるためである（7.1節・8節と同じ理由）。索引の候補の表の行数が、溜まり具合を示す。選ばれないまま古くなった候補も、自動では捨てない。期限を決める根拠が無く、人間の居ないところで記憶が減るためである。採らなかった形は2つある。

- **候補を `records/` に置き、目印の項目で区別する**: 検証状況は「確かめたか」を表すので、流用できない。新しい項目を足すと、全ての読み手と検査器が、その項目を見分けることになる。置き場で分ければ、採用の検出は `records/` だけを見る今の形のまま済む。
- **選別を置かず、候補をそのまま記録とする**: 重なりと食い違いを、誰も見ない。似た候補が、ほかのプロジェクトから重ねて届く。

## 8. 採用

Global Memory の使い方は2つある。

| 使い方 | 版 | 用途 |
|---|---|---|
| 参照 | 最新 | 一般の知識を調べる |
| 採用 | 固定 | プロジェクトの設計判断の根拠にする |

採用は、台帳へ記録する。台帳は、プロジェクト側の記憶の根の `adopted/` に、1つの記録につき1ファイルの Markdown で置く。記録の本文は写さない。台帳の項目は、`references/format.md` が定める。

採用できるのは、Global の `records/` の記録だけである。選別の前の候補は採用しない。受け入れが決まっていないものを、設計判断の根拠として固定しないためである。

1つの記録につき1件に限るのは、台帳が固定した版（6節）を、記録ごとに1つに決めるためである。ファイル名を記録の識別子だけにすると、1件であることがファイルシステムの上で成り立ち、重複の検査が要らない。同じ記録を別々の変更が採用すると、git の上で衝突する。この衝突は、どの版へ揃えるかを人間が決める機会になる。採用先の決定は、ADR に限らない。配布物は、adr プラグインを前提にできないためである。

採らなかった形は4つある。

- **YAML の1ファイルにし、解析器を同梱する**: 検査器は単一のファイルであり（3節）、同梱すると第三者のコードと許諾の管理が要る。同じファイルの末尾へ足す変更どうしも衝突する。
- **YAML の1ファイルにし、検査器が読める形に限る**: 利用者は、書けない形を検査器の違反で知ることになる。衝突も残る。
- **記録と決定の組ごとに1ファイルにする**: 同じ記録が、決定ごとに違う版で固定されうる。
- **ファイル名に記録の名前を足す**: 1つの記録につき1件を保つのに、重複の検査が要る。名前は記録の側の名前の写しになり、記録の側で変わると食い違う。

受け入れた不利益は、追随で版を書き換えると、前の版が台帳のファイルの履歴にだけ残ることである。

採用した記録が Global Memory の側で変わった、置き換えられた、または記憶の外へ移されたことは、検査器が検出する。検出は、採用した版と起点の ref とで、記録のファイルの内容を比べて行う。コミットの違いでは決めない。名前だけの変更や、変えて戻した変更を、変化として報告しないためである。front-matter の違いは、変化に含める。検証状況や確信度の変化は、採用の根拠に効くためである。

検査器は、変化を報告するが、違反にはしない。記憶の側の変化はプロジェクトの欠陥ではなく、追随するかは人間が決めるためである。変化を違反にすると、追随しないと決めたプロジェクトが赤のまま残る。赤を消すには台帳の版を書き換えるしかなく、採用の固定が崩れる。違反にするのは、採用した版か記録が、起点の履歴の中で1つに決まらない場合と、台帳の形式の誤りである。Global Memory は、記録を消さず（5.3節）、既定のブランチの履歴を書き換えない。そのため、1つに決まらないのは、次の4つのどれかである。台帳か渡した引数の誤り、手元の Global Memory の履歴が古い、版の省略形が一意でなくなった、Global Memory の側で上の約束か記録の形式が破れた、である。どれも変化ではなく、直すか取り直すものである。

検出は、プロジェクトと Global Memory の2つのリポジトリが在るセッションか、人間の手元で、明示して走らせる。プロジェクトの CI では走らせない。CI から private の Global Memory を読むには、リポジトリをまたぐ認証情報を、利用先ごとに置くことになるためである。台帳の形式の検査は、git も Global Memory も要さないので、プロジェクトの CI で走らせられる。採らなかった形は2つある。

- **Global Memory の CI が、採用しているプロジェクトへ知らせる**: どのプロジェクトが採用しているかを、記憶に持たせることになる。
- **定期実行で検出する**: 人間が居ないところで、報告が溜まる。

プロジェクトへの影響は AI が示し、追随するかどうかは人間が決める。

固定した版を後から読めるよう、Global Memory のリポジトリは既定のブランチの履歴を書き換えない。

## 9. 検査器と AI の分担

| 担い手 | 受け持つもの |
|---|---|
| 検査器 | 記録・送り出しの下書き・候補の形式、識別子の重複、記録どうしの参照切れ、置き換えの連鎖の整合、採用した記録の変化、Task Memory の残留、索引の生成、下書きの候補への写しと運び済みの判定 |
| Global の CI | 候補を足すだけのブランチかの判定と、既定のブランチへの取り込み |
| AI | 記録どうしの意味の矛盾、学びの候補と既存の記録の重なりの判定、一般化の妥当性、機密の混入の疑い、選別の案、採用した記録の変化がプロジェクトへ及ぼす影響 |
| 人間 | 送り出しの承認、選別による受け入れ、AI が示した矛盾と影響の裁定。雛形の利用規則では、判断基準の承認も受け持つ |

検査器が赤にするのは、機械で決まる欠陥に限る。入力は、記録・送り出しの下書き・候補・台帳の内容である。Task Memory の残留は、根の中にファイルが在るかどうかだけで決まる。採用した記録の変化と、運び済みの判定では、Global Memory の履歴も入力にする。採用した記録の変化そのものは、赤にしない（8節）。意味の判断を検査器へ持たせない。

記録どうしの意味の矛盾は、記録を書いた文脈とは別の文脈で突き合わせる。書いた文脈で見落としたものは、同じ文脈では見つからないためである。突き合わせは報告だけを行い、記録を直さない。直すかどうかは、人間が決める。範囲は、索引で選び、本文で確かめる2段にする。

別の文脈を作れないホストでの扱いは、照合の用途で分ける。

- **候補の提案の照合**: 同じ文脈で照合し、そう書く（7.1節）。誤りは、プロジェクトの PR と、その後の選別で取り返せる。
- **送り出しの重なりの照合**: 同じ文脈で照合し、そう報告に書く（7.2節）。送るかを決める材料であり、誤って送っても選別で除ける。送らなかった候補は、理由つきでスキルの出力に残る。
- **送り出しの機密の読み**: 同じ文脈で代えず、未実施と報告に書く（7.2節）。PR を承認する人間が、未実施を知って判断する。
- **選別と、記録の突き合わせ**: 同じ文脈で代えず、未実施と書く。人間が裁定に使う材料であり、同じ文脈で読んだ結果を「矛盾なし」と書くと、行っていない独立の確認を、行ったと記録することになる。

採らなかった形は、全ての用途で同じ文脈で照合してそう書く形と、常に別のセッションへ回す形である。

照合のサブエージェントは、水準の違う2枚を持つ。候補の提案はタスクのたびに走り、後ろに再検証を持つので、水準を下げる。送り出しの重なりの照合も、誤って送っても選別で除けるので、水準を下げる側を使う。機密の読みは、誤りを巻き戻せない。運んだ文字列は、直しても別のリポジトリの履歴に残る。選別と記録の突き合わせは、人間の裁定の材料になり、裁定を検証する担い手は後ろに居ない。この2つの用途には、水準を下げない1枚を使う。照合の手順は1つの参照が持つので、定義を2枚にしても、手順は写しにならない。

## 10. 確かめていない前提

次は実機で確かめていない。外れた場合は、右の節を直す。

| 前提 | 外れた場合に直す節 |
|---|---|
| Codex のクラウドでも、2つのリポジトリが同じ階層に置かれる | 4。別の階層に置かれるなら、指示ファイルの探し方の記述を改める |
| スタックの親がマージされ、PR の base が既定のブランチへ付け替わったとき、PR の `edited` が発火して残留の検出が走る | 5.1。発火しないなら、検出は次の push と、既定のブランチへの push に頼ると書く |
| iPad の Obsidian から、Git のクライアントを介して記憶を編集できる | 4、7 |
| Codex で、サブエージェントの定義のファイルを汎用のサブエージェントへ渡して、照合を別の文脈で行える | 7.1、7.2、7.4、9。行えないなら、Codex では、候補の提案は同じ文脈で照合すると書く。機密の読みは未実施と報告に書き、選別の突き合わせは未実施と書くと書く |
| private のリポジトリで、ブランチ保護と自動マージを使うには、有料のプランが要る | 7.3。要らないなら、候補の PR を自動マージで取り込む形を、選び直せる |
| 既定のブランチを保護しても、保護の設定で GitHub Actions を例外にでき、Global の CI が既定のトークンで取り込みを続けられる | 7.3。例外にできないなら、保護を掛けるときに、取り込みに使う権限を改める |
