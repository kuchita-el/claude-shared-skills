# Shared Memory 設計

## 位置づけ

本書は、人間と AI が共有する記憶の仕組み（Shared Memory）の設計と、その根拠を持つ。対象は、記憶のデータの形と置き場、および `shared-memory` プラグインと検査器の役割分担である。

本書はストックであり、現在真であり続ける義務を負う。実装が本書と食い違ったら、どちらかを直す。記録と採用の台帳の項目ごとの定義、採用した記録の変化の判定、検査器が違反とするものは、配布物の `references/format.md` が正本であり、本書は再掲しない。

独立プラグインとして起こした判断と、却下した代替は ADR-202611140016-01 が持つ。立ち上げをどの工程で回すかは ADR-202611140053-01 が持つ。

## 1. 目的と、設計が守ること

目的は、開発で得た知識・経験・判断基準を、次の作業で再利用できる形で蓄積することにある。AI モデルを再学習させるのではない。モデルの外に置いた記憶を更新し、次の作業で参照する。対象はソフトウェア開発に限る。

設計は次を守る。以降の節の判断は、いずれかに根拠を持つ。

| 守ること | 内容 |
|---|---|
| 所有 | 記憶の原本は、利用者が所有する Git リポジトリの Markdown である。特定の AI サービスが無くても読める |
| ホスト非依存 | Claude Code と Codex、クラウドとローカルのどれからでも、同じ記憶を同じ規則で使える |
| 未検証の区別 | 検証していない仮説は、検証状況で検証済みの事実と区別して記録する。事実として引用しない |
| 出所の区別 | AI が推測した判断基準を、人間が明示したものとして記録しない。AI は自分の提案を、検証済みの事実として記録しない |
| 根拠の追跡 | AI が提案に使った記憶を、識別子と版で特定できる |
| 採用の固定 | プロジェクトが採用した判断の根拠は、後から記憶が更新されても変わらない |

追跡できるのは、AI が実際に取得した記録と、明示した判断の根拠である。モデル内部の思考過程は対象にしない。

## 2. growth との役割の違い

学びを扱う配布物は2つある。どちらも、利用者が管理するリポジトリへ学びを置ける。決定の記録を ADR へ向ける点も同じである。異なるのは、何を残すかと、置き場の形である。

| 観点 | growth | shared-memory |
|---|---|---|
| 残すもの | 検証を経た規範と、規範へ畳めない一回性の決定。それ以外の気付きは捨てる | 規範へ畳まない知識と経験も残す |
| 置き場の形 | 1つのファイル。エントリはメタデータを持たない | 1記録1ファイル。記録ごとにメタデータを持つ |
| 効かなくなったもの | 物理的に除去する | 置き換え済みとして残す |
| リポジトリをまたぐ参照 | 持たない | 持つ。採用と昇格が、別のリポジトリの記録を指す |
| 他の利用者への配布 | プラグインの配布の経路で配る | 配らない |

growth から引き継ぐのは考え方だけである。観測と解釈を分けること、未検証のものを検証済みのものと区別して扱うこと、機械で強制できる知識を lint やテストへ移すことの3つを引き継ぐ。

## 3. 構成

資産は、データと機構に分かれる。データは利用者のリポジトリに在り、機構は本リポジトリから配る。配布物へ実データを載せない。

```
[データ] Global Memory のリポジトリ（利用者が所有する。private）
  records/                    記録。1記録1ファイル
  inbox/                      人間の未整理のメモ。索引の対象にしない
  index.md                    索引。検査器が生成する
  policies/memory-policy.md   記憶の使い方の規則
  AGENTS.md / CLAUDE.md       規則の在り処を指す
  .github/workflows/          検査と索引の再生成

[データ] 各プロジェクトのリポジトリ
  docs/memory/records/        Project Memory。Global と同じ形式
  docs/memory/index.md        索引。検査器が生成する。記録を足す変更に含める
  docs/memory/adopted/        採用した Global の記録の台帳。1つの記録につき1ファイル
  docs/memory/tasks/          Task Memory。作業中のブランチにだけ在る
  AGENTS.md / CLAUDE.md       Project Memory の置き場と、Global Memory の利用規則の在り処を指す
  .github/workflows/          形式の検査と、Task Memory の残留の検出
  docs/adr/                   決定の記録。adr プラグインが扱う

[機構] 本リポジトリ
  plugins/shared-memory/
    .claude-plugin/plugin.json      Claude Code 用の manifest
    references/format.md            記録・索引・採用の台帳の形式
    references/matching.md          既存の記録との照合の手順
    references/confidentiality.md   記録がリポジトリの境界を越えるときの、機密の確認
    references/replacement.md       置き換えの手順
    scripts/memory.mjs              検査器
    agents/                         照合と突き合わせのサブエージェント
    skills/                         スキル
```

検査器は、ビルドを持たない単一のファイルとしてプラグインへ置く。依存は Node の組み込みだけにする。writing プラグインの検査器と同じ形である。記憶のリポジトリの CI は、プラグインを導入せずに、本リポジトリを clone して検査器を実行できる。

記録の版を返すコマンドと、採用した記録の変化を報告するコマンドだけは、git を呼ぶ。版はコミットであり、採用した版の内容は git の履歴にしか無いためである。形式の検査と索引の生成は、git を要さない。記憶のリポジトリの CI が使うのは、この2つだけである。git のオブジェクトを検査器が自前で読む形は採らない。pack の形式を読む実装が要り、検査器の大半がそれになるためである。

検査器を配布物の外に置いて Release で配る形は採らない。形式を定める文書と検査器の版が別々になり、形式を変えたプラグインを古い検査器で動かせてしまうためである。

どのリポジトリを Global Memory にするかは、利用者が選ぶ。ADR の置き場は adr プラグインの設定に従う。

プロジェクト側の置き場（`docs/memory/`）は既定であり、利用先が変えられる。変えた置き場は、プロジェクトの指示ファイル（`AGENTS.md`。無ければ `CLAUDE.md`）に書く。プラグインを読み込まないセッションで AI に届くのは、指示ファイルだけだからである（4節）。CI は、ワークフローが検査器へ渡す引数として置き場を持つ。検査器は、根を引数で受け取り、既定を持たない。置き場を変えた利用先は、指示ファイルと CI の引数の2か所を直す。

採らなかった形は3つある。

- **設定ファイルを足す**: 指示ファイルの記述は要るままなので、置き場を書く箇所が3つに増える。プラグインの無いホストの AI は、設定ファイルを読む手順を持たない。
- **検査器に既定の `docs/memory/` を持たせる**: Global Memory の根はリポジトリの直下なので、既定が外れる。層によって、引数の要否が変わる。
- **目印で探す**（`records/` と `index.md` を持つディレクトリを探す）: 探す範囲が試行ごとに変わる。

記憶の根の中の配置と、記録の形式は、検査器の入力の契約として配布物が定める。記録は、検査器と複数のホストが読む交換の形式であり、形が揃わなければ索引と参照が成り立たない。設計原則 C05 は、入力の契約を配布物が持ち、格納先を利用先が選ぶと定める。本設計はこの分担に従う。

成果物ごとの維持の方針は次のとおりとする。

| 成果物 | 分類 | 手での編集 | 生成元 |
|---|---|---|---|
| 記録 | 権威あるストック | する | なし |
| 利用規則（`memory-policy.md`） | 権威あるストック | する | 初期化のときだけ、プラグインの雛形から作る |
| 採用の台帳（`adopted/`） | 権威あるストック | する | なし |
| 索引（`index.md`） | 再生成可能な派生物 | しない | 記録の front-matter |
| Task Memory（`tasks/`） | 一時的なフロー | する | なし。レビューへ出す前に消す。既定のブランチへ入れない |
| 昇格の提案を運ぶファイル（`tasks/` の2つ） | 一時的なフロー | する | なし。運んだら消す。既定のブランチへ入れない |

利用規則は、初期化したあとは利用者の資産である。プラグインの更新で上書きしない。

索引は、既定のブランチへコミットする。プラグインも検査器も無いホストから、索引を読めるようにするためである。検査器は、索引が記録と一致しないことを違反とする。

Global Memory の索引を保つのは、記憶のリポジトリの CI である。記録を足す変更には、索引を含めない。既定のブランチへ入った後に、CI が索引を作り直してコミットする。人間が直接編集した場合も、同じ経路で索引が追随する。変更のたびに書き手が索引を直す形は採らない。並行する変更が索引の同じ箇所を書き換えて衝突するためである。手で保った索引が、同じ変更の中で記録の主張とずれた例もあった。

Project Memory では、記録を足す変更と直す変更に、索引を含める。索引は手で書かず、検査器で作り直す。索引が記録と一致しないことは、プロジェクトの CI が赤にする。CI は索引をコミットしない。理由は次のとおりである。

- Project Memory の書き込みは、その PR の中で起きる（5.1節）。書き手は checkout を持ち、検査器を実行できる。人間が端末の外から直接編集する、という Global Memory の事情が無い。
- CI が索引をコミットする形は、既定のブランチへ書く権限を CI に要る。既定のブランチを保護したリポジトリでは、採りにくい。
- 既定のブランチの上で、索引と記録が常に一致する。CI が保つ形では、マージから CI のコミットまでの間、索引が古い。
- 手元の検査と CI が、同じ `check` の1コマンドで済む。CI が保つ形では、検査の前に作業ツリーの索引を書き換える必要がある。
- 手で書いた索引が、生成した索引と一致しなかった例が在る。本リポジトリの Project Memory の `MEM-202611211012-01` が、この観測を持つ。

受け入れた不利益は、並行する変更が記録を足すと、索引が衝突することである。取り込んだ後に、検査器で作り直す。これは既定であり、利用先は Global Memory と同じ形を選んでもよい。検査器は、どちらの形でも同じコマンドで足りる。索引をコミットしない形（都度生成する）は採らない。プラグインも検査器も無いホストから、索引を読めなくなるためである。

## 4. 土台を、プラグインではなくリポジトリへ置く

記憶を参照する・提案に引用する・記録の追加を提案する、の3つの基本操作は、プラグインが無くても成立させる。必要なのは、利用規則の文章と git、PR を出す手段だけである。

プラグインのスキルは、基本操作に取って代わらない。記録の追加の提案では、前段だけを担う。候補を挙げ、既存の記録と照らし、下書きを検査するところまでである。出し方は、利用規則に従う（7.1節）。

根拠は、クラウドのセッションがプラグインを読み込むとは限らないことにある。2026年11月の時点で、Claude Code on the web の公式文書は次のように述べていた。実機では確かめていない。

- リポジトリの設定でプラグインを有効にしても、クラウドのセッションは読み込まない。
- 複数のリポジトリを付けたセッションでは、リポジトリ側のフックを実行しない。
- リポジトリ内の `.claude/skills/` は読み込む。

次は、2026年11月に Claude Code on the web の1つのセッションで実測した。

- 開発対象のリポジトリ1つで始めたセッションへ、途中で2つ目の private リポジトリを追加できた。2つ目のリポジトリで、clone・push・PR の作成が通った。2つのリポジトリは、同じ階層に置かれた。
- 2つ目のリポジトリの `CLAUDE.md` と、そこから取り込んだ利用規則は、セッションを再開した時点で指示として読み込まれた。追加した直後には読み込まれなかった。

途中で追加したセッションでは、再開するまで利用規則が届かない。その間は、AI が利用規則を自分で読む。

次は、2026年11月に Codex のクラウドの1つのタスクで実測した。環境には、開発対象と Global Memory の2つのリポジトリを選んであった。

- 2つのリポジトリを、1つのタスクから読めた。
- 2つ目のリポジトリへ push し、PR を作れた。
- 2つ目のリポジトリの `AGENTS.md` は、タスクの開始の時点では AI へ示されなかった。AI がファイルを自分で読んで、初めて内容を得た。
- 既定のブランチのリモート追跡参照が無く、記録の版を得るコマンドが失敗した。既定のブランチを fetch した後に通った。

Global Memory のリポジトリの指示ファイルが届くかは、ホストによって異なる。届かないホストでも利用規則へ辿り着けるよう、開発対象のリポジトリの指示ファイルからも利用規則を指す。

人間の編集もプラグインを通らない。Obsidian から直接コミットする経路があるためである。

ここから、役割を次のように分ける。

| 担い手 | 役割 |
|---|---|
| 利用規則 | 基本操作の手順。どのホストの AI も、これを読めば操作できる |
| Global Memory のリポジトリの `AGENTS.md` / `CLAUDE.md` | 利用規則の在り処を指す。この指示ファイルを読み込むホストでは、これだけで届く |
| 開発対象のリポジトリの `AGENTS.md` / `CLAUDE.md` | Project Memory の置き場と、見る順を定める。記録を使うのに要る最小の手順を持つ。作業環境に在る Global Memory のリポジトリを、名前ではなく置き場の約束で指す。利用規則の本文は写さない |
| 記憶のリポジトリの CI | 形式の検査と、索引の再生成。人間の直接の編集も、ここで受ける |
| プロジェクトのリポジトリの CI | Project Memory の形式と、索引の一致の検査。既定のブランチへ入るツリーでの、Task Memory の残留の検出。索引はコミットしない |
| プラグインのスキル | 初期化と、手順の重い操作（学びの候補の抽出と照合・昇格・矛盾の突き合わせ・置き換え・採用した記録の見直し） |

開発対象のリポジトリの指示ファイルは、形式が定めることの一部を、重ねて持つ。Task Memory の置き場と名前の既定、取り除く時点、引用の書き方である。重複は、意図したものである。プラグインを読み込まないセッションで AI に届くのは指示ファイルだけなので、動くのに要る最小の手順を、そこへ置く。形の正本は、配布物の `references/format.md` である。食い違ったときは、指示ファイルを形式へ合わせる。置き場を既定から変えた場合だけは、指示ファイルが置き場を定める（3節）。

開発対象のリポジトリの指示ファイルには、Global Memory のリポジトリの名前を書かない。「親ディレクトリの直下に、`policies/memory-policy.md` を直下に持つ別のリポジトリが在れば、それを共有の記憶として扱う」と書く。理由は2つある。

- 開発対象のリポジトリが公開されているか、他の利用者へ配られている場合、名前を書くと、他の利用者の AI にも届かないリポジトリを読ませる指示になる。private のリポジトリの存在も開示する。
- 名前を含まない文面は、どのプロジェクトでも同じ形で使える。プラグインの初期化が書き込む文面を、利用者ごとに作り分けずに済む。

受け入れた不利益は、Global Memory のリポジトリを付け忘れたセッションで、何も起きないことである。指示は「無い場合は何もしない」と定めるので、付け忘れに AI は気づかない。

置き場の約束で指すと、約束を満たすリポジトリの中身が、そのまま AI への指示になる。そのため、指示ファイルは次の3つを定める。

- **探す範囲**: 親ディレクトリの直下だけを見る。そこに無ければ、無いものとして扱う。範囲を定めないと、どこまで探すかが試行ごとに変わり、無関係な場所の同名のファイルを拾う。
- **規則の効力**: 利用規則が定めるのは、記憶の読み方と書き方だけである。開発対象のリポジトリの指示と利用者の指示を上書きしない。
- **疑わしい場合**: 作業の対象として付けたリポジトリが同名のファイルを持つ場合など、記憶として付けられたものか疑わしいときは、従う前に利用者へ確かめる。

採らなかった形は2つある。

- **スキルを基本操作の担い手にする**: プラグインを読み込まないセッションで、記憶が使えなくなる。
- **スキルの写しを各リポジトリの `.claude/skills/` と `.agents/skills/` へ置く**: 正本がリポジトリの数だけ増える。プラグインを更新しても、写しは古いまま残る。

## 5. 記憶のモデル

### 5.1 層

記憶は、適用できる範囲で3層に分ける。

| 層 | 範囲 | 置き場 | 書き込みの経路 |
|---|---|---|---|
| Global | すべてのプロジェクト | Global Memory のリポジトリ | 人間は直接。AI は PR |
| Project | そのプロジェクト | プロジェクトのリポジトリ | その PR の中 |
| Task | そのタスク | タスクのブランチの上の、Project Memory の根の `tasks/` | 作業中に随時 |

Task Memory は、既定のブランチへ持ち込まない。作業を進めるためのフローであり、記録の形（front-matter・識別子・検証状況）を持たず、形式も検査しないためである。未検証であること自体は、理由にしない。未検証の知識は、検証状況を添えた記録として残せる（1節）。レビューへ出す前に、残す価値のあるものを記録の候補として取り出し、Task Memory 自体は消す。置き場をブランチにするのは、クラウドのセッションでは push したものしか残らないためである。

候補を取り出す段では、プラグインのスキルが、Task Memory を材料として読める（7.1節）。必須の経路ではない。スキルは、Task Memory を消さない。消すのは、タスクを進めている持ち主である。

Task Memory は、Project Memory の根の `tasks/` に、タスクごとに1ファイルで置く。ファイル名の既定は、ブランチの名前から作る。名前を1つに固定する形は採らない。スタックしたブランチで、子が親のファイルへ追記するためである。親が消しても、子のファイルに親の内容が混ざったまま残る。並行するセッションも、同じファイルを取り合う。Issue の番号を名前にする形も採らない。配布物は、Issue の仕組みを前提にしない。根の外に置く形は採らない。AI と CI が知るべき場所が、2つになるためである。

取り除く時点は、レビューへ出す前とする。レビューを待つ間じゅう検出が赤い、という状態を作らないためである。レビューの指摘で作業が続く場合は、作り直してよい。

残留は、プロジェクトの CI が検出する。判定は、検査器の `check` の `--no-task-memory` が持つ。見るのは、既定のブランチへ入るツリーである。時点は2つある。既定のブランチを base にする PR と、既定のブランチへの push である。前者はマージの前に止め、後者はすり抜けたものを拾う。手元の検査と、base が既定のブランチでない PR では見ない。作業中のブランチには、Task Memory が在ってよいためである。既定のブランチへの push だけで見る形は採らない。入った後にしか分からないためである。

既定のブランチを base にする PR は、draft の間も見る。Task Memory を持ったまま PR を開くと、取り除くまで検出は赤い。スタックしていない普通のタスクが、これに当たる。この赤は、まだレビューへ出せないことを表す。draft の間は見ない形は採らない。レビューへ出す前に取り除くと決めたので、見ない期間を作る必要が無い。draft の有無に判定を掛けると、ホストの機能への依存も増える。

スタックしたブランチでは、親の Task Memory が子に残ることがある。2026年11月に git 2.43 で確かめた。親がファイルを消してから squash でマージされた場合、子が既定のブランチを merge で取り込むと、親のファイルが子に残った。親の旧い先端を起点に `rebase --onto` で載せ替えると、残らなかった。残ったファイルは、子が既定のブランチへ出す前に消す。

次は、2026年11月に Claude Code on the web の1つのタスクで確かめた。タスクのブランチは、既定のブランチではない別のブランチを base にしていた。

- Task Memory を commit して push し、別の文脈のエージェントが、ブランチから読んで検証に使い、追記できた。
- 申し送りとしては働いた。ただし、追跡していない計画の記号に頼る文は、そのファイルだけでは解けなかった。本リポジトリの Project Memory の `MEM-202611211045-01` が、この観測を持つ。
- レビューへ出す前に、残すものを取り出して、ファイルを消せた。
- 検査器の残留の検出は、ファイルが在るツリーで違反を返し、消したツリーで通った。手元で実行した。
- base が既定のブランチでない PR では、残留の検出のジョブは飛ばされた。

### 5.2 種類

層とは独立に、記録を5種類に分ける。

| 種類 | 内容 |
|---|---|
| Knowledge | 学んだ知識・事実 |
| Experience | 実際の作業・検証から得た経験 |
| Belief | 現在の判断基準・設計思想 |
| Decision | 意思決定と、その理由 |
| Evolution | 判断基準や知識が、何からなぜ変わったか |

Evolution は、旧い記録と新しい記録を結ぶ遷移の記録である。置き換えられた記録と、置き換えた記録を、それぞれ1件以上指す。片方しか指さない Evolution は作らない。記録を別の記録で置き換えるときは、必ず Evolution を作る。

プロジェクトの Decision は ADR を正本とする。Project Memory へ同じ決定を書かず、ADR の識別子で指す。決定を2か所に持つと、片方だけが更新されて食い違うためである。

ADR を正本とする方針は、検査器の規則にしない。検査器は、根がどの層かを知らない。ADR を使うかは、利用先が決める。ADR を使わないプロジェクトは、決定を Project Memory へ `decision` として書いてよい。ADR を使うプロジェクトは、指示ファイルで `decision` を使わないと定める。

### 5.3 記録の形

| 方針 | 理由 |
|---|---|
| 記録を種類ごとのディレクトリへ分けず、`records/` へ平置きする | 種類を直すたびにパスが変わると、記録を指す参照が切れる |
| 識別子は起票の時刻から作る | 複数のセッションが並行して記録を作っても、衝突しない |
| 層を識別子で区別しない。層は置き場が表し、引用と出典が層の名前を添える | 検査器は、根がどの層かを知らないまま、同じ形式を検査できる。記録の中にも層を書くと、置き場と記録の2か所が層を持つ |
| 種類・適用条件・出所・検証状況・確信度は front-matter に持つ | 索引を機械で作れる。Obsidian のプロパティとしても読める |
| 承認の状態を front-matter に持たない | 既定のブランチに在ることが、承認済みであることを表す。未承認のものは PR と `inbox/` にだけ在る。承認の正本を2つにしない |
| Belief は、人間が明示したものか、AI が推測したものかを出所として持つ。この区別は利用規則で外せない | 推測した判断基準を、本人の判断基準として扱わないため |
| 置き換えた記録は消さず、置き換え済みとして残す。置き換え済みの記録は、置き換えた先を必ず持つ | 変遷を辿れる。置き換え済みの記録は、既定の索引から外す |

承認と検証は別のものである。既定のブランチに在る記録は「残してよいと認められたもの」であり、「正しいと確かめたもの」とは限らない。後者は検証状況が表す。

### 5.4 記憶の出口

記憶は、参照される根拠の置き場である。次に当たるものは、記憶に留めず移す。

- 機械で強制できるものは、lint・テスト・型へ移す。
- 毎回守る規範は、`CLAUDE.md` / `AGENTS.md` へ移す。

移した記録は置き換え済みとし、移した先を記録自身が指す。移した先は記録ではないため、この場合は Evolution を作らない。出口を持たないと記憶は増える一方になり、索引が読み切れなくなる。

## 6. 参照

AI は、索引を先に読み、関連する記録の本文だけを取得する。全文を読み込まない。

- **順序**: Project Memory を先に、Global Memory を後に見る。プロジェクト固有の制約は、一般の知識より優先するためである。食い違う場合は、Project Memory を優先し、食い違いを示す。
- **採用済みの優先**: プロジェクトが採用した記録は、台帳が固定した版で読む。最新の版と食い違う場合は、両方を示す。
- **索引の1行**: 識別子・種類・主張の要約・適用条件・検証状況を持つ。本文を取るかどうかを、この1行で判断できるようにする。

記録の候補を足す前の、既存の記録との照合も、同じ順序と2段で行う。索引で選び、本文で確かめる。手順の正本は、配布物の `references/matching.md` である。

AI は、設計や方式に関わる提案に、次を添える。

- 参照した記録の層の名前・識別子・版（`Project MEM-…@…`、`Global MEM-…@…`）
- 判断に使った前提
- 既存の記録との矛盾
- 確かめていない事項

記録の版は、その記録が在るリポジトリの既定のブランチで、その記録を最後に変えたコミットである。マージの前のブランチにあるコミットは、版として使わない。マージの方式によっては、そのコミットが既定のブランチに残らないためである。まだ既定のブランチに無い記録は、版の代わりに「未マージ」と書く。同じ変更で足した記録を引用する場合が、これに当たる。版を得る前に、既定のブランチの履歴を取り直す。クラウドの checkout は、履歴を一部しか持たないことがある。履歴が足りないまま git で版を数えると、エラーにならず、誤ったコミットが返る。履歴を1件だけ持つ clone で、記録を最後に変えたコミットではなく先頭のコミットが返ることを、2026年11月に git 2.43 で確かめた。

そのため、検査器の版を返すコマンドは、履歴が浅い checkout では版を返さずに止まり、取り直し方を示す。取り直すのは呼び出す側であり、検査器は、ネットワークへ出る git のコマンドを呼ばない。この約束の射程は、`references/format.md` が定める。採らなかった形は3つある。

- **浅くても、求めたコミットが履歴の切れた地点でなければ返す**: 正しさが、git が履歴を辿る順序の細部に掛かる。
- **検査器が自分で履歴を取り直す**: 認証と失敗の扱いが、検査器へ入る。
- **警告だけ出して版を返す**: 誤った版が標準出力に出て、呼び出す側がそれを引用する。

版を数える起点の ref は、呼び出す側が指す。省いたときは、clone のときに git が記録した remote の既定のブランチを使う。それも無ければ止まる。作業中の HEAD へは落とさない。記憶のリポジトリで PR 用のブランチに居ると、マージの前のコミットが版として出るためである。既定のブランチの名前を推測する形（`main`・`master` を順に試す）も採らない。名前の違うリポジトリで、存在しないブランチや別の用途のブランチを起点にするためである。remote へ尋ねる形も採らない。検査器がネットワークを使うことになる。既定のブランチの名前を知っているのは利用規則であり、起点を決める責任をそこへ置く。

起点が remote 追跡の ref のとき、ref が古いと、検査器は誤った版を正常終了で返す。記録が古い ref に無ければ「無い」と答え、下書きの手順はそれを「未マージ」と書く。浅い履歴と同じく、エラーにならない誤りである。そこで検査器は、起点が remote 追跡の ref か `FETCH_HEAD` のとき、その worktree の `FETCH_HEAD`（最後に取り直した結果）と照合する。食い違えば止まる。省いたときの既定も、解決した先の remote 追跡の ref で照合する。照合する行は、同じ枝を、その remote の URL から取り直した行に限る。枝の名前だけで照合すると、remote が複数ある checkout で、別の remote から同じ名前の枝を取り直した行と一致し、古い ref が通る。URL は、insteadOf を解いた remote の URL と、認証情報と末尾の `/`・`.git` を除いて比べる。git は、`FETCH_HEAD` へ書く URL をこの形に整える。クラウドの checkout でも、`FETCH_HEAD` の URL が remote の URL と一致することを、2026年11月に2つのリポジトリで確かめた。ローカルのブランチ・タグ・コミットは照合しない。それが既定のブランチを指すかは検査器には分からず、渡す側が責任を持つ。

枝が remote の fetch の refspec の外にあると、取り直しても remote 追跡の ref は作られないか、進まない（`--single-branch` の clone など）。そのとき検査器は、取り直しではなく `FETCH_HEAD` を起点にするよう案内する。取り直しを案内すると、従っても通らないためである。

照合で防げるのは、最後に取り直した結果と食い違う起点までである。取り直した後に上流が進み、ref と `FETCH_HEAD` が揃って古くなった状態は、ネットワークへ出ずには見分けられない。この残りは、版を求める直前に取り直す手順で塞ぐ。手順の正本は `references/format.md` である。採らなかった形は5つある。

- **remote へ尋ねて最新かを確かめる（`git ls-remote` など）**: 検査器がネットワークを使うことになり、認証と失敗の扱いが入る。検査器が自分で履歴を取り直す形を退けた理由と同じである。
- **起点に `FETCH_HEAD` だけを受ける**: `FETCH_HEAD` は、どの枝を取り直したかを起点として名指さない。別の枝だけを取り直した後でも、その枝を指したまま通る。remote 追跡の ref なら、同じ枝の行と突き合わせられる。
- **枝の名前だけで照合し、URL を比べない**: 別の remote から同じ名前の枝を取り直した行で、古い ref が通る。
- **URL が一致する行が無ければ、枝の名前だけの照合に落とす**: 同じ経路が残る。一致しない checkout では止まり、`FETCH_HEAD` を起点にする経路がある。
- **取り直してからの経過時間で判定する**: 上流が進む速さはリポジトリごとに違い、閾値を決める根拠が無い。同じ checkout でも、判定が時刻で変わる。

版は、コミットの省略形（7桁以上）で書く。利用規則と既存の記録が、この形を既に使っているためである。完全な形だけにする案は採らない。提案に添える引用が長くなり、既存の書き方と割れる。台帳の版は、文字列のまま比べない。コミットへ解決してから、その版での記録の内容を読む（8節）。省略形の長さが違っても、結論は変わらない。

AI が読むのは作業ツリーの記録であり、版は取り直した ref から数える。作業ツリーが古いと、読んでいない内容の版を引用する。そこで検査器は、作業ツリーの記録がその版と内容が違うとき、止めずに知らせる。止めないのは、作業用のブランチで記録を直している最中には、食い違って当然のためである。

利用規則は、版を得る手順として検査器のコマンドを指す。あわせて、検査器を入手できないホスト向けに、git だけの手順を予備として残す。基本操作を、利用規則と git だけで成り立たせるためである（4節）。

## 7. 更新

更新に人間の承認を置くかは、利用規則が定める。配布物は、承認を一律には求めない（設計原則 C06）。雛形の利用規則は、次のとおり承認を置く。

- **AI の更新**: AI は、既定のブランチへ直接書かない。追加と修正は PR として出し、人間が承認する。人間の判断基準を変える提案は、本人が承認するまで確定しない。
- **人間の更新**: 人間は直接編集してよい。形式の誤りは CI が検出する。走り書きは `inbox/` へ置き、後から記録へ整える。
- **昇格**: Task から Project へ、Project から Global へ昇格できる。上の層の記録は写しではなく、一般化した新しい記録である。元の記録を出典として指す。
- **修正**: 新しい経験で既存の記録を直すときは、旧い記録を置き換え済みにし、Evolution に理由を残す。

昇格の出典は、層の名前・元の記録の識別子・版で指す（`Project <識別子>@<版>`）。リポジトリの名前・所有者・URL は書かない。Global Memory は全てのプロジェクトのセッションへ運ばれるので、名前を書くと、公開していないプロジェクトの名前が別のプロジェクトの文脈へ流れるためである。層の名前を添えるのは、識別子が根ごとにしか一意でないためである。受け入れた不利益は、Global の記録から元のリポジトリを機械では辿れないことである。辿るときは、手元のリポジトリを識別子で検索する。

昇格しても、元の記録は変えない。層が違う記録は、置き換えの関係に立たない。同じ記録を2度昇格しないことは、昇格先の記録の出典を、元の識別子で検索して確かめる。識別子は根ごとにしか一意でないので、一致した出典の版が、元のリポジトリのコミットであることも確かめる。コミットでなければ、別のプロジェクトの記録とみなして進め、人間に示す。元の記録へ「昇格済み」を書き戻す形は採らない。2つのリポジトリを、1つの変更でそろえられないためである。

出典の書き方で採らなかった形は、ほかに3つある。

- **リポジトリの名前も書く**: 上の理由で採らない。
- **利用規則で書き方を切り替える**: 外せない確認（機密）の対象を、利用規則で狭めることになる。
- **検査器で名前を禁じる**: 何が名前かは、記録の内容だけからは決まらない。

昇格するのは、既定のブランチに在る記録だけである。既定のブランチに在ることが、承認済みであることを表す（5.3節）。未検証の記録は、`unverified` のまま昇格できる。検証済みの事実とは、検証状況が区別する（1節）。その場合は、確認の結果と、人間が決めることに、未検証であることを書く。利用規則が認めないと定めていれば、昇格しない。

置き換えは、同じ根の中でそろえる。旧い記録の `superseded-by` と Evolution の記録は、同じコミットに入れる。片方だけの状態は、検査器が違反にするためである。新しい記録は、それより前か同じコミットに入れる。順序と確かめ方の正本は、配布物の `references/replacement.md` である。

置き換えの3つは、同じ変更（同じ PR）に入れる。新しい記録に使えるのは、その変更で足す記録だけである。既定のブランチに入った記録を、後の変更で新しい記録にする形は採らない。3つを同じ変更で行うという形式の定めと、記憶の利用規則に反するためである。昇格した記録で既存の記録を置き換えるときは、昇格の PR をマージする前に、同じブランチで置き換える。どちらも既に既定のブランチに在る2件の記録の食い違いは、置き換えのスキルの対象の外である。既定のブランチに在るかは、検査器の `version` が、起点の ref にその記録を見つけるかで決める。通信はしない。判定は、手元の ref の時点のものである。

昇格の PR は、次を確かめた結果を持つ。

- 元の経験は検証済みか
- 他のプロジェクトにも当てはまるか
- 適用条件と例外は何か
- 機密の情報を含まないか
- 既存の記録と矛盾しないか

このうち機密の情報の確認は、利用規則で外せない。記録がリポジトリの境界を越えるためである。ほかの項目を確かめるか、誰が確かめるかは、利用規則が定める。

5つの確認は、どれも結果を PR の本文に書く。省いた確認も、行を残して省いたと書く。確かめなかったことが、確かめたことと見分けられなくなるのを避けるためである。ほかの4つは、利用規則に定めが無ければ AI が確かめる。

機密の情報の確認は、2段で行う。1段目は語の照合である。元のプロジェクトのリポジトリの名前と所有者の名前を、記録と PR の本文から機械で探す。2段目は読みである。認証情報、個人の情報、語に載らない固有名を、記録を書いた文脈とは別の文脈が読んで探す。書いた文脈は、プロジェクトの名前を普通の語として読むので、混入に気づきにくい。確認を通るまで、記録を昇格先の根へ書かない。下書きは、根の外の置き場に置く（7.1節）。別の文脈を作れないホストでは、読みを同じ文脈で代えず、未実施として扱う。Global Memory へ直接書く候補の提案も、同じ2段を通す（7.1節）。入る経路ごとに確認の強さが違うと、弱い側から混入するためである。対象と手順の正本は、配布物の `references/confidentiality.md` である。

機密の確認で採らなかった形は2つある。

- **検査器に秘密の走査を持たせる**: 認証情報の型の一覧は、保守の対象が増える。プロジェクトの名前は、記録の内容だけからは決まらない。
- **書いた文脈の読み直しだけにする**: 同じ文脈の再確認であり、足しても見落としは減らない。

昇格・突き合わせ・置き換えは、別々に起動できるスキルにする（設計原則 C03）。候補の提案と昇格は、起動の契機・入力・書き先が違う。突き合わせを単独のスキルにするのは、プラグインを通らない書き込みを、後から確かめる入口が要るためである。1つのスキルにまとめる形と、突き合わせをサブエージェントだけにする形は採らない。

Global Memory のリポジトリへ PR を出せないホストでは、提案をファイルとしてプロジェクト側の PR に載せ、出せるホストか人間が運ぶ。置き場は、Project Memory の根の `tasks/` である。記録と PR の本文を、2つのファイルとして置く。`tasks/` は、既定のブランチに在ると検査が違反にする置き場である（5.1節）。運ぶ前にマージされることを、プロジェクトの CI が止める。語の照合は、元のプロジェクトのセッションでしか行えないので、運ぶ前に済ませる。機密の読みが済んでいない提案は、運ばない。運んだ先には、済ませる入口が無いためである。元のプロジェクトで、別の文脈を作れるホストから、昇格をやり直す。既存の記録との矛盾の確認は、昇格先が見えないので、運んだ先で行う。受け入れた不利益は、運ぶまでの間、プロジェクトの PR の検査が赤いことである。Project の根に恒久の置き場を作る形は採らない。未承認のものが、既定のブランチに在る場所を作るためである。PR の説明の文として運ぶ形も採らない。記録は、そのまま置けるファイルとして運ぶ。

### 7.1 候補の提案

タスクで得た学びを記録の候補にし、既存の記録と照らして、下書きにして検査する。ここまでを、プラグインのスキルが受け持つ。手順の正本は、配布物のスキルと参照である。本節は、決めた形と理由を持つ。

**起動。** 人間か AI が、明示して起動する。配布物は、自動の起動を持たない。指示ファイルへ、促しの文面も書き込まない。候補を確かめる時点を促すかは、利用規則が決める。理由は3つある。クラウドのセッションは、プラグインもフックも読み込むとは限らない（4節）。候補を挙げる時点は、利用先の工程である。設計は、レビューへ出す前に残すものを取り出す、という時点を既に持つ（5.1節）。採らなかった形は3つある。

- **配布物が、指示ファイルへ促しを書き込む**: プラグインを読み込まないセッションで、存在しないスキルを指す指示が残る。
- **定期的にまとめて行う**: 材料である会話が、セッションの外に残らない。人間の居ないところで、PR が溜まる。
- **フックで起動する**: プラグイン単位のフックを持たないホストで動かず、ホストで挙動が割れる。

**層。** 候補は、Project Memory へ置く。次の3つを全て満たす候補だけを、Project を経ずに Global Memory の下書きにする。迷えば、Project へ置く。

- Global Memory の根が在る。
- 主張と当てはまる条件が、プロジェクトのコード・構成・規約・決定を条件に含まない。
- 機密の情報を含めずに書ける。

理由は3つある。

- 層は、適用できる範囲で決まる（5.1節）。範囲がプロジェクトを越える記録を Project に置くと、他のプロジェクトから見えない。
- 昇格は、一般化した新しい記録を作る。既に一般的な主張には、一般化の余地が無い。Project を経由させると、同じ主張の記録が2件残る。
- AI が PR で Global Memory へ足すことは、利用規則が定める基本操作である（4節）。スキルだけが禁じても、基本操作では起きる。

検証状況は、層を分ける条件にしない。確かめていない候補は、`unverified` と書いて、決まった層へ置く。未検証の仮説は、置き場ではなく検証状況で区別するためである（1節）。別の文脈が観測し、スキルを実行する文脈が確かめていないものも、`unverified` とする。出典に、誰が観測したかを書く。AI は、自分で確かめていないことを、検証済みの事実として記録しないためである（1節）。既存の記録と食い違う未検証の候補は、置き換えにしない。食い違いを本文に書いた仮説として足す。置き換えは、確かめた候補に限る。採らなかった形は4つある。

- **常に Project を経由する**: 上の誤配置と重複が残る。Project Memory の根が無いプロジェクトでは、道具の知見の行き先が無い。
- **条件を定めず、AI の判断に任せる**: 判定の入力が決まらず、試行ごとに層が割れる。
- **種類で決める**: 種類と層は独立である（5.2節）。プロジェクトに固有の経験も在る。
- **検証済みの候補だけを Global Memory へ置く**: 未検証の仮説を、層で隔てることになる。区別は、検証状況が受け持つ。

**件数。** 候補は、単位と関門で絞る。そのうえで、下書きにする数に目安を置く。

- 単位は、1つの主張である。同じ1回の試行や、同じ対象から出た複数の観測は、それぞれが別々に次の行動を変えるときだけ分ける。
- 関門は、次を確かめる。このタスクでの観測が在る。次の作業で行動が変わる。記憶の出口（5.4節）と、決定の正本（5.2節）へ送るものでない。
- 下書きにする候補が、根ごとに目安の数を超えるときは、次の行動の変化が大きい順に並べ、上位だけを下書きにする。残りは、見送りとして、理由つきで表に残す。捨てた候補も、同じく表に残す。

目安は上限ではない。超えるときに絞る手順の起点である。数と並べる基準は、配布物のスキルが持つ。利用規則が別の数を定めれば、それに従う。目安を置くのは、単位と関門だけでは絞り切れないためである。1つのタスクの材料から、関門を通る候補が、人間が1件ずつ承認できる量を大きく超えて出たことが在る。どれも観測を伴い、行動が変わると言えるものだった。数を根ごとに数えるのは、承認の単位が、根ごとの変更だからである。採らなかった形は4つある。

- **目安を置かず、単位と関門だけで絞る**: 関門を通る候補が多いタスクで、承認が形だけになる量の下書きが出る。
- **固定の上限を置き、超えた分を落とす**: 長いタスクの正当な学びを、数を理由に黙って落とす。見送りとして表に残せば、人間が名指して戻せる。
- **多いときに、読み直して減らすよう促す**: 書いたものを、同じ文脈で読み直す手順になる。同じ文脈は、同じ見落としを繰り返す。並べる基準を先に定めておけば、読み直しに頼らずに絞れる。
- **下書きの前に、人間の承認を挟む**: 利用規則が置く承認と、二重になる。

**照合の文脈。** 照合は、候補を書いた文脈とは別の文脈で行う。ホストの機構に合わせて、3段で落とす。定義済みのサブエージェントを起動できれば、起動する。できなければ、汎用のサブエージェントへ定義のファイルを渡す。それもできなければ、同じ文脈で同じ手順どおりに照合し、出力にそう書く。別の文脈を必須にしないのは、照合の誤りを取り返せるためである。下書きは、記録の PR で人間が見る。採らなかった形は3つある。

- **別のセッションで照合する**: スキルが途中で止まり、人間が結果を運ぶ工程を課す。
- **照合を省く**: 重なる候補を、足す側へ入れてしまう。
- **どのホストでも、同じ文脈で行う**: 索引と本文が、候補を書いた文脈に載る。独立の利点も捨てる。

**出し方。** スキルは、下書きと検査までを自分の道具で行う。出し方は、その根の規則に従い、セッションに在る手段で行う。commit・push・PR の作成を、スキルは事前に許可しない。了承は、ホストの許可の確認が受け持つ。応答で尋ねて止まらない。許可されない・確かめられないときは、昇格は運ぶ経路へ進み、候補の提案は下書きで止まる。規則を読めない根では、下書きで止まり、出していないと報告する。理由は2つある。PR を出す手段は、ホストで違う（4節）。push と PR を事前に許可すると、利用者の許可の設定を、配布物が飛び越える。採らなかった形は4つある。

- **スキルが PR まで出す**: 特定の道具を前提にすると、動かないホストが出る。承認を置くかを、配布物が決めることにもなる。
- **下書きで必ず止める**: 利用規則が在る根でも、起動した人が、続きを自分で指示することになる。
- **文で尋ね、未回答なら運ぶ**: 非対話の実行では、答えが来ないまま了承待ちで止まる。未回答をいつ見切るかを、スキルが決めることにもなる。ホストの許可の確認なら、対話では答えを待ち、非対話では拒むので、未回答が残らない。
- **`AskUserQuestion` を許可に足す**: 対話の経路が無い実行では尋ねられず、未回答の扱いが残る。対話の経路が在っても、ホストの許可の確認と二重に尋ねる。

**索引。** 下書きを置いた根の規則に従う。Project Memory の既定では、作り直した索引を同じ変更に含める。Global Memory では含めない（3節）。検査の合否は、どちらも検査器の違反の行で決める。含めない根では、索引の不一致の行を除いて数える。

**機密。** Global Memory へ置く下書きは、機密の確認を通るまで、根の外の置き場に置く。Global Memory の根へ書くのは、通った下書きだけである。通らなかった下書きは、根にも、出す変更にも入れず、置き場に残して報告する。根へ先に書いて後から確かめる形は採らない。別のリポジトリの作業ツリーへ書いた時点で、記録は境界を越えている。通らなかった下書きが根に残り、出す変更に混ざる。固有名のうち、語として挙げられるものは、コマンドで照合する。語に載らないものは、読んで確かめる。読みは、記録を書いた文脈とは別の文脈に委ねる。別の文脈を作れなければ、Global Memory へ出さない（7節）。対象と手順の正本は、配布物の `references/confidentiality.md` である。

**実装していない経路。** Global Memory のリポジトリへ PR を出せないホストで、提案をファイルとして運ぶ経路は、候補の提案のスキルは持たない。昇格のスキルが持つ（7節）。Global Memory の根が無ければ、候補を Project へ置き、Global 向きと示すところまでである。

## 8. 採用

Global Memory の使い方は2つある。

| 使い方 | 版 | 用途 |
|---|---|---|
| 参照 | 最新 | 一般の知識を調べる |
| 採用 | 固定 | プロジェクトの設計判断の根拠にする |

採用は、台帳へ記録する。台帳は、プロジェクト側の記憶の根の `adopted/` に、1つの記録につき1ファイルの Markdown で置く。記録の本文は写さない。台帳の項目は、`references/format.md` が定める。

1つの記録につき1件に限るのは、台帳が固定した版（6節）を、記録ごとに1つに決めるためである。ファイル名を記録の識別子だけにすると、1件であることがファイルシステムの上で成り立ち、重複の検査が要らない。同じ記録を別々の変更が採用すると、git の上で衝突する。この衝突は、どの版へ揃えるかを人間が決める機会になる。採用先の決定は、ADR に限らない。配布物は、adr プラグインを前提にできないためである。

採らなかった形は4つある。

- **YAML の1ファイルにし、解析器を同梱する**: 検査器は単一のファイルであり（3節）、同梱すると第三者のコードと許諾の管理が要る。同じファイルの末尾へ足す変更どうしも衝突する。
- **YAML の1ファイルにし、検査器が読める形に限る**: 利用者は、書けない形を検査器の違反で知ることになる。衝突も残る。
- **記録と決定の組ごとに1ファイルにする**: 同じ記録が、決定ごとに違う版で固定されうる。
- **ファイル名に記録の名前を足す**: 1つの記録につき1件を保つのに、重複の検査が要る。名前は記録の側の名前の写しになり、記録の側で変わると食い違う。

受け入れた不利益は、追随で版を書き換えると、前の版が台帳のファイルの履歴にだけ残ることである。

採用した記録が Global Memory の側で変わった、置き換えられた、または記憶の外へ移されたことは、検査器が検出する。検出は、採用した版と起点の ref とで、記録のファイルの内容を比べて行う。コミットの違いでは決めない。名前だけの変更や、変えて戻した変更を、変化として報告しないためである。front-matter の違いは、変化に含める。検証状況や確信度の変化は、採用の根拠に効くためである。

検査器は、変化を報告するが、違反にはしない。記憶の側の変化はプロジェクトの欠陥ではなく、追随するかは人間が決めるためである。変化を違反にすると、追随しないと決めたプロジェクトが赤のまま残る。赤を消すには台帳の版を書き換えるしかなく、採用の固定が崩れる。違反にするのは、採用した版か記録が、起点の履歴の中で1つに決まらない場合と、台帳の形式の誤りである。Global Memory は、記録を消さず（5.3節）、既定のブランチの履歴を書き換えない。そのため、1つに決まらないのは、次の4つのどれかである。台帳か渡した引数の誤り、手元の Global Memory の履歴が古い、版の省略形が一意でなくなった、Global Memory の側で上の約束か記録の形式が破れた、である。どれも変化ではなく、直すか取り直すものである。

検出は、プロジェクトと Global Memory の2つのリポジトリが在るセッションか、人間の手元で、明示して走らせる。プロジェクトの CI では走らせない。CI から private の Global Memory を読むには、リポジトリをまたぐ認証情報を、利用先ごとに置くことになるためである。台帳の形式の検査は、git も Global Memory も要さないので、プロジェクトの CI で走らせられる。採らなかった形は2つある。

- **Global Memory の CI が、採用しているプロジェクトへ知らせる**: どのプロジェクトが採用しているかを、記憶に持たせることになる。
- **定期実行で検出する**: 人間が居ないところで、報告が溜まる。

プロジェクトへの影響は AI が示し、追随するかどうかは人間が決める。

固定した版を後から読めるよう、Global Memory のリポジトリは既定のブランチの履歴を書き換えない。

## 9. 検査器と AI の分担

| 担い手 | 受け持つもの |
|---|---|
| 検査器 | 記録の形式、識別子の重複、記録どうしの参照切れ、置き換えの連鎖の整合、採用した記録の変化、Task Memory の残留、索引の生成 |
| AI | 記録どうしの意味の矛盾、学びの候補と既存の記録の重なりの判定、一般化の妥当性、機密の混入の疑い、採用した記録の変化がプロジェクトへ及ぼす影響 |
| 人間 | AI が示した矛盾と影響の裁定。雛形の利用規則では、判断基準の承認も受け持つ |

検査器が赤にするのは、機械で決まる欠陥に限る。入力は、記録と台帳の内容である。Task Memory の残留は、根の中にファイルが在るかどうかだけで決まる。採用した記録の変化では、Global Memory の履歴も入力にする。採用した記録の変化そのものは、赤にしない（8節）。意味の判断を検査器へ持たせない。

記録どうしの意味の矛盾は、記録を書いた文脈とは別の文脈で突き合わせる。書いた文脈で見落としたものは、同じ文脈では見つからないためである。突き合わせは報告だけを行い、記録を直さない。直すかどうかは、人間が決める。範囲は、索引で選び、本文で確かめる2段にする。

別の文脈を作れないホストでの扱いは、候補の提案と昇格で分ける。候補の提案は、同じ文脈で照合し、そう書く（7.1節）。誤りは、記録の PR と、その後の昇格の突き合わせで取り返せる。昇格の突き合わせは、同じ文脈で代えず、未実施と書く。昇格の後ろには、もう1段が無い。同じ文脈で読んだ結果を「矛盾なし」と書くと、行っていない独立の確認を、行ったと記録することになる。採らなかった形は、同じ文脈で照合してそう書く形と、常に別のセッションへ回す形である。

照合のサブエージェントは、水準の違う2枚を持つ。候補の提案はタスクのたびに走り、後ろに再検証を持つので、水準を下げる。昇格と突き合わせは、後ろに再検証の担い手が居ない。機密の読みは、誤りを巻き戻せない。push した文字列は、直しても別のリポジトリの履歴に残る。照合の手順は1つの参照が持つので、定義を2枚にしても、手順は写しにならない。

## 10. 確かめていない前提

次は実機で確かめていない。外れた場合は、右の節を直す。

| 前提 | 外れた場合に直す節 |
|---|---|
| Codex のクラウドでも、2つのリポジトリが同じ階層に置かれる | 4。別の階層に置かれるなら、指示ファイルの探し方の記述を改める |
| スタックの親がマージされ、PR の base が既定のブランチへ付け替わったとき、PR の `edited` が発火して残留の検出が走る | 5.1。発火しないなら、検出は次の push と、既定のブランチへの push に頼ると書く |
| iPad の Obsidian から、Git のクライアントを介して記憶を編集できる | 4、7 |
