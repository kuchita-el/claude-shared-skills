# Shared Memory 設計

## 位置づけ

本書は、人間と AI が共有する記憶の仕組み（Shared Memory）の設計と、その根拠を持つ。対象は、記憶のデータの形と置き場、および `shared-memory` プラグインと検査器の役割分担である。

本書はストックであり、現在真であり続ける義務を負う。実装が本書と食い違ったら、どちらかを直す。記録の項目ごとの定義は検査器のスキーマが正本になり、本書は再掲しない。

独立プラグインとして起こした判断と、却下した代替は ADR-202611140016-01 が持つ。立ち上げをどの工程で回すかは ADR-202611140053-01 が持つ。

## 1. 目的と、設計が守ること

目的は、開発で得た知識・経験・判断基準を、次の作業で再利用できる形で蓄積することにある。AI モデルを再学習させるのではない。モデルの外に置いた記憶を更新し、次の作業で参照する。対象はソフトウェア開発に限る。

設計は次を守る。以降の節の判断は、いずれかに根拠を持つ。

| 守ること | 内容 |
|---|---|
| 所有 | 記憶の原本は、利用者が所有する Git リポジトリの Markdown である。特定の AI サービスが無くても読める |
| ホスト非依存 | Claude Code と Codex、クラウドとローカルのどれからでも、同じ記憶を同じ規則で使える |
| 未検証の隔離 | 検証していない仮説を、長く残す記憶へ入れない |
| 出所の区別 | AI が推測した判断基準を、人間が明示したものとして記録しない。AI は自分の提案を、検証済みの事実として記録しない |
| 根拠の追跡 | AI が提案に使った記憶を、識別子と版で特定できる |
| 採用の固定 | プロジェクトが採用した判断の根拠は、後から記憶が更新されても変わらない |

追跡できるのは、AI が実際に取得した記録と、明示した判断の根拠である。モデル内部の思考過程は対象にしない。

## 2. growth との役割の違い

学びを扱う配布物は2つある。どちらも、利用者が管理するリポジトリへ学びを置ける。決定の記録を ADR へ向ける点も同じである。異なるのは、何を残すかと、置き場の形である。

| 観点 | growth | shared-memory |
|---|---|---|
| 残すもの | 検証を経た規範と、規範へ畳めない一回性の決定。それ以外の気付きは捨てる | 規範へ畳まない知識と経験も残す |
| 置き場の形 | 1つのファイル。エントリはメタデータを持たない | 1記録1ファイル。記録ごとにメタデータを持つ |
| 効かなくなったもの | 物理的に除去する | 置き換え済みとして残す |
| リポジトリをまたぐ参照 | 持たない | 持つ。採用と昇格が、別のリポジトリの記録を指す |
| 他の利用者への配布 | プラグインの配布の経路で配る | 配らない |

growth から引き継ぐのは考え方だけである。観測と解釈を分けること、未検証のものを長く残す記憶へ入れないこと、機械で強制できる知識を lint やテストへ移すことの3つを引き継ぐ。

## 3. 構成

資産は、データと機構に分かれる。データは利用者のリポジトリに在り、機構は本リポジトリから配る。配布物へ実データを載せない。

```
[データ] Global Memory のリポジトリ（利用者が所有する。private）
  records/                    記録。1記録1ファイル
  inbox/                      人間の未整理のメモ。索引の対象にしない
  index.md                    索引。検査器が生成する
  policies/memory-policy.md   記憶の使い方の規則
  AGENTS.md / CLAUDE.md       規則の在り処を指す
  .github/workflows/          検査と索引の再生成

[データ] 各プロジェクトのリポジトリ
  docs/memory/records/        Project Memory。Global と同じ形式
  docs/memory/adopted.yaml    採用した Global の記録の台帳
  docs/adr/                   決定の記録。adr プラグインが扱う

[機構] 本リポジトリ
  tools/shared-memory/        検査器
  plugins/shared-memory/      スキル
```

どのリポジトリを Global Memory にするかは、利用者が選ぶ。プロジェクト側の置き場（`docs/memory/`）は既定であり、利用先が変えられる。ADR の置き場は adr プラグインの設定に従う。

Global Memory のリポジトリの中の配置と、記録の形式は固定する。成果物の形を指定しないという設計原則（C05）の例外である。記録は、検査器と複数のホストが読む交換の形式であり、形が揃わなければ索引と参照が成り立たない。

成果物ごとの維持の方針は次のとおりとする。

| 成果物 | 分類 | 手での編集 | 生成元 |
|---|---|---|---|
| 記録 | 権威あるストック | する | なし |
| 利用規則（`memory-policy.md`） | 権威あるストック | する | 初期化のときだけ、プラグインの雛形から作る |
| 採用の台帳（`adopted.yaml`） | 権威あるストック | する | なし |
| 索引（`index.md`） | 再生成可能な派生物 | しない | 記録の front-matter |
| Task Memory | 一時的なフロー | する | なし。タスクの完了後は更新しない |

利用規則は、初期化したあとは利用者の資産である。プラグインの更新で上書きしない。

## 4. 土台を、プラグインではなくリポジトリへ置く

記憶を参照する・提案に引用する・記録の追加を提案する、の3つの基本操作は、プラグインが無くても成立させる。必要なのは、利用規則の文章と git、PR を出す手段だけである。

根拠は、クラウドのセッションがプラグインを読み込むとは限らないことにある。2026年11月の時点で、Claude Code on the web の公式文書は次のように述べていた。実機では確かめていない。

- リポジトリの設定でプラグインを有効にしても、クラウドのセッションは読み込まない。
- 複数のリポジトリを付けたセッションでは、リポジトリ側のフックを実行しない。
- リポジトリ内の `.claude/skills/` は読み込む。

人間の編集もプラグインを通らない。Obsidian から直接コミットする経路があるためである。

ここから、役割を次のように分ける。

| 担い手 | 役割 |
|---|---|
| 利用規則と、それを指す `AGENTS.md` / `CLAUDE.md` | 基本操作の手順。どのホストの AI も、これを読めば操作できる |
| 記憶のリポジトリの CI | 形式の検査と、索引の再生成。人間の直接の編集も、ここで受ける |
| プラグインのスキル | 初期化と、手順の重い操作（昇格・矛盾の突き合わせ・採用した記録の見直し） |

採らなかった形は2つある。

- **スキルを基本操作の担い手にする**: プラグインを読み込まないセッションで、記憶が使えなくなる。
- **スキルの写しを各リポジトリの `.claude/skills/` と `.agents/skills/` へ置く**: 正本がリポジトリの数だけ増える。プラグインを更新しても、写しは古いまま残る。

## 5. 記憶のモデル

### 5.1 層

記憶は、適用できる範囲で3層に分ける。

| 層 | 範囲 | 置き場 | 書き込みの経路 |
|---|---|---|---|
| Global | すべてのプロジェクト | Global Memory のリポジトリ | 人間は直接。AI は PR |
| Project | そのプロジェクト | プロジェクトのリポジトリ | その PR の中 |
| Task | そのタスク | タスクのブランチ | 作業中に随時 |

Task Memory は未検証のものを含むため、既定のブランチへ持ち込まない。マージの前に、残す価値のあるものを記録の候補として取り出し、Task Memory 自体は消す。置き場をブランチにするのは、クラウドのセッションでは push したものしか残らないためである。

### 5.2 種類

層とは独立に、記録を5種類に分ける。

| 種類 | 内容 |
|---|---|
| Knowledge | 学んだ知識・事実 |
| Experience | 実際の作業・検証から得た経験 |
| Belief | 現在の判断基準・設計思想 |
| Decision | 意思決定と、その理由 |
| Evolution | 判断基準や知識が、何からなぜ変わったか |

Evolution は、旧い記録と新しい記録を結ぶ遷移の記録である。置き換えられた記録と、置き換えた記録を、それぞれ1件以上指す。片方しか指さない Evolution は作らない。記録を別の記録で置き換えるときは、必ず Evolution を作る。

プロジェクトの Decision は ADR を正本とする。Project Memory へ同じ決定を書かず、ADR の識別子で指す。決定を2か所に持つと、片方だけが更新されて食い違うためである。

### 5.3 記録の形

| 方針 | 理由 |
|---|---|
| 記録を種類ごとのディレクトリへ分けず、`records/` へ平置きする | 種類を直すたびにパスが変わると、記録を指す参照が切れる |
| 識別子は起票の時刻から作る | 複数のセッションが並行して記録を作っても、衝突しない |
| 種類・適用条件・出所・検証状況・確信度は front-matter に持つ | 索引を機械で作れる。Obsidian のプロパティとしても読める |
| 承認の状態を front-matter に持たない | 既定のブランチに在ることが、承認済みであることを表す。未承認のものは PR と `inbox/` にだけ在る。承認の正本を2つにしない |
| Belief は、人間が明示したものか、AI が推測したものかを出所として持つ。この区別は利用規則で外せない | 推測した判断基準を、本人の判断基準として扱わないため |
| 置き換えた記録は消さず、置き換え済みとして残す。置き換え済みの記録は、置き換えた先を必ず持つ | 変遷を辿れる。置き換え済みの記録は、既定の索引から外す |

承認と検証は別のものである。既定のブランチに在る記録は「残してよいと認められたもの」であり、「正しいと確かめたもの」とは限らない。後者は検証状況が表す。

### 5.4 記憶の出口

記憶は、参照される根拠の置き場である。次に当たるものは、記憶に留めず移す。

- 機械で強制できるものは、lint・テスト・型へ移す。
- 毎回守る規範は、`CLAUDE.md` / `AGENTS.md` へ移す。

移した記録は置き換え済みとし、移した先を記録自身が指す。移した先は記録ではないため、この場合は Evolution を作らない。出口を持たないと記憶は増える一方になり、索引が読み切れなくなる。

## 6. 参照

AI は、索引を先に読み、関連する記録の本文だけを取得する。全文を読み込まない。

- **順序**: Project Memory を先に、Global Memory を後に見る。プロジェクト固有の制約は、一般の知識より優先するためである。
- **採用済みの優先**: プロジェクトが採用した記録は、台帳が固定した版で読む。最新の版と食い違う場合は、両方を示す。
- **索引の1行**: 識別子・種類・主張の要約・適用条件・検証状況を持つ。本文を取るかどうかを、この1行で判断できるようにする。

AI は、設計や方式に関わる提案に、次を添える。

- 参照した記録の識別子と、その版（コミット SHA）
- 判断に使った前提
- 既存の記録との矛盾
- 確かめていない事項

## 7. 更新

更新に人間の承認を置くかは、利用規則が定める。配布物は、承認を一律には求めない（設計原則 C06）。雛形の利用規則は、次のとおり承認を置く。

- **AI の更新**: AI は、既定のブランチへ直接書かない。追加と修正は PR として出し、人間が承認する。人間の判断基準を変える提案は、本人が承認するまで確定しない。
- **人間の更新**: 人間は直接編集してよい。形式の誤りは CI が検出する。走り書きは `inbox/` へ置き、後から記録へ整える。
- **昇格**: Task から Project へ、Project から Global へ昇格できる。上の層の記録は写しではなく、一般化した新しい記録である。元の記録を出典として指す。
- **修正**: 新しい経験で既存の記録を直すときは、旧い記録を置き換え済みにし、Evolution に理由を残す。

昇格の PR は、次を確かめた結果を持つ。

- 元の経験は検証済みか
- 他のプロジェクトにも当てはまるか
- 適用条件と例外は何か
- 機密の情報を含まないか
- 既存の記録と矛盾しないか

このうち機密の情報の確認は、利用規則で外せない。記録がリポジトリの境界を越えるためである。ほかの項目を確かめるか、誰が確かめるかは、利用規則が定める。

Global Memory のリポジトリへ PR を出せないホストでは、提案をファイルとしてプロジェクト側の PR に載せ、出せるホストか人間が運ぶ。

## 8. 採用

Global Memory の使い方は2つある。

| 使い方 | 版 | 用途 |
|---|---|---|
| 参照 | 最新 | 一般の知識を調べる |
| 採用 | 固定 | プロジェクトの設計判断の根拠にする |

採用は、台帳（`adopted.yaml`）へ記録する。台帳は、記録の識別子・コミット SHA・採用の理由・採用先の ADR・採用の日時を持つ。記録の本文は写さない。

採用した記録が Global Memory の側で変わった、または置き換えられたことは、検査器が検出する。プロジェクトへの影響は AI が示し、追随するかどうかは人間が決める。

固定した版を後から読めるよう、Global Memory のリポジトリは既定のブランチの履歴を書き換えない。

## 9. 検査器と AI の分担

| 担い手 | 受け持つもの |
|---|---|
| 検査器 | 記録の形式、識別子の重複、記録どうしの参照切れ、置き換えの連鎖の整合、採用した記録の変化、索引の生成 |
| AI | 記録どうしの意味の矛盾、一般化の妥当性、採用した記録の変化がプロジェクトへ及ぼす影響 |
| 人間 | AI が示した矛盾と影響の裁定。雛形の利用規則では、判断基準の承認も受け持つ |

検査器が赤にするのは、記録の内容だけから機械で決まる欠陥に限る。意味の判断を検査器へ持たせない。

## 10. 確かめていない前提

次は実機で確かめていない。外れた場合は、右の節を直す。

| 前提 | 外れた場合に直す節 |
|---|---|
| クラウドのセッションに、開発対象と Global Memory の2つのリポジトリを付けられる | 3、4 |
| Codex のクラウドから、2つ目のリポジトリへ push し、PR を出せる | 7 の迂回の経路を既定にする |
| 2つ目のリポジトリの `AGENTS.md` / `CLAUDE.md` が読み込まれる | 4。読み込まれないなら、開発対象のリポジトリの側から利用規則を指す |
| Task Memory をブランチで運び、マージの前に取り除ける | 5.1 |
| iPad の Obsidian から、Git のクライアントを介して記憶を編集できる | 4、7 |

次の2つは決めていない。1つは、検査器がプロジェクト側の置き場をどう解決するかである。もう1つは、索引を既定のブランチへコミットするか、読むたびに生成するかである。前者はプラグインの無いホストでも読めるが、並行する PR で衝突する。後者は衝突しないが、検査器を要する。
