# トークン規律の全体見直し（基盤ルーティング＋model/effort 規律）設計メモ

2026-08-21 の設計議論の決着状態。次工程（骨子作成）の引き継ぎファイル。

## 背景

プラグイン設計ガイドラインのうちトークン規律を全体見直しする。発端はユーザー提示の4点:

1. 下位モデル（Sonnet, Haiku, Luna）のフル活用
2. タスクに合わせた effort 選択
3. 汎用サブエージェントを含むサブエージェントのフル活用
4. 同一プロンプトで model/effort が場合により異なるとき、カスタムサブエージェントを定義せずプロンプトファイル＋汎用サブエージェントで組む

前提: Luna は ChatGPT（Codex コーディングエージェント）。本プロジェクトは Claude Code と Codex を併用している（`run-codex-local.sh`、Codex 用 Superpowers 導入済み）。

## 決定事項

- **D1: 規約を2段に分ける**。Luna は Claude の Agent tool（model enum: sonnet/opus/haiku/fable）では起動できず、model 選択ではなく実行基盤の選択である。(1) 基盤ルーティング（Claude 系か Codex 系か）、(2) 基盤内のパラメータ選択（model/effort）を別層とし、同一の表に並べない。
- **D2: Codex の起動経路は当面 b（人間が並行セッションで運用）**。a（Claude がスキル実行中に Bash でディスパッチ）は将来目標。ディスパッチ機構の条文（allowed-tools・認証・受け渡し形式）は a が現実になるまで書かない。設計だけ将来互換にする。
- **D3: 構成は2層＋布石1本**。
  - 層1: 基盤ルーティング指針（新設）。読み手は人間。タスク型の割当軸、生成と検証の基盤交差（Codex 生成→Claude 検証・逆）、並行セッションの競合回避（Issue 単位の分担）を扱う。
  - 層2: Claude 基盤内の model/effort 規律。既存 `plugins/dev-workflow/references/subagent-execution-parameters.md` の拡張。
  - 布石: 役割内容のベンダー中立プロンプトファイル化（内容の単一出典）。a への移行時に内容資産を持ち越すため。
- **D4: 層1の置き場所はユーザースコープ（`~/.claude/docs/execution-platform-routing.md`）**。当初はリポ内部文書（案A、`docs/development/` 等）で決着していたが、2026-08-23 に再決着した。層1が扱うのは「どの基盤で作業を回すか」であり、特定のリポジトリに属さず契約構成という個人の事実に依存する。配布物（plugins/*/references）に入れない点は変わらない。
- **D5: ADR-202607251922-01（実行パラメータ固定）/-02（統制点＝frontmatter 集約）は維持・拡張**。上書きしない見込み。薄い運搬体パターンは統制点集約と整合する。
- **D6: 層2への追加は2節**。(1) 下位モデル活用の選定基準＋検証契約（下げた分の再検証を対で規定。サブエージェント捏造の実例が根拠）、(2) 運搬体/内容分離パターン（カスタムエージェント定義は effort/tools を運ぶ薄い殻、内容はプロンプトファイル参照。定義数は effort×tools の組み合わせに抑える）。
- **D7: effort はベンダー間で水準名を 1:1 写像しない**。役割の要求水準（既存の「必要最小水準/許容最大水準」2分類）で書き、各ベンダーの水準への写像は運搬体側（Claude: frontmatter、Codex: profile/config）が持つ。

## 議論で確認した制約（既存規約との整合）

- Agent tool の引数に effort は存在しない。effort の統制点は登録済みエージェント定義の frontmatter のみ（Workflow の `agent()` は per-call 指定可だが opt-in 制約があり既定経路にしない）。
- 汎用サブエージェント（general-purpose）は Tools: * であり、tools 最小化の原則と衝突する。元の4点のうち点4はこのため「汎用サブエージェント」半分を薄い運搬体定義へ差し替えた形で採用。
- 既存規約「値を省略しない」（配布物で利用者設定へ従属させない）は維持。
- context-budget.md（実行時フロー軸）とは軸が別。コスト軸の規律を新設してもフロー軸と混ぜない（委譲はフロー軸で常に有利だがコスト軸では逆転しうる、の区別を層1に明記）。

### 層2骨子への入力（D6-(1) 下位モデル選定基準・検証契約の素材）

1. **失敗タイプ→軸の診断規則**（claude 側・原則1）。「深く考えても結論が誤る・トレードオフの筋が悪い」→ model を上げる、「調査が浅い・エッジケースを見ていない」→ effort を上げる、「合っているが遅い・冗長」→ effort を下げる。既存の「必要最小水準/許容最大水準」は静的宣言であり、これは水準を誤ったときの動的な是正規則として補完する。軸の言葉で書けるため D7 とも整合する。
2. **検証可能性軸**（claude 側・原則3）。型・テスト・lint で機械検証できる作業ほど下げられる。例外則として、機械検証があっても巻き戻しコストが非対称に高い作業（IaC 型）は下げない。下げる条件を検証可能性で書くと、D6-(1) の検証契約（下げた分の再検証を対で規定）と一貫した条文になる。
3. **収束/発散軸**（claude 側・原則4）。仕様確定済みで答えがほぼ一意なら低、仮説の生成と棄却を繰り返すなら高。付随する誤分類警告: デバッグは「調査」に見えて最も発散的であり、調査系サブエージェントと同じ低設定にすると浅い失敗をする。
4. **エスカレーション規定**（両文書一致）。「high 以下から始めて失敗の証拠が出たら上げる」「低水準が粘ること自体を、分類を一段上げるシグナルとして使う」（claude 側・原則6）、「Plan 逸脱時は上位モデルへ戻して re-plan し、新 Plan を下位で再実行する」（chatgpt 側・⑤）。現行 D1〜D7 は静的割当のみで実行中の昇格・降格規定が空白であり、これを埋める素材。`token-usage-audit-2026-08-15.md` の未決「implementation Phase 5 のエスカレーション条件追加」（同 61 行）・提案B「指摘件数が前周比で減っていない」への回答素材でもある。昇格トリガ候補: (a) 同一問題への複数回失敗、(b) Plan 前提の崩壊、(c) 低水準が粘る。
5. **最大水準（max 相当）の限定列挙**（両文書一致）。再現困難なバグ・並行性問題・大規模 migration・security-sensitive・high で複数回失敗した問題、に限る。許容最大水準の条文素材。

Codex 側の `-c` による effort 上書きは 2026-08-23 に実測で確認した。`codex exec -c model_reasoning_effort="high"` を1回走らせ、セッション記録（`~/.codex/sessions/**/rollout-*.jsonl`）に `"reasoning_effort":"high"` が残ることを確認している（`config.toml` の既定は `medium` であり、上書きが実効したことを示す）。なお `codex doctor --json` は解決後の `model` を報告するが effort は報告せず、未知のキーを `-c` へ渡してもエラーにならない（`-c bogus_key_xyz=1` が exit 0）。したがって受理されたことは実効の証拠にならず、判定はセッション記録で行う。

Codex の profile は `$CODEX_HOME/<name>.config.toml` を base config へ重ねる名前付きレイヤであり、Claude の front-matter に機能上対応する。ただし粒度が異なる。front-matter は役割単位であって1セッション内に複数の水準が共存できるが、profile はプロセス起動単位であって1起動に1つしか掛からない。役割ごとに水準を変えるには起動を分ける必要がある。現時点で profile 定義ファイルは0件であり、器は空である。

### 文脈の自動構築（2026-08-23 実測）

D 節の根拠に関わるため測定した。サブエージェント4型（`research` / `sweeper` / `adversary` / `general-purpose`）と `claude -p` の計5条件で、ツール使用0回のまま両スコープの CLAUDE.md と MEMORY.md 索引を逐語引用することを確認した。親セッションの会話履歴はいずれの条件でも含まれない（`subagent_type: "fork"` のみ例外）。

したがって「プロセス境界や基盤を越えると文脈再構築の固定費が乗る」という当初の想定は成り立たない。規約文脈はどの経路でも自動で載り、会話文脈はどの経路でも載らない。縮退の優先順位は別の非対称で根拠づける必要がある。

測定手段には注意が要る。セッション記録の grep で判定してはならない。`claude -p` は実際に載っていても記録に現れず、記録を根拠にすると逆の結論になる。判別テスト（ツール使用を禁じたうえで文脈の内容を逐語引用させる）で確かめる。

### B 節: 選択規則の骨

- 水準が役割に固有で不変なら、カスタムサブエージェント定義で固定する。
- 同一の内容を場合によって異なる水準で動かすなら、内容をプロンプトファイルへ置き、水準は呼び出し側で与える。
- `effort` を呼び出しごとに動かす必要が生じた時点で、既定の in-process 経路（Agent tool）は使えない。Workflow 経路・水準別の運搬体を複数枚置く・子プロセスを起こす、の三択になる。この分岐が選択規則の中心である。
- Codex では逆に、役割ごとの固定に profile の新設が要る。固定と動的のどちらが安いかが基盤で入れ替わるため、Claude の都合だけで規則を書かない。

### D 節: 縮退の方向と優先順位（案）

層1が層2へ委ねた本体規定。文脈再構築コストが根拠にならないことが判明したため、2つの非対称で順序づける。(a) 同一契約の窓を消費し続けるか、別契約の窓へ移すか。(b) その縮退手段を配布物の条文として書けるか。

> **2026-08-23 訂正（Issue #771）**: (b) は当初、水準を実際に下げられる実現手段の有無を根拠に置いていた。これは実測と食い違うため上記へ改めた。`CLAUDE_CODE_EFFORT_LEVEL=low` が front-matter に優先して実効した記録（`docs/superpowers/specs/2026-07-25-subagent-exec-params-design.md`「配布先の環境に依存しないこと」節）と、`-c model_reasoning_effort` の実効（未決論点2 の決着）により、`effort` を下げる実現手段は実在する。存在しないのは配布物の条文として書ける手段であって、手段そのものではない。この訂正は (b) の定義・下記の方向1・末尾の結論の3箇所に及ぶ。

1. 同一基盤内で水準を下げる。下げられる軸は基盤で非対称であり、Claude 側の既定 in-process 経路では `model` に限られるが、Codex 側では `-c model_reasoning_effort` の上書きで `effort` も下げられる（未決論点2 の決着済み事項。当初は `model` を下げる形のみを書いており、Codex 側の非対称が落ちていた）。
2. 計画へ投資を移し、実行側の水準を下げる（入力素材7）。
3. 別基盤へ移す（層1が持つ手段）。契約の窓が別になるため枯渇そのものを回避するが、返却形式と実効値の記録を自前で設計する必要がある。
4. 窓の回復を待つ（層1が持つ手段）。

`effort` を単独で下げる形を1・2の位置に置かないのは、配布物制約により、利用者の環境変数設定を前提とする縮退手段を条文へ書けないためである。この根拠の射程は Claude 側の既定 in-process 経路に限る。Codex 側は上記1 のとおり `-c` による上書きで `effort` を下げられるため、基盤を跨いで一般化しない（当初は実現手段の不在を根拠にしていたが、実測と食い違うため制約由来の根拠へ改めた。順序の結論そのものは変えていない）。

### ADR 化要否の判定（AC6、2026-08-23）

判定対象の決定: **層2の規約の記述単位を「front-matter に何を書くか」から「役割が要求する水準は何か」へ移し、枯渇時の縮退規定を層2へ置く。** 基準は `plugins/adr/skills/manage-adr/references/adr-scoping.md`（必要条件・粒度判定基準4項目）、`adr-judgment-contract.md`（実測事実の値域）、`adr-scoring-thresholds.json`（項目1閾値=3、項目2閾値=2、スコア境界=3）。

**発見型の短絡**: 適用しない。本決定は既に運用されている未記録の規範の発見ではなく、新たに下した設計判断である。

**必要条件（採らなかった選択肢とその却下理由が対として在ること）: 不成立。** したがって粒度判定基準4項目は採点せず、「ADR 化しない」で確定する。

根拠は次のとおり。判定対象は「これから記録しようとしている決定そのもの」であり、他の決定が持つ却下代替は当たらない。本決定の直接の対立案は「front-matter を主語とする記述単位を維持したまま、新しい手段を既存の『実装上の制約』節へ追記する」であるが、記録に在るのは採用側の理由（手段に固定された記述単位では呼び出しごとに水準を動かす場合の規則を表現できない）だけであり、この対立案を**名指しして却下した理由**が対として残っていない。記述単位の転換はユーザー裁定 J1 として下されており、裁定の場で対立案の検討と却下が記録されていない。

記録に在る却下代替は、いずれも本決定そのものではなく下位の面に付随するものである。(a) 未決論点1: E 節に Codex profile の整備を含めない（理由: profile は個人環境にあり配布物から配れない）。(b) 未決論点3: 検証可能性を選定軸として立てない（理由: 層1が「傾き」の軸として同じ語を使っており、層2で同名の別役割を作らない）。(c) 未決論点4: 環境変数による一括強制を射程外とする（理由: 未検証）。(d) 条文化時の実装判断4件（節の配置順・既存節の吸収可否・変数名の直書き可否・節構成の機械検査の要否）。これらは決定の適用範囲・条件・パラメータに属し、記述単位の転換という core の却下代替ではない。

必要条件は成否に迷う場合は不成立へ倒す規定であり、粒度判定基準の同点処理・「判断に迷ったら ADR 化しない」と向きが一致する。上記のとおり成立は確定できないため、規定どおり不成立とした。

**判定結果の行き先**: 本決定はツールで自動強制できないが、複数の作業者・複数の箇所へ効かせたい規範であるため、一般則により**共有規約文書**へ置く。現に `plugins/dev-workflow/references/subagent-execution-parameters.md` が置き場所であり、採用理由と既知の限界（節D の順序の根拠が制約由来であること、節B の写像表が環境変数を載せない理由、節E の枚数の目安が新設時の抑止であって既存定義への上限ではないこと）は同文書へ併記して自己完結させてある。

**既存 ADR との関係**: 本改訂は ADR-202607251922-01 / -02 が立てた枠組み（実行パラメータを固定し役割ごとの必要水準として選ぶ／統制点をサブエージェント定義へ集約する）の中に収まり、その結論・方向・前提のいずれも反転させない（下記「ADR-01 / -02 との無矛盾照合」節のとおり矛盾ありは0件）。したがって仮に粒度判定基準へ進んでいたとしても、行き先は新規 ADR ではなく既存 ADR への非core 改訂の側であった。本 PR ではその改訂も行わない——層2が既定と例外の関係として整理しており、両 ADR の条文に手を入れる必要が生じていないためである。
