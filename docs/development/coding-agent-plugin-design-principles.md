# コーディングエージェント向けプラグインの共通設計原則

## 位置づけ

- **対象**: 本リポジトリが配布するプラグイン全件の設計・配布・保守。新しいプラグインを起こすとき、既存プラグインへ能力を足すとき、配布物が何を宣言すべきか迷ったときに着手前に読む。
- **権威関係**: 本書は ADR の上位に立たない。`docs/adr/` の決定や配布物側の契約が改訂されれば、本書が追随して正しくなる側である。本書と ADR が食い違って見える場合は ADR が正であり、本書を直す。
- **定めること**: 配布プラグインに共通して掛かる8つの原則と、それぞれの適用対象・非適用条件・既知の例外。原則の内容を条文・宣言・語彙の3系統へ分ける規則と、各系統の置き場。構成要素へ共通して要求できる契約項目とその上限。host 共通の意味論として保てるものの範囲。原則ごとに何が共通化でき、何が固有設計へ残るか。
- **定めないこと**: 次の5つは別の正本が持つ。いずれも本書へ転記せず、そのまま従う。
  - 資産を配布物（`plugins/`）と配布元（リポジトリルートの `scripts/`・`docs/`）のどちらへ置くかの判断軸。`docs/distribution-boundary.md`（配置の判断軸を3点で定める文書）が定める。
  - 自律度レベルの定義と判定手順。定義は `docs/principles.md`「承認ゲート軸（自律度レベル別）」が、判定手順は `docs/references/autonomy-rubric.md` が持つ。
  - host 適合性の検査契約。`docs/references/cross-host-plugin-conformance.md` が持つ。
  - スキル定義の分量、許可ツールの最小化、実行時のコンテキスト規律。リポジトリ共通の規約（`CLAUDE.md` と、そこが指す文書）が掛かる。
  - 各プラグイン固有のドメイン設計と workflow。各プラグインが持つ。
- **識別子**: 原則の識別子は、原則を抽出した検討時の候補 ID（C01〜C10）を引き継ぐ。そのうち C08 と C10 を共通原則として採らないと判定したため、原則の識別子は C01〜C09 から C08 を除いた8件になる。C08 の欠番は欠落ではない。

## 用語

- 配布物は、利用先の営みを補助する部品として配る側の資産である。`plugins/` 配下がこれに当たる。
- 工場は、配布物を設計・検証・配布するための資産である。本リポジトリのうち配布されない部分がこれに当たる。
- プラグインは、コーディングエージェントへ能力を追加する配布単位である。
- skill は、目的、手順、入出力、停止条件、許可ツールを定めた能力の契約である。
- agent は、独立した文脈と役割で委譲された作業を実行する主体である。
- hook は、host 上のイベントを契機に自動実行される接続点である。
- script は、決定的な処理や検査を実行するプログラムである。
- reference は、skill などが必要時に読む補助規範または仕様である。
- manifest は、プラグインの名前、版、能力、接続面を機械可読に宣言するファイルである。
- host は、Claude Code や Codex など、プラグインを動かす実行環境である。
- adapter は、共通の意味を host 固有のツール、権限、呼び出し方法へ接続する層である。
- MCP/app adapter は、外部サービスやアプリケーションとの接続を host 上で実現する adapter である。
- workflow は、複数の能力を順序や分岐で結ぶ作業経路である。
- profile は、独立能力を既定の経路として組み合わせた推奨設定である。
- context は、エージェントが判断時に参照できる入力情報の集合である。
- degraded は、本来の機構を使えず、明示した制限付きの代替経路で動く状態である。
- 正本は、同じ意味を管理する権威ある情報源である。
- 条文は、なぜその設計を採るか、何を却下したか、作者が守る手順を述べる散文である。
- 宣言は、原則が各プラグインへ要求する、外から読める記述である。
- 語彙は、宣言を読むために要る用語とその値域である。

## 1. 8つの原則

### 1.1 適用区分

各原則は、及ぶ範囲を示す適用区分を持つ。値域は2値である。

| 適用区分 | 意味 |
|---|---|
| 全体 | 配布対象の全プラグインが、この原則について判断を要求される |
| 種別限定 | 特定の性質を持つプラグインまたは構成要素だけが判断を要求される |

区分は判断の結果ではなく、判断そのものが発生するかで分ける。
判断の結果が自明であっても、判断が発生するなら `全体` とする。
判断そのものが発生しないプラグインがある場合に限り `種別限定` とする。

### 1.2 原則と、それが解決する問題

| 原則ID | 原則 | 解決する問題 | 適用区分 |
|---|---|---|---|
| C01 | 工場と配布物が持つ資産の内容を分ける。工場は設計判断の履歴、網羅的な契約テスト、観測記録、host 間の比較、互換性と移行の責任、fixture と失敗事例、規範を採用した理由を持つ。配布物は起動条件、入力契約、出力契約、権限、必須の停止条件、不変条件、必要な参照先、host 差分を隠す adapter を持つ。工場の複雑さを利用者へ漏らさず、同時に配布物の単純化を理由に工場側の検証を減らさない | 工場側の資産が配布物へ紛れる。逆に、配布物を軽くする名目で工場側の検証が削られる | 全体 |
| C02 | 工場固有の工程を、そのまま利用者へ要求しない。対象は工程、監査、設計履歴である | 配布物が、作者が正しさを確かめるためだけに要る工程・監査・設計履歴を、利用者の手順として課す | 全体 |
| C03 | 能力を独立に起動できる単位として提供し、一続きの経路は薄い推奨プロファイルとして分ける。推奨経路そのものは有用だが、唯一の正規経路として固定すると利用先へ工程を強制する | 能力が一続きの工程へ強く結合し、利用先のプロセスと自律度へ適応できない | 種別限定 |
| C04 | 成果物を工程名で分けず、寿命と権威で4つに分類する。権威あるストックは再生成できない確定判断であり数を少なく保つ。実行可能な契約は正しさを機械的に判定でき、コードと同時に変更して強制する。一時的なフローは一つの変更を進める作業状態であり、完了後に更新し続ける対象にしない。再生成可能な派生物は別の正本から生成でき、手編集せず、不一致は生成元を直す。分類に加えて、成果物ごとの維持方針（手編集の可否、生成元、更新の停止時点）を宣言する | 成果物の維持の仕方が決まらず、転記と不要な永続化が増える。生成できるものを手で直し、生成元との不一致が残る | 全体 |
| C05 | 成果物の形と格納先を指定せず、必要な情報を契約として要求する。要求するのは、なぜ変更するか、何を満たせば完了か、何を変えてはいけないか、どう検証するか、誰の判断が必要かであり、格納先は利用先が選ぶ。配布物が自ら持つのは、起動条件、入力契約、出力契約、権限、必須の停止条件、不変条件、必要な参照先である | 配布物が成果物の形と格納先を指定して利用先の環境と衝突する。構成要素ごとに契約の語彙が揃わず、入出力・停止・権限を同じ形で読めない | 全体 |
| C06 | 配布物は判断点、リスク、必要な検証を示し、実際に人間承認を置くかは利用先ポリシーへ委ねる。経路選択の軸は作業量ではなく、意図の不確実性、影響範囲、可逆性、検証可能性、損害、公開契約の変更、ドメイン境界の変更である | 配布物が一律に人間承認を要求し、利用先の自律度設計と衝突する。作業量だけの分類では、小さい高リスク変更と大きい機械的変更に適切な経路を選べない | 種別限定 |
| C07 | 依存方向を、能力の意味論、共通の入出力と停止契約、host adapter によるツール・権限・サブエージェント機構への接続、の順に固定する | host 固有のツール名と実行機構が共通の意味へ混ざり、host の変化が配布物の意味論を巻き込む | 全体 |
| C09 | 正本を少数にし、同じ意味を複数箇所へ書かない。ただし共通化そのものを目的にしない。同じ文面でも変更理由が異なるなら各プラグインへ残す。共有資源を増やすと単独インストール可能性を損ねうるため、共通原則を巨大な横断規約や常時ロード文書にしない | 同じ規範が複数箇所へ転記され、整合の維持が作業になる。逆に、共通化を目的化すると変更理由の違う規範まで束ねてしまう | 全体 |

C01 と C02 は隣接するが重ならない。
C01 は資産と内容がどちらへ属するかの分類と、逆方向の禁止を持つ。
C02 は工場側から利用者側への一方向で、配布物が利用者へ課す手順を制限する。
C01 だけでは課す手順が無規定になり、C02 だけでは逆方向と内容の分類が落ちる。

### 1.3 適用対象・非適用条件・既知の例外

| 原則ID | 適用対象 | 非適用条件 | 既知の例外 |
|---|---|---|---|
| C01 | 両側が持つ資産の内容の別と、逆方向の禁止 | 配布しない内部資産だけを扱う変更 | 配布物内に配布元専用の記述を残す場合。「配布先で解決すべき参照ではない」と当該箇所で宣言して処理する |
| C02 | 配布物が利用者へ課す手順、成果物、記録、参照先 | その工程自体が配布価値であるもの。ADR 運用機構が利用者へ求める ADR の起票と維持が当たる | 配布物の検証のために作者が足す手順は、配布元へ置く限り利用者へ課していない |
| C03 | 利用者が直接起動できる能力を複数持つプラグイン。agent と script は利用者が直接起動する能力ではないため数に含めない | 直接起動できる能力が1件のプラグイン | 工程の順序そのものが配布価値であるもの。独立起動を宣言しても、段の順序が入力契約に残る場合がある |
| C04 | 配布物が生成・更新する全成果物 | なし。永続化しない出力も一時的なフローとして分類の対象になる | 同じ資産群が2分類にまたがる場合。ADR 本体が権威あるストック、その有効性 index が再生成可能な派生物であるのが実例である |
| C05 | 配布物が外部へ見せる面を持つ全構成要素（skill、agent、hook、script、adapter） | 全項目を必須にしない。構成要素の型が表せない項目は宣言しない | hook の入力は host のイベント契約が決める。script は exit code が停止条件の実体を兼ねる |
| C06 | 副作用、権限、自律実行を持つ構成要素 | 承認の対象になる操作を持たないプラグイン | 不可逆操作、外部公開、秘密、金銭、法務は配布物側で固定し、利用先へ委ねない |
| C07 | 複数 host へ配布する全プラグイン | 単一 host のみを宣言する配布物 | hook は host のイベント名自体が意味を持ち、共通意味論へ抽象化できない。片 host 固有と宣言した能力 |
| C09 | 配布物内の規範と参照面 | 変更理由が異なる規範。同じ文面でも改訂の契機が別なら各プラグインへ残す | 参照到達性の制約で、正本を層の分け方から外れた場所へ置く場合。これは複製ではなく再配置であり、層から外れることを当該箇所へ明記する |

C06 が決めるのは、承認の設置を配布物と利用先のどちらが持つかという配置である。
承認を減らしてよいかは別の問いであり、本原則は答えない。
既知の例外に挙げた5種は委ねる範囲の下限であり、下限を超えて委ねる判断は本原則の外にある。

### 1.4 運用属性

| 原則ID | 利用者 | 検証主体 | 変更契機 |
|---|---|---|---|
| C01 | 配布物へ資産を足す作者と、配置境界を改訂する作者 | なし。配布物から配布元への参照を検査する仕組みはパス形式の参照だけを台帳と突き合わせ、ADR 識別子による名指しと散文での名指しを対象に含めない | 配布物へ新しい資産の種別が加わったとき。配置境界の3軸が改訂されたとき |
| C02 | 手順を書く作者と、手順を実行する導入先の利用者 | なし。契約項目の被覆を見る検査は語の出現だけを見るため、手順の中身が工場側の工程かを判定しない | 配布物が利用者へ求める成果物・記録・参照先が増えたとき。配布物の検証のための工程を配布物側へ足そうとしたとき |
| C03 | 能力を選んで組み合わせる導入先の利用者と、プロファイルを設計する作者 | なし。skill の説明はいずれも自然文であり、依存の有無を機械的に読める形を持たない | 直接起動できる能力が1件から2件以上へ変わったとき。推奨経路の順序を変えるとき |
| C04 | 成果物を更新・破棄する導入先の利用者と、生成経路を書く作者 | ADR 運用機構のみ。有効性 index の再生成と整合の検査が動く。ほかのプラグインに検査はない | 配布物が生成する成果物の種類が増えたとき。4分類に収まらない成果物が現れたとき |
| C05 | 能力を起動する導入先の利用者と、構成要素を追加する作者 | 契約項目の被覆を見る検査。ただし対象が配列リテラルで固定されており、残る agent、全 hook、全 script は検査の外にある | 構成要素の型が増えたとき。母集団に MCP/app adapter が現れたとき。契約項目を増減するとき |
| C06 | 自律度ポリシーを決める導入先の運用者と、承認点を置く作者 | なし。自律度の語を使う配布物はあるが、使用を検査する機構はない | 配布物が持つ副作用のある操作が増えたとき。配布物側へ固定する下限を動かすとき |
| C07 | 別 host で導入する利用者と、host 接続を書く作者 | 適合性と manifest の検査。ただし前者が読むのは配布元の適合 matrix であり、配布物側の適合宣言はほぼ検査に載らない | 対応 host が増減したとき。適合水準の値域が変わるとき。host が機構を変えたとき |
| C09 | 規範を改訂する作者 | 走査面の排他を見る検査と、実装が正本を指し定義し直していないことを見る検査。`dev-workflow`・ADR 運用機構・作者向け規約を覆い、`dependency-insight`・`growth`・`writing`・`domain-design` は検査の外にある | 同じ意味の規範が2箇所目へ現れたとき。参照到達性の制約で再配置が要る箇所が増えたとき |

`検証主体` は、現に検査している主体を書く。
検査が存在しない場合は「なし」と書き、代わりに何が抜けているかを示す。
検査を足したり被覆を広げたりしたときは、この列を追随させる。

## 2. 原則の内容を条文・宣言・語彙へ分ける

### 2.1 到達対象

原則の内容を利用者が読む必要があるなら、その内容は配布物から到達できなければならない。
`docs/` 配下とリポジトリルートの `CLAUDE.md` は配布されず、配布物内から配布元の文書へリンクを張ることも配置境界が禁じる。
したがって、何が到達対象なのかを先に分ける必要がある。

8つの原則を1件ずつ当てると、利用者が到達しなければならないのは次の2つだけである。

| 到達対象 | 内容 | 例 |
|---|---|---|
| 宣言 | 原則が各プラグインへ要求する宣言 | 独立起動できる能力の別、成果物の分類と維持方針、契約の項目、判断点とリスク |
| 語彙 | その宣言を読むために要る用語とその値域 | 自律度レベル、成果物の4分類の名前、適合水準の4値 |

条文は到達対象ではない。
なぜその設計を採るか、何を却下したか、作者が守る手順は、作者だけが読めばよい。
条文が配布元にあることは、原則が利用者へ届いていないことを意味しない。

この分け方は、8つの原則に限って成り立つ。
実行主体が実行時に読む規範は、宣言でも語彙でもない第3の到達対象になるが、8つの原則にはそれに当たるものがない。
実行時に読む規範を配布物へ届ける必要が生じた場合、本節の2値では足りない。

### 2.2 宣言と語彙の置き場

宣言の正本は、各プラグインが既に持つ面である。横断の共有 reference を新設しない。

| 原則ID | 宣言の正本 |
|---|---|
| C01 | なし。両側が持つ資産の内容の別は作者の判断であり、利用者へ届ける宣言を要しない |
| C02 | 各 skill 本文。配布物が利用者へ課す手順は、対象範囲と成果物の記述に現れる |
| C03 | 各プラグインの `README.md` と各 skill の説明。どの能力が独立に起動でき、どれが推奨プロファイルかを述べる |
| C04 | 維持方針（手編集の可否、生成元、更新の停止時点）は、その成果物を生む skill の出力契約が持つ。4分類の値域を持つ機械可読な宣言と検査は現時点で存在しない。導入するときは後掲の語彙表が述べる形をとる |
| C05 | 構成要素ごとの面。skill は front-matter と本文、agent は front-matter、hook は hook 定義、script は冒頭の usage である |
| C06 | 各 skill 本文。判断点とリスクを述べる |
| C07 | 各プラグインの適合宣言と権限台帳 |
| C09 | 各プラグイン自身の `references/` と、その参照面を走査する検査 |

語彙は、その語を使うプラグインだけが自己完結で持つ。
置き方は「利用者が値域の全体を要るか、使う値だけでよいか」で分かれる。
どちらの場合も、散文の定義本文を配ることは要らない。

| 語彙 | 利用者が要るもの | 置き方 |
|---|---|---|
| 自律度レベル（C06） | 使う値だけ。梯子の全体は要らない | 使用箇所で語釈を添える |
| 適合水準の4値（C07） | 値域の全体 | 値域は機械可読な検査が持ち、意味は使用箇所の残余リスクの記述と `README.md` が持つ |
| 成果物の4分類（C04） | 値域の全体 | 導入時に適合水準と同じ形をとる。散文の定義を配る設計にしない |

### 2.3 条文の正本の分担

条文は配布元へ置く。新規の横断規約も、全プラグインが常時読み込む文書も、共有プラグインも作らない。
どの正本が受け持つかは、その原則の主題で決める。

| 正本 | 対象の原則 | 責務 | 条文の現況 |
|---|---|---|---|
| `docs/distribution-boundary.md` | C01 | 配置境界 | 後続で追記する。同書が現に持つのは §2 の配置の判断軸3点であり、両側が持つ資産の内容の別は本文に無い |
| `docs/references/autonomy-rubric.md` | C06 | 自律度の判定基準 | 後続で追記する。同書が現に持つのは L0〜L3 を5要因で判定するルーブリックであり、承認の設置をどちらが持つかと経路選択の7軸は本文に無い |
| `docs/references/cross-host-plugin-conformance.md` | C07 | host 適合契約 | 後続で追記する。同書が現に持つのは適合水準の4値と権限台帳であり、依存方向の固定は本文に無い |
| 本書 | C02、C03、C04、C05、C09 | 配布プラグインの設計規律 | 現に持つ |

本表が分担するのは条文だけである。
原則そのものと、適用対象・非適用条件・既知の例外・運用属性は、8件すべてを §1 が一元して持つ。
条文を持つ正本は、自身の主題の中で当該原則がどう効くかを述べ、§1 の内容を再掲しない。

C02（工場固有の工程を、そのまま利用者へ要求しない）は主題としては配置境界に隣接するが、`docs/distribution-boundary.md` は「プラグインと利用者側の責務分担の一般原則」を自ら射程外と宣言している。
§2.4 が C03・C04・C05・C09 の追記先から同書を落とした理由は同じ宣言の別の句であり、その句は C02 にも同様に掛かる。
したがって C02 は本書が受け持つ。同書の射程を広げるかどうかは同書側の決定であり、本書は行わない。

`条文の現況` が `後続で追記する` の3件は、当該原則の条文をその正本がまだ持たない。
読者が当該正本へ当たっても、現時点では当該原則の記述に行き当たらない。
追記されるまでの間、これら3件の条文は §1 と、本書の §4・§5 の記述が担う。この状態は §2.5 が既知の限界として持つ。

新しい原則を足す場合も、既存の正本の責務へ割り当てる。
どの正本の責務にも収まらない場合に限り、本書が受け持つ。

### 2.4 採らなかった配置と、その理由

配置は、条文をどこへ置くかで8案を比較した。
比較の観点は、配布物の常時コンテキスト量、プラグイン間結合、単独インストール可能性、host 可搬性の4つである。
採ったのは §2.1〜§2.3 が述べる形、すなわち条文を配布元の既存正本へ分散し、宣言を各プラグインの既存の面へ落とし、語彙は値域を機械可読な検査が・意味を使用箇所が持つ案である。

| 採らなかった案 | 却下理由 |
|---|---|
| 配布元へ新規の横断規約を1本立てる | 8件の条文は複数の既存正本の責務へ分かれる。1本へまとめると各正本の射程と二重化する |
| リポジトリルートの `CLAUDE.md` へ追記する | host がセッションごとに自動で載せるため常時コンテキストが増え、C09 の上限（常時ロード文書にしない）に触れる。加えて Claude Code 固有の機構であり、Codex では同じ位置に載らない |
| 新規の共有プラグインを配布し、各プラグインが参照する | プラグイン間の依存を宣言する機構がどちらの marketplace にもなく、依存が暗黙になる。共有プラグイン未導入の利用者から参照が解決せず、単独インストール可能性を損なう |
| 既存の1プラグインの `references/` を横断の正本にする | 参照の向きが非対称になり、被参照プラグインの改訂が他を巻き込む。当該プラグインを導入していない利用者から参照が解決せず、配置境界の第1軸（配布先で参照を解決できない資産を配布物へ置かない）に反する |
| 各プラグインへ条文を複製する | C09 自身に反する。複製箇所の整合維持が新たな作業になる |
| 条文を置かず、機械可読な宣言面へ形だけを落とす | 形は落とせるが、なぜその形かという条文と、語彙の定義を置く場所がない。宣言と組み合わせる形でのみ成立する |
| 配布元の既存正本へ条文だけを追記する | 条文の置き場としては正しいが、宣言と語彙が利用者へ届かない。単独では、読み手に利用者を含む原則を満たせない |

4観点だけでは決まらない組が2つある。
「配布元の既存正本へ条文だけを追記する」と「配布元へ新規の横断規約を1本立てる」は4観点で同値であり、弁別は配布元内の責務境界（根拠から構造・操作への一方向）で行った。
「各プラグインへ条文を複製する」と採用案は単独インストール可能性の欄で分かれるが、その分かれ目は複製を作るかどうかであって観点そのものではない。

C02・C03・C04・C05・C09 の条文を本書が受け持つことについても、採らなかった追記先がある。

| 採らなかった追記先 | 却下理由 |
|---|---|
| `docs/principles.md` | 3つある。第1に、根拠から構造・操作への一方向を固定した決定に反する。5件はいずれも「配布物が何を宣言するか」を述べる操作規定である。第2に、C04 を同書のストック／フロー節へ拡張することは同節の定義を改めることであり、過去記録の廃止を決めた ADR-202608301012-01 が却下代替として名指した「`docs/principles.md` のストック／フローの定義自体を改める」に当たる。同 ADR がこれを却下した理由は、ADR-202607182303-01 の core 反転にあたり、規範の内容を変えたいわけではないのに ADR を1本動かすことになる、である。同 ADR は射程の限定としても既存のストック／フロー軸へ接続し新しい軸は立てないと述べており、拡張はこの限定にも反する。第3に、同 ADR にはもう1件「ストック／フローとは別の新しい軸を立てて説明する」という却下代替があるが、C04 の4分類はこれに当たらない。4分類は配布物が生成する成果物を対象とし、`docs/` 配下の文書分類軸を置き換えないためである |
| `docs/distribution-boundary.md` | 同書は「配布物の内部構成」と「プラグインと利用者側の責務分担の一般原則」をいずれも射程外と自ら述べる。C03・C04・C05・C09 は前者に、C02 は後者に当たる |
| `docs/behavior-invariants.md` | 同書の射程は実行時の生成量と作業範囲であり、宣言面の契約項目ではない |
| リポジトリルートの `CLAUDE.md` | 常時コンテキスト量と host 固有性が、配置の案3を落とした理由と同じ形で掛かる。落とすのは条文本体の追記であり、本書を指すポインタ1行はこの理由に触れないため対象外である |
| 一般部分だけを新しい文書へ切り出す | 切り出すと同じ規律が2文書へ分かれ、以後どちらへ書くかの判断が改修のたびに発生する |

### 2.5 既知の限界

第1に、`docs/development/adr-plugin-design-guideline.md` の §1 と §2.2 は本書の一般形と重なる。
§1（中核と周辺）は C01・C02 を、§2.2（参照面の正本の一意性）は C09 を、いずれも ADR 運用機構1件に限って述べた形である。
本書がこれらの一般形を持つため、同書の2節は本書を指す形へ縮退させる必要がある。
縮退させるまで、同じ規律が2箇所に載る状態が残る。これは C09 が禁じる状態である。
縮退は Issue #832（同書の §1・§2.2 を本書の一般形へ縮退させる）が追う。

第2に、§2.3 の `条文の現況` が `後続で追記する` の3件（C01・C06・C07）は、条文をその正本がまだ持たない。
分担は §2.3 が定めたが、読者が当該正本へ当たっても現時点では当該原則の記述に行き当たらない。
追記されるまでの間、これら3件の条文は §1 と、本書の §4・§5 の記述が担う。
追記は Issue #830（C01）、#835（C06）、#836（C07）が追う。

第3に、条文を4面へ分けたため、原則そのもの（§1）と条文の間で改訂が同期しない可能性がある。
§1 を改訂したときは、当該原則の条文を持つ正本も見る。

### 2.6 語彙を配る必要が生じたら、複製ではなく生成で配る

散文の定義本文を複数の配布物へ配る必要が将来生じた場合は、正本を1つ置き、各プラグインの語彙ファイルをそこから生成する。
生成物へ手動編集禁止のヘッダを付け、再生成一致を検査する。
複製と一致検査は採らない。

複製はドリフトが起きてから検出することになる。
一致検査を逐語にすると、文脈に合わせた言い換えで赤になる。
言い換えを許すと検査が空振りする。
生成はこの二律背反を作らない。
ADR の有効性 index の生成が同型の先例であり、生成物へ手動編集禁止を出力し、lint が不一致を落とす形をとる。

## 3. 構成要素へ共通して要求できる契約

### 3.1 契約項目の意味

7項目の意味は、構成要素の型が違っても一つに保つ。

| 契約項目 | 共通の意味 |
|---|---|
| 起動条件 | どんなときにその構成要素が動き始めるか |
| 入力契約 | 動き始めるために外から受け取る情報と、その形 |
| 出力契約 | 動き終えたときに外へ渡す情報と、その形 |
| 停止条件 | 動作を完了扱いにせず止める条件 |
| 変更境界 | 変えてよい対象と、変えてはいけない対象 |
| 権限 | 実行してよい操作の集合 |
| 検証責務 | その構成要素の正しさを誰がどの手段で確かめるか |

### 3.2 構成要素ごとに宣言できる面

意味は共通でも、宣言できる面は構成要素の型が決める。
「宣言する場所がない」は、その型に当該項目を書く面が存在しないことを示す。

| 構成要素 | 起動条件 | 入力契約 | 出力契約 | 停止条件 | 変更境界 | 権限 | 検証責務 |
|---|---|---|---|---|---|---|---|
| skill | front-matter の説明 | 本文の散文。対象範囲の記述が代理する | 本文の成果物の記述 | 本文の停止条件の記述 | 本文の変更境界の記述 | front-matter の許可ツール。Bash はコマンドパターンで粒度を制御する | skill ごとに異なる。同梱検査器の呼び出しと、独立レビューの委譲に分かれる |
| agent | front-matter の説明 | 本文の節。見出しは不揃いである | 本文の節 | 専用の節がなく、注意事項などへ混在する | 同上 | front-matter のツール指定。指定しない場合は起動元の権限を継ぐ | agent 自身が検証の担い手である場合と、生成の担い手である場合で責務が逆になる |
| hook | hook 定義のイベント・matcher・条件式。観測した4型で唯一、起動条件を機械が評価できる述語として宣言する面である | stdin の JSON。形は host のイベント契約が決め、配布物は宣言しない | stdout の JSON または stderr | 終了コード | 宣言する場所がない | 宣言する場所がない。host が hook へ与える実行権限に従う | 配布元のテストが担う |
| script | 呼び出し元 skill の許可ツールのコマンドパターンと、冒頭コメントの usage | 引数と環境変数。既定と上書きを分ける形をとれる | stdout。形式は冒頭コメント | 終了コード | 宣言する場所がない | 宣言する場所がない。呼び出し元 skill のコマンドパターンが実質の上限になる | script 自身が検査器である場合が多い。script の正しさは配布元のテストが担う |
| MCP/app adapter | 未観測 | 未観測 | 未観測 | 未観測 | 未観測 | 未観測 | 未観測 |

MCP/app adapter は、2026-08-30 時点の配布プラグインに実装も宣言も存在しなかった。
不存在を観測として記録し、将来の共通契約を推測で補わない。
母集団に MCP/app adapter が現れた時点で、この行を観測で埋める。

### 3.3 共通化の上限

C05 が要求できるのは次の2点までである。

第1に、7項目の意味を全構成要素で同じ語として読めること。
第2に、各構成要素がその型で表せる項目を、その型の面で宣言すること。

全項目を全構成要素へ必須にはしない。
必須にすると、hook と script の変更境界・権限のように、宣言する場所のない項目を作ることになる。
hook の入力の形は host のイベント契約が決めるため、配布物が同じ形を宣言すると host と二重管理になる。
script の停止条件は終了コードが実体であり、散文の再掲は転記になる。

観測した4つの構成要素すべてが機械可読な宣言を持つ項目は、7項目のうち1つもない。
権限を機械可読に宣言するのは skill だけであり、agent は指定が任意、hook と script は宣言する場所を持たない。

## 4. host 共通の意味論と adapter の境界

共通意味論として保てるのは、「能力の起動」と「検査器の実行」の意味、および「プラグインルートの解決」の結果である。
実現機構はいずれも host ごとに違う。

| host 差分を比較した項目 | 共通意味論 | Claude Code の実現機構 | Codex の実現機構 |
|---|---|---|---|
| プラグインルートの解決 | 保つ（結果のみ） | 環境変数で解決する | host が解決した絶対パスを入力として受ける |
| 能力の起動 | 保つ | スコープ付きの skill 呼び出し | manifest の skills 宣言と既定プロンプト |
| サブエージェントの起動 | 保たない | agent 定義を native に起動する | agent 定義の全文を汎用サブエージェントへ注入する。読み取り専用の制約を機械強制できない |
| 自動実行 | 保たない | hook 定義のイベントで起動する | plugin 単位の hook がない |
| 権限の宣言 | 保たない | skill の front-matter の許可ツール。ツール単位の粒度を持つ | manifest がプラグイン単位の粗い capability を宣言する。skill ごとの許可ツールに当たる粒度の面はなく、実行時の許可は host の承認に従う |
| 検査器の実行 | 保つ | 同梱 script を bash で実行する | 同じ |
| 配布の登録 | 保たない | Claude 側の marketplace | Codex 側の marketplace |

本表が並べるのは host 差分を比較した項目であって、共通意味論の構成要素ではない。
`共通意味論` が `保たない` の4項目は比較のために並べたものであり、共通意味論へは載せない。

「自動実行」は Codex に機構そのものがない。
これを共通意味論へ載せると片 host で成立しないため、載せない。
C07 の既知の例外（hook は host のイベント名自体が意味を持つ）がここに当たる。

片 host 固有であることを宣言できる面は、配布元の適合 matrix だけである。
配布物側の適合宣言は自身の適合を述べるが、両 host の marketplace の集合一致を見る検査はそれを読まない。
C07 の被覆の不足は、この非対称として現れる。

## 5. 共通化できる部分と固有設計へ残る部分

原則の採用は、原則が要求する判断を共通化するものであって、実現方法まで共通化しない。

| 原則ID | 共通化できる部分 | 固有設計へ残る部分 |
|---|---|---|
| C01 | 両側が持つ資産の内容の別と、逆方向の禁止 | 配布元固有データを既定値へ退避する機構 |
| C02 | 配布物が利用者へ課す手順の制限 | 何が配布価値の工程かの線引き |
| C03 | 独立起動できる能力と推奨プロファイルの別の宣言 | 順序そのものが意味を持つ経路の扱い |
| C04 | 4分類の名前と、成果物ごとの維持方針の宣言 | 同じ資産群が2分類にまたがる場合の扱い |
| C05 | 契約項目の意味と、型で表せる項目をその型の面で宣言すること | 構成要素ごとの宣言面と、格納先の既定値の与え方 |
| C06 | 判断点とリスクの宣言、および承認の設置の委譲 | 配布物側へ固定する下限の具体 |
| C07 | 依存方向の固定と、適合水準の宣言 | host に機構がない能力の縮退の書き方 |
| C09 | 参照面の正本の一意性 | 複製を許す例外の判定。到達性の制約によるものか、変更理由の別によるものかを分ける |

固有設計へ残る部分が原則ごとに在ることは、原則そのものを各プラグインへ委ねることを意味しない。
前者は原則の実現方法の帰属であり、後者は原則そのものの帰属である。
