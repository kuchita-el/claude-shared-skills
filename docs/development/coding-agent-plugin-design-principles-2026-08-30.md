# コーディングエージェント向けプラグインの共通設計原則

## 用語

- プラグインは、コーディングエージェントへ能力を追加する配布単位である。
- skillは、目的、手順、入出力、停止条件、許可ツールを定めた能力の契約である。
- agentは、独立した文脈と役割で委譲された作業を実行する主体である。
- hookは、ホスト上のイベントを契機に自動実行される接続点である。
- scriptは、決定的な処理や検査を実行するプログラムである。
- referenceは、skillなどが必要時に読む補助規範または仕様である。
- manifestは、プラグインの名前、版、能力、接続面を機械可読に宣言するファイルである。
- hostは、Claude CodeやCodexなど、プラグインを動かす実行環境である。
- adapterは、共通の意味をhost固有のツール、権限、呼び出し方法へ接続する層である。
- MCP/app adapterは、外部サービスやアプリケーションとの接続をhost上で実現するadapterである。
- workflowは、複数の能力を順序や分岐で結ぶ作業経路である。
- profileは、独立能力を既定の経路として組み合わせた推奨設定である。
- inquiryは、根の問いへ答えるために、複数の問いを統治する調査単位である。
- pivotは、結論によってほかの問いを決めうる中核の問いである。
- 枝刈りは、pivotの結論により、別の問いを直接解かず明示的に決着させることである。
- dogfoodは、配布物を作者自身の実作業へ適用して効果と副作用を観測することである。
- contextは、エージェントが判断時に参照できる入力情報の集合である。
- degradedは、本来の機構を使えず、明示した制限付きの代替経路で動く状態である。
- 正本は、同じ意味を管理する権威ある情報源である。
- 未決は、調査の問いがまだ決着しておらず、完了を阻む状態である。
- SoTはSingle Source of Truthの略で、同じ意味を管理する単一の正本を指す。
- ADRはArchitecture Decision Recordの略で、設計判断と却下代替を残す記録である。
- ACはAcceptance Criteriaの略で、成果を受け入れられるかを判定する条件である。
- lintは、定めた形式や規則への違反を機械的に検出する検査である。

## 判定値域と完了則

### 候補原則の判定値

候補原則は次の3値で判定する。Task 2 で全10件へ値を付けた。

| 判定値 | 意味 |
|---|---|
| 採用 | 定めた適用範囲の共通原則として採る |
| 個別設計へ委譲 | 共通原則にはせず、構成要素またはプラグイン固有の設計へ残す |
| 棄却 | 共通原則としても個別設計の既定としても採らない |

採否とは別に、候補が及ぶ範囲を `適用区分` として持つ。値域は次の4値である。

| 適用区分 | 意味 |
|---|---|
| 全体 | 配布対象の全プラグインへ及ぶ |
| 種別限定 | 特定の性質を持つプラグインまたは構成要素にだけ及ぶ |
| 個別 | 共通の範囲を持たず、各プラグインの設計が範囲を決める |
| 該当なし | 共通原則として採らないため、及ぶ範囲を定めない |

両者の写像は次のとおりで、判定表の全10行はこの対応のいずれかを取る。

| 採否 | 取りうる適用区分 |
|---|---|
| 採用 | `全体` または `種別限定` |
| 個別設計へ委譲 | `個別` |
| 棄却 | `該当なし` |

| 決着値 | 意味 |
|---|---|

| 推移的に決定済み | 別の問いである pivot の結論から答えが論理的に導かれた |

## 根拠採用基準

根拠の権威性は、主張の種類と資料の射程を組み合わせて判定する。
上位の資料であっても、明示された射程外の主張には使わない。

| 優先 | 権威性 | 採用方法 |
|---|---|---|
| 1 | 現行の規範・正本 | 現在の規則や用語の定義に使う。単一出典の宣言と射程を優先する |
| 2 | `承認済み` かつ `有効` な ADR | 決定の骨子、却下代替、射程の根拠に使う。可変な現行手順の代用にはしない |
| 3 | 実行可能契約・機械可読宣言・実装 | 現在の挙動、権限、停止条件、host 差分の観測に使う。規範の存在は推定しない |
| 4 | Issue と実装計画 | 要求、仮説、調査範囲の出典に使う。既存挙動の証明には使わない |
| 5 | 時点固定の設計・観測記録 | 既存事例、測定、調査手法の参考に使う。現在の規範へ自動昇格させない |
| 6 | `上書き済み` または廃止済みの ADR | 歴史的経緯だけに使う。現行規範は有効な後継または運用上の正本で確認する |

同じ主張が競合する場合は、現行の正本を優先する。
ADR は自身が保持する決定の骨子に限って優先し、運用詳細は現在の実行可能契約で確認する。
観測記録には観測時点と限界を残す。根拠から導けない一般化は、仮説または仮対応と明記する。

上表は主張の種類ごとの優先であり、同じ主張について後段の資料が前段を上書きする場合がある。
本調査ではこれが1件ある。候補原則が何を述べているかという主張については、I04（Git管理外のローカルメモ）を I01（Issue #822 本文）より優先する。
I01 の10項目は I04 の本文を1行へ圧縮した見出しであり、圧縮の過程で定義、解決する問題、想定する読み手が落ちているためである。
この優先は候補の定義に限る。要求の範囲、AC、完了成果物は I01 が正本であり、I04 は仮説として扱う。

## 候補原則の定義

Issue #822 本文の10項目は、`.local/agent-native-development-notes.md`「全プラグインへ適用しうる原則」の10項目を写したものである。
どちらも1行の見出しであり、定義、解決する問題、想定する読み手は同メモの本文側にある。
判定は、その本文から復元した定義に対して行う。

`読み手` は、その原則の内容を誰が読める必要があるかを表す。値域は `作者` / `利用者` / `両方` の3値である。
利用者が読む必要があるなら、原則の正本は配布物（`plugins/` 配下）から到達できなければならない。
作者だけが読めばよいなら、正本は配布元に置いてよい。
原則を守る主体はどの候補でも作者であるため、守る主体では区別しない。

`docs/` 配下とリポジトリルートの `CLAUDE.md` は配布されない。
`docs/distribution-boundary.md` §3 は、配布物内から配布元の文書へリンクを張ることも禁じる。
したがって配布元の規範は、読み手に利用者を含む原則の正本にはなれない。

本節が「正本」と呼ぶものを、Task 3 は条文・宣言・語彙の3つへ分ける。
分けた結果、利用者へ到達しなければならないのは宣言と語彙であり、条文は配布元でよいことが分かった。
Task 2 の採否は動かない。詳細は「読み手の要求の精緻化」が持つ。

### 判定の補足

表の欄に収まらない限定を7件残す。

- **C01 と C02 の分担**: メモは両者を別項目として立てる。C01 は資産と内容がどちらへ属するかの分類と、逆方向（配布物の単純化を理由に工場側の検証を減らさない）を持つ。C02 は工場側から利用者側への一方向で、配布物が利用者へ課す手順を制限する。両者の適用対象は重ならない。どちらか一方だけを採ると、C01 のみでは課す手順が無規定になり、C02 のみでは逆方向と内容の分類が落ちる。
- **`全体` と `種別限定` の別**: `全体` は、配布対象の全プラグインが判断を要求される場合に付す。判断の結果が自明であっても、判断そのものが発生するなら `全体` とする。`種別限定` は、判断そのものが発生しないプラグインがある場合に付す。C03 は直接起動できる能力が1件のプラグインに宣言すべき経路がなく、C06 は `dependency-insight` に承認の対象となる操作がないため、いずれも `種別限定` とした。
- **C04 の軸の出所**: メモは軸を「寿命と権威」と名指す。各分類が伴う維持方針（数を少なく保つ、CIで強制する、更新し続けない、手編集せず生成元を直す）は、その軸から導かれる帰結として本文に書かれている。本判定は軸をメモの語のまま扱い、N03 との差分を権威の軸に、N17 との差分を射程（保護手段の選択か成果物の分類か）に置いた。維持方針そのものを軸として立て直してはいない。
- **C06 と未決仮説の別**: メモは「人間承認を減らしても品質を維持できるか」を実測待ちの未決とする。本判定はこの仮説を解いていない。C06 の採用が決めるのは、承認の設置を配布物と利用先のどちらが持つかという配置であり、承認を減らしてよいかではない。委ねる範囲の下限（不可逆操作、外部公開、秘密、金銭、法務）は非適用条件として配布物側に固定し、下限を超えて委ねる判断は実測を待つ。
- **C09 と共通原則自身の配置**: C09 は「共通原則を巨大な横断規約や常時ロード文書にしない」という上限を自らの内容として持つ。したがって C09 の採用は、本調査が採った8件をどこへ置くかに跳ね返る。配置の決定は Task 3 の責務であり、本 Task では採否と適用区分までを固定する。
- **C10 と Issue のスコープ**: Issue #822 のスコープ IN は「dogfood と互換性維持の原則」を含み、AC6 は dogfood 対象と比較方法の定義を求める。C10 の型B棄却はこれと衝突しない。AC6 が求めるのは本調査の採用原則をどう dogfood するかであり、dogfood 運用の二層化を配布物の共通原則にするかではない。前者は Task 4 が扱う。
- **採用8件と共通化の目的化**: メモは「共通化そのものを目的にしてはならない」と述べる。本判定が8件を採ったのは、8件それぞれについて既存の正本が存在しないか、存在しても読み手が一致しないことを個別に確認したためである。8件を1つの横断規約へ束ねることは含意しない。束ねるか分けるかは C09 の内容が縛る Task 3 の判断である。

## 読み手の要求の精緻化

Task 2 は、原則の内容を利用者が読む必要があるなら正本は配布物から到達できなければならない、と述べた。
配置を決めるには、この要求が何の到達可能性を求めているかを分ける必要がある。
採用8件を1件ずつ当てると、利用者が到達しなければならないのは次の2つであり、原則の条文そのものではない。

| 到達対象 | 内容 | 例 |
|---|---|---|
| 宣言 | 原則が各プラグインへ要求する宣言 | 独立起動できる能力の別、成果物の分類と維持方針、契約の項目、判断点とリスク |
| 語彙 | その宣言を読むために要る用語の定義 | `L0`〜`L3`、成果物の4分類の名前、適合水準の4値 |

条文（なぜその設計を採るか、却下した代替、作者が守る手順）は作者だけが読めばよい。

この分離が Task 2 の採否を動かさないことを、読み手に利用者を含む5件で1件ずつ確かめた。

| 候補ID | 届いていないもの | 採用を支える主張 | 精緻化で弱まる主張 |
|---|---|---|---|
| C03 | 宣言。どの能力が独立に起動でき、どれが推奨プロファイルかを述べる面がない | 宣言を求める規範がどこにもない。母集団3件のうち経路の任意性を宣言するものは0件である | 「N20 は配布元にあり正本になれない」。条文としてなら配布元でよい |
| C04 | 宣言。成果物ごとの維持方針を述べる面が `plugins/adr/` 以外にない | N03 が権威の軸を持たず、N17 の射程が保護手段の選択である | なし。差分は射程の別であって到達可能性ではない |
| C05 | 宣言。契約の被覆が配列リテラルで固定され、格納先が `docs/plans` に固定されている | X07 の被覆と述語の不足、および保存先固定の実例 | 「N18 は配布元の散文であり」。C03 の N20 と同型で、条文としてなら配布元でよい |
| C06 | 語彙。`L0`〜`L3` の定義本文が配布されず、`plugins/growth/` は識別子でしか本体を指せない（X08） | 判断点とリスクを宣言し承認の設置を利用先へ渡す配置を求める規範がない | なし。語彙の不到達は精緻化後も残る |
| C09 | 宣言。参照面の正本が一意であることを求める規範が `plugins/adr/` に限られる | N15 §2.2 の射程限定と、例外則・上限の不在 | なし。差分は射程の別である |

弱まるのは C03 と C05 で、いずれも「配布元にあるから正本になれない」という同型の支持主張1つずつである。
C03 は「宣言を求める規範がどこにもない」、C05 は「X07 の被覆と述語が不足する」というもう一方の主張だけで立つ。
採用8件のいずれも判定は変わらない。

## 採用原則の運用属性

AC2 は採用候補ごとに7属性を求める。
このうち `適用対象`、`非適用条件`、`既知の例外` の正本は「候補原則の判定」の同じ候補IDの行である。
下表の当該3列は、その行を特定するための見出しとして短く書いた。
判定表の側にしかない補足（適合例、破れの実例、件数）は写していない。
ただし判定表の値が既に1行に収まる短さの場合は、要約が原文と逐語で一致する。
C05 の非適用条件と C07 の既知の例外がこれに当たる。
C09（同じ意味を複数箇所へ書かない）は本文書自身にも掛かるため、詳細は判定表の側だけが持つ。

`利用者` は `読み手` とは別の属性である。
`読み手` は Task 2 の判定で使った「原則の内容を誰が読める必要があるか」の3値である。
`利用者` は「その原則に従って作られたものを受け取り、判断に使う主体」を指す。

`検証主体` は、現に検査している主体を書く。
検査が存在しない場合は「なし」と書き、代わりに何が抜けているかを示す。

### 分離の結論

7項目のうち、観測できた4つの構成要素すべてが機械可読な宣言を持つ項目は1つもない。
MCP/app adapter は母集団に存在せず、以下の比較には入らない。
起動条件は skill と agent が `description`、hook が `hooks.json` で持つが、script は冒頭コメントに留まる。
権限を機械可読に宣言するのは skill だけであり、agent は10件中2件、hook と script は宣言する場所を持たない。

hook の入力の形は host のイベント契約が決めるため、配布物が同じ形を宣言すると host と二重管理になる。
script の停止条件は終了コードが実体であり、散文の再掲は転記になる。
`manage-adr/SKILL.md:112` の再掲は現にこの形をとっている。

したがって C05 が要求できるのは次の2点までである。
第1に、7項目の意味を全構成要素で同じ語として読めること。
第2に、各構成要素がその型で表せる項目を、その型の面で宣言すること。
全項目を全構成要素へ必須にすると、hook の変更境界と権限のように、宣言する場所のない項目を作ることになる。

## 条文の追記先の確定

Task 3 は採用8件の条文の追記先のうち4件を未定として残した。
本節で C03、C04、C05、C09 の4件を確定する。
確定は案8の枠内で行う。条文は配布元、宣言は各プラグインの面、語彙は値域を検査へ・意味を使用箇所へ、という分け方は変えない。

追記先を選ぶ条件は2つである。

第1に、追記先の既存の射程が当該の条文を含むこと。
含まない場合は、その追記先が自ら射程外と宣言した空白を埋めるものであり、かつ他のどの正本もその空白を持たないことを示す。
Task 3 が確定した C01・C02 の `docs/distribution-boundary.md` への追記もこの形である。
同書 §1 は「プラグインと利用者側の責務分担の一般原則」を射程外と自ら宣言しており、追記は射程の拡大を伴う。
第1条件を「射程に含まれること」だけに読むと、既決の2件も落ちる。

第2に、A18 が固定した「根拠から構造・操作への一方向」を跨がないこと。
`docs/principles.md` は根拠ハブであり、構造と操作の正本を持たない。

第2に、C04 を同書「情報設計の原則」へ置く案は、ADR-202608301012-01 が却下代替として名指した案そのものである。
当該の却下代替は「`docs/principles.md` のストック／フローの定義自体を改める」である。
同 ADR は射程の限定でも「既存のストック／フロー軸へ接続し、新しい軸は立てない。既存の定義を改めることも本決定に含めない」と述べる。
`docs/references/document-permanence.md` はこの2値の上に立っており、4分類への拡張はその依存を陳腐化させる。
第3に、同案は本文書自身の除外根拠を崩す。

C04 を `docs/` 配下の文書分類軸へ書き込めば、どちらの根拠も成り立たない。

第2に、同書は自らを ADR への追随側と宣言する（`:6`「本書は ADR の上位に立たない」）。

## dogfood 対象と比較設計

### 対象の選定

採用8件のうち、変更範囲が小さく前後を同じ指標で比較できるものを選ぶ。
選定条件は3つである。
第1に、原則が要求する形と現状の差が観測済みであること。
第2に、変更が既存の1機構に閉じ、新しい恒久文書を作らないこと。
第3に、変更の効果を件数で数えられること。

選んだのは C07 の適合水準の自己記述である。
検査器は `degraded` と `surface-specific` にだけ `residualRisk` を非空で必須とし、`adapted` には同じ要求を持たない（X14）。
`adapter` という字段は `plugins/writing/compatibility.json` に実在する。
しかしこの字段は、`cross-host-plugin-conformance.md` の schema 表にも検査器にも現れない。
`adapted` は「host adapter を介して同じ成果を得る」という、結果を左右する主張である。その adapter を名指す要求がないまま宣言できる。

選ばなかったものと理由も残す。
C03 と C04 の宣言は、宣言の形式そのものを先に決める必要があり、変更が1機構に閉じない。
C01 と C02 は条文が未着手であり、変更前の判定基準が定まらない。
C09 は検証主体として X04・X09・X13 の3機構を持つが、検査の外に4プラグインが残る。被覆を広げる変更はその4件へ及び、最小変更にならない。

## ADR 処遇の判定

本節は判定だけを行う。ADR の起票、承認、上書き、分割、廃止、却下、直接編集はいずれも本調査の OUT であり、実施しない。

判定は `plugins/adr/skills/manage-adr/references/adr-scoping.md` に従う。手順は3段である。
第1に必要条件、すなわち当該決定について採らなかった選択肢とその却下理由が対として特定できることを確かめる。不成立なら点数を数えず ADR 化しない。
第2に4項目（後戻りコスト、適用先、理由の揮発、自動強制）を各1点で数え、合計3点以上を ADR 化推奨とする。
第3に行き先を `adr-destination.md`「判定結果の行き先」で決める。
項目単位でも合計でも、該当するか迷う場合は該当しない側へ倒す。

### 根拠文書間の衝突 #4 の判断

衝突 #4 は、ADR-202607261002-02 と `scripts/tests/behavior-invariants.bats` 第1ケースの並存である。
同 ADR の決定1は、振る舞いの規律の実体を配布物内の共有 reference へ置き、配布物からポインタで参照すると定める。

**判断**: 本調査は「どちらを改めるか」を決めない。決めるための前提が本調査の射程の外にある。
決まるのは次の3点である。

第1に、現行の強制手段は検査である。決定1は実装されておらず、配布物側に実体はない。

当該 ADR は `提案中` であるため、取りうる遷移は `承認` と `却下` の2つに限られる。
`上書き`・`分割`・`廃止` はいずれも `承認済み` を伴う構成子への移動であり、取れない。
したがって「退役させる」は選択肢として構成できない。

第2に、どちらを選ぶかは「`docs/behavior-invariants.md` の読者が実行主体か作者か」に依存し、本調査はこれを決められない。
同書は冒頭で自らを実行主体向けの規約と宣言し、各スキルとサブエージェント定義が参照する形を前提に置く。
一方、リポジトリルートの `CLAUDE.md` は同書を新規追加時の設計時の単一出典として引く。
両者は食い違っている。
読者別配置の一般基準そのものが repo 横断の規範として確立されていないことは、Issue #580 が射程に持つ。

第3に、本調査が到達対象を宣言と語彙の2つへ分けた結果は、この問いを解かない。
同書が定めるのは実行主体が実行中に読む判断規律であり、宣言でも語彙でもない。
条文・宣言・語彙の3系統は、実行主体が実行時に読む規範という到達対象を持たない。
これは本調査の枠組みが持つ限界であり、限界として記録する。
8つの採用原則はいずれも作者が設計時に守る規律か、各プラグインが外へ見せる宣言であるため、この限界は採用8件の判定を動かさない。

## 根の問いへの統合

根の問いは「共通設計原則として何を採り、どの適用範囲と強制力を与え、どこを正本とし、何を個別設計へ残すか」である。
9問すべてが決着したため、次のとおり統合する。

**何を採るか**。10候補のうち8件を共通原則として採る。

- C01: 両側が持つ資産の内容の別と、逆方向の禁止。
- C02: 配布物が利用者へ課す手順の制限。
- C03: 独立して起動できる能力と推奨プロファイルの別の宣言。
- C04: 成果物を寿命と権威で4分類し、維持方針を宣言すること。
- C05: 成果物の形ではなく契約項目を要求すること。
- C06: 判断点とリスクを宣言し、承認の設置を利用先へ委ねること。
- C07: 依存方向を意味論・契約・adapter の順に固定すること。
- C09: 参照面の正本を一意に保ち、変更理由が異なる規範は分けたまま残すこと。

`個別設計へ委譲` は0件である。棄却は2件で、C08 は同じ規律を持つ正本が既にあり読み手も一致するため、C10 は読み手が作者であり採っても配布物が変わらないためである。C10 の規律そのものは否定せず、工場の運用の規律として #823 へ移送する。

**どの適用範囲か**。8件のうち6件は `全体`、すなわち配布対象の全プラグインが判断を要求される。2件は `種別限定` である。C03 は利用者が直接起動できる能力を1件しか持たないプラグインでは宣言すべき経路がなく、C06 は承認の対象になる操作を持たないプラグインでは判断が発生しない。
`全体` と `種別限定` の別は、判断の結果ではなく判断そのものが発生するかで分ける。結果が自明でも判断が発生するなら `全体` とする。

**どの強制力か**。強制力は一律ではなく、原則の内容を3系統へ分けたうえで系統ごとに与える。
条文（なぜその設計を採るか、却下した代替、作者が守る手順）は散文であり、読み手は作者に限られる。強制は人が読むことに依存する。
宣言（原則が各プラグインへ要求する宣言）は各構成要素の既存の面に置き、機械可読な面については検査で強制できる。
語彙（宣言を読むために要る用語）は、値域を機械可読な検査が持ち、意味を使用箇所が持つ。
現時点で採用8件のうち、現行の検査が適用対象の全体を覆っているものは1件もない。強制の水準を上げる作業は原則の採否とは別の単位であり、後続へ分ける。

**どこを正本とするか**。条文は配布元の既存正本4面へ分散し、新規の横断規約も常時ロード文書も新しい共有プラグインも作らない。C01・C02 は配置境界の正本、C06 は自律度の判定基準の正本、C07 は host 適合契約の正本、C03・C04・C05・C09 は配布プラグイン一般の設計規律である本書が受け持つ。
宣言の正本は各プラグインの既存の面である。README と skill の説明、skill 本文の契約項目、front-matter の許可ツール、hook 定義、配布物側の適合宣言と権限台帳が当たる。
語彙の正本は、値域については機械可読な検査、意味については使用箇所である。散文の定義本文を複数の配布物へ配ることはしない。配る必要が将来生じた場合は、複製と逐語一致検査ではなく、正本1つからの生成と再生成一致の検査を採る。

**何を個別設計へ残すか**。8件の採用は、原則が要求する判断を共通化するものであって、実現方法まで共通化しない。
次の8つは、いずれも各プラグインの設計が決める。
配布元固有データを既定値へ退避する機構、何が配布価値の工程かの線引き、順序そのものが意味を持つ経路の扱い、同じ資産群が2分類にまたがる場合の扱いの4つ。
構成要素ごとの宣言面と格納先の既定値の与え方、配布物側へ固定する下限の具体、host に機構がない能力の縮退の書き方、複製を許す例外の判定の4つ。
`個別設計へ委譲` が0件であることと、固有設計へ残る部分が原則ごとに在ることは矛盾しない。前者は原則そのものの帰属、後者は原則の実現方法の帰属である。

#### 語彙の置き方の再判定

B5 の反映後、「利用者が到達できないと困る語彙はどれか」を実物へ当て直した。
その結果、当初「2件以上のプラグインが同じ語を使う場合は現行の機構で解けない」とした判定を撤回する。

判定を分けたのは、利用者が値域の全体を要るか、使う値だけでよいかである。

- `L0`〜`L3` は `growth` が L2 と L3 の2値しか使わず、両方とも使用箇所に語釈が付いている。梯子の全体は利用者に要らない。
- 適合水準の4値は値域の全体が要るが、散文の定義は要らない。X14 が値域を `case` で固定する。`degraded` と `surface-specific` には `residualRisk` を必須にし、ラベルが結果を左右する場面でだけ自己記述を強制する。
- 成果物の4分類は未導入であり、導入時に同じ形を採れる。

したがって3件とも散文の定義本文の複製を要さない。
当初の判定は、語彙の到達性を「定義本文が読めること」と等値に置いたために生じた過大評価である。

散文の定義本文を配る必要が将来生じた場合の解も、この機会に固定した。
複製と逐語一致検査ではなく、正本1つからの生成と再生成一致の検査を採る。
複製はドリフトを起きてから検出することになり、逐語一致にすると文脈に合わせた言い換えで赤になり、言い換えを許すと検査が空振りする。
生成はこの二律背反を作らない。`gen-adr-index.sh` が同型の先例であり、N17 が条文を持つ。
