# サブエージェント実行パラメータ規約

サブエージェントの `model` と `effort` をどこに置き、どのような意図で値を選ぶかを判断するための単一の出典。本ファイルがこの規約の実体であり、統制点・選定基準をここ以外で独自に再定義しない。

## 統制点

実行パラメータは `agents/{name}.md` の front-matter に置く。SKILL.md の front-matter には置かない。

スキル側に置かない理由は起動経路によって異なる。対話経路では `model` が実効値を動かさず、統制として成立しない（同経路の `effort` は未確認）。ヘッドレス（`-p`）経路では `effort` が最初のターンにしか効かない一方、`model` は効いた上で持続し、スキルを1度起動するとセッションのモデルが書き換わったまま残る（別のスキルを起動するとその宣言値へ上書きされ、セッションは跨がず `settings.json` も書き換えない）。効かないことと、意図しない範囲まで効き続けることは、いずれも統制点をスキル側へ置かない理由になる。経路差は 2026-08-06 時点、`effort` のターン限定は 2026-08-05 時点の実測に基づく。

またサブエージェント側を明示している以上、スキル側の指定はサブエージェントの実行には届かない（スキル側の指定は最後尾の「親セッション」の位置に入るにとどまり、定義が値を明示している限り参照されない）。この到達可否は `model` と `effort` で共通である。統制点を2箇所に分散させれば、どちらが効いているかの追跡が難しくなる。

なお仮にスキル側へ置くと、指定したモデルが利用者の環境で使えない場合にフォールバックが起きず、スキル本体が実行されない（2026-08-06 時点、存在しないモデル ID で確認。エラー文言はアクセス権の不足と区別されない）。統制が効かないだけでなく、スキルそのものが動かなくなる。

## 値を省略しない

配布物であり、利用者の親セッションがどのモデル・どの effort で動いているかは不定である。`effort` を省略すると、各サブエージェントの思考深度は利用者側の設定に従属する。検証を担うサブエージェントが低い effort で見落としを出した場合、それは利用者の設定ミスではなくプラグインの欠陥として現れる。

## 要求水準の選定

役割が要求する水準を決める。どの手段でその水準を実現するかは「水準を実現する手段」節が扱い、本節は手段に先立って「何を要求するか」だけを決める。

値は次のいずれかの意図で選ぶ。この2分類は要求する水準の宣言であり、どの手段で実現するかには依存しない。

| 意図 | 選び方 | 適用する役割 |
|---|---|---|
| 必要最小水準 | その役割が成立するために必要な下限として選ぶ | 生成・検証など、品質が成果を左右する役割 |
| 許容最大水準 | その役割に対して許容する上限として選ぶ | 定型性が高く、処理量が出る役割 |

**front-matter による固定を選んだ場合**、front-matter が表現できるのは固定値のみであり、下限や上限を表す機構は存在しない。固定値である以上、それと異なる設定で動かしている利用者に対しては引き上げと引き下げの双方が生じる。これは許容する。水準を呼び出しごとに与える役割ではこの帰結は生じないが、代わりに水準を与える側の統制が要る（「水準を実現する手段」節）。なお選択規則 (iii) の三択のうち「水準別の運搬体を複数枚置く」を採った役割は、各運搬体が front-matter による固定であるため、前段の主語には当たらず、本段落の帰結が固定側と同じに生じる。

**値がモデル既定に対して上か下かを確認する。** `effort` のモデル既定は `high` であり、利用者は `settings.json` の `effortLevel` に `xhigh` まで永続できる（`max` のみセッション限定）。したがって比較の基準はモデル既定の `high` か利用者が永続させた値であり、環境変数を伴わない構成が普通である。モデル既定を下回る値を「必要最小水準」として選ぶと、既定構成の利用者に対しては下限ではなく上限として働く。

`model` と `effort` は別々の軸であり、一方が下限として、他方が上限として作用することもある。ラベルはその役割にとっての意図を表すものであり、すべての利用者構成に対して一様に下限や上限として働くことを意味しない。

同じ処理でも用途が違えば必要水準は違う。件数の多寡ではなく、その出力が何の判断に使われるかで分ける。判断の根拠になる出力は深度が要り、仕分けや一次スクリーニングは要点を押さえられればよい。

**`effort` を上げれば `model` の差を埋められるとは限らない。** 役割に必要なのが分析の深さである場合、`model` が支配的な要因になる。値を下げる方向で検討するときは、`model` を落として `effort` で補おうとする前に、その役割が求めているのが処理量なのか分析の深さなのかを見極める。

### 収束と発散

水準を決める軸は、その役割が担う作業が収束的か発散的かである。仕様が確定していて答えがほぼ一意に定まるなら低く選ぶ。仮説の生成と棄却を繰り返して初めて答えに至るなら高く選ぶ。

**「調査」というラベルで水準を決めない。** 同じラベルの下に、性質の異なる2つの型が混在する。答えの所在が既知か未知かで分ける。

| 型 | 見分け方 | 収束・発散 |
|---|---|---|
| 事実照合型 | 答えの所在が既知であり、照合すれば一意に定まる（掃き出し検索・実在確認・設定値の読み取り） | 収束的 |
| 探索型 | 仮説の生成と棄却を要する（原因不明の挙動の追跡・広域探索・選択肢の洗い出し） | 発散的 |

原因不明の挙動を追う作業はラベル上「調査」に見えるが、実際には最も発散的である。これを事実照合型と同じ水準に置くと、浅いまま結論を出す型の失敗をする。

### 下げてよい条件と検証契約

検証可能性は選定の軸として立てない。下げてよい条件として扱う。その役割の出力が型・テスト・lint などの機械検証で赤緑を判定できるほど、水準は下げられる。

下げる判断は単独で決めない。下げた分を誰がどう再検証するかを対で決める。再検証の担い手と手段が決まらないなら、下げない。

例外がある。機械検証が掛かっていても、誤りの巻き戻しコストが非対称に高い作業——実行によって外部の状態が変わり、元へ戻す経路が同じコストでは用意できないもの——は下げない。

### 値域の最上位に手を伸ばしてよい場面

値域の最上位は常用しない。次の場面に限って手を伸ばす。

- 再現条件が定まらない不具合を追うとき
- 並行性に起因する問題を扱うとき
- 大規模な移行を設計するとき
- 安全性に関わる変更を扱うとき
- 下位の水準で複数回失敗した問題を扱うとき

**この列挙が限定しているのは「値域の最上位に手を伸ばしてよい場面」であり、「どの役割に許容最大水準のラベルを付けてよいか」ではない。** ラベルの付与基準は本節冒頭の2分類が持つ。両者を混ぜない。

## 水準を実現する手段

本規約の主語は役割が要求する水準であり、front-matter はその水準を実現する手段の一つである。唯一の手段ではない。

ただし**本リポジトリが配布するサブエージェント定義では、front-matter による固定を既定とする**。以下に挙げる他の手段は、同一の内容を場合によって異なる水準で動かす必要が生じたときの選択肢であって、既定を置き換えるものではない。

### 手段の写像

| 経路 | プロセス | `model` の指定 | `effort` の指定 |
|---|---|---|---|
| Claude: カスタム定義の front-matter | 同一プロセス | 固定 | 固定（役割単位で固定できる唯一の経路） |
| Claude: Agent tool の引数 | 同一プロセス | 呼び出しごと | 指定不可 |
| Claude: Workflow の `agent()` | 同一プロセス | 呼び出しごと | 呼び出しごと（利用者の明示 opt-in が要る） |
| Claude: 子プロセス `claude -p` | 別プロセス | `--model` | `--effort` |
| Codex: `config.toml` | 別プロセス | 既定を固定 | 既定を固定（`model_reasoning_effort`） |
| Codex: CLI 引数 | 別プロセス | `-m` / `--model` | 専用フラグ無し。`-c model_reasoning_effort=…` で呼び出しごと |
| Codex: profile `-p` | 別プロセス | レイヤとして指定 | レイヤとして指定 |

本表が並べるのは、本規約の読者が選べる手段である。読者が選ぶのではなく利用者がセッションへ上から被せる経路の扱いは「統制が及ぶ範囲」節が持つ。

### 選択規則

- **(i)** 水準が役割に固有で不変なら、サブエージェント定義で固定する。
- **(ii)** 同一の内容を場合によって異なる水準で動かすなら、内容をプロンプトファイルへ置き、水準は呼び出し側で与える。プロンプトファイルの形式と置き場所は本規約で定めない。
- **(iii)** `effort` を呼び出しごとに動かす必要が生じた時点で、既定の同一プロセス内経路（Agent tool）は使えない。Workflow 経路を採る・水準別の運搬体を複数枚置く・子プロセスを起こす、の三択になる。この分岐が選択規則の中心である。
  三択は動的の度合いが一様ではない。「水準別の運搬体を複数枚置く」は各運搬体が front-matter による固定であり、水準の実現手段としては固定側に属する。動的なのはどの運搬体を呼ぶかの選択であって、水準そのものの与え方ではない。残る2つ（Workflow 経路・子プロセス）が、水準を呼び出しごとに与える形にあたる。
- **(iv)** Codex では逆に、役割ごとの固定に profile の新設が要る。固定と動的のどちらが安いかは基盤で入れ替わるため、片方の基盤の都合だけで規則を書かない。

### 指定が実効したことの確認

設定キーが受理されたことは、その指定が実効した証拠にならない。未知の設定キーを渡してもエラーにならない経路が実在する。実効は起動ごとの記録で確かめる（記録の所在は「実効値の確認方法」節が持つ）。

### 水準を呼び出しごとに与える役割の統制点

既定は固定であり、統制点は定義の側にある。**統制点が定義から呼び出し側へ移るのは、水準を呼び出しごとに与える形——選択規則 (ii)、および (iii) のうち Workflow 経路と子プロセス——を採った役割に限られる。** この場合は、どの形を採るかを定義の側で明示したうえで、水準を与える側を統制点とする。明示のないまま呼び出し側が水準を与える形は、固定を前提とした統制を崩す逸脱である。

選択規則 (iii) のうち「水準別の運搬体を複数枚置く」を採った役割はここに含まれない。各運搬体は front-matter による固定であり、統制点は定義の側のまま動かない。動くのはどの運搬体を呼ぶかの選択であって、水準を与える場所ではない。

## 水準を誤ったときの是正

要求水準の選定は誤りうる。誤りは失敗の型として現れるため、型から動かす軸を診断する。

| 観察される失敗 | 動かす軸 |
|---|---|
| 深く考えても結論が誤る。トレードオフの筋が悪い | `model` を上げる |
| 調査が浅い。見ていない条件がある | `effort` を上げる |
| 結論は合っているが、遅く冗長である | `effort` を下げる |

### 昇格のトリガ

- 同一の問題に複数回失敗したとき
- 計画の前提が崩れたとき
- 低い水準が粘ること自体を、分類を一段上げる合図として使う。粘りは「もう少しで解ける」の証拠ではなく、水準の選定を誤った証拠として読む

### 降格のトリガ

- 出力が要件を満たしており、冗長さを削る側に手間が掛かっているとき
- 作業が探索型から事実照合型へ移り、答えの所在が既知になったとき
- 出力に機械検証が掛かる形へ変わり、再検証の担い手と手段が決まったとき（「下げてよい条件と検証契約」の条件を満たしたとき）
- より低い水準でも出力が要件を満たすことが確かめられたとき。一時的な事情を待たず、平常時の水準として反映する

### 生成と検証の分業

上位の水準で計画と検証を行い、下位の水準で実行する。実行が計画から逸脱したら、下位で取り繕わずに上位へ戻して計画を作り直し、新しい計画を下位で再実行する。生成と検証を別の担い手へ分ける構えを、基盤を跨がずに基盤内の水準の交差として適用したものである。

### 是正の実施手段

**是正をどう実施するかは「水準を実現する手段」節の写像に従う。** 既定の同一プロセス内経路では `effort` を呼び出しごとに動かせないため、是正が定義の書き換えになるのか経路の切り替えになるのかは、当該役割が選んでいる手段によって決まる。手段を確かめずに上げる・下げるだけを決めても実施できない。

## 残量が枯渇したとき

**本規約は、残量の枯渇を理由に水準を下げる規定を持たない。** 水準は「要求水準の選定」節が定める平常時の判断で決め、枯渇を条件とした一時的な引き下げの経路を別に設けない。

理由は2つある。第一に、残量の枯渇を規約の側で検知する手段が無い。検知できない条件を発動条件に置いた規定は、書いても発動を判定できない。第二に、下げた水準で成果が要件を満たすのなら、それは枯渇時に限って許される譲歩ではなく、選定そのものが過大であったことを意味する。その場合に採るべきは「水準を誤ったときの是正」節の降格であり、枯渇の有無に関わらず平常時から反映する。逆に成果が要件を満たさないのなら、枯渇を理由にしても下げてはならない。

残量そのものへの応答（別の実行基盤へ移す、窓の回復を待って別作業を先へ回す）は水準の選定ではなく基盤の選択であり、それを扱う層が持つ。本規約はその層の所在を指さない（配布物から配布元の個人資産を指せないため）。

## 運搬体と内容の分離

サブエージェント定義は、水準と `tools` を運ぶ薄い殻——運搬体——として扱う。役割の内容（何を調べ、何を判断し、何を返すか）は運搬体に固有ではなく、プロンプトファイルとして分離できる。選択規則 (ii) の「内容をプロンプトファイルへ置き、水準は呼び出し側で与える」と (iii) の「水準別の運搬体を複数枚置く」は、いずれもこの分離を前提とする。

**定義数は役割の名前ではなく作業の性質で切る。** 名前ごとに1枚ずつ立てると、内容が違うだけで水準と `tools` が同じ運搬体が並ぶ。切る単位は水準と `tools` の組み合わせである。

**枚数の目安は、現に要る水準と `tools` の組み合わせの数である。** 役割の名前の数ではない。この目安は新しい運搬体を足す前の確認として使う。新設しようとしたら、まず既存の運搬体で必要な水準と `tools` が満たせるかを確認する。満たせるなら内容をプロンプトファイルとして分け、既存の運搬体へ載せる。満たせない組み合わせが要るときにだけ新設する。

**この目安は既存定義の統廃合を要求しない。** 現に配布されている定義の枚数に対する上限としては働かない。統廃合の要否は本規約とは別に判断する。

プロンプトファイルの形式と置き場所は本規約で定めない。

Codex 側で役割ごとに水準を固定する器は profile であり、その整備は個人環境の責務である（profile の新設は本規約の射程外）。

## 実効値の確認方法

指定した値が実際に効いているかは、セッション記録から検証できる。自己申告ではなく記録を根拠にする。

| 取得対象 | 参照先 |
|---|---|
| 実効 `model` / `effort` | `~/.claude/projects/{project}/{session-id}/subagents/agent-*.jsonl` の各アシスタントエントリの `.message.model` と `.effort` |
| 起動されたエージェント種別 | 同ディレクトリの `agent-*.meta.json` の `.agentType` |

親セッションの設定を変えて挙動を比較する場合は、対話セッションの切り替えではなく `claude -p`（ヘッドレス）で条件ごとに独立したセッションを作る。`--model` / `--effort` / `--plugin-dir` はいずれもヘッドレスで有効である。

ただしヘッドレスで得た観測を、そのまま対話経路の挙動として記述しない。スキル front-matter の `model` のように、経路によって実効値を動かすかどうかが変わる項目が実在する。運用経路での事実として書くなら、その経路で確認する。

## 実装上の制約

本節が扱うのは**同一プロセス内の Agent tool 経路**である。他の経路の指定可否は「水準を実現する手段」節の写像が持つ。

この経路で `effort` を指定できるのは front-matter を持つ登録済みのサブエージェントに限られる。Agent tool の引数に `effort` は存在しない（引数は `description` / `isolation` / `model` / `prompt` / `run_in_background` / `subagent_type`）。

したがってスキルから `subagent_type` を指定せずに Agent tool を呼ぶ形では `effort` を制御できない。**`effort` を制御したい役割には専用のサブエージェント定義を設ける。** これが既定の処方であり、選択規則 (i)（水準が役割に固有で不変なら定義で固定する）に当たる。

ただし同一の内容を場合によって異なる水準で動かす必要がある役割では、単数の定義に固定する形では足りない。その場合は選択規則 (iii) の三択（Workflow 経路を採る・水準別の運搬体を複数枚置く・子プロセスを起こす）へ分岐する。専用定義の新設が唯一解になるのは、水準が役割に固有で不変な場合である。

`model` については逆に、Agent tool の `model` 引数が front-matter を上書きする（解決順は環境変数 → `model` 引数 → front-matter → 親セッション）。**front-matter による固定を選んだ役割については**、本規約の統制は呼び出し側で `model` 引数を指定しないことを前提に成立する。当該役割を起動するスキル本文には「モデルと effort は定義の frontmatter に従い、呼び出し側では指定しない」と明記する。水準を呼び出しごとに与える役割の統制点は「水準を実現する手段」節が定める。

## 統制が及ぶ範囲

front-matter の値が効くのは、そのサブエージェントが `subagent_type` 指定で起動された場合に限られる。

本プラグインのスキルが `subagent_type` で起動するのは `plan` / `plan-reviewer` / `issue-refiner` / `issue-refiner-batch` である。`code-reviewer` / `test-designer` / `test-spec-validator` / `refactorer` は定義を持つが、`implementation` からは深刻度基準などの準拠先として参照されるだけで起動されない。実装とレビューは superpowers 側へ委譲されており、`requesting-code-review` は `general-purpose` サブエージェントにテンプレートを流し込む形を採る。

したがってこれら 4 本の値は、利用者が `@agent-dev-workflow:...` で直接起動したときに効く。委譲先を含めた統制は本規約の対象外であり、必要になった時点で別途扱う。

- 本規約の統制を貫通する経路が1つある。利用者がセッションへ環境変数で被せる経路であり、解決順の最上位に位置する。解決順で front-matter の上位にはもう1つ `model` 引数があるが、そちらは本規約が扱う経路であり（「実装上の制約」節）、統制を貫通するのは環境変数の側だけである。
- この経路は役割単位では効かず、全サブエージェントに一律に掛かる。
- 規約の読者が選ぶ手段ではなく、利用者がセッションへ上から被せるものである。したがって水準を実現する手段ではなく、統制の射程の外側にある事実として扱う。「水準を実現する手段」節の写像表に載せないのはこのためである。

## 新規サブエージェントを追加するとき

1. `model` と `effort` を front-matter に明示する。省略しない
2. 値の意図（必要最小水準か許容最大水準か）を決め、`README.md` の表に追記する
3. `tools` を必要最小限に絞る

手順1 は front-matter による固定を既定とする本リポジトリの手順である。同一の内容を場合によって異なる水準で動かす必要がある役割については、「水準を実現する手段」節の選択規則へ分岐する。

## 現行の値

front-matter による固定を選んだ役割については、各 `agents/{name}.md` の front-matter が権威である。一覧は [README](../../plugins/dev-workflow/README.md) を参照。本ファイルには値を転記しない。水準を呼び出しごとに与える形（選択規則 (ii)、および (iii) のうち Workflow 経路と子プロセス）を採った役割については、水準を与える側が権威であり、front-matter は権威にならない（「水準を実現する手段」節）。(iii) のうち水準別の運搬体を複数枚置く形では、固定側と同じく各運搬体の front-matter が権威である。現行の全定義は固定側にある。
