# model × effort 費用対効果ガイド

ソフトウェア開発の各ロールが、自分のタスクへどの model × effort を最初に使い、失敗したらどう再試行するかを選ぶための参照文書。第三者ベンチマークの実測を根拠に置く。射程は Claude / OpenAI / DeepSeek の 3 ベンダーである。

観測時点は 2026-09-13 で、本文の実測値はすべてこの時点の取得である。個人運用の設定集ではなく、他者へ「こういう前提でスキルや運用を設計できる」と伝えるための文書として書いている。

## 位置づけ

### 既存 2 文書との役割分担

`docs/references/subagent-execution-parameters.md` は、サブエージェントの `model` と `effort` をどこに置き、どの意図で値を選ぶかを定める単一の出典である。同文書が持つのは、役割が何を要求するかという選定基準と、その統制点である。本ガイドはその選定基準を再定義しない。本ガイドが持つのは、第三者実測の上でどの組み合わせが安く済むかである。

`docs/references/model-characteristics.md` は、Claude のモデル特性とモデル振り分け指針を定める文書である。同文書が持つのは、公式情報に由来するラインナップ・価格・fast mode である。本ガイドはベンダー公式の特性表を持たない。

本ガイドの主表は、人間または上位のオーケストレータが段を起こす前提で書いている。規約が既定とする front-matter 固定のサブエージェント定義では、1 枚の定義の中で `effort` を段ごとに動かせない。梯子を単一の定義へ埋め込めないことは、本ガイドを読むときの制約である。

**上の 2 つの前提のうち前者——人間または上位のオーケストレータが段を起こす形——では、4 規則の全てが同じ強さで立つわけではない。** 規則①（段を増やすと残失敗率が下がる）は人手が段を起こす形では主張しない。期待完遂コストの式にトークン代しか入っていないためである。規則②③④の扱いも含め、判定者が人間に替わったときに何が残るかは「検証可能性」節が持つ。

### 別文書にした理由と、ADR を起こさない判断

理由は 3 点である。第一に、根拠が観測時点に紐づく第三者実測であり、鮮度の性質が既存 2 文書と違う。実測の更新のたびに規範や公式情報の文書まで書き換える形になる。第二に、射程が銘柄 × effort の組み合わせを 3 ベンダーで横断する。既存 2 文書は一方が Claude のモデル特性、他方がサブエージェントの実行パラメータであり、この射程はどちらにも収まらない。第三に、本ガイドの主表の根拠は単一ベンチマークの per-task 実測に閉じており、規範として置ける強さではない。以上から新しい参照文書として分けた。この 3 点は `subagent-execution-parameters.md` 側の射程段落と同じ内容である。

ADR は起こしていない。粒度判定は 4 点で ADR 化を推奨する側だったが、起票時期の規定——まず PR 説明へ書き、同じ判断が再び出た時点で昇格する——に従って見送った。見送る以上、採用理由と既知の限界は本節に併記して自己完結させる。

本ガイドは `docs/references/document-permanence.md`（`docs/` 配下へ何を残すかを定める規約。恒久文書に追随義務を課し、過去記録を残さないと定める）の下で**恒久文書**として置いている。過去記録ではない。以下の区分で読む。

## 主表: 交差検証を通った 4 規則

梯子を回すには前段の合否が付くことが要る。何をもって合否とするかは「検証可能性」節が扱う。

### 梯子の形と期待完遂コスト

梯子とは「初回設定（初段）で 1 回試す → 落ちたものだけを別の設定（受け皿）へ渡す → それでも落ちたら人手へ渡す」形を指す。受け皿を上位設定に限定しないのは、実測の前線には受け皿のほうが安い組も乗るためである（「前線の形」節）。

期待完遂コストは `E = c_A + (1 − p_A)·c_B` で測る。`c_A` は初段の 1 回あたり平均コスト、`p_A` は初段の成功率、`c_B` は受け皿の 1 回あたり平均コストである。残失敗率は `(1 − p_A)(1 − q)` で、`q` は初段が落としたタスクを受け皿が拾う割合（補完率）である。

**この式の中で、コストと成功率の試行単位が揃っていない。** コストは 1 回あたりの平均で、成功率は 4 run の多数決である。実害の量は次の例で読める。`sol/medium → opus-5/high` の残失敗率は、多数決で測ると 0.195、単発試行で測ると 0.151 で、多数決の側が悲観に出る。後者はタスクごとに両段の試行失敗率の積を取り 113 タスクで平均した値であり、2 段の試行が独立という仮定の下での推定である（同じ仮定を「同一設定の再試行は独立ではない」の段落が否定している）。定義を替えれば値は動く。1 回でも通ったかで測ると 0.044、pass@1 の積で出すと 0.106 である。安い config を初段へ置くほど多数決との差は開く。

本節の実測は次の条件に閉じる。DeepSWE v1.1（Datacurve）の per-task 実測、harness は mini-swe-agent 固定、113 タスク、7 モデル × 5 effort = 35 config。タスク単位の合否は 4 run の多数決（同点は失敗側）で、コストは 1 回あたり平均 USD である。別定義の値を引くときは、その都度定義を併記する。

7 モデルの内訳は次のとおりである。本文で `astra` / `sol` / `terra` / `luna` と略記するのは掲載 slug `gpt-6-astra` / `gpt-5-6-sol` / `gpt-5-6-terra` / `gpt-5-6-luna` であり、生データの provider 欄はいずれも `openai` である。Claude 側の 3 銘柄は `claude-opus-5` / `claude-sonnet-5` / `claude-fable-5`（現行の Fable 5.1 ではなく旧版の Fable 5）である。本文が「初段は全て OpenAI 系」と書くときのベンダー帰属はこの欄に拠る。

多数決には不完全なセルがある。3,955 セル（35 config × 113 タスク）のうち 113 セル（2.9%）は 4 run に満たず（3 run 103・2 run 6・1 run 4）、そこでは 2/3 や 1/1 が多数決成功に当たる。「4 run 中 3 以上」を厳格適用すると層化の値が動く（難度レジーム節「層の定義」）。

### 規則① 段を増やすと残失敗率が下がる

1 段は 35 点、2 段は全順序対 1,190 点（残失敗率だけを見るなら組み合わせ 595 通り）を総当たりした。3 段以降は別の母集団であり、段の集合として 3 段 6,545 通り・4 段 52,360 通り・5 段 324,632 通りを総当たりしている。到達できる最小残失敗率は 1 段 25.7%、2 段 12.4%、3 段 8.9%、4 段 6.2%、5 段 3.5% である。113 タスクを train 56 / test 57 へ分割した交差検証でも、この向きは保たれた。

**ただしこの向きはデータに依らず真である。** k 段の残失敗集合は「k 個の config が解くタスク集合の和集合の補集合」であり、段を足せば和集合は縮まない。単調非増加であることは定義から従い、交差検証で向きが保たれることも自動的に成立する。反証可能なのは減り方の大きさだけであるため、規則①を反証可能な主張として読んではならない。

### 規則② コストを目的関数に含めると、同一モデルの effort だけを上げる組は前線にほぼ現れない

全 1,225 点のパレート前線 24 点のうち、同一モデルの effort を上げる組は 2 点しかない（`terra/low → terra/high`、`terra/medium → terra/high`）。しかもこの 2 点は残失敗率 0.522 と 0.504 で、どちらも半分以上を落とす帯にある。実用になる帯の前線に、この形は 1 点も乗らない。

同一モデルの組そのものが現れないわけではない。前線 24 点のうち同一モデルの組は 3 点あり、3 点目は effort を下げる `luna/high → luna/medium` である。本規則が言えるのは方向を限定した場合に限る。

交差検証でも同じ向きが出るが、**強さは選び方に依存する**。残失敗率の目標を与えて最安の梯子を選ばせると、同一モデルの effort を上げる段を含む梯子は 30 シード中 0〜2 本である。一方、段数を固定して残失敗率だけを最小化させると、同一モデルの effort を上げる段が現れ始める。**ただしその頻度は探索プロトコルに依存し、特定の分数を結論として置けない。** ビーム幅 200 のビームサーチでは 4 段で 6/30 だが、4 段を全探索して最小残失敗率のうち期待完遂コスト最小を選ぶと 5/30 になる。理由は 2 つあり、どちらもデータの性質ではない。ビームが真の最適を取り逃していること（train 最小残失敗率がビーム 0.0381 に対し全探索 0.0345）と、同着が大量にあること（4 段で train 最小残失敗率に並ぶ config 集合は 30 シード合計 1,229 個、うち同一モデルのペアを含むのが 318 個＝25.9%）である。読めるのは「コストを目的関数から外すと同一モデルの effort 上げが現れ始める」までであり、「ほぼ現れない」と言えるのはコストを目的関数に含めた場合に限る。

per-task の補完率でも別モデルへの移行が優る。全順序対 1,190 のうち `cost_A < cost_B` を満たすのは 595 で、内訳は別モデルへ移る組 525 と同一モデルの組 70 である（**2 つの群は重ならない**）。A が落としたタスクを B が拾う割合は、別モデル 525 ペアで 0.455、同一モデル 70 のうち effort を 1 段上げる 28 ペアで 0.254 である（1.79 倍）。`cost_A < cost_B` の絞りは梯子の形（安い初段から高い受け皿へ）に合わせたものであり、外して別モデルの全順序対 1,050 で測ると 0.371 へ下がる。コスト比 1.5〜4.0 の組へ揃えると 0.422 対 0.264 で、向きは変わらない。

この 1.79 倍は受け皿の絶対的な強さを揃えていない値である。初段と受け皿の多数決成功率をいずれも ±0.02 で揃えた 23 組で照合すると 0.416 対 0.264（1.58 倍）となり、向きは保たれるが差は縮む。per-task 結果が公開されている第三者データは DeepSWE v1.1 のみであるため、この統制を別題材で追試する手段は無い（欠落 G9）。

独立な裏づけが Artificial Analysis 側にある。τ²-bench Banking では `opus-5` が high 0.4474 > xhigh 0.4330 > max 0.4206、`astra` が xhigh 0.4309 > max 0.4144 で、effort を上げ切ると成功率自体が下がる。これらは Artificial Analysis の掲載値（1 設定 1 スコア）であり、4 run 多数決とは別定義である。加えて同ベンチにはコスト列が無く期待完遂コストを計算できないため、この裏づけで格付けは動かさない。

規約 `subagent-execution-parameters.md` は是正手段として「調査が浅い → `effort` を上げる」を持つ。あれは対話中の是正手順であり、本規則が扱うのは初段と受け皿の選び方である。両者の射程は重ならない。

### 規則③ 最適化した config 列は再現しない

113 タスクを train 56 / test 57 へ 30 通りに分割し、train で選んだ梯子を test で評価した。残失敗率は全帯で悪化し、目標 0.30 / 0.20 / 0.15 / 0.10 の各帯で train 0.301 / 0.199 / 0.145 / 0.105 に対し test 0.366 / 0.255 / 0.216 / 0.191 である（+0.056〜+0.087）。コストの差は段数に単調増加し、4 段では平均 +$1.34・最悪 +$5.52 だった。選ばれる梯子はほぼ毎回別解になり、30 シードでの種類数は帯ごとに 20〜29 である。

**次の段落は規則③の系ではなく、別の軸である。** 規則③が言うのは同一ベンチ内での train → test の過適合であり、次に挙げるのはベンチが変われば順位が変わること（外的妥当性）である。どちらも「手元の実績で選んだ config 列を推奨にしない」根拠になるが、由来は別である。

別のベンチマークでも結論が反転する。Artificial Analysis の Terminal-Bench v4.0 では、`astra` が low 0.4192 → xhigh 0.5960、`opus-5` が low 0.2626 → xhigh 0.4646 である。一方 `sol` は low 0.0101 → xhigh 0.2475、`terra` は low 0.0152 → xhigh 0.1010 にとどまる。DeepSWE で完遂コスト前線に多数乗る `sol` が、Terminal-Bench v4.0 では Claude 系へ大きく劣後する。これらは Artificial Analysis の掲載値（1 設定 1 スコア）であり、4 run 多数決とは別定義である。

### 規則④ 手元の実績でコストを詰めた最適化は、コストで勝ち信頼性で負ける

比較対象に置いた固定梯子（`sol/medium → opus-5/high`）は、**性能の実測を一切見ずに組んだものである**。「安い中位のモデルから始め、落ちたら別ベンダーの上位モデルへ渡す」という作法だけで決め、初段の `sol` は OpenAI 系 4 モデルから機械的に選んだ。規則④が意味を持つのはこの盲目性が担保されているからで、良い組を後から選んで比べたのではない。

30 シードの交差検証で、この固定梯子の test 残失敗率は平均 0.202・期待完遂コストは $4.65 である。train で残失敗率 0.20 を目標に最適化した梯子は test 残失敗率 0.255・$2.69 だった。シード単位では、最適化が信頼性で勝ったのは 30 回中 6 回、コストで勝ったのは 30 回すべてである。

**ただしこの向きは、最適化が何を目的関数に置いたかに依存する。** 上の最適化は「目標の残失敗率を満たす最安の梯子」を選んでいる。コストを目的関数から外し、段数を固定して残失敗率だけを最小化させると向きは入れ替わり、最適化が信頼性で勝つのが 30 回中 16 回、コストで勝つのが 3 回になる。読者が持ち帰れるのは「手元の実績でコストを詰めると信頼性を失う」までであり、最適化一般が信頼性で負けるという主張ではない。

### 5 番目の観測: 残失敗率には下限がある

2 段で残失敗率 10% を下回る構成はゼロで、最小は 0.124 である。35 config の和集合でも 113 タスク中 3 件が多数決で解けず、梯子の理論下限は残失敗率 2.65% になる。

これは交差検証の産物ではなく、35 config の和集合から出た別の観測である。規則①〜④と同格には扱わない。

**この下限は「4 run 多数決・同点は失敗」という採点規則の下での下限であり、能力の下限ではない。** 解けないとされた 3 件は、単発試行ではいずれも通っている（139 試行中 9 回、140 試行中 3 回、140 試行中 3 回）。全試行の和集合で 1 度も通らないタスクは 0 件である。

### 前線の形

1,225 点のうちパレート前線に乗るのは 24 点で、初段は 24 点すべてが OpenAI 系である。Claude は受け皿としてのみ乗る。例として `astra/low → opus-5/high`（E $4.23・残失敗率 0.150）を挙げる。この組は `opus-5/xhigh` 単独（$9.07・0.257）も `astra/high` 単独（$5.72・0.274）も支配するため、Claude 系の単独点が前線から消える。これは例であって推奨ではない（規則③）。

**初段が OpenAI 系に揃うことは、母集団の構成に依存する。** 掲載されている Claude 3 銘柄は最安が Sonnet 5（$2 / $10）で、OpenAI 側の `terra`・`luna` はそれより安い帯にある。安い初段が OpenAI 側にしか無い母集団であり、Haiku 4.5 を入れて前線の形が変わるかは確かめられない（欠落 G1）。

ベンダーを跨ぐかどうかは前線の形から決まらない。交差検証の 30 シード × 4 帯＝120 本で見ると、初段が OpenAI 系なのは 118 本だが、梯子のどこかに Claude を含むかどうかは目標水準で動く。残失敗率の目標 0.30 / 0.20 / 0.15 / 0.10 の各帯で、Claude を含む梯子は 30 本中 9 / 13 / 20 / 26 本である。厳しい水準を求めるほどベンダーを跨ぐ側へ寄るが、どの帯でも一方に振り切らない。

### 数値を引くときに崩れやすい前提

**単発 config の完遂コスト前線と、多数決・複数段の梯子の前線は別の量である。** 単発側は pass@1 と `E = 1 回あたりコスト ÷ pass@1`（独立再試行の仮定）で測る。この定義では、単価帯が 1 桁下の `terra` / `luna` を除いた 5 モデル（Claude 3 種と Astra・Sol）の前線は 9 点で、`sol` は low から high まで乗る。2 モデルを除いたのは、入れると前線が安価側で埋まり、上位階級どうしの順序が読めなくなるためである（7 モデル全体では前線は 13 点になり、`sol` は medium と high が残る）。成功を 4 run 多数決へ定義し直すと、同じ 5 モデルで `sol` は low だけが残る。terra / luna を含めて 2 段以上を許すと、`sol` は初段からは消え、受け皿として 1 点だけが残る（`luna/high → sol/low`、E $1.50・残失敗率 0.496）。成功率の定義だけで前線の構成が変わるため、数値には必ず定義を添える。

**effort の効き方は階級で逆転する。** 上位階級（Opus 5 / Astra / Sol / Fable 5）は low でも pass@1 が 45〜67% に届き、low から max へ上げるとコストが 5.7〜7.8 倍になる。完遂コストが最小になるのは low である。下位階級（Terra / Luna）は low が壊滅的で、effort を使えるかどうかが成否を決める。完遂コスト最小は Terra が medium、Luna が high である。

この段落は規則③の射程の中にある。同じ処方が別の難度帯で反転する実例が、規則③に挙げた Terminal-Bench v4.0 にある——DeepSWE で完遂コスト前線に多数乗る `sol` は同ベンチの low で 0.0101 しか取れず、`terra` は medium 0.0101 が low 0.0152 を下回る。DeepSWE で読み取った「上位階級は low、Terra は medium」は、この題材の難度帯に紐づいた観測である。本ガイドの外へ持ち出すときは、階級で効き方が変わるという向きだけを取り、上に挙げた具体の階級名と effort 名を処方として持ち出さない。

**同一設定の再試行は独立ではない。** pass@4 の実測は独立仮定の予測を大きく下回る（`opus-5/high` は実測 87.6%、独立仮定の予測 99.5%）。1〜2 割のタスクは同じ設定では解けない。梯子の段でモデルか階級を替える形になるのはこのためである。

### DeepSeek の扱い

DeepSeek は DeepSWE の 35 config に含まれない。現行リリース（V4 Pro 0813 / V4.1 Flash）は max effort の 1 件しか掲載が無く（effort 別の系列を持つのは旧リリースのみである。欠落 G2）、補完率もパレート前線も計算できない。**主表の規則を DeepSeek へ当てる根拠は無い。**

**以下は推奨ではなく、単価という別の軸での観測である。** トークン単価あたりの性能では突出する。Artificial Analysis の Terminal-Bench v4.0 を max effort の掲載値で揃えると、DeepSeek v4.1 Flash 26.8%・`terra` 35.4%・`opus-5` 49.0% である。**ここでの max は、effort を suffix で指定しない base slug の掲載値であり、effort 付き slug の系列とは連続しない。** 同じ `terra` が effort 付き slug では xhigh 10.1%、base slug では 35.4% である（`sol` は 24.8% 対 39.9%、`sonnet-5` は 7.1% 対 14.1% で、いずれも base 側が大きく上回る）。3 モデルとも base slug で揃えているため比較自体は同一系列の中で閉じるが、この段落の数値を規則③の段落が引く effort 別系列（`terra` low 1.5% → xhigh 10.1% 等）と地続きに読んではならない。トークン単価は blend(3:1) で DeepSeek v4.1 Flash $0.52/Mtok、`terra` $4.50、`opus-5` $10.00 であり、8.7 分の 1・19 分の 1 に当たる。成功率の差より単価の差のほうがはるかに大きい。

ただしこれはトークン単価であって、タスクあたりの完遂コストではない。初段に置いて何割を片付けるか（`p_A`）も、落とした分を誰が拾うか（補完率）も分からない。Terminal-Bench v4.0 は 1 設定 1 スコアの掲載値であり、4 run 多数決とは別定義である。

`reasoning_effort` は `none` / `low` / `high` / `max` の 4 値で、既定は `high` である。`medium` と `xhigh` は `high` へ丸められる。Claude / OpenAI の 5 段階とは段数が違うため、effort 軸を横並びにするときは注記が要る。

## 難度レジーム

DeepSeek は 35 config に入らない。本節の層の話を DeepSeek へ当てられない（欠落 G2）。

### 層の定義

各タスクを「35 config のうち 4 run 多数決で解かれた個数」で層化する。hard は 5 個以下（11 件）、mid は 6〜24 個（71 件）、easy は 25 個以上（31 件）である。この閾値は先に 31 / 71 / 11 という層の大きさを決めてから逆算したもので、その大きさを再現する閾値の組が 1 つしかないことを全探索で確認した。閾値が一意であることは層化の妥当性の証拠ではない。この一意性は 4 run 多数決という採点規則の下での性質でもある。不完全セル（主表節）を切り捨てて「4 run 中 3 以上」を厳格適用すると層は easy 30 / mid 71 / hard 12 へ動き、31 / 71 / 11 を再現する閾値の組は存在しなくなる。

この層は 35 config という母集団に依存した操作的定義である。config 集合を替えれば層も動く。読者のタスクで「解かれた個数」を観測する手段は無い。35 config すべてが解く完全飽和タスクも 0 件である（最大は 33 個）。

**この定義は、評価される config 自身を層の定義へ含む。** ある config が解いたタスクはその分だけ hard から押し出されるため、層の定義から当の config を抜くと結果が動く。`astra` の 5 設定を層の定義から抜いて残り 30 config で hard を定義し直すと（閾値 ≦4、14 件）、`astra` は xhigh 5/14・high 4/14・low 4/14・medium 3/14・max 3/14 と全 effort で非ゼロになる。同じ手続きで `opus-5` を抜くと、`opus-5` は high・medium・xhigh が 5/14 で並ぶ。以下の層別の観測は、この自己包含を含んだ値である。

### 事前に難度は測れない。梯子が測る

per-task の難度が公開されている第三者データは DeepSWE v1.1 のみで、Terminal-Bench はタスク別結果を公開していない（欠落 G8）。着手前に層を当てる手段が無いため、梯子を実行すること自体が難度の判別になる。判別のための追加費用は発生しない。

ただし**初段の失敗集合を見るだけでは難度の判別にならない**。初段が落としたタスクの集合に占める hard の比率は、母集団の基準率 9.7% に対して次のとおりである。`astra/low` 28.9%（3.0 倍）、`sol/medium` 22.0%（2.3 倍）、`luna/xhigh` 15.1%（1.6 倍）、`terra/medium` 13.3%（1.4 倍）。この 4 件のうち最も濃い `astra/low` でも、失敗の 7 割は hard 以外が占める。濃縮が効くのは段を重ねた後で、2 段 `astra/low → opus-5/high` の残失敗では 58.8%（6.0 倍）になる。

**この濃縮率を初段の安さへ帰してはならない。** 35 config 全体での最大は `astra/high` の 35.5%（3.65 倍）であり、`astra/medium`・`astra/max` 34.4%、`sol/max` 33.3%、`opus-5/max` 32.4%、`opus-5/high` 32.3%、`astra/xhigh` 31.3%、`opus-5/xhigh` 31.0% が `astra/low` の 28.9% を上回る。濃縮率が沿うのは価格ではなく config の強さである。さらに列挙した 4 件のうち 3 件（`astra/low`・`sol/medium`・`terra/medium`）は hard 11 件を 1 件も解いていないため分子が 11 に固定され、濃縮率は 113 ÷ 失敗件数に厳密一致する。3.0 / 2.3 / 1.4 という並びは、その config の多数決成功率の言い換えにすぎない。

「初段で通った ⇒ 易しかった」は層の定義の言い換えに近い。新しい情報は、層ごとに梯子の形が違うことの側にある。

### 層ごとに動かす場所が違う

| 層 | 件数（全体比） | 梯子から事後に分かる合図 | 次の一手 |
|---|---|---|---|
| easy | 31 件（27%） | 初段で通った | 初段を上げない。ただし下げ切らない |
| mid | 71 件（63%） | 初段で落ち、受け皿で通った | 受け皿だけを動かす |
| hard | 11 件（9.7%） | 受け皿でも落ちた | 段を積む前に、分割・人手と比べる |

層ごとの config 列と期待完遂コストは載せない。層内で最適化した量は規則③の射程に入り、再現しないためである。

easy 層でも階級の下限はある。`luna/low` は 113 タスク全体で多数決による成功が 0 件であり、完遂コストが定義できない。どれだけ易しい層でも、最安階級の最低 effort は初段として成立しない。

### 残失敗は hard 層へ集中する

全 113 タスクでの 2 段最良（残失敗率 0.124）は 2 通りあり（{`opus-5/high`, `astra/high`} と {`opus-5/high`, `sol/max`}）、残す 14 件の集合は一致しない（共通は 12 件）。層分布はどちらも同じで、14 件のうち 10 件（71%）が hard 層に入る。hard 層は全体の 9.7%（11 件）にすぎない。残失敗率をもう一段下げたいという要求は、段数の問題ではなく hard 相当のタスクをどう扱うかの問題である。

hard 層で 3 段を組んだときの最小残失敗は 4/11 である（1 段後 8 件 → 2 段後 6 件 → 3 段後 4 件）。3/11 には 3 段では到達しない。和集合から算術で出る「3 段目以降で拾える上限 3 件」に対し、3 段目の実効は 2 件である。hard 層 11 件のうち 3 件は 35 config の和集合でも多数決で解けない。この「解けない」が採点規則の産物であることは、主表節の 5 番目の観測が述べる。なお 8 → 6 → 4 は hard 層 11 件に対する 35 config の in-sample 最適化であり、規則③の射程に入る。層別の config 列を載せないのと同じ理由で、ここでも config 名は挙げず段数ごとの到達点だけを引く。

### hard 層では階級とコストの順序が成功率の順序を予測しない

hard 層 11 件を単独で最も多く解いたのは、最安階級の `luna/xhigh` で 3 件である。次が `luna/max`・`opus-5/xhigh`・`sonnet-5/max` の各 2 件である。`astra` は low / medium / high / max の 4 設定すべてが 0 件で、xhigh のみ 1 件である。単独の完遂コスト前線から全 effort で脱落する `sonnet-5` が、上位階級と同じ件数を出している。

ただし hard 層は 11 件しかなく、1 件が 9.1 ポイントに当たる。3 件と 2 件の差は量子化 1 単位であり、順位としては読めない。書けるのは「階級とコストの順序が hard 層の成功率の順序を予測しない」までである。hard と判明したタスクへ最上位階級を買い増す根拠は、この実測からは出てこない。

**ただしこれは本節の層定義（35 config 中 5 個以下）の下での話である。** 読者にとっての hard は「自分の梯子が落とした案件」であり、そちらで操作化すると結果が変わる。固定梯子 `sol/medium → opus-5/high` が残す 22 件を最も多く拾えるのは `sol/max` と `astra/high` の各 9/22 で、次いで `luna/max`・`astra/xhigh` の各 8/22 である。上位階級を買い増す根拠が出ないと言えるのは、前者の操作化に限る。

### 自分の題材がどの層に近いかを当てる材料

同じ config のスコアは、測定場所で大きく動く。`terra/high` は Terminal-Bench v2.1 で 75.7%、DeepSWE v1.1 の 113 タスクで 46.0%、Terminal-Bench v4.0 で 1.5% である。Terminal-Bench 側は Artificial Analysis の掲載値（1 設定 1 スコア）で、DeepSWE 側は 4 run 多数決の 52/113 である。DeepSWE 内の層内訳は easy 24/31・mid 27/71・hard 1/11 である。easy / mid / hard は 113 タスクの分割であるため、内訳の合計が全体と一致すること自体は恒等式であり、層混合比がベンチ間差を説明するという主張の裏づけにはならない。

読者は「自分の題材が Terminal-Bench v2.1 側（易しい定型作業）か v4.0 側（前例のない横断変更）か」で当たりを付けられる。

ただし**層混合比だけでベンチ間差を説明する読み方には反例がある**。`astra` は DeepSWE の hard 層で 0〜1/11 しか解いていないのに、Terminal-Bench v4.0 では射程モデルの最上位である（low 0.4192）。Terminal-Bench 側はタスク別結果が非公開で、層混合比としての検証ができない（欠落 G8）。

### この層化の限界

題材は OSS リポジトリの機能追加と不具合修正で、harness は mini-swe-agent 固定である。別ドメイン・別 harness への外挿を支える第三者データは無い（欠落 G5・G8）。

## 検証可能性（修飾条件）

検証可能性は、どの model × effort を選ぶかの軸ではない。**主表の梯子を回せるかどうかを決める前提条件である。**

この位置付けは規約 `subagent-execution-parameters.md`（サブエージェントの `model` と `effort` の選定規則の単一出典）と同じ向きである。同規約は「検証可能性は選定の軸として立てない。下げてよい条件として扱う」と定める。本ガイドも軸としては立てない。ただし本ガイドが問うのは「水準を下げてよいか」ではなく「梯子を回せるか」であり、別の問いである。

### 2 つの条件

(a) その段の出力に対して合否の判定が下せるか。(b) その判定が、次の段へ進むかどうかを決める時点までに出るか。(a) が付かなければ (b) は問えないため、順は (a) → (b) である。

いずれかが判別できないときは「梯子が組めない」側へ落とす。組める前提で初段を安くすると、検出されない失敗がそのまま成果物へ残るためである。この向きは規約の「再検証の担い手と手段が決まらないなら、下げない」と同一であり、新しい規則ではない。

### 梯子が組める場合

(a)(b) を満たす形——テスト・型・lint・CI で赤緑が付く形——では、規則①〜④と期待完遂コストの式をそのまま使える。根拠層は実測である。**この宣言が掛かるのは、合否の判定者が機械である場合に限る。**

本節は 2 つの軸を分けて扱う。第一は**段を起こす手**が自動か人手かという軸、第二は**合否の判定者**が機械か人間かという軸である。前者は 1 段あたりの費用の中身を変え、後者は合否の定義そのものを変える。

この形には限界が組み込まれている。機械検証が掛かっていても、実行によって外部の状態が変わり、元へ戻す経路が同じコストで用意できない作業では、初段を安い設定にしない。これは規約が既に定める例外であり、本ガイドが新たに置く条件ではない。

まず第一の軸である。**段を起こす手が自動か人手かは、梯子が組めるかを分けない。分けるのは 1 段あたりの費用の中身である。** 人手が次段を起こす形では、合否が機械で付いていても、4 段の梯子は人間が 4 回手を掛けることと同義になる。人間の往復コストは数値化しない。

数値化しない代わりに、規則①の扱いを決めておく。期待完遂コストの式にはトークン代しか入っていない。段を増やす向き（トークン代で安くなる）と往復を減らす向き（人間の手数で安くなる）が逆を向く。したがって**人手が段を起こす形では、規則①の成立を主張しない**。「反転する」とも書かない。どちらが勝つかを決める根拠が無いためである。

ここからは第二の軸である。規則②③④は、いずれも機械採点された合否の上で測られている。判定者が人間に替わると、合否の定義そのものが替わる。したがってこの形での 3 規則は外挿（判定者を差し替えた外挿）であり、隣接する第三者データはゼロである（欠落 G3）。この形には数値を置かない。

### 梯子が組めない場合

(a) が付かないか、(b) に間に合わない形では、段の概念が成立しない。期待完遂コストの式も使えない。独立再試行の形も段階的エスカレーションの形も、失敗を検出できることを前提に置いているためである。

規則の適用は分かれる。規則①②と 5 番目の観測（下限）は段の存在を前提とするため使えない。規則③は「手元の実績で選んだ config 列を推奨にしない」根拠としてそのまま残る。規則④は段が無くても当てはまる。④が述べるのは手元のタスク集合で最適化したことの帰結であり、段の有無に由来しないためである。ただし測定は梯子で行われており、単発の設定選びへの適用は由来が共通であることを根拠とする。

この形では、問題は初段 1 発の成功率を最大化する設定選びへ退化する。**本ガイドはここで単一の推奨を出さない。** 理由は 2 つある。第一に、主表の前線は「安い初段と受け皿」の組を最適化した結果であり、単発最大化の推奨には使えない。第二に、単発で最も成功率が高い設定はタスク難度層で入れ替わる（難度レジーム節: hard 層では階級とコストの順序が成功率の順序を予測しない）。

打てる手として本ガイドが書けるのは、規約の向き——再検証の担い手と手段が決まらないなら下げない——を引くところまでである。その先の選び方（タスクを検証可能な単位へ割る、人手で受ける、着手しない）は本ガイドの射程外であり、根拠が無い。規則の形では書かず、判断の材料として示す。

## 写像表と根拠層

### 根拠層の 3 語（本節が単一出典）

根拠層は、その行のタスクについて**本ガイドが主張を持てる強さ**を表す。モデルの優劣を表さない。語はこの 3 つに固定し、4 つ目の語を作らない。

| 語 | 成立条件 | その層で読者がしてよいこと |
|---|---|---|
| 実測 | 行のタスクに近い題材で、二値の成功率と、同一実行から得られるコストが、effort 別に揃った第三者データがある | 規則と数値をそのまま使う。金額の比較は同一ソース内に限る |
| 外挿 | 根拠が別の条件から持ち込まれている。軸を必ず併記する | 順序と向きだけを使う。金額と閾値を持ち込まない |
| 根拠なし | 射程モデルについて引ける第三者データが無い。データが在っても格付けできない場合（射程外世代のみの掲載・版が不確定・拒否で測定が成立しない）を含む | 本ガイドを初段の根拠に使わない。自分の題材で 1 回測る |

外挿の軸は次の 2 つで、1 語にまとめない。前者には隣接データが在り、後者には 1 件も無いためである。

- **題材を跨いだ外挿**: 近傍ベンチマークに成功率はあるが、コストまたは effort 別系列が無い。費用対効果の形を、機械採点のコード題材から持ち込む
- **判定者を差し替えた外挿**: 機械採点の合否で測った規則を、人間が合否を付ける場へ持ち込む。この軸に隣接する第三者データはゼロである

格付けが 2 語の間で決まらないときは、弱い側（実測より外挿、外挿より根拠なし）へ落とす。強い側へ寄せると、読者が本ガイドの数値をそのまま使い、外れたときに検出が効かないためである。

### 行の決め方

読者が自分のタスクについて答えられるのは、次の 2 問である。この 2 問で行が決まる。

1. 合否が、次の一手を打つ前に付くか
2. 付くなら、その題材に近傍ベンチマークがあるか。あるなら、成功率・コスト・effort 別のどれが揃っているか

第 1 問は検証可能性節の 2 条件と同じ問いを使っており、新しい軸を足していない。答えるものが違う。写像表は「どの根拠が届くか」、検証可能性節は「梯子を回せるか」を答える。

### 表 M1: ロール × タスク写像表

本表は金額と成功率を 1 つも持たない。持つのは近傍ベンチマークの名と、その被覆・欠落の質だけである。

| タスク（該当するロールの例） | 近傍ベンチマーク | 根拠層 |

| **1.** 受け入れ条件が機械検証へ落ちているコード変更とターミナル作業（実装・不具合修正・リファクタ・依存更新・テストコード作成・CLI と環境の操作。開発者、SRE の自動化作業） | DeepSWE v1.1（OSS リポジトリの機能追加と不具合修正。per-task 結果が公開され、成功率・コスト・effort 5 段が同一 harness で揃う）／Terminal-Bench v2.1・v4.0（ターミナル作業。effort 別の成功率はあるが per-task 結果は非公開） | **実測**。補完率まで測れるのは DeepSWE のみで、Terminal-Bench は階級の順序の交差検証に使った |

| **6.** 合否が下流工程でしか付かない判断（技術選定、アーキテクチャ判断、要求の取り違えが実運用で露見する作業。アーキテクト、PM） | 該当なし（探索して不在を確定） | **根拠なし**（G10） |

表の読み方として 3 点を添える。

1. **行を決めるのはタスクの名前ではなく、合否の付き方である。** 同じ「機能を実装する」でも、受け入れ条件がテストへ落ちているなら行 1、何を作るかの妥当性を人間が判定するなら行 3、判定が実運用に出てから付くなら行 6 へ置く。仕様の確定度が下がると行も下がる。仕様が未確定なタスクでは、実装の誤りと仕様の誤りが同じ「失敗」として観測されるためである
2. ロール名は目印であって行の定義ではない。1 人のロールが複数の行のタスクを持つ（開発者は行 1 の実装と行 3 のレビューを双方持つ）
3. 行 4 と行 5 はどちらも根拠なしだが、欠落の理由が違う。行 4 は拒否により測定そのものが成立しない。行 5 は合否が機械検証で付くのに近傍データが無い
