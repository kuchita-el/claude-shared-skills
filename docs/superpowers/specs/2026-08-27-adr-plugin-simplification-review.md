## A. 存続対象が判定の実体を削除対象へ外出ししている（最優先）

spec 節1「存続対象」は次のように書いている。

> `adr-scoping.md`（ADR化要否の判定基準の条文）。… 得られた知見は条文へ反映済みとみなす。

**この前提は現物と一致しない。** `adr-scoping.md` は判定の実体を、削除対象の 2 ファイルへ外出ししたままである。

- `adr-scoping.md:55` — 「各項目が判定する入力の定義は `adr-judgment-contract.md`「実測事実の値域と定義」を参照し、閾値は `adr-scoring-thresholds.json` を参照する」
- `adr-scoping.md:57-62` の判定表は、全セルが「設定ファイルの項目1閾値以上」「契約仕様が定める最小単位の数」という**間接参照**で書かれている。数値の実体は `adr-scoring-thresholds.json` の `{item1_file_count: 3, item2_unit_count: 2, adr_score_boundary: 3}` にしかない
- `adr-scoping.md:64` — 「項目1・2の数え方、項目3の保持先と同居判定は、`adr-judgment-contract.md`「実測事実の値域と定義」に**移設した**」

`adr-judgment-contract.md`（122行）は単一の機械可読契約ではなく、**前半（「実測事実の値域と定義」＝条文の実体）と後半（30フィールドJSON直列化契約＝機械可読部分）の二重構造**である。spec は削除対象の説明を「判定器返却JSONの30フィールド直列化契約」とだけ書いており、前半の存在が射程から落ちている。このまま削除すると、`adr-scoping.md` は指示先を失った空文になる。

**対処**: 閾値の数値を条文へ直書きし、前半の値域定義（項目1・2で数える／数えない対象、項目3の保持先の値域(A)(B)と条件1〜3、項目4の阻止状態の値域）を条文へ吸収したうえで、後半だけを落とす。判定の枠組み（4項目・閾値・合計点）自体は現状維持とする。`ADR-202608011651-01` 決定2 が項目名・スコア境界を保持対象から外しているため、この内製化は同 ADR の反転にあたらない。

（この対処は §0 決定1 として確定済み。）

## C. 受入条件が検証できない／穴が開いている

### C-1. skip 検出の機構が存在しない

> `bash scripts/run-tests.sh` が全緑で、登録テストに0件照合のままskipで緑になるものがない

`run-tests.sh` に skip を数える処理は無い。同スクリプトが行うのは (a) bats 自身の `Executed .* instead of expected` の検出、(b) TAP のプラン行と `grep -c '^ok \|^not ok '` の件数照合の 2 つだけである。bats の skip は `ok N # skip` として出力されるため `^ok ` に一致し、件数照合を通過する。**この受入条件は、現行のコマンドでは充足も違反も観測できない。**

対処は 2 択。skip 行を数える検査を足して観測可能にするか、受入条件を現行 runner が実際に検出する事象（上記 2 ガードの不発火）へ書き直すか。

### C-2. 走査語彙が対象を取りこぼす

> adr-scoping-cases 系の検査器・テスト・fixtures・台帳・判定契約に該当するファイルがリポジトリに存在しない

B-1 のとおり `scripts/migrate-return-schema.sh` はこの語に掛からない。受入条件は「系」という包含語ではなく、削除対象をパスで列挙して照合する形にする。

### C-3. spec の指示が既存規定と正面衝突している

spec は `test-execution.md:199`（旧スクリプト→bats の移行対応表）の更新を求めるが、`scripts/run-tests.sh:78` は次を規定している。

> §7 の移行対応表は移行完了時点の凍結記録であり、追随の対象ではない

`:185` も同様に、過去時点の ADR 化要否判定の採点根拠＝当時の観測である。spec はこの規定を検出しないまま無条件の更新を求めており、そのまま実行すると規定違反になる。**凍結記録・観測記録を据え置く（そのぶん受入条件の参照残存検査から除外集合としてパスで固定する）か、規定を今回の例外として破るかの判断が要る。** 現時点で未決。

### C-4. 受入条件が自己言及している

> 本簡素化の設計判断が ADR 化要否の判定を経て決着している

判定に用いる条文（`adr-scoping.md`）が、まさに本 PR で改訂される対象である。どの版の条文で判定するかが未規定であり、改訂後の条文で判定すれば「自分に都合の良い基準で自分を判定する」形になる。判定に使う版を先に固定する。

### C-5. 「新旧 lint の出力一致」は情報量がない

リスク節:

> 移行中は新旧 lint を同一 corpus に当てて出力一致を確認してから旧実装を落とす

同一 corpus（`docs/adr/`）は commit ゲートを通っている以上、新旧いずれも緑になる。**緑同士の一致は検査内容が同一であることの証拠にならない。** 検査内容の同一性を示すなら、5 レイヤそれぞれの負例（違反を含む corpus）を通して、新旧が同じ違反を同じレイヤで検出することを確かめる必要がある。受入条件「正例/負例テストで示せる」とリスク節の手段が対応していない。

## D. 背景で挙げた保守摩擦の帰属が実測と食い違う

> 行番号固定台帳が bats への1行挿入で commit をブロックする等の保守摩擦もこの系統に由来する。

摩擦の実体は `docs/development/plugin-path-reference-ledger.md`（行番号固定台帳）だが、その構成を数えると全 119 行のうち削除対象の bats を指すのは 31 行で、残りは `CLAUDE.md`(15)・`writing-lint.bats`(13)・`writing-contract.bats`(11) 等の**別系統**である。台帳と据え置き型検査の機構そのものは PR1 の射程外であり、**廃止後も `writing-*.bats` へ 1 行入れれば同じブロックが起きる。**

さらに spec 節4 は「行番号固定・版据え置き型の常設ゲートは持ち込まない」と宣言しているが、これはテスト再設計（PR3）の話であり、既存の行番号固定台帳の存廃には触れていない。**「この系統に由来する」という帰属は成立しない。** 廃止の動機としては A（配布価値の本体でない）と規模比だけで十分であり、摩擦を根拠に加えると、廃止しても摩擦が残ったときに「効かなかった」と評価されることになる。台帳機構の是非は別 Issue として切る。

## E. 工程順序が二度手間を生む

節5 は「PR1 が先行（判定契約が消えた状態でスキルを再設計する）。PR2 と PR3 は相互に独立」とする。しかし A の対処により、PR1 は `adr-scoping.md` へ判定の実体を吸収する編集を含む。一方 PR2（節2）は「1判断=1参照ファイルへ分解し直す」「既存の文書構成は引き継ぎの前提としない」と定めており、**PR1 で 1 ファイルへ集約したものを PR2 で再度分解する**構図になる。

加えて節2 の目標規模「references 合計 約986行 → 500行前後」は、A の内製化で `adr-scoping.md` が増える分を織り込んでいない。

順序を「PR1 は削除と参照掃きに限り、条文の実体をどこへ置くかは PR2 の分解と同時に決める」へ寄せる案と、現行どおり PR1 で吸収し PR2 で再配置する案がある。前者は PR1 の間だけ条文が判定の細部を欠く期間を作る。どちらでもよいが、**現行の spec は二度手間になることを認識せずに順序を決めている。**

## F. 「既存ADRとの矛盾決着」の見積もりが実測と乖離

節1 付随工程:

> 判定仕様・固定題材集合・退行検出網を定めた既存ADRを洗い出し、`manage-adr` スキルの遷移（上書き/廃止）で決着させる。

`docs/adr/` 53 件を走査した実測では、**遷移（上書き/廃止）を要する ADR は見当たらない。**

- `ADR-202607230648-01`（機構のプラグイン抽出、`validity: 有効`）— `adr-scoping-cases.sh` を決定 2 の射程注記の**例示**として引用しているのみ。決定内容（テスト・fixture の配布境界は本 ADR の射程外）は無効化されない。例示の陳腐化を注記で処理する範囲
- `ADR-202608011651-01`（必要条件と粒度判定基準、`validity: 有効`）— 決定 2 が「項目名・スコア境界は本 ADR が保持しない。実体は運用文書が保持する」と明記し、「項目の追加・削除・改名、境界の点数の変更は運用文書の改訂として行い、本 ADR の反転を要さない」と続く。閾値の条文への内製化は反転にあたらない
- `adr-scoping` を含む他 3 件は、既に `validity: 上書き済み` か、参照先が旧 ADR のファイル名というだけで判定パイプラインと無関係

**工程としては「洗い出しと、各件の判定結果（変更不要を含む）の記録」で足りる。**「遷移で決着させる」という書き方は、実施者に上書き ADR の起票を期待させる。

## G. 前提の消える在庫が spec に一切現れない

判定器・判定契約・点数化・台帳・退行検出網そのものを直す OPEN Issue が **14 件**存在する（#604 / #606 / #607 / #608 / #718 / #719 / #720 / #722 / #724 / #727 / #745 / #747 / #750 / #766）。廃止すればこれらの前提は消えるが、spec の工程・受入条件のいずれにも Issue 処理が現れない。

このうち #718 / #720 / #745 / #722 は、指摘された条文欠陥自体は `adr-scoping.md` に残るが、受入条件の過半が廃止対象の機構（題材の再導出・独立2試行・欠陥台帳の更新・検査器サブコマンドとの同期）に依存しており、そのままでは充足不能になる。#700 のみ本文に機構依存がなく変更不要で存続する。

**廃止 PR の中で処理しない限り、前提の消えた Issue が在庫に残り続ける。** 「別途対応」と書いた残作業が追跡から落ちるのは既知の型である。

（処理方針は §0 決定2 として確定済み。）

## 優先度

§0 の 2 件は確定済みのため、以下の優先度づけは残る指摘に対するもの。A と G は対処方針が既に定まっており、実装へ落とす作業だけが残る。

1. **A・B・C-1・C-2** — 直さないと PR1 が壊れる、または受入条件が機能しない
2. **C-3・C-4・F・G** — 実行前に判断が要る（未決を残したまま着手すると手戻りになる）
3. **D・E・C-5** — 根拠と順序の再考。方向性は変わらないが、書かれている理由づけが実測と合っていない
