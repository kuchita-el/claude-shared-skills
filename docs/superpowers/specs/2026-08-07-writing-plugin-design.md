# writing プラグイン設計 — 日本語文書のガードレールと起草基盤

作成日: 2026-08-07

## 1. 目的

Claude が書く日本語の文書（ドキュメント・規約条文・仕様書）の品質を、規約・機械検査・独立レビューの3層で担保する。あわせて、特定用途の文書作成スキル（ADR・PRD・仕様書など）が共通して呼べる起草基盤を提供する。

本設計は新規プラグイン `writing` を対象とする。既存の `dev-workflow` および `adr` プラグインには手を入れない。

**チャット応答は対象に含めない**。本設計の成果物はいずれもファイルを入力に取るため、チャット応答には作用しない。加えて規約は参照ファイルとして置かれ、対話中に自動で読み込まれることがない。手段を持たない対象を目的に掲げないための除外である。チャット応答の日本語を扱うかどうかは別件とする（3.2）。

## 2. 診断

### 2.1 調査方法

セッションログ（`~/.claude/projects/` 配下の JSONL、対象33ディレクトリ・11,015ターン）から、ユーザーがClaudeの書いた日本語に反応した箇所を抽出した。抽出は2段構えで行った。

1. ユーザー発話1,218件から、書き方に言及する語（分かりにくい・日本語で・どういう意味・冗長など）を含むものを機械抽出
2. 抽出結果と直前のClaude出力を組にした事例集を作り、サブエージェント6体で並列分類

得られた指摘ペアは計63件（第1次）と55件（高信号）である。このうち書き方に起因するものは約48件だった。残りは技術判断への指摘であり、分類対象から除いた。

### 2.2 欠陥の型（5系統）

| 系統 | 内容 | 根拠 |
|---|---|---|
| F1 語の未接地 | 未訳の英語・専門用語の圧縮・その場の造語を、定義せずに使う | 指摘33件 |
| F2 参照の未解決 | 指示語・ID・略称の指す先が、本文から復元できない | 指摘6件。散文中で不透明な識別子を含む文の54%が、参照先を開かないと意味を取れない |
| F3 文書の自立不能 | 外部文書への参照が本文の骨格を成し、単独で読めない | ADRの参照密度が中央値82件/100行 |
| F4 判断依頼の不備 | 前提・判断軸・材料を欠いたまま問う。論点を一度に複数投げる | 素の問いが24%、2件以上の同時提示が31% |
| F5 根拠なき断定 | 結論と根拠が同じ場所にない | 指摘2件 |

F1・F2・F5 の実例を挙げる。

- F1: `retention`・`verbatim`・`load bearing`・`facet`・`grandfather 条項`・「パークしていた」「目的接地」「題材集合」「値域」「述語」
- F2: 「新規ADRってなんのことだっけ？」「J5: これって何の話だっけ？」
- F5: 「〜と矛盾する」に対する「具体的に何と矛盾するの？」

**F4 と F5 の根拠はチャット応答での観測である**。観測された場所と、規約が適用できる場所は別である。F4 は判断依頼を含む文書へ、F5 は結論を述べる箇所へ適用する。チャット応答そのものは 1 のとおり対象外とする。

ただし**現時点で F4 が自動的に届く文書は存在しない**。判断依頼を含む代表的な文書は実装プランである。その起草は `dev-workflow` の plan エージェントが担い、`docs/plans/` へ直接書き込む。`write-doc` を通らない。既存プラグインへ手を入れない方針（決定1）を保つ限り、この経路は変わらない。F4 が実装プランへ自動で効くのは、`dev-workflow` 側が `writing` のスキルまたはエージェントを呼ぶようになった後である。それまでは、規約としては適用範囲（3.3）に含まれるが、検査は手動起動に限られる。本設計はこの接続を行わない（決定17）。

### 2.3 一般的な文章作法との突き合わせ

日本語技術文書の定番技法を実測に当てた。大半は既に満たしており、規約化しても違反ゼロの項目に投資することになる。

| 技法 | 実測値 | 判定 |
|---|---|---|
| 二重否定の回避 | 0.0% | 対処不要 |
| 主観副詞（非常に・かなり・やや） | 0.0% | 対処不要 |
| 曖昧語（適切に・適宜・可能な限り） | 0.0〜0.2% | 対処不要 |
| 読点4個以上の文 | 0.3% | 対処不要 |
| ヘッジ（と思われる・可能性がある） | 0.2% | 対処不要 |
| 一文の長さ | チャット p90 83字、文書 p90 100〜119字、p99 172〜225字 | 対処する |
| 初出語・略語の定義 | カタカナ異なり976語中294語、英語異なり2,878語中1,224語が全ログ中1回のみ出現 | 対処する |
| 判断依頼の粒度 | 質問を含む応答の31%が2件以上を同時に問う | 対処する |

「一文の長さ」と「判断依頼の粒度」の実測値にはチャット応答由来のものが含まれる。観測はチャットで行われたが、規約の適用先は文書である（2.2 末尾）。

したがって本設計は網羅的な文章作法規約を採らない。実測で違反が観測された F1〜F5 に絞る。

### 2.4 文書群ごとの計量

| 文書群 | 一文平均 | p90 | 80字超の割合 | 参照密度の中央値（件/100行） |
|---|---:|---:|---:|---:|
| チャット応答 | 43字 | 83字 | 11% | — |
| `docs/adr` | 61字 | 117字 | 26% | 82 |
| `docs/plans` | 62字 | 119字 | 25% | — |
| `plugins/*/references` | 59字 | 108字 | 25% | 43 |
| `plugins/*/skills` | 53字 | 100字 | 17% | 28 |
| `docs/development` | 54字 | 102字 | 18% | 46 |

参照密度とは、外部参照（ADR識別子・Issue番号・`.md` パス）と参照句（「参照」「に従う」「が規定する」等）の合計を100行あたりに正規化した値を指す。この値は症状の把握に用いる。規約の閾値としては使わない（理由は 5.3 第2条）。

参照の解決可能性も測った。見出しと参照節を除いた散文のうち、不透明な識別子（ADR識別子・Issue番号）を含む文は1,061件ある。そのうち識別子が文の骨格（主語・目的語）に置かれているものが612件（58%）で、さらにそのうち同じ文の中で指す内容が述べられているものは39件（6%）にとどまる。残る573件は参照先を開かないと意味が取れない。全体の54%にあたる。

ファイル名は名前自体が中身を示すため、この測定から除いた。`principles.md` のような参照に要旨を求めると誤検出になる。

F3 の実例として `docs/adr/ADR-202607200855-01`（distill の入力定義を台帳へ拡張した決定の記録）を挙げる。74行の本文に対し、理解に9本の外部文書を要する。ただし参照が集中しているのは決定そのものを述べる `## Decision`（実質10行、単独で読める）ではなく、`## Context` に置かれた分割の経緯と改変の開示である。つまり手続き的な記述が本文の骨格を占拠している。

## 3. 範囲

### 3.1 作るもの（最小構成）

- 基盤スキル `write-doc` 1本
- 共通規約 `japanese-writing.md`
- 文書種別プロファイルの既定 `document-type-profiles.md`
- 機械検査 `lint-ja.sh`
- 独立レビューエージェント `doc-reviewer`
- 起草エージェント `doc-writer`（基盤スキルが呼ぶ）

あわせて、新規プラグインをリポジトリの既存経路へ登録する。いずれも明示列挙で管理されており、未登録だと黙って対象から外れる。

| 登録先 | 現状 | 未登録だとどうなるか |
|---|---|---|
| `.claude-plugin/marketplace.json` | dev-workflow / growth / adr の3件を列挙 | 配布されない |
| `setup-local.sh` | `--plugin-dir` は dev-workflow と adr の2本のみ | ローカル起動で読み込まれず、8 の検証が実行できない |
| `scripts/validate-skills.sh` | 走査対象が `plugins/dev-workflow/skills/*/SKILL.md` に固定 | スキル定義の検査から外れる |
| `scripts/run-tests.sh` の `EXPECTED_BATS` | 期待するテストファイルの固定リスト | 未登録なら不在として検出される（この経路だけは気づける） |

あわせて、本リポジトリ用の ADR 種別プロファイルを `.claude/writing/type-profiles.md` へ登録する。登録の目的は、必須節・読み手・一文長の上限という既定値を ADR に与えることである。節の配置については、未登録でも第3条の既定が移動を要求しないため（決定13）、開示義務が壊れることはない。

### 3.2 作らないもの

- 特定用途の文書作成スキル（ADR・PRD など）。基盤の契約が固まってから足す
- コミット前フック。基盤スキルが動いてから追加を判断する
- 用語集。定義は正典文書の各節へ組み込む方針が既に決まっているため（後述 7.3）
- チャット応答への適用。手段を持たないため（1）。扱うなら CLAUDE.md 本体へ条文の要約を置く必要があり、本プラグインの外の作業になる

### 3.3 規約の適用範囲

`japanese-writing.md` の5条を要求する対象を次のとおり定める。

**適用範囲**: 本規約の導入以後に新しく起草する文書、および既存文書のうち編集で実際に触れた箇所に適用する。

**適用限界**: 退役した ADR（`validity: 上書き済み` / `廃止済み`）の `## Decision` は対象から除く。凍結原則が優先する。退役という事実がその記述に時点を供給しており、記録としての読み方は保たれるためである。

**範囲外**: 既存文書の一括是正は本設計の範囲に含めない。第2条だけで573件が対象となり、是正が終わるまで検査が赤のままになる。一括是正を行うなら別 Issue として起こす。

この書き分けは ADR-202607191825-01 決定4 に前例がある。同決定は横断規範に対して「適用範囲」と「適用限界（退役 ADR の `## Decision` は除く）」を明記し、適用限界を例外ではなく規範の構成要素として位置づけている。

## 4. 制約

### 4.1 プラグイン間でファイルをパス参照できない

`${CLAUDE_PLUGIN_ROOT}` はスキル本文では展開されない。スキルの markdown で展開が保証されるのは `${CLAUDE_SKILL_DIR}` と `${CLAUDE_PROJECT_DIR}` である。`${CLAUDE_PLUGIN_ROOT}` の展開が保証されるのは hooks.json の `command` フィールドに限られる。

インストール後の配置は `cache/<マーケットプレイス名>/<プラグイン名>/<バージョン>/` である。隣のプラグインを指すにはバージョン文字列を埋め込む必要があり、破綻する。

**帰結**: 他プラグインの特化型スキルは、`writing` の規約ファイルを直接読めない。規約は基盤スキルの呼び出しを通じてのみ渡る。この制約が、基盤スキルが起草まで担う設計の根拠である。

### 4.2 プラグインを跨いでルールを効かせる経路

| 経路 | 仕組み | 相手プラグインの改修 |
|---|---|---|
| フック | `hooks.json` の `command` では `${CLAUDE_PLUGIN_ROOT}` が展開される。commit 前にリポジトリ内の `.md` を出自を問わず検査できる | 不要 |
| サブエージェント名 | `writing:doc-reviewer` はプラグインを跨いで名前指定できる | 呼び出し1行 |
| スキル名 | `writing:write-doc` も同様に呼べる | 呼び出し1行 |

## 5. 設計

### 5.1 プラグイン構成

```
plugins/writing/
  .claude-plugin/plugin.json
  references/
    japanese-writing.md         共通規約（F1〜F5に対応する5条）
    document-type-profiles.md   文書種別ごとの差分の既定
  scripts/
    lint-ja.sh                  機械検査
    allowlist/                  説明を要しない語の登録簿
  agents/
    doc-reviewer.md             独立レビュー（読み取り専用）
    doc-writer.md               起草
  skills/
    write-doc/SKILL.md          基盤スキル
```

`write-doc` から共有資源を読む経路は `${CLAUDE_SKILL_DIR}` を基点とする。規約は `../../references/`、検査器は `../../scripts/` にあたる。制約4.1により `${CLAUDE_PLUGIN_ROOT}` は使えない。

`doc-reviewer` と `doc-writer` の front-matter には `model` と `effort` を明示する。値の選び方は `plugins/dev-workflow/references/subagent-execution-parameters.md`（サブエージェントの実行パラメータの単一出典）に従う。特に検証役の `effort` を省くと、利用者の環境によってレビュー精度が変わる。

### 5.2 基盤スキル `write-doc` の契約

呼び出し側が渡す情報だけで起草できることを要件とする。制約4.1により、呼び出し側は規約ファイルを読めないためである。

**入力**

| 引数 | 内容 | 省略時の扱い |
|---|---|---|
| 文書種別 | 表示名。プロファイルの選択に使う | 汎用プロファイルを適用する |
| 構造 | 必須節と、各節に何を書くかの意図 | 素材から基盤が節を立てる |
| 素材 | 確定した内容（決定・根拠・前提・実測値） | 起草不能として返す |
| 読み手 | 誰が読むか。前提にしてよい語彙の水準 | リポジトリの一般読者を仮定する |
| 出力先 | ファイルパス | 一時ファイルへ書き、そのパスを返す（後述） |

**処理**

1. 種別プロファイルを解決する（プロジェクト固有 → プラグイン同梱の既定の順）
2. 起草エージェント `doc-writer` が規約と構造に従って書く
3. `lint-ja.sh` を走らせる
4. `doc-reviewer` が意味的な判定を行う
5. 指摘を反映する。反映の周回には上限を設ける
6. 結果を返す

**出力**

- 書き出したファイルのパス
- 残った違反の構造化サマリ（機械検査・レビューの双方）
- 未決として書かなかった点

**文書本体は返さない**。本文を返り値に載せると、呼び出し側のメイン context へ全文が滞留する。`context-budget.md` は、スキル実行時に何をメイン context へ載せるかの単一出典である。同規約はサブエージェントの返却を構造化サマリに限り、中間生成物の本文やファイル全文を返却させない。既存の `plan-issue` スキルも同じ理由で「plan 本文はメインに載らない」と明示している。

この規定は検査の実行可能性にも効く。`lint-ja.sh` はシェルスクリプトであり、検査対象のファイルが実在することを前提とする。本文を返すだけでファイルを作らない経路があると、その経路では検査が黙って素通りする。出力先が省略された場合に一時ファイルへ書くのは、この経路を塞ぐためである。

**一時ファイルの扱い**: 置き場所はプロジェクト規約が定める形式（`/tmp/{名前}-{timestamp}.md`）に従う。呼び出し側が内容を確定の場所へ移すまで残し、`write-doc` は削除しない。呼び出し側が受け取るのはパスのみであり、スキルが先に消すと内容を取り出せなくなる。

**未決の扱い**: 素材に穴がある場合、埋めた条文を書かずに未決として列挙して返す。暗黙の前提を置いて書き進めない。

### 5.3 共通規約 `japanese-writing.md`（5条）

**第1条 語の接地**

初出の語は、渡された読み手の語彙水準で意味を復元できないなら、定義または言い換えを同じ場所に添える。英語をそのまま使う場合も同様とする。読み手が指定されない場合は、当該リポジトリの一般読者を仮定する。

この義務を免除するのは、許可リスト（5.4）に登録された語に限る。登録は人手で行い、読み手が知っている見込みを基準に判断する。使用頻度を免除の根拠にしない。

**第2条 参照の自己完結（文のレベル）**

参照の数は制限しない。参照先を開かなくても文意が通ることを条件とする。

不透明な識別子とは、名前から中身が分からない参照を指す。ADR識別子・Issue番号がこれにあたる。不透明な識別子を文の骨格（主語・目的語）に置く場合は、それが何を指すかを同じ文か直後の文で述べる。述べ方は括弧注でも連体修飾でも、述部で内容を述べる形でもよい。読み手が参照先を開かずに読み進められることが判定の基準であり、述べ方の形式は問わない。

自己説明的な参照（ファイル名・節見出しなど、名前自体が中身を示すもの）はこの限りでない。

「前回」「上記」「例の」のように、文書外の文脈に依存する指示は使わない。

**第3条 文書の自立（文書のレベル）**

結論と決定の骨格は本文で完結させる。

節の構成は種別プロファイル（5.6）が定めるものに従う。

プロファイルが節の配置を定めていない場合、手続き的な記述の移動を要求しない。`doc-reviewer` が「本文の主流から分離できないか」を指摘するに留め、起草時に節を動かさない。既定を移動側へ倒すと、プロファイル未登録の文書種別に対して、その種別が持つ既存の義務を黙って壊しうる。ADR の開示義務がその例である（本条末尾）。未設定時は現状を保つ向きへ倒す。

見出しは、その配下に書かれている内容を指す。見出しが名乗る対象と中身が食い違ってはならない。

単一出典の規律が禁じるのは定義の重複であって、参照先の要旨を書くことではない。両者を混同しない。

この条文がプロファイルへ委ね、かつ未設定時に移動を要求しないのは、承認済み ADR の運用と二重に立たないためである。ADR-202607112231-01 は多決定 ADR の分割にあたり、原 ADR から改変した箇所と理由を後継 ADR の `## Context` に記載することを決定として持つ。`manage-adr` スキルはこれを手順と締めの検査に落としている。手続き的な記述を無条件に末尾へ寄せると、規約に従えば分割の検査が落ち、検査に従えば規約違反という状態になる。ADR プロファイルが「改変の開示は `## Context` に置く」と宣言することで、両者が衝突しない。

**第4条 判断依頼の材料**

判断を求める箇所では、前提・判断軸・選択肢と各々の帰結・推奨とその理由を揃える。論点は一度に1件へ絞る。

**「判断依頼」の語の扱い**: この語は ADR-202606211417-01 が正準用語として確定済みである。同 ADR は最小データ構造（観点ID・説明・検出フェーズ・判断者ロール、任意で関連AC番号）も定めている。同 ADR が定めるのは台帳としてどの項目を持つかであり、本条が定めるのは読み手へ提示するときにどの材料を添えるかである。軸が異なるため、本条は同 ADR の最小データ構造を置き換えない。

**第5条 根拠の同居**

結論と、その結論を支える根拠を同じ場所に置く。「〜と矛盾する」「〜に反する」と述べる場合は、何とどう矛盾するかを同じ箇所に書く。

**補則（一文の長さ）**: 一文は100字を超えない。超える場合は文を分ける。種別プロファイルが一文長の上限を定めている場合はそちらが優先し、本補則は上限が指定されていないときの既定として働く。

### 5.4 機械検査 `lint-ja.sh`

文書種別を引数に取り、プロファイルの閾値を適用する。

**入力単位**: 差分を既定とする。ファイル全体を検査するモードも持つが、既定にはしない。適用範囲（3.3）が「編集で実際に触れた箇所」であるため、ファイル全体を既定にすると、既存文書を1行直しただけで既存の違反が赤になり、一括是正を範囲外とした宣言と食い違う。

**判定の粒度**: 検出項目のうち「一文の長さ超過」と「説明を伴わない不透明な識別子」は文を単位とする判定である。差分のハンクは行で切れるため、変更行だけを見ると文が途中で終わり、長さも説明句の有無も誤って判定する。変更行を含む文をファイル本体から復元してから判定する。8 の fixture もこの単位で組む。

| 検出項目 | 検出方法 | 検査を置く根拠 |
|---|---|---|
| 未接地語 | 許可リストにない語で、近傍に定義表現（「＝」「とは」括弧注）がないもの。対象の字種は英語トークンとカタカナ語に限る | 説明を伴わない語の多さ。異なり語の3割前後が全ログ中1回のみ出現（カタカナ294/976、英語1,224/2,878）。この統計は検査を置く動機であって、候補を絞る基準ではない |
| 一文の長さ超過 | 100字超 | 文書群のp90が100〜119字、p99が172〜225字 |
| 説明を伴わない不透明な識別子 | 骨格位置にあるADR識別子・Issue番号で、同じ文に説明句がないもの | 散文中で不透明な識別子を含む文1,061件のうち、開かないと意味が取れないものが54% |

参照の数は測らない。第2条が数を制限しないため、密度の閾値は設けない。

**この検査は候補を出すところまでとする**。連体修飾で意味が通っている文（例:「ADR-202606040737-01 が確立した読み込み優先順位を踏襲し」）は、括弧注を探す検査では拾えず誤検出になる。開かずに読めるかどうかの確定判断は `doc-reviewer` が行う。

実装上の注意として、識別子がインラインコードで囲まれている場合がある。この形では識別子と括弧注の間にバッククォートが挟まるため、素朴な正規表現では説明句を取り逃す。本設計文書を自ら検査した際に、実際にこの取りこぼしが出た。

**漢字の複合語を機械検査の対象にしない理由**: 第1条は字種を問わないが、機械検査は英語とカタカナに限る。`lint-ja.sh` はシェルスクリプトであり、形態素解析を持たないため、漢字の連なりを素朴に切る以上のことができない。

`docs/adr` の68本を素朴な字種検出に掛けると、漢字2字以上の異なり語は1文書あたり中央値176件、最大504件になる。中身は「中央値」「主流」「二重否定」といった通常の語が大半を占める。確定を担う `doc-reviewer` の負荷にそのまま乗る規模である。

出現の稀少さで候補を絞る案は採らない。同じ計測で「他の文書に一度も現れない語」に絞ると1文書あたり中央値10件まで落ち、数の上では扱える。しかし絞った先に「値域」「facet」のような反復して使われる語は残らない。読み手が実際に分からないと訴えた語はそこにある。稀少さは頻度の裏返しであり、次に述べる理由で免除の根拠にならないのと同じ理由で、優先順位の根拠にもならない。

漢字造語の判定は `doc-reviewer` が担う（5.5）。「目的接地」「題材集合」のような造語はここで拾う。

**許可リストの作り方**: 人手で登録する。使用頻度からの自動生成は採らない。

頻度が測っているのは書き手の癖であって、読み手の理解ではない。読み手が分からないと訴えた語ほど書き手は繰り返し使うため、頻度は高くなる。実際に数えて確かめた。対象は `docs/` と `plugins/` 配下の `.md` 193件（本設計文書を除く）である。F1 の実例として挙げた語の出現ファイル数は、値域45・facet 27・retention 13・パーク9・題材集合6だった。頻度を基準にすると、規約が最も止めたい語が真っ先に免除される。

登録の基準は、読み手がその語を知っている見込みである。初期の登録内容は実装時に人手で選ぶ。

許可リストは語形のリストであり、意味定義を持たない。これは用語集を作らないという既存決定（7.3）と衝突させないための制約である。

**検査対象の書き分け**: コードブロックは検査しない。インラインコードは、識別子の参照検査（第2条）については対象に含める。ADR識別子の出現1,730件のうち234件（14%）がインラインコード内にあり、除外すると参照検査がその分だけ届かなくなる。未接地語の検査（第1条）については、インラインコードは識別子として扱い対象外とする。

### 5.5 `doc-reviewer` エージェント

機械検査で取れない意味的判定を担う。読み取り専用とする。

判定項目は次のとおり。

- 語の復元可能性（第1条。読み手が意味を取れるか。漢字の造語はここでのみ拾う。機械検査が字種として扱わないため）
- 参照の自己完結（第2条。参照先を開かずに文意が通るか。機械検査が出した候補の確定を含む）
- 文書としての自立（第3条。結論と決定の骨格が本文で完結しているか。見出しと中身が一致しているか）
- 判断依頼の材料充足（第4条）
- 結論と根拠の同居（第5条）

第3条は機械検査を持たない。参照の数を測らない方針を採ったため、文書レベルの自立を判定する定量指標が無い。本エージェントが唯一の執行手段である。

**入力契約**: 対象の差分（またはファイルパス）、文書種別、読み手、許可リストのパスを渡す。素材および起草時の判断の経緯は渡さない。渡すと初見の読み手という前提が崩れ、書き手の意図で補って読んでしまう。

許可リストを渡すのは、第1条の免除規則が本エージェントにも適用されるためである。渡さないと、機械検査は免除する語を本エージェントが未接地として指摘し、同じ条文に対する判定が2つに割れる。渡すのはパスのみとし、本文は本エージェントが自前で読む。

差分を初見の読み手として読む独立検証であり、書き手自身の読み直しではない。この区別は、自己確認ステップの追加を禁じる既存規約（7.2）との整合上必要である。

### 5.6 文書種別プロファイル

種別ごとに異なる値を持つ。読み込み優先順位は既存の DoR 定義と同じ形にする。

1. `${CLAUDE_PROJECT_DIR}/.claude/writing/type-profiles.md`（プロジェクト固有）
2. プラグイン同梱の既定

保持する値は、節構成（必須節と、手続き的な記述をどの節へ置くか）・読み手の既定・一文長の上限とする。この形により、ADR や PRD といった具体的な種別はプロジェクト側で登録でき、基盤プラグインが特定の文書種別を知る必要がない。

節構成をプロファイルが持つのは、第3条が節の配置をプロファイルへ委ねているためである（5.3 第3条）。ADR プロファイルは、改変の開示を `## Context` に置くことを宣言する。

## 6. 消費者からの利用

特化型スキルの置き場所には2通りある。

| | パターン1（同居） | パターン2（跨ぎ・ソフト依存） |
|---|---|---|
| 特化型スキルの居場所 | `plugins/writing/skills/` | 他プラグイン |
| 規約ファイルの読み方 | `${CLAUDE_SKILL_DIR}/../../references/` で直接読める | 読めない。基盤スキルの呼び出し経由でのみ取得する |
| 基盤が不在の場合 | 起こらない | 消費側が縮退挙動を持つ必要がある |

パターン2の方が前提が弱い。基盤スキルをパターン2の契約で書けば、パターン1は自動的に成立する。逆は成らない。したがって基盤スキルはパターン2の契約で作り、特化型の置き場所は実際に作る段で決める。

ソフト依存とは、次の形を指す。消費側は `writing:write-doc` を `Skill` ツールで呼ぶ。プラグインが未導入なら呼び出しは skip され、消費側は自前の最小手順へ縮退する。これは `dev-workflow` が `superpowers` に対して既に採っている方式と同じである。

## 7. 既存資産との関係

### 7.1 `doc-author` サブエージェント

ユーザースコープ `~/.claude/agents/doc-author.md` に、確定済みの決定を条文へ落とす執筆エージェントが存在する。責務が本設計の起草役と重なる。

| 観点 | 既存 `doc-author` | 本設計の起草役 |
|---|---|---|
| 配布 | ユーザースコープ。プラグインとして配れない | プラグイン同梱で配布できる |
| 対象文書 | 規約文書・仕様書・設計記録 | 上流文書や、読み手が非専門家の文書も含む |
| 語の接地 | 「新しい用語を勝手に導入しない」のみ。既存語なら使ってよいため、読み手が知らない既存語は止まらない | 読み手の語彙水準に照らして判定する |
| 参照・自立可読性 | 規定なし | 第2条・第3条 |
| 判断依頼の材料 | 規定なし | 第4条 |
| 検査との連結 | なし | 機械検査・独立レビューと連結 |

`doc-author` の執筆規律のうち、決定を行わないこと・未決は書かずに列挙して返すこと・単一出典を維持することは流用する。

`doc-author` の退役は、基盤スキルが実際に使えると確認してから別途判断する。基盤の完成と同時に削除はしない。退路を残すためである。

### 7.2 `behavior-invariants.md`

`docs/behavior-invariants.md` は、出力・成果物の分量と作業範囲を扱う規約である。本設計の規約は語彙・参照・判断依頼の材料を扱う。軸が異なるため内容を重複させない。境界は次のとおり。

- どれだけ書くか、どこまでやるか → `behavior-invariants.md`
- どう書けば読み手が意味を取れるか → `japanese-writing.md`

**重なる1点**: `behavior-invariants.md` の不変条件1 は「その場で作った略語で短くしない」を含み、第1条（語の接地）と重なる。同不変条件が扱うのは分量を削る手段としての略語であり、第1条が扱うのは読み手が意味を復元できない語一般である。略語は後者の部分集合にあたる。

`behavior-invariants.md` は冒頭に3軸の境界表（作成時の静的軸・実行時のデータフロー軸・実行時の生成範囲軸）を持つ。本規約は4軸目にあたるため、同表へ行を追加し、上記の境界もその表に書く。`japanese-writing.md` へ境界の文を転記しない。同ファイルは背景節で「同じ趣旨の文言が分散して drift する」ことを問題として挙げており、境界を2箇所へ置けばその型を自ら作ることになる。当初の指定は `japanese-writing.md` から同表を参照させるものだったが、これを採らない。`writing` は基盤側のプラグインである。利用側である `dev-workflow` のファイルを名指しすると、`writing` が `dev-workflow` の存在を前提にする逆依存が生まれる。境界表への行追加と合わせると両プラグインが相互参照になる。代わりに `japanese-writing.md` は冒頭で自身の射程のみを述べ、他プラグインのファイルを名指ししない。境界の出典が境界表の1箇所に留まる点は、参照を置かない扱いでも変わらない。なお境界表の実装では、表現の軸を既存の3軸には数えず、4行目として併記する形を採った。上記の「4軸目」は表の4行目という位置を指す。

また `behavior-invariants.md` の由来となった決定は、書き手自身の読み直し型の確認ステップを新たに追加することを禁じている。独立した文脈による検証は対象外とされているため、`doc-reviewer` は独立エージェントとして構成する。入力契約で素材と起草の経緯を渡さないこと（5.5）が、この独立性の実体である。

### 7.3 用語集を作らない決定

`growth` プラグインの `glossary.md` は廃止済みであり、定義は正典文書の各節へ組み込む方針が確定している。本設計の許可リストは、意味定義を持たない語形のリストに留めることで、この決定と衝突しない。

## 8. 検証

- `lint-ja.sh` は正例・負例の fixture を用意し、既存のテスト実行経路（`scripts/run-tests.sh`）に載せる
- 負例が実際に赤になることを、検査条件を変異させて確かめる。検査語彙を狭めると負例が無力化するため
- 基盤スキルは、2.2で列挙した欠陥の型を含む素材を与えて起草させ、指摘の型が再発しないことで確認する

`doc-reviewer` も fixture で押さえる。第3条の全体と、第1条のうち漢字の造語は、機械検査を持たず本エージェントが唯一の執行手段である（決定12・13・15）。回帰を検出する手段が無いままにしない。手順は次のとおり。

- 欠陥の型ごとに負例文書を用意する。第1条は無定義の造語を含む文書、第3条は結論の骨格が参照先にしか無い文書、第4条は前提と選択肢を欠いた判断依頼を含む文書
- 各負例を `doc-reviewer` に読ませ、対応する型の指摘が出ることを確かめる
- 正例（同じ内容で欠陥を取り除いた文書）を読ませ、当該の指摘が出ないことを確かめる

判定は決定的でないため、`lint-ja.sh` の fixture と同じ扱いにはしない。回帰の検出を人手の記憶に委ねないための最小の手当てである。

**合否の判定者**: 基盤スキルの検証は人が判定する。`doc-reviewer` に合否を出させると、検証対象の一部である同エージェントが自らの働きを採点することになる。`doc-reviewer` が出すのは指摘であって合否ではない。

この検証を実行するには、3.1 の登録作業のうち `setup-local.sh` への追加が先に済んでいる必要がある。未登録ではプラグインが読み込まれず、起草の実行そのものができない。

## 9. 決定事項

1. 新規プラグイン `writing` として作る。既存プラグインには手を入れない
2. 最小構成は基盤スキル1本とその資源。特化型の文書作成スキルは作らない
3. 基盤スキルは起草まで行う。起草に必要な情報は消費側から渡す
4. 基盤スキルの契約はパターン2（ソフト依存）で書く
5. 規約は実測で違反が観測された F1〜F5 に絞る。網羅的な文章作法規約は採らない
6. `doc-author` は基盤へ寄せる。退役は基盤の動作確認後に別途判断する
7. 参照の数は制限しない。参照先を開かずに文意が通ることだけを条件とする。参照密度は診断に使い、閾値には使わない
8. 参照の解決可能性について、機械検査は候補提示までを担い、確定判断は `doc-reviewer` が行う
9. チャット応答は対象に含めない。手段を持たないため。扱うなら CLAUDE.md 本体への条文追加が要り、本プラグインの外の作業になる
10. 規約の適用範囲は新規起草物と編集で触れた箇所とする。退役 ADR の `## Decision` は適用限界として除く。既存文書の一括是正は範囲外
11. 許可リストは人手で登録する。使用頻度からの自動生成は採らない
12. 第3条は節の配置を種別プロファイルへ委ねる。承認済み ADR の開示義務と二重に立たせないため
13. プロファイルが節の配置を定めていない場合、手続き的な記述の移動を要求しない。未設定時は現状を保つ向きへ倒す
14. 機械検査の入力単位は差分を既定とする。ファイル全体は明示指定のときだけ
15. 機械検査の未接地語検出は英語とカタカナに限る。漢字の造語は `doc-reviewer` が担う。形態素解析なしでは候補が実務的な数に収まらないため
16. プラグイン名は `writing` とする。名前が実体（書き方の規約と起草基盤）を示すこと、および「どの文書を持つか・文書のライフサイクルをどう回すか」を扱う文書運用トラックのために `documentation` の名前を空けておくことによる
17. `dev-workflow` の plan 経路へは本設計では接続しない。決定1（既存プラグインに手を入れない）を保つ。F4 は規約に残すが、執行は `write-doc` の明示起動に限る。再検討の条件は、8 の検証で基盤スキルが実利用に耐えると確認できたことであり、その時点で別 Issue として判断する

### 9.1 ADR 化要否の判定

プロジェクト規約に従い、上記の決定に対して ADR 化要否を判定した。却下代替を明示的に持つ決定は次の13件である。

| 決定 | 却下した代替 |
|---|---|
| 3（起草まで行う） | 検査のみ／検査＋規約取得 |
| 4（パターン2の契約） | パターン1（同居）を前提に書く |
| 5（F1〜F5 に絞る） | 網羅的な文章作法規約 |
| 7（参照の数を制限しない） | 参照密度の閾値を設ける |
| 9（チャット応答を対象外） | 範囲に残す／ユーザースコープへ条文を置く |
| 10（適用範囲） | 新規起草物のみ／既存文書も全件 |
| 11（許可リストは人手登録） | 使用頻度からの自動生成 |
| 12（節配置をプロファイルへ委ねる） | ADR を適用対象から外す／ADR 側の開示義務を改訂する |
| 13（未設定時は移動を要求しない） | 末尾へ寄せることを既定にする |
| 14（入力単位は差分が既定） | ファイル全体を既定にする |
| 15（漢字造語は機械検査の対象外） | 稀少さで候補を絞る／形態素解析を導入する |
| 16（プラグイン名は `writing`） | `documentation`／`authoring` |
