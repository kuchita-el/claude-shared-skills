# ADR の状態モデルと識別子規約（adr-model.md）

ADR の状態（承認軸・有効性軸）の役割と各役割の定義、合法な front-matter を表す状態の型、操作ごとの遷移の表、用語集、ファイルの配置と採番方式を定める。本ファイルがこれらの規約の実体であり、状態の役割・採番規則をここ以外で独自に再定義しない。各役割の値（front-matter に書く綴り）の正本は本ファイルの外にある（後掲「状態の2軸」）。

## 状態の2軸

状態は**承認軸**と**有効性軸**に分離して管理する。1つの状態欄に混在させると、「承認された歴史事実」と「現在効力を持つか」という性質の異なる2つの情報が互いを上書きしてしまうためである。

本ファイルは各軸の値を**役割**として定め、役割を設定のキーの名前で呼ぶ。役割に与える値は設定が決め、1つのリポジトリの中では1つの言語で揃える。値の正本は、プラグインに同梱した既定値のファイル（プラグインの `scripts/adr-config.default`）である。導入先は、git のトップレベルに `.claude/adr/config` を置いて値を置き換えられる。置き場・語の群を揃えて置く規則・誤りの扱いは、プラグインの README の「設定」節に従う。

下の表の「既定値」の列は、既定値のファイルの値を読みやすさのために併記したものである。以降の節は、`status-approved` のように役割の名前で値を書く。front-matter に現れるのは、その役割に設定が与えた値である。

### 承認軸（`status`・不変の履歴事実）

| 役割 | 既定値 | 定義 |
|---|---|---|
| `status-proposed` | `提案中` | 起案され、承認者の判断を待っている状態 |
| `status-approved` | `承認済み` | 承認された履歴事実。以後不変 |
| `status-rejected` | `却下` | 提案が承認に至らず終了。一度も運用されない終端 |

### 有効性軸（`validity`・可変の現在の効力）

| 役割 | 既定値 | 定義 |
|---|---|---|
| `validity-active` | `有効` | 現在運用中 |
| `validity-superseded` | `上書き済み` | 後継 ADR に置き換えられた（`superseded-by` に後継の full slug を保持） |
| `validity-abandoned` | `廃止済み` | 後継 ADR なしで ADR としての効力を終えた。決定そのものを放棄した場合と、記録の正本が ADR 外の資産へ移った場合の両方を含む。いずれの場合も、この ADR を現在の効力の判断材料にしない |

### 軸の関係

- `status-rejected` と `validity-superseded` / `validity-abandoned` は別の役割である。前者は承認軸で、一度も承認されなかった終端を表す。後者は有効性軸で、承認後に ADR としての効力を失った状態を表す。2軸が語彙レベルで衝突しないよう、両者を混同して扱わない。6つの役割の値は互いに異なる（重複は設定の誤りになる）
- `status-proposed` をスキップして直接 `status-approved` に到達する経路は持たない。即承認のケースは「提案 → 承認」を連続実行として扱う

## front-matter（状態の唯一の権威）

状態系は各 ADR ファイル冒頭の front-matter に置く。キーは英語の構造的フィールド名に固定し、導入先の言語によらない。値は、前掲の役割に設定が与えた値とする。

```yaml
---
status: <status-proposed | status-approved | status-rejected の値>
validity: <validity-active | validity-superseded | validity-abandoned の値 | （空）>
superseded-by: <後継ADRの full slug | （空）>
---
```

- front-matter が状態の唯一の権威である。**本文に `## Status` 節を置かない**。新規起票時も、承認・上書き・廃止・却下のいずれの遷移時も同様である。本文へ状態を書き足すことは重複を生むだけで、以後の遷移で取り残される drift 源になる
- 「キー省略」と「キーあり値空」は同じ「空」として扱う。空にする軸は値を空にする（キー行自体は残してよい）
- 有効 ADR の一覧（index）は front-matter から機械生成する導出ビューであり、人手編集しない。これにより「本文を読めば確実（確実性）」と「一覧で探せる（検索性）」を drift させずに両立する

## 状態の型

front-matter は次の直和型のシリアライズ形式である。合法な状態はこの5構成子に尽き、各構成子が `status` / `validity` / `superseded-by` の組み合わせを一意に決める。遷移後の front-matter は必ずいずれかの構成子として構成できる形にする。構成子は、その構成子を他と分ける役割の名前で呼ぶ。

```
ADRState =
  | status-proposed                                -- status=status-proposed, validity=（空）,                superseded-by=（空）
  | status-rejected                                -- status=status-rejected, validity=（空）,                superseded-by=（空）
  | validity-active                                -- status=status-approved, validity=validity-active,     superseded-by=（空）
  | validity-superseded of NonEmptyList<FullSlug>  -- status=status-approved, validity=validity-superseded, superseded-by=後継の full slug 列
  | validity-abandoned                             -- status=status-approved, validity=validity-abandoned,  superseded-by=（空）
```

各遷移は、ADR を構成子へ移す操作である（定義は後掲「遷移の表」）。

各操作の遷移前の状態、遷移後の構成子、取り消しが遷移でないことは、後掲「遷移の表」が持つ。ここでは型との関係だけを述べる。分割も取り消しも、構成子を足さず、有効性軸の値域も変えない。型は、退役した ADR の構成子（`validity-superseded`・`validity-abandoned`）から `validity-active` への遷移を持たない。取り消しの判定基準と手順は `transitions.md`「取り消し（誤った退役の訂正）」が持つ。

型が課す制約:

- **制約1**: すべての構成子が `status` の値を伴う。`status` が空の状態はどの構成子としても構成できない
- **制約2**: `status=status-approved` を伴うのは3構成子だけである。`validity-active` / `validity-superseded` / `validity-abandoned` がそれに当たる。いずれも `validity` の値を伴う。上書き・廃止で `status` を変更しないのはこの制約による（承認は歴史事実であり不変）
- **制約3**: `validity` を伴わないのは `status-proposed` / `status-rejected` の2構成子だけである。承認前・却下の状態に現在の効力は定義されない
- **制約4**: `superseded-by` を伴えるのは `validity-superseded` だけである。他の4構成子は当該フィールドを持たず、値を伴う形では構成できない
- **制約5**: `validity-superseded` が保持する後継は**非空**リストである。後継を持たない `validity-superseded` は構成できない
- **制約6**: `status` / `validity` の値は各軸の値域（3つの役割に設定が与えた値）に限る。値域の外の語はどの構成子にも当たらない

### 型の制約と機械検査の対応

同梱の drift-lint がレイヤ1（front-matter スキーマ検証）で数える違反種別は、いずれも上の型が排除する状態に当たる。違反種別と、当該状態を排除する型の制約の対応は次のとおりであり、対応の付かない違反種別は0件である。

| 違反種別 | 排除する制約 |
|---|---|
| `status` 欠落（空） | 制約1 |
| `status=status-approved` かつ `validity` 欠落（空） | 制約2 |
| `validity=validity-superseded` かつ `superseded-by` 欠落（空） | 制約5 |
| `status` の値が語彙外 | 制約6 |
| `validity` の値が語彙外（空は合法） | 制約6 |
| `status=status-proposed` または `status-rejected` かつ `validity` が非空 | 制約3 |
| `status=status-proposed` または `status-rejected` かつ `superseded-by` が非空 | 制約4 |
| `validity=validity-active` または `validity-abandoned` かつ `superseded-by` が非空 | 制約4 |
| front-matter 欠落（先頭行が `---` でない） | 制約1（front-matter を持たない ADR は `status` の値を伴わない） |

**逆向きは成り立たない。** 型として構成できない状態のすべてをレイヤ1 が報告するわけではない。レイヤ1 が見るのは各欄が空か否かと値が値域内かであり、欄が非空で値域も踏むが制約を満たさない病的値は素通りする。既知の経路は制約5 である。`superseded-by` が区切り文字と空白だけで、有効な参照先の full slug を1件も含まない値がこれに当たる（`superseded-by: ,` 等）。この値は raw 文字列として非空であるため、レイヤ1 の空判定を通過する。これを報告するのはレイヤ3（相互参照双方向性）である。この経路の是正手段は `transitions.md`「上書き（上書き済み・双方向相互参照）」が持つ。

**是正手段**: レイヤ1 違反は front-matter を直して解消する。報告された違反種別に対応する制約を上表で引き、当該制約を満たす構成子の値組（前掲の型定義の注記）へ `status` / `validity` / `superseded-by` を揃える。どの構成子へ揃えるかは、当該 ADR がどの遷移を終えた状態かで決まる。値を空にする場合はキー行を残して値だけを空にしてよい。

補足:

- 後継は単一を既定とするが、1本の ADR が複数の後継へ分割される場合はリスト値（カンマ区切り）を取りうる。この 1→N のケースでは、`validity-superseded` の原 ADR が全後継を列挙し、各後継が本文の関連 ADR 節に逆参照を持つ（双方向で照合される）
- 後継 ADR は full slug の参照のみで保持し、実体への直接参照は持たない（自己参照・循環参照の構造的不整合を防ぐ）

## 遷移の表

ADR の状態（front-matter）に加える操作は、次の7つである。既存の ADR の直接編集（非core・些末）は、状態を変えず `validity` も変えないため、この表に含めない。各操作の遷移前の状態と遷移後の構成子は、前掲「状態の型」の構成子の名前で書く。構成子の定義は「状態の型」が持ち、本節では再定義しない。実行の手順は `transitions.md` が持つ。

「種別」の列は、操作が状態の型の上でどこに位置するかを表す。遷移は、状態の型の構成子へ ADR を移す操作である。起票は、既存の状態を持たない ADR を構成子へ置く。起票・承認・上書き・廃止・却下の5つが遷移である。分割は、原 ADR を上書きと同じ構成子へ移すが、決定のファイル間再配置であるため、5遷移に数えない構造操作である。取り消しは、退役の記録の訂正であり、遷移ではない。

| 操作 | 種別 | 遷移前の状態 | 遷移後の構成子 | `validity` を変える | ガード |
|---|---|---|---|---|---|
| 起票 | 遷移 | なし（新規の ADR） | `status-proposed` | いいえ | なし |
| 承認 | 遷移 | `status-proposed` | `validity-active` | はい | なし |
| 上書き | 遷移 | `validity-active` | `validity-superseded`（後継は1本） | はい | 後継が承認されて `validity-active` であること |
| 廃止 | 遷移 | `validity-active` | `validity-abandoned` | はい | 後継を持たないこと（後継があれば上書きか分割である） |
| 却下 | 遷移 | `status-proposed` | `status-rejected` | いいえ | なし |
| 分割 | 構造操作 | 原 ADR は `validity-active` | 原 ADR は `validity-superseded`（全後継を列挙）。後継は起票と承認を経て `validity-active` | はい | 後継へ逐語転記する決定が1つ以上あること（無ければ分割にならない） |
| 取り消し | 訂正（遷移ではない） | `validity-superseded` または `validity-abandoned` | `validity-active`。退役が行われなかった場合の構成子へ置き直す | はい | 退役が誤りと判定されていること。判定の基準と射程は `transitions.md`「取り消し（誤った退役の訂正）」が持つ |

「遷移前の状態」の列は、各操作の実行前に確かめる期待値である。「ガード」の列は、それに加えて実行前に確かめる条件である。操作の後に書く内容は、表に写さず、`transitions.md` の手順が持つ。起票は、既存の ADR を持たないため、遷移前の状態を持たない。

### `validity` を変える操作の集合

`validity` を変える操作とは、操作の前後で、操作の対象になる ADR のいずれかの `validity` の値が変わる操作である。上の表で「`validity` を変える」の列が「はい」の、承認・上書き・分割・廃止・取り消しの5つがこれに当たる。起票と却下は、`validity` を空のまま置くため、これに当たらない。

この集合を区切るのは、操作が有効 ADR の集合を動かすかどうかである。動かす操作は、index の再生成を要する（後掲「index の同期」）。この集合の正本は上の表の列であり、他の箇所で操作を列挙し直さない。

## 用語集

本節は、意味が揺れやすい語を、語の族ごとに1つの語へ定める。各行は、定義と、その語が指す範囲（含むもの・含まないもの）を持つ。範囲を正本が定める行では、範囲の列を「—」とし、定義の列が正本を指す。族の中の別の語は、別の概念として行を持つか、使わない語として表の後に挙げる。

### 退役・廃止・格下げ

| 用語 | 定義 | 含むもの | 含まないもの |
|---|---|---|---|
| 退役 | 承認済みの ADR が、`validity-active` から `validity-superseded` または `validity-abandoned` へ移り、現在の効力を失うこと | 上書き・分割・廃止 | 起票・承認・却下。取り消しも含まない（退役の記録の訂正であり、退役の一種ではない） |
| 廃止 | `validity-active` から `validity-abandoned` への遷移。後継 ADR を持たない退役である | 決定そのものを取り下げる場合と、記録の正本が ADR 外の資産へ移る場合の両方 | 上書き・分割（後継を持つ）。却下（承認前の終端） |
| 格下げ | 既存の ADR を廃止するかを決める判定。実体は `adr-demotion.md` が持つ | 結果が廃止である場合と、存置である場合の両方 | 廃止の遷移そのもの。起票の粒度判定 |

- 退役させた ADR は「退役 ADR」と呼ぶ。`validity-superseded` と `validity-abandoned` の ADR がこれに当たる。
- 廃止の理由は、「放棄」（決定そのものを捨てた）と「移管」（規範本文を ADR の外の資産へ移した）の2つに分ける。この区分は理由の記述に使う語であり、状態や遷移の名には使わない。`validity-abandoned` の値は「廃止済み」と呼び、遷移は「廃止」と呼ぶ。

### core・反転・再承認

| 用語 | 定義 | 含むもの | 含まないもの |
|---|---|---|---|
| core | 変更種別（core／非core／些末）の1つ。値の定義と判定は `edit-decision.md` が持つ | 反転を伴う変更（「core 変更」と呼ぶ） | 決定そのもの。決定を core と呼ばない |
| 反転 | `edit-decision.md` の判定基準の第1問が YES になる変化 | core 変更の中身を指す語 | 第1問が NO になる変化（非core・些末の変更） |
| 再承認 | core 変更が有効になるために、後継 ADR が承認を受けること | 後継への承認の遷移 | 承認済みの ADR へ承認を取り直すこと。承認済みは不変であり、承認の遷移前の状態は `status-proposed` だけである。非core・些末の変更は再承認を要さない |

- 変更を指すときは「core 変更」、変更の中身を指すときは「反転」と言う。「core 反転」とは言わず、単に「反転」と言う。
- 束ねた ADR の一部の決定だけが反転することは「部分反転」と呼ぶ。分割の反転駆動のトリガである。
- 決定について言うときは、「core な決定」「独立に反転しうる core」と言わず、「独立に反転しうる決定」と言う。

### 逐語転記・却下代替の持ち越し

この2つは別の概念である。対象が、決定本文と却下代替で異なる。規定は、どちらも `transitions.md`「分割（多決定 ADR の部分上書き）」が持つ。

| 用語 | 定義 | 含むもの | 含まないもの |
|---|---|---|---|
| 逐語転記 | 分割で、生存決定を後継の `## Decision` へ写すこと。規定は `transitions.md` の分割の手順2 が持つ | — | 同じ結論の再記述 |
| 却下代替の持ち越し | 分割で、担当決定の却下代替を後継の本文へ運ぶこと。規定は `transitions.md` の分割の「却下代替の持ち越し」が持つ | — | — |

- 生存決定を後継へ移す行為を指して、「逐語 restate」「restate」「救出」「re-home」とは言わず、「逐語転記」と言う。移した結果を言うときは「逐語転記された」と言う。ただし `transitions.md` の取り消しの射程の規定は、「逐語の restate」と「同じ結論の再記述」を並べて、後継が旧 ADR の決定を写している場合を指す。再記述は逐語転記ではなく、この規定が並べる別の事象である。

### 識別子・full slug

| 用語 | 定義 | 含むもの | 含まないもの |
|---|---|---|---|
| 識別子 | `ADR-YYYYMMDDHHMM-NN`。時刻部（`YYYYMMDDHHMM`）と連番部（`NN`）からなり、ファイル名・H1・index が ADR を同定する鍵である | ファイル名と H1 に現れる、同じ形の文字列。時刻部・連番部を持たない旧ファイル名形式では、先頭の `ADR-<数字>[-<数字>]` を識別子と読む（「識別子の一意性」の判定が使う読み方） | `<slug>` |
| full slug | `ADR-YYYYMMDDHHMM-NN-<slug>`。ファイル名から `.md` を除いた文字列である。相互参照が保持する値である | `superseded-by`・`Supersedes:`・`Superseded by:`・`Related:` に書く値 | 識別子だけの略記。参照先として解決されない |

- 「番号部」「stem」は使わない。前者は「識別子」、後者は「full slug」と言う。
- 「識別子部」は、識別子の置かれた場所を限って言うときに限り使ってよい（「H1 の識別子部」「ファイル名の識別子部」）。値としては識別子と同じである。

### 凍結の射程

| 用語 | 定義 | 含むもの | 含まないもの |
|---|---|---|---|
| 凍結 | 退役 ADR に対し、決定内容の編集を認めない原則。射程は `edit-decision.md` が持つ | 決定内容の編集 | 決定内容に触れない編集。どの編集が射程の外に在るかは `edit-decision.md` が定める |
| 決定内容 | `edit-decision.md` の判定基準の第1問または第2問が YES になる変化が触れる対象 | どの節に書かれているかを問わない。`## Decision`・`## Context`・`## Consequences` のどれに在っても同じである | `edit-decision.md` が些末とする編集 |
| 決定本文 | `## Decision` 節にあるトップレベル決定1件の文章 | 逐語転記と照合の対象 | `## Context`・`## Consequences` の記述 |
| 本文 | front-matter を除いた、ADR ファイルの内容 | H1 と全ての節 | front-matter |

- 凍結が止めるのは、本文の編集全体ではなく、決定内容の編集である。凍結の射程を言うときは「本文編集」と言わず、「決定内容の編集」と言う。

## 配置

- ADR は**対象ディレクトリ**配下にフラット構造で配置する。サブディレクトリは作らない
- 対象ディレクトリは、操作の呼び出しで明示されていればその値を用いる。明示がない場合は、導入先の設定の `adr-dir` の値とし、設定に無ければ既定の `docs/adr` とする。`adr-dir` と既定の `docs/adr` は、git のトップレベルからの相対パスとして読む（トップレベルを決められなければ、カレントディレクトリからの相対パス）
- 同梱スクリプトの第1引数で渡した対象ディレクトリは、`adr-dir` より優先する。スクリプトは `next-adr-id.sh` / `gen-adr-index.sh` / `lint-adr.sh` / `print-adr-config.sh` である。第1引数を省けば、カレントディレクトリから git のトップレベルを決めて `adr-dir` を読む
- commit 前ゲートは引数を取らず、`adr-dir`（無ければ `docs/adr`）を検査する。既定以外の配置を採る導入先は、`adr-dir` を設定すればゲートが働く。設定ファイルの置き場と `adr-dir` の書き方は、プラグインの README の「ADR ディレクトリの指定」節に従う

## 採番方式

ファイル名規則: `ADR-YYYYMMDDHHMM-NN-<slug>.md`

- `YYYYMMDDHHMM`: ADR の起票時刻（採番時刻＝起票時刻）を分粒度で表す。**作業者のローカル時刻**を用い、UTC 等へ変換しない（日付部の意味を起票日からずらさないため）
- `-NN`: 同一時刻部内の連番。`01` 始まりの2桁ゼロ埋めとし、同一時刻部1件目にも `-01` を付与する。ゼロ埋めするのは、ファイル名の `LC_ALL=C sort` による辞書順整列だけで起票順が再現されるようにするため（ゼロ埋めしないと10件目で `-10` が `-2` より前に照合される）。取りうる値は `01`〜`99` であり、上限に達したときの挙動は後掲「発番スクリプトの契約」が定める
- `<slug>`: 内容を表す短い文字列。**小文字の英数字**（`a`〜`z` / `0`〜`9`）をハイフン1個で区切って並べる。大文字・連続するハイフン・先頭または末尾のハイフンはいずれも不適合とする

時刻部・連番部の双方を常に必須とし、いずれかを省略した形は作らない。**時刻部が並行ブランチ間の一意性を担い、連番部が同一分内に起票されるバースト（多決定 ADR の分割で後継を同時に起票する場合など）の順序を担う**。バースト内の順序は決定クラスタ順であって時間順ではないため、時刻部だけでは順序づけられない。

**識別子**と **full slug** の定義は、前掲「用語集」の「識別子・full slug」が持つ。両者は別の値であり、相互参照が保持するのは full slug の方である。

**時刻の取得**: 実行時コンテキストは日付までしか持たず分粒度の時刻を含まないため、時刻部は同梱の発番スクリプト（`next-adr-id.sh`）から取得する。スキル側で `date` 等の外部コマンドを直接実行しない（許可するコマンドを同梱スクリプトに限る）。

同一時刻部の採番例:

| 同一時刻部の件数 | ファイル名 |
|---|---|
| 1件目 | `ADR-YYYYMMDDHHMM-01-<slug>.md` |
| 2件目 | `ADR-YYYYMMDDHHMM-02-<slug>.md` |
| 3件目 | `ADR-YYYYMMDDHHMM-03-<slug>.md` |

**ファイル名形式の是正手段**: 規則に適合しないファイル名を検出したら、規則に沿う名へリネームする。時刻部・連番部を持たない**旧ファイル名形式**からの移行は後掲「採番衝突時の解消手順」の遡及移行の規則に従う。リネームで識別子が変わる場合は、本文 H1・相互参照・index も追随させる。相互参照は `superseded-by` / `Supersedes:` / `Superseded by:` / `Related:` である。

### 採番衝突時の解消手順

発番は同梱スクリプトが担い、列挙の対象を**同一時刻部を持つ既存ファイルに限る**。

1. `SKILL.md`「手順の参照（各 references を直接参照）」節が示す実行形で発番スクリプト（`next-adr-id.sh`）を `<対象ディレクトリ>` に対して実行する
2. スクリプトはローカル時刻から時刻部を決め、`ADR-<時刻部>-*.md` に一致する既存ファイルの連番部から最大番号を特定して、最大番号 + 1 を2桁ゼロ埋めで発番する（同一時刻部の既存が無ければ `01`）
3. 出力された識別子に `-<slug>` を付してファイル名とする

**配置ディレクトリ全体・同日全体を列挙して最大番号 + 1 を取らない**。日単位で最大 + 1 を取る手順は、配置ディレクトリについて単一の直列化されたビューが存在することを前提とするため、並行するブランチがそれぞれ自分の base に対して正しく実行しても同一識別子を発番する。時刻部が異なれば連番は互いに独立し、ブランチ間の調整なしに一意性が保たれる。

既存 ADR を遡及的に新形式へ移行する場合、各 ADR の時刻部は git の初回コミット時刻から取る。時刻源は**現在のパスに対する初回追加コミット**の時刻を分粒度で採り、`--follow` は使わない（`--follow` の有無で結果が変わるファイルが実在し、うち一部は日付部まで変わるため、規則として一意に定める）。同一時刻部に複数の ADR が落ちる場合、連番部は**現行ファイル名の識別子の昇順**で `01` から振り直す。旧連番の絶対値は引き継がず、相対順序のみを引き継ぐ。移行の適用手段は本規約の対象外であり、移行を行う側が定める。

**発番スクリプトの契約**

`next-adr-id.sh` は次の3つの終了コードで結果を返す。呼び出し側はこの契約に従って分岐する。

| 終了コード | 発生条件 |
|---|---|
| `0` | 発番に成功した。識別子（`ADR-<時刻部>-<連番部>`）を stdout へ1行で出力する |
| `1` | 同一時刻部の既存の**最大連番**が `99` で、次の連番が `99` を超える。または時刻部が暦として妥当な12桁でない（環境変数で固定した場合を含む） |
| `2` | 対象ディレクトリが存在しない、または設定に誤りがある。いずれも発番しない |

終了コード `1` の上限判定は同一時刻部の**最大連番**で決まり、同一時刻部のファイル**件数**では決まらない。欠番があれば件数は 99 に満たなくても上限に達しうる。

## index の同期

コミット済みの `<対象ディレクトリ>/index.md` は、`gen-adr-index.sh` の出力と一致していなければならない。index は front-matter から機械生成する導出ビューであり人手編集しない（前掲「front-matter（状態の唯一の権威）」）。`index.md` の不在も不一致として扱う。

前掲「遷移の表」が定める `validity` を変える操作は、有効 ADR の集合を動かすため、操作のたびに再生成する。それ以外の操作は `validity` を変えないため、再生成を要さない。

**是正手段**: `transitions.md`「index の再生成・検証」の生成手順を実行して `index.md` を作り直す。index 側を手で編集して一致させない（次の生成で戻るため）。

## 識別子の一意性

同一の識別子を持つ ADR が対象ディレクトリに2本以上存在してはならない。識別子は、ファイル名・index・本文 H1 が ADR を同定する鍵である。相互参照が保持する full slug も識別子を先頭に含むため、重複すると参照が一意に解決しない。

**この重複は発番側では構造的に消せない残余である。** 時刻部が分粒度である以上、同一分に別ブランチで起票された2本は連番部だけで識別され、発番スクリプトが各ブランチの base に対してそれぞれ正しく実行しても同じ連番を返しうる。`transitions.md`「採番規則」が求める「複数の ADR を続けて起票する場合は1件ずつ発番する」（発番 → ファイル作成 → 次の発番の順に進める）は同一ブランチ内のバーストを防ぐが、ブランチをまたぐ重複には効かない。

一意性の判定は識別子の先頭一致（`ADR-<数字>[-<数字>]`）で行い、ファイル名形式への適合を前提としない。形式適合を前提にすると、旧ファイル名形式どうしの重複が判定の外へ落ちるためである。

**是正手段**: 片方を `next-adr-id.sh` で再発番してリネームし、本文 H1・相互参照（`superseded-by` / `Supersedes:` / `Superseded by:` / `Related:`）・index を追随させる。再発番する側は、当該識別子を指す既存の参照が少ないほうを選ぶ。

## H1 見出しの形式と識別子部の整合

本文の最初の見出し（H1）は `# ADR-YYYYMMDDHHMM-NN: <タイトル>` 形式にする。`gen-adr-index.sh` が `: ` 以降をタイトルとして抽出するためである。

**H1 の識別子部はファイル名の識別子部と一致しなければならない。** H1 に識別子が現れない場合（見出しを持たない場合を含む）も不整合とする。照合は識別子に限り、slug の一致は要求しない。識別子だけの形（`# ADR-…-01: タイトル`）と slug を含む形（`# ADR-…-01-slug: タイトル`）はいずれも合法である。

整合を規約として要求するのは、`gen-adr-index.sh` が H1 の `: ` 以降しか読まないためである。識別子が陳腐化しても生成物には現れず、index の同期では捕まらない。

**是正手段**: H1 見出しの識別子部をファイル名の識別子部へ揃える。リネームで識別子を変えた場合は H1 も同じ操作で追随させる。

## 検査項目と正本の対応

同梱の drift-lint（`lint-adr.sh`）が実装する検査は次の7項目である。ある検査項目が報告する規範を直すときは、当該項目の正本文書だけを直す。是正手段は各正本の側に置き、本表には持たせない（本表が第二の正本になるのを避けるため）。

| 検査項目 | 正本 |
|---|---|
| レイヤ1 front-matter スキーマ | `references/adr-model.md`「状態の型」 |
| レイヤ2 index 同期 | `references/adr-model.md`「index の同期」 |
| レイヤ3 相互参照双方向性 | `references/transitions.md`「上書き（上書き済み・双方向相互参照）」 |
| レイヤ4 `Related:` 参照の生存性・実在性 | `references/cross-references.md`「機械検査の範囲」 |
| レイヤ5 ファイル名形式 | `references/adr-model.md`「採番方式」 |
| レイヤ5 識別子重複 | `references/adr-model.md`「識別子の一意性」 |
| レイヤ5 H1 整合 | `references/adr-model.md`「H1 見出しの形式と識別子部の整合」 |

**検査対象集合**: drift-lint の検査対象は、対象ディレクトリ配下の `ADR-*.md` 全件である。front-matter を持たない ADR（先頭行が `---` でないもの。本文の `## Status` 節で状態を書く形式を含む）は、レイヤ1 が front-matter 欠落として報告する。front-matter を持たない ADR は状態を読めず、index にも載らない。違反に数えないと、スキーマ検証も index も commit 前ゲートも通らないまま統治の外へ置かれるためである。レイヤ1 の残りの違反種別と、front-matter を起点とする検査（レイヤ3 の順方向・レイヤ5）は、front-matter を持つ ADR だけを対象にする。front-matter 欠落の ADR をファイル名や H1 の違反として重ねて報告しない。本文を起点とする検査（レイヤ3 の逆方向・レイヤ4）は全件を走査する。レイヤ4 は有効な ADR だけを起点にするため、front-matter 欠落の ADR からは発火しない。レイヤ3 の逆方向は、front-matter 欠落の ADR の本文にある `Supersedes:` からも発火する。参照先の front-matter が宣言元を指していないという、front-matter 欠落とは別の欠陥だからである。

改行コードが CRLF の ADR は、先頭行が `---` と一致しないため、front-matter 欠落として報告する。このときは、改行コードを名指しするメッセージを出す。

front-matter 欠落の ADR は、ファイル名形式の違反とは別に扱う。front-matter は持つが時刻部・連番部を持たない**旧ファイル名形式**（前掲「採番方式」）は、レイヤ5 が報告する。

**是正手段**（front-matter 欠落）: 前掲「front-matter（状態の唯一の権威）」の形式で front-matter を付け、本文の `## Status` 節を除く。状態の値は、当該 ADR がどの遷移を終えたかに応じて「状態の型」の構成子から選ぶ。付けた後は index を再生成する（`validity` が `validity-active` の値の ADR は index に載るため）。
