# ADR の状態モデルと識別子規約（adr-model.md）

ADR の状態（承認軸・有効性軸）の値域と各値の定義、合法な front-matter を表す状態の型、ファイルの配置と採番方式を定める。本ファイルがこれらの規約の実体であり、状態語彙・採番規則をここ以外で独自に再定義しない。

## 状態の2軸

状態は**承認軸**と**有効性軸**に分離して管理する。1つの状態欄に混在させると、「承認された歴史事実」と「現在効力を持つか」という性質の異なる2つの情報が互いを上書きしてしまうためである。値は日本語のユビキタス言語で確定する。

### 承認軸（`status`・不変の履歴事実）

| 値 | 定義 |
|---|---|
| `提案中` | 起案され、承認者の判断を待っている状態 |
| `承認済み` | 承認された履歴事実。以後不変 |
| `却下` | 提案が承認に至らず終了。一度も運用されない終端 |

### 有効性軸（`validity`・可変の現在の効力）

| 値 | 定義 |
|---|---|
| `有効` | 現在運用中 |
| `上書き済み` | 後継 ADR に置き換えられた（`superseded-by` に後継の full slug を保持） |
| `廃止済み` | 後継 ADR なしで ADR としての効力を終えた。決定そのものを放棄した場合と、記録の正本が ADR 外の資産へ移った場合の両方を含む。いずれの場合も、この ADR を現在の効力の判断材料にしない |

### 軸の関係

- `却下`（承認軸・一度も承認されなかった終端）と `上書き済み` / `廃止済み`（有効性軸・承認後に ADR としての効力を失った状態）は別語である。2軸が語彙レベルで衝突しないよう、両者を混同して扱わない
- `提案中` をスキップして直接 `承認済み` に到達する経路は持たない。即承認のケースは「提案 → 承認」を連続実行として扱う

## front-matter（状態の唯一の権威）

状態系は各 ADR ファイル冒頭の front-matter に置く。キーは英語（構造的フィールド名）、値は上記の日本語ユビキタス言語とする。

```yaml
---
status: <提案中 | 承認済み | 却下>
validity: <有効 | 上書き済み | 廃止済み | （空）>
superseded-by: <後継ADRの full slug | （空）>
---
```

- front-matter が状態の唯一の権威である。**本文に `## Status` 節を置かない**。新規起票時も、承認・上書き・廃止・却下のいずれの遷移時も同様である。本文へ状態を書き足すことは重複を生むだけで、以後の遷移で取り残される drift 源になる
- 「キー省略」と「キーあり値空」は同じ「空」として扱う。空にする軸は値を空にする（キー行自体は残してよい）
- 有効 ADR の一覧（index）は front-matter から機械生成する導出ビューであり、人手編集しない。これにより「本文を読めば確実（確実性）」と「一覧で探せる（検索性）」を drift させずに両立する

## 状態の型

front-matter は次の直和型のシリアライズ形式である。合法な状態はこの5構成子に尽き、各構成子が `status` / `validity` / `superseded-by` の組み合わせを一意に決める。遷移後の front-matter は必ずいずれかの構成子として構成できる形にする。

```
ADRState =
  | 提案中                               -- status=提案中,   validity=（空）,     superseded-by=（空）
  | 却下                                 -- status=却下,     validity=（空）,     superseded-by=（空）
  | 有効                                 -- status=承認済み, validity=有効,       superseded-by=（空）
  | 上書き済み of NonEmptyList<FullSlug>  -- status=承認済み, validity=上書き済み, superseded-by=後継の full slug 列
  | 廃止済み                             -- status=承認済み, validity=廃止済み,   superseded-by=（空）
```

各遷移は構成子への移動である。起票 → `提案中`、承認 → `有効`、上書き → `上書き済み`、廃止 → `廃止済み`、却下 → `却下`。分割（1→N の部分上書き）も原 ADR を `上書き済み` へ移す点で上書きと同じ構成子に着地する。

型が課す制約:

- **制約1**: すべての構成子が `status` の値を伴う。`status` が空の状態はどの構成子としても構成できない
- **制約2**: `status=承認済み` を伴うのは `有効` / `上書き済み` / `廃止済み` の3構成子だけであり、いずれも `validity` の値を伴う。上書き・廃止で `status` を変更しないのはこの制約による（承認は歴史事実であり不変）
- **制約3**: `validity` を伴わないのは `提案中` / `却下` の2構成子だけである。承認前・却下の状態に現在の効力は定義されない
- **制約4**: `superseded-by` を伴えるのは `上書き済み` だけである。他の4構成子は当該フィールドを持たず、値を伴う形では構成できない
- **制約5**: `上書き済み` が保持する後継は**非空**リストである。後継を持たない `上書き済み` は構成できない
- **制約6**: `status` / `validity` の値は各軸の値域に限る。値域の外の語はどの構成子にも当たらない

### 型の制約と機械検査の対応

同梱の drift-lint がレイヤ1（front-matter スキーマ検証）で数える違反種別は、いずれも上の型が排除する状態に当たる。違反種別と、当該状態を排除する型の制約の対応は次のとおりであり、対応の付かない違反種別は0件である。

| 違反種別 | 排除する制約 |
|---|---|
| `status` 欠落（空） | 制約1 |
| `status=承認済み` かつ `validity` 欠落（空） | 制約2 |
| `validity=上書き済み` かつ `superseded-by` 欠落（空） | 制約5 |
| `status` の値が語彙外 | 制約6 |
| `validity` の値が語彙外（空は合法） | 制約6 |
| `status=提案中` または `却下` かつ `validity` が非空 | 制約3 |
| `status=提案中` または `却下` かつ `superseded-by` が非空 | 制約4 |
| `validity=有効` または `廃止済み` かつ `superseded-by` が非空 | 制約4 |

**逆向きは成り立たない。** 型として構成できない状態のすべてをレイヤ1 が報告するわけではない。レイヤ1 が見るのは各欄が空か否かと値が値域内かであり、欄が非空で値域も踏むが制約を満たさない病的値は素通りする。既知の経路は制約5 で、`superseded-by` が区切り文字・空白のみで有効な参照先 stem を1件も含まない値（`superseded-by: ,` 等）は raw 文字列として非空であるためレイヤ1 の空判定を通過し、レイヤ3（相互参照双方向性）が報告する。この経路の是正手段は `transitions.md`「上書き（上書き済み・双方向相互参照）」が持つ。

**是正手段**: レイヤ1 違反は front-matter を直して解消する。報告された違反種別に対応する制約を上表で引き、当該制約を満たす構成子の値組（前掲の型定義の注記）へ `status` / `validity` / `superseded-by` を揃える。どの構成子へ揃えるかは、当該 ADR がどの遷移を終えた状態かで決まる。値を空にする場合はキー行を残して値だけを空にしてよい。

補足:

- 後継は単一を既定とするが、1本の ADR が複数の後継へ分割される場合はリスト値（カンマ区切り）を取りうる。この 1→N のケースでは、`上書き済み` の原 ADR が全後継を列挙し、各後継が本文の関連 ADR 節に逆参照を持つ（双方向で照合される）
- 後継 ADR は full slug の参照のみで保持し、実体への直接参照は持たない（自己参照・循環参照の構造的不整合を防ぐ）

## 配置

- ADR は**対象ディレクトリ**配下にフラット構造で配置する。サブディレクトリは作らない
- 対象ディレクトリは、操作の呼び出しで明示されていればその値を用いる。明示がない場合の対象は既定の `docs/adr` とする
- 既定の上書きは同梱スクリプト（`next-adr-id.sh` / `gen-adr-index.sh` / `lint-adr.sh`）の第1引数で行う。現時点ではこれが唯一の上書き経路である
- commit 前ゲートの検査対象は現時点では既定の配置に固定されており、既定以外の配置を採る導入先ではゲートが働かない（commit は検査されずに通る）

## 採番方式

ファイル名規則: `ADR-YYYYMMDDHHMM-NN-<slug>.md`

- `YYYYMMDDHHMM`: ADR の起票時刻（採番時刻＝起票時刻）を分粒度で表す。**作業者のローカル時刻**を用い、UTC 等へ変換しない（日付部の意味を起票日からずらさないため）
- `-NN`: 同一時刻部内の連番。`01` 始まりの2桁ゼロ埋めとし、同一時刻部1件目にも `-01` を付与する。ゼロ埋めするのは、ファイル名の `LC_ALL=C sort` による辞書順整列だけで起票順が再現されるようにするため（ゼロ埋めしないと10件目で `-10` が `-2` より前に照合される）。取りうる値は `01`〜`99` であり、上限に達したときの挙動は後掲「発番スクリプトの契約」が定める
- `<slug>`: 内容を表す短い文字列。**小文字の英数字**（`a`〜`z` / `0`〜`9`）をハイフン1個で区切って並べる。大文字・連続するハイフン・先頭または末尾のハイフンはいずれも不適合とする

時刻部・連番部の双方を常に必須とし、いずれかを省略した形は作らない。**時刻部が並行ブランチ間の一意性を担い、連番部が同一分内に起票されるバースト（多決定 ADR の分割で後継を同時に起票する場合など）の順序を担う**。バースト内の順序は決定クラスタ順であって時間順ではないため、時刻部だけでは順序づけられない。

**識別子**は番号部（`ADR-YYYYMMDDHHMM-NN`）を指し、**full slug**（ファイル名から `.md` を除いた文字列＝`ADR-YYYYMMDDHHMM-NN-<slug>`）とは区別する。両者は別の値であり、相互参照が保持するのは full slug の方である。

**時刻の取得**: 実行時コンテキストは日付までしか持たず分粒度の時刻を含まないため、時刻部は同梱の発番スクリプト `${CLAUDE_SKILL_DIR}/../../scripts/next-adr-id.sh` から取得する。スキル側で `date` 等の外部コマンドを直接実行しない（許可するコマンドを同梱スクリプトに限る）。

同一時刻部の採番例:

| 同一時刻部の件数 | ファイル名 |
|---|---|
| 1件目 | `ADR-YYYYMMDDHHMM-01-<slug>.md` |
| 2件目 | `ADR-YYYYMMDDHHMM-02-<slug>.md` |
| 3件目 | `ADR-YYYYMMDDHHMM-03-<slug>.md` |

**ファイル名形式の是正手段**: 規則に適合しないファイル名を検出したら、規則に沿う名へリネームする。時刻部・連番部を持たない**旧ファイル名形式**からの移行は後掲「採番衝突時の解消手順」の遡及移行の規則に従う。リネームで識別子部が変わる場合は、本文 H1・相互参照（`superseded-by` / `Supersedes:` / `Superseded by:` / `Related:`）・index も追随させる。

### 採番衝突時の解消手順

発番は同梱スクリプトが担い、列挙の対象を**同一時刻部を持つ既存ファイルに限る**。

1. `bash ${CLAUDE_SKILL_DIR}/../../scripts/next-adr-id.sh <対象ディレクトリ>` を実行する
2. スクリプトはローカル時刻から時刻部を決め、`ADR-<時刻部>-*.md` に一致する既存ファイルの連番部から最大番号を特定して、最大番号 + 1 を2桁ゼロ埋めで発番する（同一時刻部の既存が無ければ `01`）
3. 出力された識別子に `-<slug>` を付してファイル名とする

**配置ディレクトリ全体・同日全体を列挙して最大番号 + 1 を取らない**。日単位で最大 + 1 を取る手順は、配置ディレクトリについて単一の直列化されたビューが存在することを前提とするため、並行するブランチがそれぞれ自分の base に対して正しく実行しても同一識別子を発番する。時刻部が異なれば連番は互いに独立し、ブランチ間の調整なしに一意性が保たれる。

既存 ADR を遡及的に新形式へ移行する場合、各 ADR の時刻部は git の初回コミット時刻から取る。時刻源は**現在のパスに対する初回追加コミット**の時刻を分粒度で採り、`--follow` は使わない（`--follow` の有無で結果が変わるファイルが実在し、うち一部は日付部まで変わるため、規則として一意に定める）。同一時刻部に複数の ADR が落ちる場合、連番部は**現行ファイル名の識別子の昇順**で `01` から振り直す。旧連番の絶対値は引き継がず、相対順序のみを引き継ぐ。移行の適用手段は本規約の対象外であり、移行を行う側が定める。

**発番スクリプトの契約**

`next-adr-id.sh` は次の3つの終了コードで結果を返す。呼び出し側はこの契約に従って分岐する。

| 終了コード | 発生条件 |
|---|---|
| `0` | 発番に成功した。識別子（`ADR-<時刻部>-<連番部>`）を stdout へ1行で出力する |
| `1` | 同一時刻部の既存の**最大連番**が `99` で、次の連番が `99` を超える。または時刻部が暦として妥当な12桁でない（環境変数で固定した場合を含む） |
| `2` | 対象ディレクトリが存在しない |

終了コード `1` の上限判定は同一時刻部の**最大連番**で決まり、同一時刻部のファイル**件数**では決まらない。欠番があれば件数は 99 に満たなくても上限に達しうる。

## index の同期

コミット済みの `<対象ディレクトリ>/index.md` は、`gen-adr-index.sh` の出力と一致していなければならない。index は front-matter から機械生成する導出ビューであり人手編集しない（前掲「front-matter（状態の唯一の権威）」）。`index.md` の不在も不一致として扱う。

`validity` を変える遷移（承認・上書き・分割・廃止）は有効 ADR の集合を動かすため、遷移のたびに再生成する。起票・却下は `validity` を変えないため再生成を要さない。

**是正手段**: `transitions.md`「index の再生成・検証」の生成手順を実行して `index.md` を作り直す。index 側を手で編集して一致させない（次の生成で戻るため）。

## 識別子の一意性

同一の識別子部（`ADR-YYYYMMDDHHMM-NN`）を持つ ADR が対象ディレクトリに2本以上存在してはならない。識別子は相互参照・index・本文 H1 が ADR を同定する鍵であり、重複すると参照が一意に解決しない。

**この重複は発番側では構造的に消せない残余である。** 時刻部が分粒度である以上、同一分に別ブランチで起票された2本は連番部だけで識別され、発番スクリプトが各ブランチの base に対してそれぞれ正しく実行しても同じ連番を返しうる。`transitions.md`「採番規則」が求める「複数の ADR を続けて起票する場合は1件ずつ発番する」（発番 → ファイル作成 → 次の発番の順に進める）は同一ブランチ内のバーストを防ぐが、ブランチをまたぐ重複には効かない。

一意性の判定は識別子部の先頭一致（`ADR-<数字>[-<数字>]`）で行い、ファイル名形式への適合を前提としない。形式適合を前提にすると、旧ファイル名形式どうしの重複が判定の外へ落ちるためである。

**是正手段**: 片方を `next-adr-id.sh` で再発番してリネームし、本文 H1・相互参照（`superseded-by` / `Supersedes:` / `Superseded by:` / `Related:`）・index を追随させる。再発番する側は、当該識別子を指す既存の参照が少ないほうを選ぶ。

## H1 見出しの形式と識別子部の整合

本文の最初の見出し（H1）は `# ADR-YYYYMMDDHHMM-NN: <タイトル>` 形式にする。`gen-adr-index.sh` が `: ` 以降をタイトルとして抽出するためである。

**H1 の識別子部はファイル名の識別子部と一致しなければならない。** H1 に識別子が現れない場合（見出しを持たない場合を含む）も不整合とする。照合は識別子部に限り slug の一致は要求しない — 識別子部のみの形（`# ADR-…-01: タイトル`）と slug を含む形（`# ADR-…-01-slug: タイトル`）はいずれも合法である。

整合を規約として要求するのは、`gen-adr-index.sh` が H1 の `: ` 以降しか読まないためである。識別子部が陳腐化しても生成物には現れず、index の同期では捕まらない。

**是正手段**: H1 見出しの識別子部をファイル名の識別子部へ揃える。リネームで識別子を変えた場合は H1 も同じ操作で追随させる。

## 検査項目と正本の対応

同梱の drift-lint（`lint-adr.sh`）が実装する検査は次の7項目である。ある検査項目が報告する規範を直すときは、当該項目の正本文書だけを直す。是正手段は各正本の側に置き、本表には持たせない（本表が第二の正本になるのを避けるため）。

| 検査項目 | 正本 |
|---|---|
| レイヤ1 front-matter スキーマ | `references/adr-model.md`「状態の型」 |
| レイヤ2 index 同期 | `references/adr-model.md`「index の同期」 |
| レイヤ3 相互参照双方向性 | `references/transitions.md`「上書き（上書き済み・双方向相互参照）」 |
| レイヤ4 `Related:` 参照の生存性・実在性 | `references/cross-references.md`「機械検査の範囲」 |
| レイヤ5 ファイル名形式 | `references/adr-model.md`「採番方式」 |
| レイヤ5 識別子重複 | `references/adr-model.md`「識別子の一意性」 |
| レイヤ5 H1 整合 | `references/adr-model.md`「H1 見出しの形式と識別子部の整合」 |

**検査対象集合**: レイヤ1 とレイヤ5 は front-matter を持つ ADR のみを対象とする。front-matter を持たない ADR はファイル名も旧規約のままであり、検査対象に含めない。この集合は、front-matter は持つが時刻部・連番部を持たない**旧ファイル名形式**（前掲「採番方式」）とは別であり、front-matter 導入前の世代を指す。
