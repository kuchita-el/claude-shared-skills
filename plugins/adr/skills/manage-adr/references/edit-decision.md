# 編集判定フローリファレンス（edit-decision.md）

`validity: 有効` な既存 ADR への変更を、core／非core／些末 のいずれかに分類し、選ぶ操作へ分岐する。分類の判定基準（decision tree）と3段構え編集機構の対応は本ファイルが実体を持ち、スキル内の編集判定はすべて本ファイルの記述に従う。

本ファイルは「どの操作を選ぶか」の**分岐判定のみ**を担う。例外として、参照面全体に掛かる後掲「参照の深さ」の規定も本ファイルが正本を持つ。選んだ操作の front-matter 写入手順・採番・相互参照の書き方は本ファイルには置かず、SKILL.md 本体が遷移手順を一元的に参照する。ADR 本文へ参照を書く／直す編集の判定（記録の参照原則）は `adr-reference-principle.md` が実体を持ち、本ファイルでは扱わない。本ファイルから他の参照ファイルを指す場合は、正本のファイル名を直接書いて指す。

**参照の深さ**: `manage-adr` の参照面（SKILL.md と `references/`）では、参照の深さを2段（SKILL.md → 参照ファイル → 正本）までとする。上限と段の数え方の正本は本段落である。

- 段は、担い手が1つの事項に答え終えるまでに、SKILL.md から順に開く参照ファイルで数える。答える事項とは、開いたファイルが冒頭で定めると述べた事項である（判定なら結論、手順なら手順の完了）
- 参照ファイル A が別の参照ファイル B を指す箇所を1段に数えるのは、A の事項に答えるのに B の内容を読む必要がある場合に限る
- 次の箇所は段に数えない。A の答えが出た後の行き先として B を示す箇所、B が持つ事項を A では扱わないと断る箇所、A の記述の出典として B を挙げる箇所である。B での作業は別の事項であり、SKILL.md から数え直す
- 指し方は段数を変えない。ファイル名を書いても、SKILL.md が指す規約として書いても同じに数える。SKILL.md 本文の節を指す箇所は起点へ戻るだけであり、段に数えない
- 2段目に開いた参照ファイルは、その事項に答えるために、さらに別の参照ファイルを読ませない

最短経路では数えない。SKILL.md 末尾の一覧は全参照ファイルを直接指すため、最短経路ではどの参照ファイルも1段になり、上限が何も制約しなくなる。ファイル名が現れる箇所をすべて段に数える方式も採らない。担い手が開かない行き先や断り書きまで連鎖に入り、正本を一意に保つための指し示しを上限が禁じてしまうためである。

## 前提: 分類はスキルが自動判定しない

分類（core／非core／些末）は**必ず利用者へ問う**。スキルが本文の変更内容から自動で core/非core を決めない。安全則「迷ったら core 寄り」に従い、既定選択肢を core とする。

`上書き済み`／`廃止済み` に退役した ADR は凍結された歴史的成果物であり、本フローの対象外である。**この凍結原則の射程は決定内容の編集である。** front-matter（状態）にも `## Decision`（内容）にも触れず、状態の重複表示を消すだけの是正は、決定の記録を書き換えないため射程外であり、退役 ADR に対しても実施してよい。除去しようとする表示が固有の情報を持つ場合、それを `## 関連ADR` へ移してから除去する操作（＝移設。除去の直前に重複を作る）も、情報の総体が保存され決定の記録が変わらない限り同じく射程外である。逆に、決定内容に触れる編集は退役 ADR に加えてはならない。以下の判定フロー（core／非core／些末 の3段構え）は `有効` な ADR への決定内容の編集を振り分けるものであり、退役 ADR には適用しない（退役 ADR の決定本文は、非core と判定できたとしても編集しない）。

## 判定基準（decision tree・境界アンカー＝「再承認が要るか」）

第0問は分類の前段であり、対象 ADR を編集する変更かどうかを確かめる。第1問・第2問が分類である。

0. その変更が決める事項は、対象 ADR が扱っている枠組みの中にあるか？ 判定の入力は対象 ADR の `## Decision` 本文である。そこにある決定を1つずつ見て、次のどちらかに当たる決定 D を名指しできるかを問う。判定の単位は `## Decision` にある決定であり、変更が決める事項を決定より細かく切り出して、その事項だけを扱う決定を探すのではない
   - (a) 変更が決める事項について、D が結論を与えている。判定は後掲のとおり字面の存否ではなく結論の有無で行う。結論を与えているか迷う場合は、名指しできたものとする（後掲「既知の限界」と同じ向き）
   - (b) 変更を「D の結論を保ったまま、D の適用範囲・条件・パラメータ値・理由付けのいずれかを変える、または新しく加える」と言い表せる。適用先を1つ足す変更もこれに当たる。言い表せるか迷う場合は、名指しできないものとする
   - **NO**（(a)(b) のどちらも名指しできない）→ 対象 ADR が扱っていない枠組みを立てる変更であり、対象 ADR の編集ではない。分類せず、後掲「先行 ADR が決めていない facet を後継が決める場合」の規定に従う（新規 ADR を起こし、対象 ADR は無編集）。本フローの手前で非core 改訂の側へ振り分けられていても、この帰結は変わらない
   - **YES（(a) を名指しできる）** → 1 へ
   - **YES（(b) だけを名指しできる）** → 当該事項を対象 ADR への改訂として扱う経路なら 1 へ。別の ADR として記録する経路なら、後掲の規定に従い分類しない。どちらの経路を採るかは本フローの手前で決まる
1. その編集で「決定の結論・方向・前提」が変わるか？
   - **YES**（結論の反転・前提の失効・後継への置換）→ **core**（再承認が要る）
   - NO → 2 へ
2. 決定内容に触れるか？（パラメータ値・適用範囲・条件・理由付け）
   - **YES**（骨子は保つが決定関連情報を更新）→ **非core**（既承認の枠内）
   - **NO**（typo・整形・リンク・語句・体裁のみ、決定内容ゼロ）→ **些末**

**先行 ADR が決めていない facet を後継が決める場合**: 先行 ADR の `## Decision` が当該 facet について**結論を与えていない**なら、後継がそれを決めても先行の結論・方向・前提は変わらない。先行 ADR は `上書き済み` へ退役させず、**無編集**・`validity` 不変とする。記録が要るなら後継側の `## 関連ADR` に `Related:` で書く。後に不要と判断された場合も先行は編集しない。

**判定は字面の存否ではなく結論の有無で行う。** facet の語が `## Decision` に現れることは、そこで結論が与えられたことを意味しない。`## Decision` の中に「本 ADR では〜を決めていない」旨の射程の注記が置かれている場合、当該 facet について結論は与えられておらず、射程外である。射程の限定はそれが効く箇所の散文として書かれ、特定の決定に掛かるものは当該決定の本文＝`## Decision` の中に置かれるため、字面の存否で判定すると、射程を明示した ADR ほど誤って退役側へ倒れる。

**本規定が掛かる範囲**: 第0問が本規定へ振り分けた場合に限る。第0問が第1問へ進めた場合は本規定の対象外であり、第1問・第2問で通常どおり分類する。

非core 改訂の経路を選んでいても、第0問が NO なら本規定が掛かる。経路を選ぶ段階で、対象 ADR が扱っていない枠組みを「枠組みの中に収まる」と読み違えることがあるためである。読み違えたまま分類へ進むと、第1問は対象 ADR の結論が変わらないため NO、第2問は YES となって非core が確定する。本来独立に記録すべき決定が、再承認を経ずに既存 ADR への面の追加として埋もれる。第0問はその読み違えを、経路の選択に依らず対象 ADR の `## Decision` 本文で問い直す。

このケースでは**先行 ADR への編集そのものが発生しない**ため、本フローの3分類（core／非core／些末）はいずれも当たらない。3分類はどれも対象 ADR に何らかの編集を加えることを帰結とし、非core・些末も直接編集を指示するため、「非core だから安全」と読むと先行 ADR を編集してしまう。本ケースは分類する対象を持たず、分類フローの外側にある。

**この規定を置く理由**: 先行が「決めなかった」ことを明示的に記録する仕組みは持たない（意図的な非決定を第一級セクションで記録する方式は、解決時のさかのぼり更新義務が drift を生み、退役後は凍結原則で更新もできないため採らない）。明示の記録が無い以上、判別を後掲の安全則へ委ねる案も採りうるが、既定が core であるため、先行が決めていなかった facet を後継が決めるたびに先行が退役し、決定の記録が index から失われる。判別材料を先行の `## Decision` 本文へ置けば走査面が閉じ、安全則へ到達する前に振り分けられる。

**既知の限界**: 結論の有無の判定はテキストの解釈に委ねられ、機械検査は存在しない。先行の `## Decision` が当該 facet を射程内に収めて結論を与えていると読めるなら、第0問の (a) として第1問へ進み、そこから先は安全則が働く。

**安全則: 判定に迷ったら core 寄り（新規 ADR）に倒す。** 根拠は、誤判定が記録に残すものの非対称にある。

- **core を非core と誤判定した場合**: 再承認を経ていない core 変更が、既承認の枠内の改訂として権威記録に残る。記録の上では正当な非core 改訂と見分けがつかず、後から検出する手掛かりも残らない
- **非core を core と誤判定した場合**: 後継の承認前なら、後継を却下（`transitions.md`「却下（却下）」）し、分類を問い直して非core の直接編集へ切り替えられる。旧 ADR は後継の承認まで上書きされないため、この時点では無傷である。承認と上書きを終えた後も、記録は失われない。旧 ADR は `superseded-by` から辿れ、後継は非core 改訂と同じ内容を持つ。誤判定の痕跡は記録の上に残り、後から見つけられる

安全則は、複数の ADR を1本へまとめる操作を前提にしない。

## AskUserQuestion の問い設計

編集操作を起動したら、`AskUserQuestion` で変更種別を問う。

- **質問**: 「この編集は core／非core／些末 のどれか？（迷う場合は core を選ぶ）」
- **選択肢（既定を先頭・core）**:
  1. **core（既定・推奨）** — 決定の結論・方向・前提が変わる。再承認が要る。
  2. **非core** — 骨子は保つが決定内容（パラメータ・適用範囲・条件・理由）を更新する。
  3. **些末** — typo・整形・リンク・語句・体裁のみで決定内容はゼロ。
- 既定（先頭）を core とし、安全則「迷ったら core」を選択肢説明に明示する。

**問う前に前段の識別を適用する**: 第0問が前掲「先行 ADR が決めていない facet を後継が決める場合」の規定へ振り分けた場合は、**この問いを立てない**。先行 ADR への編集が発生せず、分類する対象が無いためである。既定が core であるこの問いへ掛けると、決めていなかった facet を決めただけで先行 ADR が退役させられる。3分類のいずれかへ振り分けることもしない（非core・些末はいずれも先行 ADR の直接編集を指示するため）。

## 3段構え編集機構の対応表

分類ごとに、選ぶ操作と変更履歴を残す先が決まる。

| 変更の性質 | 対応 | 変更履歴の在り処 |
|---|---|---|
| **core**（再承認が要る。決定の結論・方向・前提が変わる） | 新規 ADR 起票操作 ＋ 旧 ADR 上書き操作（5遷移の起票＋上書きを実行し、旧 ADR の有効性を `上書き済み` にする） | 別 ADR ファイル＋双方向相互参照 |
| **非core**（骨子は保つが決定に関わる情報を更新: パラメータ値・適用範囲・条件・理由付け） | 直接編集 ＋ 本文 `## 変更履歴` に1行追記（front-matter の `status`／`validity` は不変） | ファイル内 `## 変更履歴` |
| **些末**（typo・整形・リンク修正・語句・体裁のみ、決定内容ゼロ） | 直接編集のみ（front-matter・`## 変更履歴` は変更しない） | git のみ |

**原則: ADR ファイルは、あらゆる consumption 面（Wiki・Confluence・artifact・抽出ファイル）に対して自己完結する。** git は repo の実装詳細であり、決定関連情報の SSoT にはしない。3段構えのうち履歴を git のみに委ねてよいのが些末に限られるのは、この原則による（些末は決定関連情報を含まないため、git の外に痕跡が残らなくても自己完結性が損なわれない）。

## 分類ごとの補足

- **core**: 起票（`status: 提案中`）と上書き（旧 `validity: 上書き済み`＋後継への双方向相互参照）の2操作を選ぶ。各操作の写入手順は SKILL.md 本体が一元的に参照する遷移手順にあるため、本ファイルでは手順を繰り返さない。旧 ADR が多決定で生存決定が残る場合（1→N の部分上書き＝分割）の実行手順も、同じ遷移手順に収録済みである。分割は core／非core／些末 に続く第4の分類ではない。本ファイルが分類するのは決定内容の編集であり、分割は決定のファイル間再配置という別軸の構造操作として5遷移表の外に位置づけられている。core と判定した編集は旧 ADR の上書きを伴うが、旧 ADR が多決定で生存決定が残る場合は上書き（1→1）ではなく分割（1→N）を経由する。この経路の選択は分類の後に遷移手順側で決まる。
- **非core**: 対象 ADR 本文を直接編集し、本文 `## 変更履歴` に変更内容の1行を追記する。front-matter（`status`／`validity`／`superseded-by`）は変更しない。**節を持たない ADR で `## 変更履歴` を新設する場合の配置**は、SKILL.md が指す雛形の配置規約に従う（配置規約の実体は雛形にあり、本ファイルでは繰り返さない）。
- **些末**: 対象 ADR 本文のみを直接編集する。front-matter・`## 変更履歴` はいずれも変更しない（変更の履歴は git のコミットのみが持つ）。

非core と些末の差は `## 変更履歴` の追記有無にある（非core＝1行追記あり、些末＝追記なし）。

**参照の付け替えの判別例**: 退役した ADR を指していた有効 ADR 側の参照を直す編集は、退役のたびに生じる。第2問（決定内容に触れるか）で次のとおり振り分ける。

- **些末**: 識別子・決定番号だけを付け替える編集。指している規則は同一で置き場所だけが変わるため、リンク修正に当たる。注釈の中の決定番号を後継の採番へ揃える編集もこれに当たる
- **非core**: 記述内容に踏み込む編集。現在形の記述を時点固定へ改める、陳腐化した記述を書き替える、名指しした決定が反転した事実を注釈へ反映する、の3つが当たる。決定に関わる記述（理由付け・帰結の記述）の内容が更新されるためである。ただし反映の結果、参照元 ADR 自身の結論・方向・前提が変わるなら、第1問が YES であり core である

分類は前掲の前提どおり利用者へ問う。上の例は問いに答える材料であり、自動判定の規則ではない。
