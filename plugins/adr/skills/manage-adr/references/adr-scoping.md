# ADR 化要否の判断基準（adr-scoping.md）

ある決定を ADR として記録すべきか、いつ起票するか、1本の ADR に何を束ねてよいか、命名規約をどこまで ADR の対象とするかを定める。本ファイルは必要条件・4項目の名称・同点処理・発見型の短絡・起票時期・行き先・束ね・命名規約の実体である。実測事実の値域・直列化形式・必須ルールは `adr-judgment-contract.md`、項目ごとの閾値とスコア境界は `adr-scoring-thresholds.json` が実体として定める。

## 格下げ判定との使い分け

本ファイルが定めるのは**起票の前段**の判定であり、対象はまだ記録されていない決定である。

既に記録された ADR を退役させる（`validity: 廃止済み` へ移して index から外す）かの判定には本ファイルを用いない。実体は `adr-demotion.md` に在る。両者は使える入力・不可逆性の向き・安全側の向きが非対称であり、判定項目・境界・安全側を共有しない（詳細は同ファイル「位置づけ: 起票判定との関係」）。**本ファイルの粒度判定基準を既存 ADR へ遡及適用して退役を決めない。**

両基準が共有するのは、ADR の固有価値を却下代替に置く定義だけである。本ファイルではそれが起票の必要条件（次節）として、`adr-demotion.md` では退役の条件1 として現れる。

## 必要条件: 却下代替が在ること

粒度判定基準へ進む前に次を確認する。**成立しなければ点数を数えず、ADR 化しない。**

**当該決定について、採らなかった選択肢とその却下理由が在ること。**

- 判定対象は、これから記録しようとしている決定そのものである。他の ADR や規約文書が持つ却下代替は当たらない
- 却下した選択肢の名指しと、それを却下した理由が、対として特定できること。代替案の名指しだけ、あるいはトレードオフや受け入れたコストの記述だけでは成立しない
- 意図的に決めなかった面（本 ADR では決めないと述べた射程外の論点）は却下代替ではない
- **成立するか迷う場合は不成立とする。** 後掲「判断に迷ったら ADR 化しない」と同じ向きである

ADR が共有規約文書・spec・実装等の資産と区別される点は、採らなかった選択肢とその却下理由を保持することにある。何が正しいかを述べる規範本文は、それらの資産の責務である。したがって却下代替を持たない決定は資産側へ書けば足りる。行き先は後掲「判定結果の行き先」の「ADR 化しない」の一般則に従う。

本条件は必要条件であって十分条件ではない。成立しても粒度判定基準の点数が境界へ届かなければ ADR 化しない。

**適用範囲**: 本条件が掛かるのは、まだ記録されていない決定を新たに ADR として記録すべきかの判定である。多決定 ADR の分割による後継への re-home は既に記録された決定の再配置であり、本条件の対象外とする（分割時に後継が満たすべき条件は `transitions.md`「分割（多決定 ADR の部分上書き）」の側の規範）。却下代替を持たない分割後継が生じた場合、その退役可否は `adr-demotion.md` の格下げ判定が扱う。

## 粒度判定基準

ADR 化要否の判定は、次の4項目チェックリストで行う。各項目に該当すれば1点とする。

1. 後戻りコストが高い
2. 複数の適用先に波及する
3. 採用理由が時間経過で揮発しやすい
4. ツールで自動強制できない

判定ルール:

- **設定ファイルのスコア境界以上**: ADR 化を推奨する
- **設定ファイルのスコア境界未満**: ADR 化しない（非該当）
- **判断に迷ったら ADR 化しない**: 原則として ADR 化しない方向に倒す。後から必要性が判明したら、その時点で遡及して ADR 化する

ADR 過多は検索性を損ね、蓄積した決定を参照する運用そのものの存在意義を失わせる。したがって判定境界では「書かない」を優先する。

### 各項目の判定手続き

前掲の4項目の名称・「判断に迷ったら ADR 化しない」の向きは変更しない。各項目を何によって判定するか（数える対象・列挙する対象・値域・時制）は `adr-judgment-contract.md`「実測事実の値域と定義」に定める。判定者や試行が変わっても同じ点数へ収束させるためである。

項目単位の同点処理は合計と同じ向きに倒す。**ある項目が該当するか迷う場合、その項目は0点とする。**

4項目は原則としてすべて判定する。ただし後掲「発見型」の短絡時だけ、項目1・2を省略する。

各項目が判定する入力の定義は `adr-judgment-contract.md`「実測事実の値域と定義」を参照し、閾値は `adr-scoring-thresholds.json` を参照する。判定は次表へ一度だけ適用する。表にない入力は該当しない側へ倒し、項目3の「理由」は判定のために言い換えない。

| 項目 | 判定する入力 | 該当（1点） | 非該当（0点） |
|---|---|---|---|
| 1. 後戻りコスト | 契約仕様が定める追跡下ファイルの数 | 設定ファイルの項目1閾値以上、または次のいずれか: ファイル群の構造変更、スキーマ／データ形式の変更、配布済み成果物への利用者影響、蓄積済みデータの移行 | 設定ファイルの項目1閾値未満で、上記4種もない |
| 2. 適用先 | 契約仕様が定める最小単位の数 | 設定ファイルの項目2閾値以上 | 設定ファイルの項目2閾値未満 |
| 3. 理由の揮発 | 契約仕様が定める値域と、規範と理由を同居できるか | 契約仕様が定める保持先がなく、条件1〜3のいずれかに該当 | 契約仕様が定める保持先が1つでもある、または条件1〜3のいずれにも該当しない |
| 4. 自動強制 | 契約仕様が定める阻止の状態 | 検査がない、警告どまり、または未実装 | コミット拒否・CI失敗・テスト失敗として現に阻止 |

項目1・2の数え方、項目3の保持先と同居判定は、`adr-judgment-contract.md`「実測事実の値域と定義」に移設した。

## 起票のタイミングとエスカレーション

ADR 化要否は上記4項目で判定するが、「いつ起票するか」は別の問題である。最初から ADR にしようとせず、まず PR の説明に判断を書く。後から他の機能でも同じ問いが出てきた時点で ADR に昇格させる。

```
特定機能の決定 → まずPRの説明に書く
      ↓
他の機能でも同じ問いが出てきた
      ↓
ADRに昇格（docs/adr/ に起票。採番方式に従う）
```

ADR 化を検討すべき決定が発生したことを示す実務シグナル（いずれかに該当したら、前掲の必要条件と粒度判定基準で要否を判定する）:

- 複数の選択肢を検討して片方を却下した
- トレードオフを受け入れた
- 制約や前提条件がある
- 既に運用されているが、どの ADR にも記録されていない規範を発見した（発見型）

### 発見型: 未記録の規範を見つけたとき

発見型では、記録が無いこと自体を欠落と読まない。記録の不在は判定の入力であって結論ではなく、判定を経ずに ADR 化へ進んではならない。判定へ入る前に、その規範が**現に何によって保たれているか**（保持先）を同定する。

- **実装・テスト資産・操作手順** — 規範を強制するコード本体、その fixture／テスト、実行を組み込む手順（フック・CI・手順書）
- **共有規約文書** — 規約ファイル・プロジェクト指示など、人が読んで従う文書
- **どこにも無い** — 実行者の記憶にのみ在る暗黙の慣行

保持先が実装・テスト資産・操作手順であり、かつ規範への違反がその資産によって**現に検出・阻止されている**なら、粒度判定基準の項目3（採用理由が時間経過で揮発しやすい）と項目4（ツールで自動強制できない）はいずれも該当しない。強制をツールが担っており、採用理由の保持先も当該資産だからである（採用理由がまだ書かれていない場合は、次節の一般則が求めるとおり当該資産へ併記して自己完結させる。ADR へ移す理由にはならない）。この時点で残る項目1・項目2 の合計上限は設定ファイルのスコア境界未満である。したがって両項目を評価するまでもなく判定は「ADR 化しない」で確定し、行き先は次節の一般則に従う。項目1・項目2 の点数を詰めても結論は動かないため、評価を要さない。

上記に当たらない場合は、4項目を通常どおり判定する。保持先が共有規約文書またはどこにも無い場合のほか、保持先は実装・テスト資産・操作手順だが強制が現に動いていない場合（検査が無い、警告どまりで阻止しない等）もここに含む。

上記の帰結は「現に強制が動いている」というこの類型に限る。4項目そのものへ操作的定義を与えるものではなく、項目の定義とスコア境界は前掲のとおりで変更しない。

## 判定結果の行き先

粒度判定基準の結論ごとに、対象の置き場所を次のとおりとする。ADR に記録が無いことは、その規範が無効であることも、置き場所が無いことも意味しない。

**ADR 化する（設定ファイルのスコア境界以上）の行き先**

- 既存 ADR が扱っていない枠組みを立てる場合、または既存 ADR の結論・方向・前提を反転・置換する場合 → **新規 ADR** の側へ振り分ける
- `validity: 有効` な既存 ADR が定める枠組みの中に収まり、**その枠組みを保ったまま別の面（適用範囲・条件・パラメータ値・理由付け）を追加するだけ**の場合 → 新規 ADR を起こさず、当該 ADR への**非core 改訂**の側へ振り分ける。同じ主題を複数の ADR へ分散させないためである

いずれも振り分け先の提示であって、分類（core／非core／些末）の確定ではない。分類基準の実体、確定の手続き（利用者へ問うこと）、安全則（迷えば core 寄り＝新規 ADR に倒す）、および選んだ操作の手順と変更履歴の残し方は、すべて `edit-decision.md` に従う。本節でこれらを再定義しない。退役（上書き済み・廃止済み）した ADR は同ファイルの凍結原則により決定内容の改訂を受けないため、上の2分岐は掛からない。

**ADR 化しない（設定ファイルのスコア境界未満）の行き先**

- **ツールで自動強制される規範** → **実装・テスト資産・操作手順**に置く。強制するコード本体・その fixture／テスト・実行を組み込む手順が置き場所であり、採用理由と既知の限界は当該資産のコメント等に併記して自己完結させる
- **ツールでは強制できないが、複数の作業者・複数の箇所へ効かせたい規範** → **共有規約文書**（規約ファイル・プロジェクト指示）に置く。採用理由と既知の限界は当該文書へ併記して自己完結させる。併記の未了が項目3の点数を動かすのは、同居判定の1点条件に当たる決定に限る（併記により値域(B) が成立し0点へ移る）。当たらない決定では点数は動かないが、併記を欠いたまま放置すれば理由は次の判定者へ渡らずに失われる
- **単一の変更に閉じる判断** → **その変更の PR 説明**に書く。前節の昇格フローの前段にあたり、他の箇所で同じ問いが再出した時点で改めて判定へ掛ける

強制する資産はあるが検査が警告どまりで阻止しない規範は、第1分岐（実装・テスト資産・操作手順）に置く。阻止まで動かすかは当該資産の実装の課題であり、置き場所を変えない。

ただし既に記録済みの決定そのものへ触れる編集は、粒度判定の点数ではなく `edit-decision.md` の分類が入口となる。スコア境界未満であることは、既存 ADR への改訂を妨げない。

この一般則が最も効くのは、ADR 運用そのものや開発の進め方を主題とする規範である。この層は規範が実装・テスト資産・操作手順の側で既に強制されていることが多く、そのぶん記録の不在が欠落と誤読されやすい。

## 新規 ADR の束ねの制約

新規に ADR を起こす場合、その1本に何を入れるかは**反転の単位**で決める。

- **独立に反転しうる core を1本の ADR に束ねない。** 束ねた ADR は、一部の決定だけが反転したときに全体を退役させられず、生存する決定を後継へ救出する分割操作を要求する
- **束ねが必要な場合は、束ねた塊が一体で反転する抽象度まで上げる。** 独立に反転する決定は、そもそも同一の core ではない

既に束ねられている ADR をいつ分割するかは別の問いであり、`SKILL.md` 本体の「分割」節が定める適用条件に従う。

## 命名規約の ADR 化基準

### 本節の射程

本節が対象とするのは、**識別子——変数・関数・型・ファイル・ディレクトリ等、コードや成果物の中で対象を指し示す名前——に、どの名前を与えるか、およびその名前をどう綴るか**を定める規範に限る。次の3つは名前そのものを定めていないため、本節の射程外とする。

- **記述の並び順とレイアウト**（import 順、宣言の並び、空白・改行・字下げ）。並べ方・空け方は名前ではない
- **成果物メタデータの値の形式**（front-matter の値、設定値、コミットメッセージの書式や言語）。名前ではない値に掛かる形式である
- **識別子の採番形式**（連番・日付・ハッシュ等の採り方と、その桁数、および採番部分の内部にある区切り記号の形式）。どの名前を与えるかではなく、値の生成規則である。識別子が採番部分と綴り部分を併せ持つ場合、射程外となるのは採番部分だけであり、綴り部分は射程内として扱う。**区切り記号は、両側とも採番部分であるものだけが採番部分に属し、片側でも綴り部分に接するものは綴り部分に属する。** 例として `ADR-YYYYMMDDHHMM-NN` では、日付部と連番部を隔てるハイフンは両側とも採番部分であるため射程外、`ADR` と日付部を隔てるハイフンは綴り部分に接するため射程内である

一方、**成果物をツリー上のどのディレクトリへ置くかを定めるファイル配置規約は、本節の射程内とする。** ツリー上の所在は、その成果物を指し示す完全なパスという識別子の一部を与えるためである。第1類型（記述の並び順とレイアウト）が射程外なのは、成果物の内部での並べ方が識別子のいずれの部分にもならないためであり、ツリー上の配置が射程内・成果物内部の配置が射程外という非対称は、この「識別子の一部を成すか」の一線に由来する。

射程外の規範には本節の表も末尾の例外も掛からない。行き先は前掲「判定結果の行き先」の一般則3分岐が決める。

### 振り分け

射程内の命名規約のうち ADR 化対象とするかどうかは、構造的か書式的かで振り分ける。

| 種別 | 特徴 | 例 | 配置 |
|---|---|---|---|
| 構造的命名規約 | 横断・後戻りコスト高 | ファイル配置規約、集約名、ドメイン用語統一 | ADR 化（`docs/adr/`） |
| 書式的命名規約 | 表記に閉じる・原理的にツール強制可能 | 変数命名、識別子の大文字小文字と区切り記号の使い分け、接頭辞・接尾辞の綴り | Linter／フォーマッタ規約として配置（ADR 外） |

本表は前掲「判定結果の行き先」の一般則を命名規約へ当てはめたものであり、強制が現に動いている場合は一般則の典型例として対応する（強制が未実装の場合の扱いは本節末尾の例外による）。構造的命名規約の行（ADR 化）は一般則の「スコア境界以上の行き先」に対応し、書式的命名規約の行（Linter／フォーマッタ規約として配置＝ADR 外）は「スコア境界未満の行き先」のうち「ツールで自動強制される規範 → 実装・テスト資産・操作手順に置く」分岐に対応する（Linter／フォーマッタ本体とその設定がここでの実装資産にあたる）。表の軸（構造的／書式的）と一般則の軸（ツール強制の可否）は直交するため、対応は一対一ではない。構造的命名規約であってもツールで現に強制されている場合は、次の指示どおり項目4に照らして振り分ける。

ツールで自動強制できる規約は ADR 外とする。判断に迷う場合は、粒度判定基準の項目4（ツールで自動強制できない）に照らして振り分ける。

本節の「ツールで自動強制できる」は項目4と同じ現在時制で読む（違反が現に検査され、作業が阻止されている状態）。ただし前段のタイブレーカーは対象が構造的か書式的かを決めるためのものであり、**原理的に**強制できるかを問う。これは項目4の点数を決める問いとは別であり、強制が未実装でも原理的に強制できる規約は書式的の側へ振り分ける。

**書式的命名規約は、強制がまだ実装されていない場合も ADR 外とする。** 行き先は強制の実装（Linter／フォーマッタ規約とその設定）であり、採用理由は当該設定へ併記する。強制が未実装であることは、記録すべき設計判断ではなく実装の欠落だからである。強制が未実装の場合に限り、本表は一般則の特化ではなく**例外**として働く。粒度判定基準の合計が設定ファイルのスコア境界へ届く場合も、振り分けは表が決める。**本例外が掛かるのは、必要条件が成立し、かつ対象が本節の射程内である場合に限る**（次項「適用順」）。

### 適用順

必要条件・射程・本表の順に掛ける。

1. **必要条件（却下代替が在ること）は本節にも前置する。** 不成立なら点数を数えず、本表も末尾の例外も掛からない。行き先は一般則3分岐が決める。必要条件より先に本節を掛けないのは、掛ければ却下代替を持たない決定について本節だけが独自の行き先を持つことになり、前掲「必要条件」節が定める「不成立なら行き先は一般則に従う」と衝突するためである
2. 必要条件が成立し、対象が**射程内**であれば、本表と末尾の例外が掛かる。このうち一般則3分岐に**優先するのは末尾の例外だけ**であり、優先が働くのは書式的命名規約について強制が未実装の場合に限る。構造的命名規約の行は一般則の「スコア境界以上の行き先」に対応する写像であって優越ではないため、粒度判定の合計がスコア境界未満であれば ADR 化せず、行き先は一般則3分岐が決める
3. 必要条件が成立していても、対象が**射程外**であれば、本表も末尾の例外も掛からず、一般則3分岐が決める
