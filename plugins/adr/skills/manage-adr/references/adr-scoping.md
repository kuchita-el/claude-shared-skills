# ADR 化要否の判断基準（adr-scoping.md）

ある決定を ADR として記録すべきか、いつ起票するかを定める。本ファイルは必要条件・4項目の名称・同点処理・発見型の短絡・起票時期の実体である。あわせて、各項目が判定する入力の値域と定義、項目ごとの閾値、スコア境界の数値、および判定結果に添える申告の規律も本ファイルが実体として持つ。判定に要るものはすべて本ファイル内に在り、判定のために外部の器を参照しない。

判定を終えた対象の**行き先**（ADR 化する側／しない側の分岐と、命名規約の振り分け）は `adr-destination.md` が、新規に起こす1本の ADR へ何を束ねてよいかは `adr-splitting.md` が実体を持つ。

## 格下げ判定との使い分け

本ファイルが定めるのは**起票の前段**の判定であり、対象はまだ記録されていない決定である。

既に記録された ADR を退役させる（`validity: 廃止済み` へ移して index から外す）かの判定には本ファイルを用いない。実体は `adr-demotion.md` に在る。両者は使える入力・不可逆性の向き・安全側の向きが非対称であり、判定項目・境界・安全側を共有しない（詳細は同ファイル「位置づけ: 起票判定との関係」）。**本ファイルの粒度判定基準を既存 ADR へ遡及適用して退役を決めない。**

両基準が共有するのは、ADR の固有価値を却下代替に置く定義だけである。本ファイルではそれが起票の必要条件（次節）として、`adr-demotion.md` では退役の条件1 として現れる。

## 必要条件: 却下代替が在ること

粒度判定基準へ進む前に次を確認する。**成立しなければ点数を数えず、ADR 化しない。**

**当該決定について、採らなかった選択肢とその却下理由が在ること。**

- 判定対象は、これから記録しようとしている決定そのものである。他の ADR や規約文書が持つ却下代替は当たらない
- 却下した選択肢の名指しと、それを却下した理由が、対として特定できること。代替案の名指しだけ、あるいはトレードオフや受け入れたコストの記述だけでは成立しない
- 意図的に決めなかった面（本 ADR では決めないと述べた射程外の論点）は却下代替ではない
- **成立するか迷う場合は不成立とする。** 後掲「判断に迷ったら ADR 化しない」と同じ向きである

ADR が共有規約文書・spec・実装等の資産と区別される点は、採らなかった選択肢とその却下理由を保持することにある。何が正しいかを述べる規範本文は、それらの資産の責務である。したがって却下代替を持たない決定は資産側へ書けば足りる。行き先は `adr-destination.md`「判定結果の行き先」の「ADR 化しない」の一般則に従う。

本条件は必要条件であって十分条件ではない。成立しても粒度判定基準の点数が境界へ届かなければ ADR 化しない。

**適用範囲**: 本条件が掛かるのは、まだ記録されていない決定を新たに ADR として記録すべきかの判定である。多決定 ADR の分割による後継への re-home は既に記録された決定の再配置であり、本条件の対象外とする（分割時に後継が満たすべき条件は `transitions.md`「分割（多決定 ADR の部分上書き）」の側の規範）。却下代替を持たない分割後継が生じた場合、その退役可否は `adr-demotion.md` の格下げ判定が扱う。

## 粒度判定基準

ADR 化要否の判定は、次の4項目チェックリストで行う。各項目に該当すれば1点とする。

1. 後戻りコストが高い
2. 複数の適用先に波及する
3. 採用理由が時間経過で揮発しやすい
4. ツールで自動強制できない

判定ルール:

- **合計3点以上（スコア境界は3点）**: ADR 化を推奨する
- **合計3点未満**: ADR 化しない（非該当）
- **判断に迷ったら ADR 化しない**: 原則として ADR 化しない方向に倒す。後から必要性が判明したら、その時点で遡及して ADR 化する

ADR 過多は検索性を損ね、蓄積した決定を参照する運用そのものの存在意義を失わせる。したがって判定境界では「書かない」を優先する。

### 各項目の判定手続き

前掲の4項目の名称・「判断に迷ったら ADR 化しない」の向きは変更しない。各項目を何によって判定するか（数える対象・列挙する対象・値域・時制）は、後掲「判定する入力の値域と定義」が定める。判定者や試行が変わっても同じ点数へ収束させるためである。

項目単位の同点処理は合計と同じ向きに倒す。**ある項目が該当するか迷う場合、その項目は0点とする。**

4項目は原則としてすべて判定する。ただし後掲「発見型」の短絡時だけ、項目1・2を省略する。

各項目が判定する入力の定義は後掲「判定する入力の値域と定義」に、閾値の数値は次表に直接示す。判定は次表へ一度だけ適用する。表にない入力は該当しない側へ倒し、項目3の「理由」は判定のために言い換えない（言明が無い場合の推定は後掲「項目3の条件1〜3」の定めによる）。

| 項目 | 判定する入力 | 該当（1点） | 非該当（0点） |
|---|---|---|---|
| 1. 後戻りコスト | 反転時に直す追跡下ファイルの数（数え方は後掲の値域定義による） | 3件以上、または次のいずれか: ファイル群の構造変更、スキーマ／データ形式の変更、配布済み成果物への利用者影響、蓄積済みデータの移行 | 3件未満で、上記4種もない |
| 2. 適用先 | 規範が適用される最小単位の数（分解の仕方は後掲の値域定義による） | 2単位以上 | 2単位未満 |
| 3. 理由の揮発 | 規範の保持先が後掲の値域(A)(B)に当たるか、および規範と理由を同居できるか | 値域に当たる保持先がなく、後掲の条件1〜3のいずれかに該当 | 値域に当たる保持先が1つでもある、または条件1〜3のいずれにも該当しない |
| 4. 自動強制 | 判定時点の阻止の状態（値域は後掲の3語による） | `検査なし` または `警告どまり` | `現に阻止`（コミット拒否・CI失敗・テスト失敗として阻止されている） |

### 判定する入力の値域と定義

各項目が観測する事実は次のとおりとする。

| 項目 | 捕捉する事実 |
|---|---|
| 項目1 | 反転時に直す追跡下ファイルの列挙と件数、および構造変更・スキーマ変更・配布済み成果物への利用者影響・蓄積済みデータ移行の各成否 |
| 項目2 | 規範が適用される最小単位（モジュール、実行可能単位、成果物種別）の列挙と件数 |
| 項目3 | 値域(A)(B)の各成否、条件1・2の評価に用いた採用理由とその出所（判定対象に言明／推定）、条件1〜3の各成否 |
| 項目4 | 判定時点の阻止の状態 |

**項目1で数える対象**: 再生成で追随する成果物、追加だけで矛盾しないファイル、決定を記録するだけの ADR（本体・`index.md`・相互参照）および追跡用 Issue は数えない。規範の適用先として直す ADR は数える。禁止規範の反転でも、記述の追加だけなら数えず、禁止を述べる既存記述が矛盾する場合は数える。構造変更・スキーマ変更・配布済み成果物への利用者影響・蓄積済みデータ移行の4種は、ファイル数とは独立に評価する。

**項目2で数える対象**: 入れ子は最小単位へ分解し、同じプラグイン内の別スキル・別スクリプト・別成果物種別は別単位とする。決定を記録する ADR と追跡用 Issue は除外し、規範の適用先である ADR は含める。作業者の人数や形容による規模は入力にしない。

**項目3の保持先の値域**: 次の閉じた値域で判定する。

- **(A)** 規範を強制する実装本体、その fixture／テスト、型定義・テンプレート・スキーマ、フック・CI・実行手順
- **(B)** 共有規約ファイル（`references/` を含む）とプロジェクト指示ファイル

散文だけの記述は(A)ではなく、(B)でも採用理由がなければ対象外である。ADR への識別子・表題・リンクだけの参照、PR説明、Issue、レビューコメント、記憶は値域外とする。値域に当たるか迷う場合も0点とする。(A) は理由の記載や強制の稼働を問わず0点とし、(B) は当該決定の採用理由が本文に現に書かれている場合だけ0点とする。

**項目3の条件1〜3**: 上記の値域に当たる保持先が無い場合だけ、次の3条件を評価する。

1. 却下理由が採用理由とは別に必要である
2. 受け入れた不利益・犠牲の説明が採用理由とは別に必要である
3. 規範が複数のファイルへ分かれざるを得ず、1つの資産の傍らへ理由を置けない（現状の配置ではなく、これから書く場合の形で判定する）

条件1・2は、判定対象の決定（必要条件の判定対象と同じく、これから記録しようとしている決定そのもの）に言明された採用理由と照らして評価する。採用理由が判定対象に言明されていない場合は、決定の本文と、必要条件で特定した却下代替の記述だけを入力として採用理由を推定し、推定した理由と照らして評価する。これ以外の資料や判定者の知識で推定を補わない。条件3は採用理由によらず判定する。

- 決定を採った者へ問い合わせられるか、PR説明・Issue・記憶から理由を回収できるかは、入力にしない。いずれも判定の時点によって値が変わり、同じ決定が判定の時期で別の点数を取るためである
- 値域(B)の成否は、当該決定の採用理由が(B)の保持先の本文に現に書かれているかで決まる。条件1・2の評価に用いる採用理由とは別の入力であり、推定した採用理由は値域(B)の成否を動かさない
- 推定した採用理由で評価しても、条件1・2が該当するか迷う場合は、前掲の同点処理どおり不成立へ倒す

**項目4の阻止の状態の値域**: `現に阻止` / `警告どまり` / `検査なし` の3語に限る。強制が**未実装**である状態は `検査なし` として扱う。

### 判定に添える申告

点数と結論だけでは、どの事実に基づいて数えたかを後から照合できない。判定結果には次を添える。

- **件数を数えた項目は、数えた対象を列挙する。** 前掲「項目1で数える対象」「項目2で数える対象」の除外規則を適用したかを、第三者が列挙と突き合わせて確かめられるようにするためである
- **発見型の短絡を適用した場合は、適用したことと適用の理由、および省略した項目（項目1・2）を申告する。** 短絡は4項目をすべて判定するという原則の例外であり、申告が無ければ省略と判定漏れが区別できない
- **判定対象に無い事実を推定で補わない。** 確かめられなかった事実は、推定値で埋めず、確かめられなかった旨を添える。事実が確かめられないことと、事実は確かめられるが該当するか迷うことは別である。後者は前掲の同点処理により0点へ倒すが、前者は0点として数える前に、確かめられなかった事実そのものを申告する。例外は項目3の条件1・2の評価に用いる採用理由の1点に限り、前掲「項目3の条件1〜3」の定めに従って推定する
- **項目3の条件1・2を推定した採用理由で評価した場合は、推定したことと推定した理由を申告する。** 申告は判断の確度を第三者へ見せるためのものであり、点数算出の入力にしない
- **起票の時点を判定した場合は、条件1のために探した範囲と、見つけた保留中の記録を申告する。** 後掲「起票のタイミングとエスカレーション」の条件1は記録の有無を入力にするため、探した範囲が無ければ、記録が無いことと探していないことが区別できない

## 起票のタイミングとエスカレーション

ADR 化要否は上記4項目で判定するが、「いつ起票するか」は別の問題である。最初から ADR にしようとせず、合計3点以上の決定も、まず保留して変更の説明に判定の記録を書く。後から他の適用先でも同じ問いが出てきた時点で ADR に昇格させる。保留中の記録の置き場所と内容、および変更の説明の定義は `adr-destination.md`「判定結果の行き先」が定める。

```
合計3点以上の決定 → まず保留し、変更の説明に判定の記録を書く
      ↓
他の適用先でも同じ問いが判定の対象になった
      ↓
改めて4項目で判定し、合計3点以上ならADRに昇格（docs/adr/ に起票。採番方式に従う）
```

**起票の時点の射程**: 起票の時点の判定が掛かるのは、合計3点以上の決定のうち、既存 ADR が扱っていない枠組みを立てるものに限る。`validity: 有効` な既存 ADR の結論・方向・前提を反転・置換する決定には掛けない。既存 ADR の枠組みの中へ別の面を追加する決定にも掛けない。いずれも `adr-destination.md` の「ADR 化する」の2分岐へ直ちに進め、分類と操作は `edit-decision.md` に従う。前者を保留すると、有効な ADR が実態と矛盾したまま残る。後者は主題が既に ADR へ昇格しており、再出を待つ理由が無い。

**起票の時点**: 射程内の決定は、次の2条件がともに成り立つときに起票の時点に達する。一方でも成り立たなければ保留する。

1. 同じ問いについての保留中の記録が、判定対象の変更とは別の変更の説明に在る。同じ問いとは、今回の判定が必要条件で特定した選択肢の対（採った選択肢と却下した選択肢）のいずれかが、保留中の記録の対と同じ2つの選択肢から成ることをいう。どちらの選択肢を採ったかは問わない
2. 今回の判定で列挙した適用先（前掲「項目2で数える対象」による）に、保留中の記録が列挙した適用先に無い単位が1つ以上ある

条件1の入力は次のとおり定める。

- 探す範囲は、判定対象の変更の基点となる版に取り込まれた変更の説明に限る。PR を経た変更はマージ済みの PR の説明、経ない変更は基点の版の履歴にあるコミットメッセージである。マージされずに閉じた PR と、基点の版に取り込まれていない変更は含めない
- 保留中の記録に数えるのは、`adr-destination.md` が保留中の判定の記録に求める4点を備えた記録だけである。合計3点未満で第3分岐に書いた判断の記録は、保留した旨を持たないため数えない
- その問いを扱う ADR が起票されると、記録は保留中でなくなる。以後の同じ問いは既存 ADR に関わる決定となり、前掲の射程から外れる

この入力は、基点の版を決めれば定まり、判定の時期によって変わらない。判定の時点で値が変わるとして項目3が入力から外した「理由を回収できるか」とは、この点で異なる。

保留中の記録が見つからない場合と、選択肢の対が同じか迷う場合は、条件1が成り立たないものとして扱う。したがって初めて判定する決定は、合計3点以上でも保留となる。初出で保留するのは、1つの変更の中では同じ問いが他の適用先でも出るかを観測できず、初出で起票すると ADR 過多を招くためである。保留中の記録と同じ適用先だけで同じ問いが再び判定された場合も、条件2が成り立たないため保留を続ける。

例として、ある機能の検査器の射程を絞る決定が3点に達しても、同じ選択肢の対を扱う保留中の記録が別の変更に無ければ、その変更の説明に判定の記録を書いて保留する。

ADR 化を検討すべき決定が発生したことを示す実務シグナル（いずれかに該当したら、前掲の必要条件と粒度判定基準で要否を判定する）:

- 複数の選択肢を検討して片方を却下した
- トレードオフを受け入れた
- 制約や前提条件がある
- 既に運用されているが、どの ADR にも記録されていない規範を発見した（発見型）

### 発見型: 未記録の規範を見つけたとき

発見型では、記録が無いこと自体を欠落と読まない。記録の不在は判定の入力であって結論ではなく、判定を経ずに ADR 化へ進んではならない。判定へ入る前に、その規範が**現に何によって保たれているか**（保持先）を同定する。

- **実装・テスト資産・操作手順** — 規範を強制するコード本体、その fixture／テスト、実行を組み込む手順（フック・CI・手順書）
- **共有規約文書** — 規約ファイル・プロジェクト指示など、人が読んで従う文書
- **どこにも無い** — 実行者の記憶にのみ在る暗黙の慣行

保持先が実装・テスト資産・操作手順であり、かつ規範への違反がその資産によって**現に検出・阻止されている**なら、粒度判定基準の項目3（採用理由が時間経過で揮発しやすい）と項目4（ツールで自動強制できない）はいずれも該当しない。強制をツールが担っており、採用理由の保持先も当該資産だからである（採用理由がまだ書かれていない場合は、`adr-destination.md`「判定結果の行き先」の一般則が求めるとおり当該資産へ併記して自己完結させる。ADR へ移す理由にはならない）。この時点で残る項目1・項目2 の合計上限は2点であり、スコア境界の3点に届かない。したがって両項目を評価するまでもなく判定は「ADR 化しない」で確定し、行き先は `adr-destination.md`「判定結果の行き先」の一般則に従う。項目1・項目2 の点数を詰めても結論は動かないため、評価を要さない。

上記に当たらない場合は、4項目を通常どおり判定する。保持先が共有規約文書またはどこにも無い場合のほか、保持先は実装・テスト資産・操作手順だが強制が現に動いていない場合（検査が無い、警告どまりで阻止しない等）もここに含む。

上記の帰結は「現に強制が動いている」というこの類型に限る。4項目そのものへ操作的定義を与えるものではなく、項目の定義とスコア境界は前掲のとおりで変更しない。
