# ADR 化要否の判断基準（adr-scoping.md）

ある決定を ADR として記録すべきか、いつ起票するか、命名規約をどこまで ADR の対象とするかを定める。本ファイルがこれらの判断基準の実体であり、判定項目・スコア境界をここ以外で独自に再定義しない。

## 粒度判定基準

ADR 化要否の判定は、次の4項目チェックリストで行う。各項目に該当すれば1点とする。

1. 後戻りコストが高い
2. 複数モジュール・複数開発者に波及する
3. 採用理由が時間経過で揮発しやすい
4. ツールで自動強制できない

判定ルール:

- **3点以上**: ADR 化を推奨する
- **2点以下**: ADR 化しない（非該当）
- **判断に迷ったら ADR 化しない**: 原則として ADR 化しない方向に倒す。後から必要性が判明したら、その時点で遡及して ADR 化する

ADR 過多は検索性を損ね、蓄積した決定を参照する運用そのものの存在意義を失わせる。したがって判定境界では「書かない」を優先する。

## 起票のタイミングとエスカレーション

ADR 化要否は上記4項目で判定するが、「いつ起票するか」は別の問題である。最初から ADR にしようとせず、まず PR の説明に判断を書く。後から他の機能でも同じ問いが出てきた時点で ADR に昇格させる。

```
特定機能の決定 → まずPRの説明に書く
      ↓
他の機能でも同じ問いが出てきた
      ↓
ADRに昇格（docs/adr/ に起票。採番方式に従う）
```

ADR 化を検討すべき決定が発生したことを示す実務シグナル（いずれかに該当したら、粒度判定基準で要否を判定する）:

- 複数の選択肢を検討して片方を却下した
- トレードオフを受け入れた
- 制約や前提条件がある
- 既に運用されているが、どの ADR にも記録されていない規範を発見した（発見型）

### 発見型: 未記録の規範を見つけたとき

発見型では、記録が無いこと自体を欠落と読まない。記録の不在は判定の入力であって結論ではなく、判定を経ずに ADR 化へ進んではならない。判定へ入る前に、その規範が**現に何によって保たれているか**（保持先）を同定する。

- **実装・テスト資産・操作手順** — 規範を強制するコード本体、その fixture／テスト、実行を組み込む手順（フック・CI・手順書）
- **共有規約文書** — 規約ファイル・プロジェクト指示など、人が読んで従う文書
- **どこにも無い** — 実行者の記憶にのみ在る暗黙の慣行

保持先が実装・テスト資産・操作手順であり、かつ規範への違反がその資産によって**現に検出・阻止されている**なら、粒度判定基準の項目3（採用理由が時間経過で揮発しやすい）と項目4（ツールで自動強制できない）はいずれも該当しない。採用理由を当該資産が保持しており、強制をツールが担っているためである。残る項目1・項目2 は通常どおり判定するが、両方に該当しても合計は2点にとどまり境界の3点へ届かない。したがって判定は「ADR 化しない」で確定し、行き先は次節の一般則に従う。

保持先が共有規約文書またはどこにも無い場合は、4項目を通常どおり判定する。

上記の帰結は「現に強制が動いている」というこの類型に限る。4項目そのものへ操作的定義を与えるものではなく、項目の定義とスコア境界は前掲のとおりで変更しない。

## 判定結果の行き先

粒度判定基準の結論ごとに、対象の置き場所を次のとおりとする。ADR に記録が無いことは、その規範が無効であることも、置き場所が無いことも意味しない。

**ADR 化する（3点以上）の行き先**

- 既存 ADR が扱っていない枠組みを立てる場合、または既存 ADR の結論・方向・前提を反転・置換する場合 → **新規 ADR を起票する**（後者は旧 ADR の上書きを伴う）
- 既存 ADR が定める枠組みの中に収まり、**その枠組みを保ったまま別の面（適用範囲・条件・パラメータ値・理由付け）を追加するだけ**の場合 → 新規 ADR を起こさず、当該 ADR への**非core 改訂**（対象 ADR を直接編集し `## 変更履歴` へ1行追記する）で扱う。同じ主題を複数の ADR へ分散させないためである

core／非core／些末 の分類基準の実体は `edit-decision.md` にあり、分類の確定と安全則（迷えば core 寄り＝新規 ADR に倒す）はそちらに従う。本節はどちらの分岐へ入るかを示すに留め、分類の判定基準をここで再定義しない。

**ADR 化しない（2点以下）の行き先**

- **ツールで自動強制される規範** → **実装・テスト資産・操作手順**に置く。強制するコード本体・その fixture／テスト・実行を組み込む手順が置き場所であり、採用理由と既知の限界は当該資産のコメント等に併記して自己完結させる
- **ツールでは強制できないが、複数の作業者・複数の箇所へ効かせたい規範** → **共有規約文書**（規約ファイル・プロジェクト指示）に置く
- **単一の変更に閉じる判断** → **その変更の PR 説明**に書く。前節の昇格フローの前段にあたり、他の箇所で同じ問いが再出した時点で改めて判定へ掛ける

この一般則が最も効くのは、ADR 運用そのものや開発の進め方を主題とする規範である。この層は規範が実装・テスト資産・操作手順の側で既に強制されていることが多く、そのぶん記録の不在が欠落と誤読されやすい。

## 命名規約の ADR 化基準

命名規約のうち ADR 化対象とするかどうかは、構造的か書式的かで振り分ける。

| 種別 | 特徴 | 例 | 配置 |
|---|---|---|---|
| 構造的命名規約 | 横断・後戻りコスト高 | ファイル配置規約、集約名、ドメイン用語統一 | ADR 化（`docs/adr/`） |
| 書式的命名規約 | 局所・ツール強制可能 | 変数命名、import 順、空白・改行 | Linter／フォーマッタ規約として配置（ADR 外） |

本表は前節「判定結果の行き先」の一般則を命名規約へ当てはめた適用例である。構造的命名規約の行（ADR 化）は一般則の「ADR 化する（3点以上）の行き先」に対応し、書式的命名規約の行（Linter／フォーマッタ規約として配置＝ADR 外）は「ADR 化しない（2点以下）の行き先」のうち「ツールで自動強制される規範 → 実装・テスト資産・操作手順に置く」分岐に対応する（Linter／フォーマッタ本体とその設定がここでの実装資産にあたる）。

ツールで自動強制できる規約は ADR 外とする。判断に迷う場合は、粒度判定基準の項目4（ツールで自動強制できない）に照らして振り分ける。
