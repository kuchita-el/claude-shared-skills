# ADR 化要否の判断基準（adr-scoping.md）

ある決定を ADR として記録すべきか、いつ起票するか、1本の ADR に何を束ねてよいか、命名規約をどこまで ADR の対象とするかを定める。本ファイルがこれらの判断基準の実体であり、判定項目・スコア境界をここ以外で独自に再定義しない。

## 粒度判定基準

ADR 化要否の判定は、次の4項目チェックリストで行う。各項目に該当すれば1点とする。

1. 後戻りコストが高い
2. 複数モジュール・複数開発者に波及する
3. 採用理由が時間経過で揮発しやすい
4. ツールで自動強制できない

判定ルール:

- **3点以上**: ADR 化を推奨する
- **2点以下**: ADR 化しない（非該当）
- **判断に迷ったら ADR 化しない**: 原則として ADR 化しない方向に倒す。後から必要性が判明したら、その時点で遡及して ADR 化する

ADR 過多は検索性を損ね、蓄積した決定を参照する運用そのものの存在意義を失わせる。したがって判定境界では「書かない」を優先する。

### 各項目の判定手続き

前掲の4項目の名称・スコア境界・「判断に迷ったら ADR 化しない」の向きは変更しない。本小節は、各項目を**何によって判定するか**（数える対象・列挙する対象・値域・時制）だけを定める。判定者や試行が変わっても同じ点数へ収束させるためである。

項目単位の同点処理は合計と同じ向きに倒す。**ある項目が該当するか迷う場合、その項目は0点とする。**

4項目は原則としてすべて判定する。ただし後掲「発見型」の短絡が適用される場合に限り、項目1・項目2 は評価を要さない（結論が動かないため）。

#### 項目1: 後戻りコストが高い

決定を反転した場合に**書き換えが必要になるバージョン管理下のファイルを列挙して数える**。

- 数える対象: 反転によって内容の修正が要る追跡下のファイル。規約文書・実装・テスト・fixture・手順書を種類で区別しない。ここでいう修正が要るとは、**反転後にそのファイルを直さなければ矛盾・破損が生じる**ことを指す。反転後も既存の記述をそのまま残せる（表記が混在するだけで動作も整合も損なわれない）ものは数えない
- 数えない対象:
  - 元を直せば再生成で追随する生成物。ただし再生成では追随せず手直しが要る場合は数える
  - 当該決定を記録する ADR（本体・`index.md`・他の ADR が持つ相互参照）と、当該決定を追跡する Issue。これらは決定を ADR 化したこと・Issue 化したこと自体の帰結として生じる器であり、決定の内容が及ぶ先ではない。数えると「ADR 化すべきか」の判定へ ADR 化した場合の副産物が入力として混ざり、判定が自身の結論に依存する。ADR がまだ無い時点で判定しても既に在る時点で判定しても、同じ点数へ収束させるためである。ただし規範そのものが ADR 文書へ適用される決定（front-matter の書式、索引の運用、相互参照の書式、束ねの制約など）では、ADR は規範の適用先であり本数に数える。数えないのは、当該決定を記録・追跡していることに由来する書き換え（記録内容の改訂・索引行の更新・他の ADR が持つ参照の張り替え）だけが要るファイルであって、規範の適用先として直すことになるファイルは、当該決定を記録する ADR 本体であっても数える。除外は書き換えが要る理由で決まり、ファイルの種類では決まらない。なお Issue は追跡下のファイルではないため冒頭の限定により元より対象外だが、誤って数えられうるため明示する
  - 禁止規範（「〜を書かない」「〜を持ち込まない」）の反転にあたり、**既存ファイルへの記述の追加だけが要るファイル**。追加が要るだけで既存の記述が矛盾も破損もしないなら、前掲の数える対象の定義（直さなければ矛盾・破損が生じる）に当たらないためである。ただし禁止そのものを述べているファイルは、反転すれば記述が現に矛盾するため数える

**3本以上で1点、2本以下で0点**とする。

本数によらず、次のいずれかに当たる場合も1点とする（本数条件との OR）。いずれも書き換え量ではなく取り消しの困難さで効くためである。

- ファイル群の構造変更（配置・分割・命名の規約変更）
- スキーマ・データ形式の変更
- 既に配布された成果物の利用者側への影響
- 蓄積済みデータの移行

例: 反転しても2ファイルの文言修正で済むが蓄積済みデータの移行を伴う決定は、本数条件では0点だが非本数条件により1点となる。

**本数条件が0点であっても、上の4種は1つずつ個別に評価する。** 本数が2本以下であることは、非本数条件の評価を省く理由にならない。両者は OR であり、非本数条件だけで1点になる決定があるためである（前掲の例がそれにあたる）。

#### 項目2: 複数モジュール・複数開発者に波及する

決定の影響が及ぶ範囲を**列挙して数える**。列挙の単位はモジュール／実行可能単位／成果物の種類とする（プラグイン構成のリポジトリではプラグイン・スキル・スクリプト・成果物種別が対応する）。これらの単位は入れ子になるため、**最も細かい単位で数える**。同一プラグインに属していても、別のスキル・別のスクリプト・別の成果物種別はそれぞれ1つと数える。

**当該決定を記録する ADR と、当該決定を追跡する Issue は単位に含めない。** ここで数えるのは規範が適用される先であり、決定を記録・追跡する器はその決定の適用先ではないためである。項目1 が同じ理由でこれらを本数に数えないのと揃える。ただし規範そのものが ADR 文書へ適用される決定（front-matter の書式、索引の運用、相互参照の書式、束ねの制約など）では、ADR は規範の適用先であり成果物種別として数える。除くのは決定を記録・追跡する器としての ADR・Issue に限る。項目1 の対応する限定と同じ切り分けである。

**2つ以上で1点、1つ以下で0点**とする。規範が全単位へ一様に適用される場合は2つ以上に当たる。他節が当該規範の規模や適用範囲について与える形容は、本項目の入力にしない。

本数によらず、決定を知らない作業者が独立に別の選択をする箇所が**現に**複数ある場合も1点とする（OR）。将来そうなりうるという見込みでは1点としない。ここでの箇所も前掲の単位で数える。

#### 項目3: 採用理由が時間経過で揮発しやすい

判定は2段で行う。まず**採用理由（なぜその選択を採ったか）の保持先**を下の閉じた値域と突き合わせ、値域を満たせば0点とする（複数の資産に理由があれば OR で読み、1つでも値域に入れば0点）。値域を満たす保持先が無い場合は、後段の同居判定で決める。判定基準は評価する時点によらない。ただし判定へ入力する事実（採用理由が現に書かれているか、その内容を確かめられるか）は時点で動きうるため、同じ決定の点数が時点で変わることはある。併記により段1で0点が確定して同居判定へ進まなくなる場合や、理由が失われて後段の条件を判定できなくなる場合がこれにあたる。

**値域(A)** — 保持先が次の資産であること自体で値域を満たす。ここでいう保持先は、採用理由が書かれている場所ではなく、規範を担っている資産を指す。採用理由の記載の有無は問わず、**強制が現に動いているかも問わない**（強制の稼働は項目4 で測る。検査が無い・警告どまりの場合でも (A) は満たされる）。

- 規範を強制する実装本体
- その fixture ／ テスト
- 型定義・テンプレート・スキーマ定義
- 検査・強制の実行を組み込む手順（フック・CI 設定・実行手順書）

規範を散文で述べるだけの記述は、置かれたファイルが上の列挙に当たっても (A) を満たさない。`references/` 配下の文書は次の (B) として扱い、それ以外（強制を担っていない実装・テンプレート・手順書の中のコメント等）はどちらにも当たらない。

**値域(B)** — 次の資産は、**当該決定の採用理由が現に書かれている**場合に限り値域を満たす。規範を言明するだけで理由が書かれていなければ値域を満たさない。

- 共有規約ファイル（`references/` 配下の共有規約文書を含む）
- プロジェクト指示ファイル（`CLAUDE.md` 等）

**当該 ADR を指す参照が置かれていることは、採用理由が現に書かれていることに当たらない。** 参照は理由の所在を指すだけで理由そのものを含まず、参照先が失われれば理由も辿れなくなるためである。識別子・表題・リンクだけの記述は、指す先が ADR であるかによらず同じ扱いとする。値域(B) を満たすのは、なぜその選択を採ったかが当該ファイルの本文に現に書かれている場合に限る。

非対称に扱うのは資産の性質差による。実装・テスト資産では fixture とテストが境界事例そのものを符号化しており、規範の実質は振る舞いから復元できる。規約文書は規範を言明するだけであり、理由が書かれていなければ復元手段が残らない。

値域は閉じた列挙であり、ここに載らない保持先（PR 説明・Issue・レビューコメント・作業者の記憶）は値域を満たさない。列挙に無い保持先は判定不能ではなく、確定した値域外として扱う。値域に当たるか（採用理由が書かれていると言えるか等）迷う場合は、前掲の同点処理どおり0点とする。

**同居判定** — 値域を満たす保持先が無い場合（理由が値域外にしかない場合、まだどこにも書かれていない場合のいずれも含む）は、理由を規範と同居させられるかで決める。次のいずれかに当たる決定は**1点**とする。理由が規範文の傍らに残らないためである。ここでいう採用理由は、判定のために言い換えたものではなく、当該決定を説明するのに現に用いられている言明を指す。書かれた言明が無い場合は、当該決定を採った者が現に説明に用いている理由を指し、判定者が判定のために定式化し直さない。採用理由を確かめられない場合は、次の条件1・条件2 に当たらないものとして扱う（条件3は採用理由によらず判定する）。ここでいう確かめられないとは、決定を採った者へ到達できない・記録が残っていない等で内容を知りようがないことを指し、単に書かれていないだけの場合は含まない。確かめられない理由は ADR にも記録できないため、判定できない条件1・条件2 は該当しない側へ倒す。

- **条件1**: 却下した選択肢があり、**その却下理由が採用理由と別に要る**（採用理由と同一の理由で却下も説明できるなら当たらない）
- **条件2**: 受け入れた不利益・犠牲があり、**その説明が採用理由と別に要る**（同上）
- **条件3**: 規範そのものが複数の資産へ**分かれざるを得ず**、理由をそのいずれか1つの傍らに置けない（規範をこれから書く場合も、書くとすればどうなるかで判定する。現在の配置がたまたま分かれていることは含まない）。ここでの資産はファイル単位で数える。値域の同じ列挙項に属していても、別のファイルであれば別の資産とする

いずれにも当たらない決定は**0点**とする。判定は理由の分量によらない。0点となった決定は、後掲「判定結果の行き先」が求めるとおり置き場所へ採用理由を併記して自己完結させること。併記の未了は ADR へ移す理由にならない。

#### 項目4: ツールで自動強制できない

**判定時点の状態のみを見る**。将来の実装可能性や実装コストの見積もりを判定に混ぜない。

- **0点**: 規範への違反が現に機械的に検出され、かつ検出が作業を阻止する（コミット拒否・CI 失敗・テスト失敗）
- **1点**: 検査が無い／検査はあるが警告どまりで作業を阻止しない／検査を実装できるが現に実装していない

## 起票のタイミングとエスカレーション

ADR 化要否は上記4項目で判定するが、「いつ起票するか」は別の問題である。最初から ADR にしようとせず、まず PR の説明に判断を書く。後から他の機能でも同じ問いが出てきた時点で ADR に昇格させる。

```
特定機能の決定 → まずPRの説明に書く
      ↓
他の機能でも同じ問いが出てきた
      ↓
ADRに昇格（docs/adr/ に起票。採番方式に従う）
```

ADR 化を検討すべき決定が発生したことを示す実務シグナル（いずれかに該当したら、粒度判定基準で要否を判定する）:

- 複数の選択肢を検討して片方を却下した
- トレードオフを受け入れた
- 制約や前提条件がある
- 既に運用されているが、どの ADR にも記録されていない規範を発見した（発見型）

### 発見型: 未記録の規範を見つけたとき

発見型では、記録が無いこと自体を欠落と読まない。記録の不在は判定の入力であって結論ではなく、判定を経ずに ADR 化へ進んではならない。判定へ入る前に、その規範が**現に何によって保たれているか**（保持先）を同定する。

- **実装・テスト資産・操作手順** — 規範を強制するコード本体、その fixture／テスト、実行を組み込む手順（フック・CI・手順書）
- **共有規約文書** — 規約ファイル・プロジェクト指示など、人が読んで従う文書
- **どこにも無い** — 実行者の記憶にのみ在る暗黙の慣行

保持先が実装・テスト資産・操作手順であり、かつ規範への違反がその資産によって**現に検出・阻止されている**なら、粒度判定基準の項目3（採用理由が時間経過で揮発しやすい）と項目4（ツールで自動強制できない）はいずれも該当しない。強制をツールが担っており、採用理由の保持先も当該資産だからである（採用理由がまだ書かれていない場合は、次節の一般則が求めるとおり当該資産へ併記して自己完結させる。ADR へ移す理由にはならない）。この時点で残る項目1・項目2 の合計は最大2点であり、境界の3点へ届かない。したがって両項目を評価するまでもなく判定は「ADR 化しない」で確定し、行き先は次節の一般則に従う。項目1・項目2 の点数を詰めても結論は動かないため、評価を要さない。

上記に当たらない場合は、4項目を通常どおり判定する。保持先が共有規約文書またはどこにも無い場合のほか、保持先は実装・テスト資産・操作手順だが強制が現に動いていない場合（検査が無い、警告どまりで阻止しない等）もここに含む。

上記の帰結は「現に強制が動いている」というこの類型に限る。4項目そのものへ操作的定義を与えるものではなく、項目の定義とスコア境界は前掲のとおりで変更しない。

## 判定結果の行き先

粒度判定基準の結論ごとに、対象の置き場所を次のとおりとする。ADR に記録が無いことは、その規範が無効であることも、置き場所が無いことも意味しない。

**ADR 化する（3点以上）の行き先**

- 既存 ADR が扱っていない枠組みを立てる場合、または既存 ADR の結論・方向・前提を反転・置換する場合 → **新規 ADR** の側へ振り分ける
- `validity: 有効` な既存 ADR が定める枠組みの中に収まり、**その枠組みを保ったまま別の面（適用範囲・条件・パラメータ値・理由付け）を追加するだけ**の場合 → 新規 ADR を起こさず、当該 ADR への**非core 改訂**の側へ振り分ける。同じ主題を複数の ADR へ分散させないためである

いずれも振り分け先の提示であって、分類（core／非core／些末）の確定ではない。分類基準の実体、確定の手続き（利用者へ問うこと）、安全則（迷えば core 寄り＝新規 ADR に倒す）、および選んだ操作の手順と変更履歴の残し方は、すべて `edit-decision.md` に従う。本節でこれらを再定義しない。退役（上書き済み・廃止済み）した ADR は同ファイルの凍結原則により決定内容の改訂を受けないため、上の2分岐は掛からない。

**ADR 化しない（2点以下）の行き先**

- **ツールで自動強制される規範** → **実装・テスト資産・操作手順**に置く。強制するコード本体・その fixture／テスト・実行を組み込む手順が置き場所であり、採用理由と既知の限界は当該資産のコメント等に併記して自己完結させる
- **ツールでは強制できないが、複数の作業者・複数の箇所へ効かせたい規範** → **共有規約文書**（規約ファイル・プロジェクト指示）に置く。採用理由と既知の限界は当該文書へ併記して自己完結させる。併記の未了が項目3の点数を動かすのは、同居判定の1点条件に当たる決定に限る（併記により値域(B) が成立し0点へ移る）。当たらない決定では点数は動かないが、併記を欠いたまま放置すれば理由は次の判定者へ渡らずに失われる
- **単一の変更に閉じる判断** → **その変更の PR 説明**に書く。前節の昇格フローの前段にあたり、他の箇所で同じ問いが再出した時点で改めて判定へ掛ける

強制する資産はあるが検査が警告どまりで阻止しない規範は、第1分岐（実装・テスト資産・操作手順）に置く。阻止まで動かすかは当該資産の実装の課題であり、置き場所を変えない。

ただし既に記録済みの決定そのものへ触れる編集は、粒度判定の点数ではなく `edit-decision.md` の分類が入口となる。点数が2点以下であることは、既存 ADR への改訂を妨げない。

この一般則が最も効くのは、ADR 運用そのものや開発の進め方を主題とする規範である。この層は規範が実装・テスト資産・操作手順の側で既に強制されていることが多く、そのぶん記録の不在が欠落と誤読されやすい。

## 新規 ADR の束ねの制約

新規に ADR を起こす場合、その1本に何を入れるかは**反転の単位**で決める。

- **独立に反転しうる core を1本の ADR に束ねない。** 束ねた ADR は、一部の決定だけが反転したときに全体を退役させられず、生存する決定を後継へ救出する分割操作を要求する
- **束ねが必要な場合は、束ねた塊が一体で反転する抽象度まで上げる。** 独立に反転する決定は、そもそも同一の core ではない

既に束ねられている ADR をいつ分割するかは別の問いであり、`SKILL.md` 本体の「分割」節が定める適用条件に従う。

## 命名規約の ADR 化基準

命名規約のうち ADR 化対象とするかどうかは、構造的か書式的かで振り分ける。

| 種別 | 特徴 | 例 | 配置 |
|---|---|---|---|
| 構造的命名規約 | 横断・後戻りコスト高 | ファイル配置規約、集約名、ドメイン用語統一 | ADR 化（`docs/adr/`） |
| 書式的命名規約 | 表記に閉じる・原理的にツール強制可能 | 変数命名、import 順、空白・改行 | Linter／フォーマッタ規約として配置（ADR 外） |

本表は前掲「判定結果の行き先」の一般則を命名規約へ当てはめたものであり、強制が現に動いている場合は一般則の典型例として対応する（強制が未実装の場合の扱いは本節末尾の例外による）。構造的命名規約の行（ADR 化）は一般則の「ADR 化する（3点以上）の行き先」に対応し、書式的命名規約の行（Linter／フォーマッタ規約として配置＝ADR 外）は「ADR 化しない（2点以下）の行き先」のうち「ツールで自動強制される規範 → 実装・テスト資産・操作手順に置く」分岐に対応する（Linter／フォーマッタ本体とその設定がここでの実装資産にあたる）。表の軸（構造的／書式的）と一般則の軸（ツール強制の可否）は直交するため、対応は一対一ではない。構造的命名規約であってもツールで現に強制されている場合は、次の指示どおり項目4に照らして振り分ける。

ツールで自動強制できる規約は ADR 外とする。判断に迷う場合は、粒度判定基準の項目4（ツールで自動強制できない）に照らして振り分ける。

本節の「ツールで自動強制できる」は項目4と同じ現在時制で読む（違反が現に検査され、作業が阻止されている状態）。ただし前段のタイブレーカーは対象が構造的か書式的かを決めるためのものであり、**原理的に**強制できるかを問う。これは項目4の点数を決める問いとは別であり、強制が未実装でも原理的に強制できる規約は書式的の側へ振り分ける。

**書式的命名規約は、強制がまだ実装されていない場合も ADR 外とする。** 行き先は強制の実装（Linter／フォーマッタ規約とその設定）であり、採用理由は当該設定へ併記する。強制が未実装であることは、記録すべき設計判断ではなく実装の欠落だからである。強制が未実装の場合に限り、本表は一般則の特化ではなく**例外**として働く。粒度判定基準の合計が3点へ届く場合も、振り分けは表が決める。
