# 判定結果の行き先（adr-destination.md）

ADR 化要否の判定を終えた対象を、どこへ置くかを定める。判定そのもの（必要条件・粒度判定基準・判定する入力の値域と定義・閾値とスコア境界の定義）は `adr-scoping.md` が実体を持ち、本ファイルでは再定義しない。本ファイルの分岐ラベルに現れる閾値と値域語は、`adr-scoping.md` が定義した判定結果を指すためのものである。

## 判定結果の行き先

粒度判定基準の結論ごとに、対象の置き場所を次のとおりとする。ADR に記録が無いことは、その規範が無効であることも、置き場所が無いことも意味しない。合計3点以上の決定のうち、起票の時点の判定が掛かるものは、起票の時点に達した場合だけ次の「ADR 化する」の2分岐へ進む。判定が掛かる射程は `adr-scoping.md`「起票のタイミングとエスカレーション」が定める。達していないものの行き先は後掲「起票の時点に達していない決定の行き先」による。

**ADR 化する（合計3点以上）の行き先**

- 既存 ADR が扱っていない枠組みを立てる場合、または既存 ADR の結論・方向・前提を反転・置換する場合 → **新規 ADR** の側へ振り分ける
- `validity: 有効` な既存 ADR が定める枠組みの中に収まり、**その枠組みを保ったまま別の面（適用範囲・条件・パラメータ値・理由付け）を追加するだけ**の場合 → 新規 ADR を起こさず、当該 ADR への**非core 改訂**の側へ振り分ける。同じ主題を複数の ADR へ分散させないためである

いずれも振り分け先の提示であって、分類（core／非core／些末）の確定ではない。分類基準の実体、確定の手続き（利用者へ問うこと）、安全則（迷えば core 寄り＝新規 ADR に倒す）、選んだ操作の手順と変更履歴の残し方は、すべて `edit-decision.md` に従う。本節でこれらを再定義しない。第2分岐へ振り分けた対象も、当該 ADR の枠組みの中に収まるかを同ファイルが分類の前に問い直し、収まらなければ新規 ADR の側へ戻す。退役（上書き済み・廃止済み）した ADR は同ファイルの凍結原則により決定内容の改訂を受けないため、上の2分岐は掛からない。

**ADR 化しない（合計3点未満）の行き先**

次の3分岐を上から順に当てはめ、最初に当たった分岐へ置く。第3分岐は第1・第2分岐のどちらにも当たらないものを受けるため、どの対象もちょうど1つの分岐へ置かれる。必要条件が成り立たず点数を数えなかった決定にも、同じ3分岐を掛ける。

- **第1分岐: 規範を担う保持先が値域(A)に在る** → その資産である**実装・テスト資産・操作手順**に置く。値域(A)は `adr-scoping.md`「判定する入力の値域と定義」の項目3の保持先の値域を指す。採用理由と既知の限界は当該資産のコメント等に併記して自己完結させる
- **第2分岐: 第1分岐に当たらず、次の2条件の少なくとも一方に当たる規範** → **共有規約文書**（規約ファイル・プロジェクト指示）に置く。2条件は選言であり、一方に当たれば足りる。採用理由と既知の限界は当該文書へ併記して自己完結させる。併記の未了が項目3の点数を動かすのは、同居判定の1点条件に当たる決定に限る（併記により値域(B) が成立し0点へ移る）。当たらない決定では点数は動かないが、併記を欠いたまま放置すれば理由は次の判定者へ渡らずに失われる
  - **後続の変更を拘束する**: 規範の本文が、判定対象の変更より後に行われる変更へ、何をする・しないを指示している
  - **適用先が2単位以上ある**: 項目2で数えた適用先が2単位以上である。何を1単位と数え、何を除外するかは `adr-scoping.md`「判定する入力の値域と定義」の項目2の定めが正本であり、本分岐は独自に数え直さない。必要条件が成り立たず点数を数えなかった決定でも、本条件のために同じ定めで適用先を数える
- **第3分岐: 第1・第2分岐のいずれにも当たらない判断** → **その変更の説明**に書く。変更の説明とは、その変更が PR を経る場合は PR 説明、経ない場合はコミットメッセージをいう。後続の変更を拘束せず、適用先も1単位以下であるため、単一の変更に閉じる判断である。この記録は、`adr-scoping.md`「起票のタイミングとエスカレーション」の条件1が数える保留中の記録に当たらない。他の箇所で同じ問いが再出したときは、改めて4項目から判定する

**第1分岐の入口と置き場所の区別**: 入口を決めるのは、規範を担う保持先が値域(A)に在るかどうかだけである。第1分岐の入口と、項目3が値域(A)として0点に数える保持先は、同じ集合を指す。値域(A)が散文だけの記述を含まないことも、`adr-scoping.md` の同じ節が定めるとおりである。「実装・テスト資産・操作手順」は入口に当たった規範の置き場所の呼び名であり、入口の条件ではない。値域(A)の保持先が在るかは、判定対象の変更を適用した後の状態で見る。同じ変更で実装や検査を足して規範を担わせる場合は、第1分岐に当たる。行き先は、判定対象の変更が規範をどこへ置くかを決めるものだからである。したがって、実装ファイル・テスト・手順書の中に書かれていても、規範を担わない散文だけの記述しか持たない規範は第1分岐に当たらない。

違反を検査する仕組みの状態（項目4 の `現に阻止`／`警告どまり`／`検査なし`）は、第1分岐の入口を左右しない。値域(A)の保持先が在れば、検査が警告どまりで阻止しない場合も、検査が皆無の場合も第1分岐に置く。阻止まで動かすか、検査を足すかは当該資産の実装の課題であり、置き場所を変えない。値域(A)の保持先が無い規範は、検査の状態を問わず第1分岐に当たらない。値域(A)に当たるか迷う場合は、第1分岐に当たらないものとして第2分岐の判定へ進む。

**「後続の変更を拘束する」の判定**: 入力は規範の本文だけであり、作業者の人数や将来の見込みは入力にしない。判定対象の変更で何を採ったかだけを述べ、以後の変更への指示を含まない判断は当たらない。当たるか迷う場合は当たるものとする。共有規約文書へ置いた規範は不要になれば外せるが、変更の説明にだけ置いた規範は後続の変更から読まれないためである。

ただし既に記録済みの決定そのものへ触れる編集は、粒度判定の点数ではなく `edit-decision.md` の分類が入口となる。スコア境界未満であることは、既存 ADR への改訂を妨げない。

この一般則が最も効くのは、ADR 運用そのものや開発の進め方を主題とする規範である。この層は規範が実装・テスト資産・操作手順の側で既に強制されていることが多く、そのぶん記録の不在が欠落と誤読されやすい。

**起票の時点に達していない決定の行き先**

合計3点以上と判定しても、`adr-scoping.md`「起票のタイミングとエスカレーション」が定める起票の時点に達していない決定は、前掲「ADR 化する」の2分岐へ進めず保留する。保留中の決定は次のとおり置く。

- **判定の記録** → **その変更の説明**（前掲の第3分岐の定義による）に書く。記録には次の4点を含める。第1に決定の内容、第2に必要条件で特定した却下代替（採った選択肢・却下した選択肢・却下理由）である。第3に4項目の点数と `adr-scoping.md`「判定に添える申告」が求める申告（適用先の列挙を含む）、第4に起票の時点に達していないため保留した旨である。後の判定が起票の時点を判定するとき、この記録の選択肢と適用先の列挙が照合の入力になる
- **決定の本文** → 前掲「ADR 化しない」の3分岐が決める置き場所に置く。第3分岐に当たる場合は、判定の記録と同じ変更の説明に置くことになる。第1・第2分岐に当たる場合、変更の説明に書いた判定の記録は本文の置き場所の代わりにならない
