# 要求の構造化

要求を3層の正本（RDRA の表・要求票・例）へ落とし、機械検査を通し、規則間の矛盾が突き合わせで潰れた状態で終える。

書式・置き場・検査の規則の正本は `${CLAUDE_PLUGIN_ROOT}/references/format.md`。着手前に読む。雛形は `${CLAUDE_PLUGIN_ROOT}/references/templates/`。

## 引数

要求の出どころ（会話の内容・ファイルのパス・Issue 等）。無ければ会話の直近の要求を使い、それも無ければ何を構造化するかを問う。

## 手順

### 起点と根（全ての手順に掛かる）

起点の渡し方と替え方・根の取り方・注記の伝え方は `${CLAUDE_PLUGIN_ROOT}/references/starting-point.md` に従う。着手前に読む。このスキルでは次のとおりとする。

- 扱っているファイルとは、利用者が直す対象として示した正本のファイルかディレクトリである。要求の出どころ（メモ・Issue 等のファイル）は起点にしない
- 注記を伝えたら、答えを待ってから続ける
  - 移すと答えたら、対象を根の置き場へ移し、移した先を以後の起点にする
  - 独立させると答えたら、その領域を根にする（`.living-spec.json` を置くか `docs/rdra` を作る）。その根を以後の起点にする

### 1. 現状を読む

`node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" check [起点]` を実行し、結果で分ける。標準エラーの1行目が「living-spec の検査器が、このプラグインの前提より古い」なら、注記より先に下のその分岐で扱う。それ以外で注記が出ていれば、下の分岐より先に、`starting-point.md` の「注記の伝え方」の問いを済ませる。答えに応じて起点を替えたら、その起点で手順1 をやり直す。

- 終了コード 2 で「検査器が見つからない」: 表示された導入の手順を利用者に示して止まる。検査器なしで構造化を進めない
- 終了コード 2 で標準エラーの1行目が「living-spec の検査器が、このプラグインの前提より古い」: その行を利用者に示して止まる。続く出力に下の分岐の文面があっても当てはめない。古い検査器で構造化を進めない
- 終了コード 0 か 1: 1行目から根を取る。根の `.living-spec.json` があれば置き場を読む。無ければ既定（`docs/rdra` 等）。表・要求票・例を読み、検査の結果から出発点の違反を把握する。違反があれば、要求の構造化より先に直すかを利用者に問う
- 終了コード 2 で「表の置き場が見つからない」: 1行目から根を取り、置き場を同じく読む。その根の置き場へ新規に始める
- 終了コード 2 で「正本が見つからない」（1行目が無い）: 根にするディレクトリを利用者に問う（既定は作業ディレクトリ）。そこへ新規に始め、作った根を以後の起点にする（`starting-point.md` の起点を替える3つ目の場合）
- それ以外の終了コード 2: 標準エラーを示して止まる。終了コード 2 の理由は `format.md` の「検査の規則」の終了コードが定める
- 新規に始めるときは、可視化の書き出し先（既定 `.cache/living-spec/`）を `.gitignore` へ足すかを利用者に問う

### 2. 要求を表へ写す

要求の文から、アクター・外部システム・情報・状態モデル・UC・条件・バリエーションを拾い、表へ足す。既存の要素と同じものは既存の名前を使い、新しい名前を作らない。

- 名前は業務の言葉で、利用者が実際に使う語にする。1つの概念に1つの名前
- 条件の中身（どういうときに満たすか）は条件の表の `条件の説明` だけに書く。要求文・例に書き直さない
- 状態の遷移は `state` 表に1遷移1レコードで書き、遷移 UC を付ける
- 情報を表へ写すときは、親の情報と一体で作られ扱われる集約の子か、独立した情報かを決める。集約の子なら `集約の親` に親を書き、UC の `情報` には親を挙げる。要求の文から決まらなければ、推測で埋めず問いとして溜める。書き方は `format.md` の「集約の子」が定める
- 決まっていない要素（試す段階の仮説）は `仮説` キーを付けて登録だけにとどめ、要求票・例は書かない
- 要求の文から決まらない業務の事実（誰が・いつ・何を基準に）は、推測で埋めず問いとして溜める

アーキテクチャ特性に `分類` を書くとき、または既存のレコードに `分類体系` を足すときは、`分類体系` を次のとおり決める。値の書き方は `format.md` が定める。

- 特性の表の既存のレコードから `分類体系` の値を集める。値は前後の空白を除いた文字列で比べ、「不明」は数えない。
- 値が無ければ（プロジェクトで最初の分類なら）、どの体系で分類するかを利用者に問う。`format.md` の `分類` の目安を示し、既定は置かない。
- 値が1つなら、それにそろえ、その体系の語で分類する。別の体系を採るとき（その体系で分類できない特性など）は利用者に問う。
- 値が2つ以上あれば、どれにそろえるかを利用者に問う。
- 既存のレコードに `分類体系` を足すときは、集めた値によらず、どの体系で分類したかを利用者に問う。推測で埋めず、答えを `format.md` のとおりに書く。

### 3. 問いを解く

溜めた問いを、業務の言葉で1件ずつ利用者に問う。表の語や記号を前に出さず、「申請を差し戻したら、前の内容は残りますか」の形で問う。情報の形・状態の数が変わる問いを先に問う。答えは表へ反映する。

### 4. 要求票と例を書く

仮説でない UC ごとに、雛形に沿って要求票と例を書く。例を求めない行は `format.md` の「例」が定める。

- 要求文は EARS の型。UC の条件と、UC が遷移先にする状態を RDRA 欄に挙げる
- 例のルール名は要求文をそのまま写す。例は規則の境界を分けるものに限り、1ルール3件を目安にする。束と組み合わせの扱いは `format.md` の「例」に従う
- 既存の票・例を直すときは、要求文とルール名を両方直す

### 5. 機械検査を通す

`node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" check [起点]` と `check --doc-missing [起点]` を実行し、違反を0件にする。起点は手順1 と同じものを渡す（手順1 の後に3つの場合のどれかで替えたときは、替えた起点）。PostToolUse フックが入っていれば、表・票・例の編集のたびに全体検査が走り、違反は編集の直後に返る。違反を消すために検査を外したり、規則を緩める書き方へ逃げたりしない。

### 6. 規則間の矛盾を突き合わせる

機械検査は意味を見ない。`rule-crosschecker` エージェントへ、根（直近の `check` の1行目の根）・置き場・この回で足したり変えたりした要素の名前と、plugin root path（`${CLAUDE_PLUGIN_ROOT}`）を渡し、独立した文脈で矛盾を探させる。起草の経緯は渡さない。

返った指摘を全て読んでから扱う。同じ原因の指摘は束ね、1つの直し方で直す。

- 指摘の箇所を直す前に、構造へ戻る。同じ状態・条件・情報に触れる他の規則を読み、表の分け方（条件・状態・情報の切り方）を見直す。指摘の箇所だけを継ぎ当てで直さない。分け方を変えると業務の事実が変わるなら、手順3 の形で利用者に問う
- 直す表の説明・要求文・例へ、実装の語を持ち込まない。何を実装の語とみなすかは `format.md` の「要求の層の語」が定める。実装の語なしで書けないときは、業務の言葉へ戻す。戻せなければ、手順3 の形で利用者に問う
- 基準の空白（C9）の指摘は、推測で埋めて直さない。evidence の表の側の `<path:行>` が指すレコードの、挙がった欄へ、未決の項目として記録する（書き方は `format.md` の「未決の印」）。記録したら、suggestion の問いを手順3 の形で利用者に問う。答えが出たら欄の本文を直して項目を外し、出なければ項目を残す。C9 には、重さによらず次の blocker・warning の項を当てない
- blocker は直す。どちらの正本を直すかが業務の判断なら、両方の規則を並べて利用者に問う
- warning は直すか、直さない理由を利用者に示す。
- 分類体系の混在の指摘は、自分の判断では直さず、意図したものかを利用者に問う。意図していなければ、そろえる体系を利用者に問い、その体系で分類し直す。手順2 で利用者が体系を答えた回は、その答えで生じた混在を問い直さない。利用者が意図したと答えた混在も、同じ回の中では問い直さない。
- 直したら手順5 へ戻る。突き合わせは、直した範囲を焦点にもう一度回す。分け方を変えたときは、変えた表の要素も焦点に入れる。C9 を記録しただけで欄の本文を変えていない回は、手順5 を通したら突き合わせを回し直さない
- 終わるのは、直近の突き合わせの指摘のうち、記録済みでない C9 が0件で、C9 以外の blocker が0件になったときである。一覧は `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" check --open [起点]` で取る（起点は手順5 と同じ）。記録済みの C9 とは、evidence の表の側の `<path:行>` が指すレコードの欄が、一覧の行で印に覆われているものをいう。覆われているかは `format.md` の「未決の印」が定め、対象の文字列では照らさない

### 7. 描いて見せる

`node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" render [起点]` で可視化を描き（起点は手順1 と同じ。替えたときは替えた起点）、書き出した場所と開き方を `view` スキルの手順で示す。

## 出力

終えたときに次を報告する。

- 足した・変えた要素（表ごと）、要求票・例のファイル
- 機械検査の結果（全体検査・書き漏らしの検査それぞれの違反件数）
- 突き合わせの結果（blocker・warning の件数とそのうちの C9 の件数、直したもの、直さなかったものと理由、未決として記録したもの）
- 表の分け方を見直した結果（変えたものと変え方。変えなかったなら、その旨）
- 利用者の判断で決めたこと
- 可視化の書き出し先
- 残った問い（あれば）。未決の項目は、終わりに取った `check --open` の一覧を示す

## 注意

- 表・票・例は正本で、可視化は派生物。可視化の HTML を手で直さない
- 1つの事実を2層に書かない。食い違いの種になる
- 終わりの判定は、機械検査の違反0件と、手順6 の終わりの条件の両方。片方だけで終えない。未決として記録した問いは、終わりを妨げない
