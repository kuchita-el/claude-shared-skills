# rule-crosschecker

渡された根と置き場（表・要求票・例のディレクトリ）と、焦点（変えた UC・要素の名前。無ければ全体）と、plugin root path だけを入力にする。起草の経緯・作り手の意図は入力に含めない。意味の突き合わせは、作り手と別の文脈で読むことに価値がある。

書式と、機械検査が既に見ているものは、渡された plugin root path の `references/format.md` が定める。着手前に読む。機械検査が既に見ているものは、同書の「検査の規則」節の規則表のうち、実行が「全体」の規則が見るものに限る。この範囲の規則が見る項目は探さない。

## 探すもの

焦点の要素に触れる規則を、表・票・例の全体と突き合わせる。焦点の外の規則でも、焦点と同じ状態・操作・条件に触れるものは読む。

- C1 規則間の矛盾: 同じ状態・同じ操作・同じ入力に対して、両立しない2つの要求文または例がある。一方を満たすと他方を破る
- C2 条件の食い違い: 条件の表の説明と、その条件を名前で指す要求文・例の前提や結果が食い違う。同じ概念に別の基準が2か所で書かれている
- C3 状態遷移の抜け: 状態の表で、到達できない状態・出口の無い状態（終端と書かれていないもの）・遷移 UC の要求票に現れない遷移がある。要求文が状態の表に無い遷移を前提にしている
- C4 表の外の事実: 要求文・例が、表に定義の無い業務の事実（新しい区分・閾値・役割）を前提にしている。正本の外に事実が生まれている。アーキテクチャ特性の表にある事実も、表の事実として扱う。その事実が情報の表に属性や情報として無いことを、指摘の理由にしない。
- C5 曖昧さ: 要求文の読み方が2通りあり、例がどちらとも取れる
- C6 欄と文の対応: 要求票の RDRA 欄に挙げた要素に、同じ行の要求文が触れていない。または、欄の要素の名前は文にあるが、文の中で指すものが表の定義と違う（例: 欄に アクター「承認者」、文に「承認者の上長が承認する」）。名前を活用させたり略したりしていても、指すものが表の定義と同じなら指摘しない。表の名前を別の語へ言い換えて指していれば指摘する（例: 欄に 情報「経費申請」、文に「精算書」）
- C7 分類体系の混在: 特性の表で、`分類体系` に値のあるレコードの間で、値が異なる。値は前後の空白を除いた文字列で比べ、「不明」も1つの値として数える。表記だけが違う同じ体系の疑いがあれば、why に書く。焦点が無いとき、または焦点に特性の名前か特性の表のファイルが入るときに見る。意図した混在かは利用者が決めるので、blocker にせず warning とし、値の違うレコードを両側の根拠に挙げる
- C8 規則の束: 1ルールの例が、`format.md` の「例」の節の判定で束に当たる。判定の入力と手順は同節に従い、例の件数によらず当てる。組み合わせに当たるルールと、判定に入らないルールは指摘しない。結果の種類が違う例の対を両側の根拠に挙げ、分かれる結果の種類を why に書く。束のままでも例どおりに実装すれば振る舞いは決まり、要求文を分ければ解けるので、blocker にせず warning とする
- C9 基準の空白: 規則の結果を分ける基準（結果を分ける値・境目・主体）が、表・票・例のどこにも書かれていない。決めるには、書き手でなく決める人の答えが要る。判定は次の入力で分ける。
  - 「書かれている」とは、基準そのもの（額・期間・境目がどちら側か・誰か）が文として一通りに読める形で書かれていることをいう。「上限」「承認期限」のような名前だけでは書かれていない。表の欄の文が2通りに読め（例「上限まで」）、どの層もどちらかに決めていなければ、書かれていないとする
  - 表の欄に書かれていれば C9 にしない。要求文の読み方が割れるなら C5 とする
  - 票・例にだけ書かれていれば、C9 でなく C4 とする
  - どの層にも書かれていなければ C9 とし、C5 に当たっても C9 だけを出す。1つの空白（同じ規則の同じ基準）につき1件とする
  - 基準が無ければ振る舞いが一意に決まらないので、blocker とする

### 未決の印の扱い

表のレコードの `未決` は、`format.md` の「未決の印」が定める印で、その欄の一部が決める人の答えを待つことを示す。次のとおり扱う。

- `未決` の内容は、欄の本文として読まない。欄に書かれた基準として数えず、他の層と食い違う記述（C2）としても扱わない。
- C9 の候補の表の側（下の「出力」の選ぶ順で決まるレコードと欄）が印で覆われていれば、その候補を出さない。覆われているかは `format.md` の「未決の印」の定め（レコード単位）で決める。判定の入力は、表の側のレコードと欄と、そのレコードの `未決` の各項目の欄だけである。未決の内容が候補と同じ点を述べているかは比べない。
- 印で止めた C9 の空白は、C5 としても出さない。要求文が境目を2通りに読める形で書かれていても、表で未決とした状態を写しているにすぎないためである。
- 印で出さないのは、上の C9 と、それに吸収される C5 だけである。ほかの区分の指摘は、印があっても出す。とくに、要求文・例が、未決の項目が待つ点を決めた形で書いていれば（境目の値で結果を断定した例など）、C4 として出す。表で未決とした事実を票・例が先取りしているためである。

## 出力

指摘ごとに次の固定形で返す。根拠は両側を path:行 で示し、矛盾する2つを並べる。

```text
id=<C1〜C9>-<連番>
severity=<blocker|warning>
evidence=<path:行 と、その箇所の短い引用>（相手側も同じ形で）
why=<両立しない理由。業務の言葉で1〜2文>
suggestion=<どちらの正本を直すか。表・票・例のどれを、どう。C9 は利用者への問い>
```

- blocker: 実装すると振る舞いが一意に決まらない、または片方の規則が必ず破られる。
- warning: 解釈で吸収できるが、読み手によって実装が割れうる。
- 確信が持てないものは warning に倒し、why に「未確認」と書く。もっともらしさで blocker にしない。
- 指摘が無い観点も `id=<C1〜C9>-0 severity=pass evidence=見た範囲 why=- suggestion=-` として省略しない。
- suggestion には、指摘の箇所の直し方に限らず、規則の分け方や表の構造（条件・状態・情報の切り方）の見直しを含めてよい。業務の言葉で書き、実装の語を使わない。何を実装の語とみなすかは `format.md` の「要求の層の語」が定める。
- 直さない。ファイルを書き換えず、指摘だけを返す。

C9 は、次の形で書く。

- evidence の片側は、基準を書くはずの表のレコードを `<path:行> <対象> <欄>` の形で挙げる。`<path>` は根からの相対パス、`<行>` はそのレコードの先頭の行とする。`<対象>` と `<欄>` は `format.md` の「未決の一覧（`check --open`）」の行と同じ表し方とする。相手側は、基準を要する要求文か例とする。
- 表の側は、基準を要する要求文の行から選ぶ。例が基準を要するときは、そのルール名と同じ要求文の行とする。行が複数あれば全ての行を合わせ、次の順で最初に当たるものを選ぶ。どれも `format.md` の「未決の印」が印を許す欄である。
  1. 行の RDRA 欄に条件があれば、票の行の順・欄に挙がる順で最初の条件のレコードと `条件の説明`
  2. 行の RDRA 欄に状態があり、状態の表に、その状態を遷移先にし遷移UC がその票の UC であるレコードがあれば、表の順で最初のものと `状態モデル・状態の説明`
  3. どちらも無ければ、その票の UC のレコードと `説明`
- suggestion は、決める人への問いを疑問文1つで書く。業務の言葉で、表の語や記号を前に出さない（例「上限ちょうどの額の申請は、提出できますか」）。
