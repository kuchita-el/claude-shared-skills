# 書式と検査の正本

RDRA の表・要求票・例の書式と、それらに書く語の層の基準と、検査器（`living-spec`。導入は README）が掛ける規則と、基準の版との描き分けと、基準の版から変わった要素の一覧と、未決の一覧の定義の正本。雛形（`templates/`）とスキルはここを参照し、書式を書き直さない。

## 3層と正本の分担

事実の種類ごとに正本を1つに決める。同じ事実を2層に書かない。

| 層 | 正本が持つ事実 | 置き場（既定） |
|---|---|---|
| RDRA の表 | 全体の構造。アクター・外部システム・情報・状態モデル・UC・条件・バリエーション・アーキテクチャ特性と、その間の参照。条件の中身・名詞の定義 | `docs/rdra/*.yaml` |
| 要求票 | UC ごとの要求文（EARS の型）・理由・要求文が触れる RDRA の要素 | `docs/requirements/*.md` |
| 例 | 要求文ごとの合否の境界（Gherkin） | `docs/examples/*.feature` |

`検証方法` を書いたアーキテクチャ特性だけに触れる要求文の合否は、RDRA の表の特性の `検証方法` が持ち、例の層は持たない。どの行がそれに当たるかは「例」が定める。

名前は RDRA の表の語へ揃え、別の語へ言い換えない。要求票の表題と RDRA 欄、例の機能名は表の名前をそのまま書き、例のルール名は要求文をそのまま写す。検査器はこれらの名前の一致で層をつなぐ。要求文は業務の文として書き、表の名前を活用させても略してもよい。

## 置き場の設定（`.living-spec.json`）

根（下の「根の決め方」）に置くと既定を上書きする。置き場の値と `output` は根からの相対パスである。全てのキーは省略できる。未知のキー・型の誤りは終了コード 2。

```json
{
  "tables": "docs/rdra",
  "requirements": "docs/requirements",
  "examples": "docs/examples",
  "output": ".cache/living-spec/index.html",
  "hook": true
}
```

- `output`: 可視化の書き出し先。基準の版との描き分けは、ここから決まる別のファイルへ書く（「基準の版との描き分け」）。どちらもそのつど生成する派生物で、手で直さない。`.gitignore` へ入れる
- `hook`: `false` にすると、その根の編集で PostToolUse フックが検査も描画もしない（違反で AI の編集を止めたくない場合）。設定の無い領域や別の根の編集には効かないので、止めたい根ごとに置く

### 根の決め方

目印は次の2種である。

- `.living-spec.json` を持つディレクトリ
- `docs/rdra` をディレクトリとして直下に持つディレクトリ。設定が無ければ、中身が `{}` の設定とみなす

両方を持つディレクトリでは、設定が置き場を決める。

ただし `docs` か `docs/rdra` が自身の `.living-spec.json` を持つときは、その `docs/rdra` を親の目印に数えない。設定を持つ側が根になり、誰も設定していない親は根にならない。

起点から親へ1段ずつ辿り、最も近い目印を根にする。目印が入れ子になっていれば、起点に近い方が根になる。起点は次のとおりである。

- フック: 編集したファイル
- `check`・`render`・`diff`: 引数のパス（ファイルならそのディレクトリ）。引数が無ければ作業ディレクトリ

辿る範囲には境界がある。境界は、起点から上へ辿って最初に見つかる、submodule でない `.git` を持つディレクトリである。`.git` はディレクトリでもファイル（worktree）でもよい。submodule は、上の作業ツリーの `.gitmodules` の `path` に載るディレクトリである。境界のディレクトリ自身は目印になりうるが、その上へは辿らない。境界まで目印が無ければ、正本は無い。

git の外では境界を設けない。このため無関係な祖先の目印を拾いうるので、`check` の1行目で根を確かめる。

起点が同じなら、根はツールを起動した場所によらない。フックも、Claude Code を起動したディレクトリを根にしない。

### パスの比べ方

根の探索・置き場の検証・範囲の判定は、パスを字面のまま比べる。シンボリックリンクは解かない。

同じファイルを別の名前で指せる構成がある。シンボリックリンク、ハードリンク、大文字小文字や Unicode の正規化が違う綴りである。この構成では、置き場の直下のファイルを、置き場の名前どおりのパスで編集する。別の名前で編集すると、フックは検査しない。

根の外を指すシンボリックリンクの置き場は、設定の誤りにならない。

### 複数の根

1つのリポジトリに根を複数置ける。各根は独立した正本である。根をまたぐ参照と、複数の根の一括の検査はしない。`output` は根からの相対なので、根ごとに別の HTML になる。

### 置き場は根に属する

各置き場（`tables`・`requirements`・`examples`）は、その根に属さなければならない。属するとは、置き場から同じ規則で上へ辿って最も近い目印が、その根自身であることをいう。置き場がまだ無くても検証する。無いディレクトリは目印にならない。

外れる形は次の3つである。いずれも設定の誤りで、終了コード 2 になる。

- `..` で根の外へ出る。
- 別の根の中に入る。例: 置き場の値が `<X>/docs/rdra` なら、`<X>` が `docs/rdra` を直下に持つ目印になり、置き場はその中に入る。
- 根と置き場の間に、submodule でない `.git` がある。

避け方は、置き場を根の下に置き、間に別の根や submodule でない `.git` を挟まないことである。別の正本にしたい領域は、その領域を根にする。別の作業ツリーを置き場にしたいときは、submodule として登録する。

置き場の値が先頭以外の位置で `docs/rdra` の並びを含む形（例: `x/docs/rdra`）は、置き場がまだ無くても、別の根の中に入る形の誤りとする。作ると、上のディレクトリ（`x`）が目印になるからである。避け方は、別の名前の置き場にすることである。先頭の位置の並び（例: `docs/rdra/req`）は、この誤りにならない。

外れた置き場の中のファイルを編集しても、フックはその根の誤りを示さない。そのファイルからは、別の根が決まるか、根が決まらないためである。誤りを示すのは、その根に決まる `check`・`render`・`diff` と、その根の範囲（下の「検査器が読む位置とフックの範囲」）内のファイルの編集である。

### 検査器が読む位置とフックの範囲

検査器が読むのは、置き場の直下のファイルと、根の `.living-spec.json` だけである。置き場の下の深い階層は読まない。

根の範囲は、置き場の直下のファイル、根の `.living-spec.json`、置き場そのものかそれを含むディレクトリである。最後のものは、`check`・`render`・`diff` の起点にディレクトリを渡すときに当たる。

フックは、根の範囲内のファイルの編集でだけ、その根を全体検査し、`output` の HTML を描き直す。描き分けの HTML の扱いは「基準の版との描き分け」が定める。次のときフックは何もしない。

- 正本が無い（目印が無い、または根に表の置き場が無い）
- 根が決まる前の探索で、読めないファイルがある（どの根の編集かが分からない）
- その根の `hook` が偽である
- 範囲外のファイルを編集した

根の `.living-spec.json` を読めないときは、範囲を決められない。このときフックは、根が決まる全ての編集で止まる。

次のときフックは編集を止める。

- 違反がある
- 検査器が動かない
- 根が決まった後に、探索を続けられない（読めないファイルがある等）
- `.living-spec.json` を読めない
- 置き場が根に属さない
- 中継（`scripts/run.mjs`）が検査器をこのプラグインの前提より古いと判定し、その検査器が検査したか止めた。違反が無くても止める

設定の誤りと読み取りの失敗では、CLI と同じ文面を標準エラーへ出す。前提より古い検査器では、「living-spec の検査器が、このプラグインの前提より古い」で始まる行も出す。可視化を描けなくても、編集は止めない。ただし前提より古い検査器では止める。

## RDRA の表

各表は `<tables>/<id>.yaml`。トップはレコードのシーケンス、各レコードはマップ。値は文字列か文字列のシーケンス（list）である。ただし `未決` の値は `<欄>: <未決の内容>` の1組のマップのシーケンスである（「未決の印」）。「、」区切りと書いたキーは1つの文字列に「、」で並べる。表のファイルが無ければ空の表として扱う。

| id | 名前キー | ほかのキー |
|---|---|---|
| `actor` | アクター | 役割、社内外 |
| `external-system` | 外部システム | 役割 |
| `information` | 情報 | 属性・関連情報・状態モデル・バリエーション（いずれも「、」区切り）、集約の親、説明 |
| `state` | 状態モデル | 状態、遷移UC、遷移先状態、状態モデル・状態の説明 |
| `use-case` | UC | アクター・外部システム・情報・条件（いずれも list）、説明 |
| `condition` | 条件 | 条件の説明、バリエーション・状態モデル（「、」区切り） |
| `variation` | バリエーション | 値（「、」区切り）、説明 |
| `architecture-characteristic` | アーキテクチャ特性 | 分類、分類体系、説明、検証方法 |

- アーキテクチャ特性の `分類` は、品質特性の体系（例: 『ソフトウェアアーキテクチャの基礎』、ISO/IEC 25010）の語を目安に付け、1つの体系に固定しない。体系の定義はここへ写さない。写しは古び、体系の改善が届かない。
- `architecture-characteristic` で `分類` に値を書くレコードは、`分類体系` に、分類に用いた体系の名前を書く。分類の流儀は時期で変わるため、体系はレコードごとに記録する。値は自由な文字列で、体系が分からなければ「不明」と書く。空文字・空白だけの文字列は、書いていないものとみなす。`分類`・`分類体系` のキーだけを置いて値を書かない行は、値の型の誤りになる。
- `state` は1レコードが1遷移。同じ状態モデル名のレコードを並べる。初期遷移は `状態` を省略または空にし、終端の状態は `遷移UC`・`遷移先状態` を省略または空にする
- どの表も任意のキー `仮説`（list。例 `[H1]`）を持てる。キーがあれば仮説、無ければ事実。検証されたらキーを外し、棄却されたらレコードを外す。仮説の UC には要求票を求めない
- どの表も任意のキー `未決` を持てる。書くのは、レコードの文で書く欄のうち、決まっていない部分である。下の「未決の印」が定める
- 情報の表のレコードは任意のキー `集約の親` を持てる。そのレコードが集約の子であることと、その親を示す。下の「集約の子」が定める
- UC を試みる役割は、条件で通されるかによらずアクターである。拒否の例に使う、条件を満たさない役割もアクターの表に載せ、その例の UC の `アクター` に挙げる。どの役割を通すかは、条件の `条件の説明` が分ける。

### 未決の印

未決の印は、文で書く欄のうち、中身の一部がまだ決まっていないことを示す。書くのは、表のレコードの `未決` キーである。仮説はレコード単位で「試す段階」を示す。未決はそれと別に、欄の一部が「決める人の答えを待つ」ことを示す。

```yaml
- 条件: 提出可能
  条件の説明: 経費が1件以上あり、合計額が上限の範囲に収まる
  未決:
    - 条件の説明: 上限の境目（上限ちょうどを含むか）が出典で揃っていない
```

本文は境目のどちら側かを決める語（「以下」「未満」）を使わず、決まった部分だけを書く。

- 値は1件以上の項目の並びである。各項目は `<欄>: <未決の内容>` の1組のマップとする。
- 欄に書けるのは、その表の文で書く欄だけである。`actor`・`external-system` は `役割` を書ける。`condition` は `条件の説明`、`state` は `状態モデル・状態の説明` を書ける。ほかの表は `説明` を書ける。
- 未決の内容には、何が決まっていないかを書く。空白だけでない文字列とする。
- 決まったら、欄の本文を直し、その項目を外す。項目が尽きたらキーごと外す。項目の無い `未決` は書式の誤りである。
- 欄の本文には、未決を注記として書き込まない。本文は決まった部分だけを書き、決まっていない部分は `未決` に分ける。
- 要求票と例には未決の印を付けない。未決は中身が決まっていないという事実で、その正本は表である。要求文と例は、表の名前でその要素を指す。

表のレコードの欄が印で覆われているかは、レコード単位で決める。表のファイルと行で示したレコードの欄が覆われているとは、その行を含むレコードの `未決` に、その欄を挙げた項目があることをいう。レコードの範囲は、その先頭の行から、次のレコードの先頭の行の手前まで（最後のレコードはファイルの終わりまで）である。

- 未決の一覧（`check --open`）の行で確かめるときは、行の `<ファイル>` が同じで、`<行>` がそのレコードの範囲にあり、`<欄>` が同じ行があれば覆われているとする。
- `<対象>` の文字列では照らさない。`state` の表では1レコードが1遷移だが、`<対象>` は遷移元の状態しか持たず、遷移元が同じ別の遷移と区別できないためである。

`未決` は表の構造に閉じたキーである。欄の本文の中に書く記法は採らない。本文の中の記法は新しい字句の規則を要する。また、表と同じ書き方を要求票・例の中でも書けてしまい、表の外の印を構造で拒めない。

### 集約の子

集約の子は、親の情報と一体で作られ、扱われる情報である（例: 「経費申請」に対する「経費明細」）。UC が親を扱えば、子も一緒に扱う。そのため UC の `情報` には親だけを挙げればよく、子を挙げなくても参照の切れにならない。独立した情報は、これまでどおり UC から指す。

```yaml
- 情報: 経費申請
  関連情報: 従業員
- 情報: 経費明細
  集約の親: 経費申請
```

- `集約の親` の値は、親の情報の名前1つの文字列である。空白だけの値は、書いていないものとみなす。
- キーを持つ情報が集約の子で、持たない情報が独立した情報である。どちらかは、このキーの有無だけで決める。名前や `説明` の文からは推定しない。
- 親は情報の表のレコードである。表に無い名前を書くと `undefined-reference` に当たる。
- 親も集約の子でよい（孫）。親を辿ると、`集約の親` を持たない情報で終わる。辿って自身へ戻ると `aggregate-cycle` に当たる。親が自身である場合も含む。
- 集約の子は、親が接続していれば接続している（「検査の規則」の「参照の切れ」）。接続は親から子への向きだけで、子が UC から指されても親は接続しない。
- 子を UC の `情報` に併せて挙げてもよい。挙げても違反にならない。
- 親が仮説のレコードでも、UC から指されていれば子は接続している。仮説の親がどの UC からも指されなければ、事実の子は `unconnected` に当たる。子も仮説なら、`仮説` キーで判定から外れる。

`関連情報` で辿れる情報は、接続しているとみなさない。`関連情報` は、独立した情報どうしの参照（例: 「経費申請」から「従業員」）にも使う。辿れたら接続しているとみなすと、独立した情報まで参照の切れを逃れる。`関連情報` の意味は変えず、集約の子は別のキーで示す。

キーは子の側に置き、親の側に子を並べる形（`集約の子: 経費明細、…`）は採らない。親の側に並べると、1つの子を2つの親が挙げうる。それを止める規則が別に要る。また、子を足すたびに親のレコードが変わり、基準の版との差分で親が「変わった」になる。子の側に置けば、親は1つに決まり、子を足しても親のレコードは変わらない。

設計の可視化（`render`）は、UC の縦串の情報の表で、UC が挙げる情報の項に、その集約の子の名前を添える。孫は子の後ろの括弧に添える。子を UC に書かなくても、縦串で読めるようにするためである。

## 要求票

UC 1つにつき1件。雛形は `templates/requirement.md`。

- 表題 `# 要求票: <UC 名>`。UC 名が照合のキー（ファイル名は照合しない）
- `## 理由` に UC が要る理由、`## 仕様` に番号つきの要求文を1行ずつ
- 各行の直下に字下げした `- RDRA: <種類>「<名前>」、…`（状態は `状態「<状態モデル>/<状態>」`、参照が無ければ `なし`）と `- 理由: …`
- 種類の語彙: アクター／外部システム／情報／状態モデル／状態／UC／条件／バリエーション／アーキテクチャ特性
- 見出しは `## 理由` と `## 仕様` の2つだけで、1回ずつ。仕様の節には番号つきの要求文と、その直下に字下げした `- RDRA:`・`- 理由:` の欄（各1回、書くことが無ければ `なし`）だけを書く。外れた箇所は `requirement-structure` が出す
- HTML コメントの中は読まない（空行とコメントは自由に置ける）

## 例

UC 1つにつき1ファイル。雛形は `templates/example.feature`。

- `# language: ja`。機能（Feature）の名前が UC 名
- ルール（Rule）の名前は、同じ UC の要求票の要求文と完全に一致させる（前後の空白だけ無視）
- 1ルールあたりの例は3件を目安にする（シナリオアウトラインは例の表の行数で数える）。目安であり、検査器は件数を数えない
- 要求票の行のうち、RDRA 欄の要素がどれもアーキテクチャ特性で、その全ての特性が `検証方法` を持つ行には、例を求めない。合否の正本は「3層と正本の分担」のとおり特性の `検証方法` である。`検証方法` は、前後の空白を除いて空でないときに持つとする。欄の要素は、`<種類>「<名前>」` として読め、種類が語彙にあり、名前が表にあるものに限って数える。数えられない要素が1つでもある行、欄が `なし` の行、特性と他の要素を併せて挙げる行、`検証方法` を持たない特性を挙げる行には、例を求める

どのルールでも、まず同じ境界の繰り返しを削る。例のあいだでバリエーションの表の `値` が違うときは、例の件数によらず、束か組み合わせかを判定する。ここでの `値` は、要求文の行の RDRA 欄から辿れるバリエーション（欄に挙がるものと、欄に挙がる条件・情報の `バリエーション`）の値に限る。例のあいだで `値` が違わないルールと、判定に入らないルールは、束か組み合わせかを判定しない。削っても目安の3件を超えても、検査器も突き合わせも束として扱わない（「機械検査が見ないもの」）。

- 判定: 入力は、要求票の要求文とその行の RDRA 欄、条件の表の `条件の説明`、バリエーションの表の `値`、例の「前提」と「ならば」である。要求文は、分けるかを決める対象である。各例がどの `値` を持つかは「前提」から読み、読めない例は対に入れない。RDRA 欄が条件を挙げるなら、「前提」をその条件の `条件の説明` に当てて各例が条件を満たす側か満たさない側かを決め、同じ側にそろえる。条件が2つ以上なら、側は条件ごとに決め、どの条件でも同じ側にある例どうしをそろえる。「前提」が触れない条件は、満たす側とする。条件を挙げないなら、全ての例を同じ側とする。そろえた側の中で、`値` の違う例どうしの「ならば」を比べる。どの側にも `値` の違う例の対が無ければ、判定に入らない。結果の種類は、受け付けるか拒否するかと、「ならば」が触れる RDRA の要素（遷移先の状態・外部システム・情報）で読み、どちらかが違えば別の種類とする。値の語の違いは数えない。いずれかの対で結果の種類が変わるなら束、どの対でも変わらないなら組み合わせとする。
- 束: 結果の種類ごとに要求文を分ける。
- 組み合わせ: 要求文は分けない。各軸の境界の両側から代表の値を選ぶ。例は目安の3件に近づけるが、境界の両側を覆うのに3件を超えるなら、両側を覆うことを優先する。値の一覧の正本はバリエーションの表の `値` で、例に全ての値を並べない。

## 要求の層の語

表の説明・要求文・例は、要求の層の語で書く。要素の名前を業務の言葉で付けることは `structure` スキルの「要求を表へ写す」が定め、ここでは繰り返さない。この節は、何を実装の語とみなすかを定める。

- 基準: 語が指すものを、RDRA の表の欄の値として書けるかで判定する。数える欄は、各表の名前キーと、`属性`・`状態`・`遷移先状態`・`値` に限る。ほかのキーは数えない。`説明`・`役割` のように文で書く欄は、どんな語でも書けるので根拠にならない。他の表の名前を指す欄（UC の `情報` 等）に書ける語は、指す先の表の名前キーに書ける。欄の値として書けず、システムの作り（画面・データの格納・呼び出し・処理の方式）を指す語を、実装の語とする。
- 欄の値になる語でも、作りの語（画面・ボタン・カラム・API・バッチ等）を付けた形は実装の語とする。例えば `属性` に書ける「状態」も、「status カラム」と書けば実装の語である。
- 外部システムは、自システムの外にあって自システムとやり取りする別の担い手（別の組織が持つシステム・別に運用されるシステム）である。自システムの中の呼び出し口・処理・画面は外部システムではなく、表へ足さない。外部システムの名前は名前キーに書けるので、実装の語としない。表に無ければ表へ足す。名前が作りの語を含んでも（「決済 API」等）、指すものが自システムの外の担い手なら外部システムの名前として扱い、前の項より優先する。アーキテクチャ特性の `検証方法` に書く測り方も、その欄が測り方を書く欄なので、実装の語としない。
- 実装の語を業務の言葉へ戻して新しい業務の事実（区分・閾値・役割）が現れたら、その事実は表へ足す。要求文・例からは表の名前で指す。同じ事実を2層に書かない（「3層と正本の分担」）。

| 実装の語を持ち込んだ形 | 要求の層の語へ戻した形 |
|---|---|
| 申請画面の承認ボタンを押す | 承認者が経費申請を承認する |
| status カラムを 2 に更新する | 経費申請が「承認済み」へ移る |
| 承認 API が 200 を返す | 承認を受け付ける |
| 夜間バッチで未承認の申請を差し戻す | 期限を過ぎた未承認の申請を差し戻す（期限は条件の表へ） |

## 検査の規則

`living-spec check [起点]` が全体検査である。`living-spec check --doc-missing [起点]` は、書き漏らしの向き（上の層が先に進み下の層が追い付いていない状態）だけの検査である。違反は `[規則] ファイル 対象: 内容` の1行で出る。

根は、「置き場の設定」の規則で起点から決まる。根が決まると、標準出力の1行目に `根: <絶対パス>` を出す。

起点を引数で渡し、それが根の範囲（「検査器が読む位置とフックの範囲」）の外なら、その根を検査し、標準エラーへ注記を出す。引数が無ければ、注記は出さない。注記は扱いを2つ示す。1つは起点を根の置き場へ移すこと、もう1つは起点の領域を独立した正本にすることである。後者には、根にするディレクトリの候補を添えるか、候補を決められないことを示す。候補は作業ディレクトリである。作業ディレクトリが根より下にあり、起点を含み、根の置き場をどれも中に持たず、どの置き場の中にも無いときに候補として示す。注記は終了コードを変えない。

`living-spec render [起点]` も同じ規則で根を決め、同じ注記を出す。`render` の標準出力は、書き出した場所だけである。止まるときは標準出力に何も出さない。`--base <版>` を付けると、基準の版との違いを描き分ける（「基準の版との描き分け」）。

`living-spec diff --base <版> [起点]` も同じ規則で根を決め、同じ注記を出す。`diff` の標準出力は、基準の版から変わった要素の一覧だけである（「基準の版から変わった要素の一覧（`diff`）」）。

`living-spec check --open [起点]` は検査をせず、表の未決の印の一覧を出す（「未決の一覧（`check --open`）」）。`--doc-missing` と併せては渡せない。

検査器が正本（表・要求票・例）に見るのは、下の規則表の規則が検出する欠陥だけで、その種類は書式の欠け・参照の切れ・層間の追跡の切れである。

- 書式の欠け: 規則表の規則が1つのファイルの中だけで判定する書き方の定めを、そのファイルが満たさないこと。
- 参照の切れ: 表のキーや要求票の RDRA 欄が名前で指す要素が読めないか表に無いこと、または UC の表のキーが指しうる要素が接続していないこと。
  - 接続しているとは、どれかの UC から指されることをいう。情報は、集約の親が接続していても接続している（「集約の子」）。`関連情報` からの参照では接続しない。
  - 接続の判定は、`仮説` キーを持つレコードを対象に含めない。仮説の要素は検証前の状態で、書きかけではないためである。
  - 仮説の UC からの参照も参照に数え、仮説の UC からだけ指される事実のレコードは指されているとする。
- 層間の追跡の切れ: 仮説でない UC・要求文（例を求めない行を除く。「例」）と、それを受ける票・例の機能・ルールが名前で1対1に対応しないこと、または UC の条件・遷移先の状態をその票の RDRA 欄が名前で挙げていないこと。

| 規則 | 層 | 検出するもの | 実行 |
|---|---|---|---|
| `unknown-key` | 表 | 表ごとに許すキー以外のキー | 全体 |
| `invalid-shape` | 表 | YAML の構文誤り、トップがシーケンスでない、レコードがマップでない、名前キーの欠落・空、値の型の誤り、`分類` に値のある特性の `分類体系` の欠け・空、未決の印の書式の誤り（「未決の印」） | 全体 |
| `undefined-reference` | 表 | 参照先が表に無い（UC→アクター・外部システム・情報・条件、情報→関連情報・集約の親・状態モデル・バリエーション、状態→遷移UC・遷移先状態、条件→バリエーション・状態モデル） | 全体 |
| `unconnected` | 表 | 接続していないアクター・外部システム・情報・条件。どの UC からも参照されず、情報では集約の親も接続していないもの（`仮説` キーを持つレコードを除く） | 全体 |
| `aggregate-cycle` | 表 | 情報の `集約の親` を辿ると自身へ戻る（親が自身の場合を含む）。循環の上の情報ごとに出し、循環へ入るだけの情報には出さない | 全体 |
| `duplicate-name` | 表 | 名前の重複（state は（状態モデル, 状態, 遷移UC）の組） | 全体 |
| `requirement-uc` | 票 | 表題から UC 名を読めない、UC が表に無い、同じ UC の票が複数ある | 全体 |
| `requirement-structure` | 票 | 見出しの欠け・雛形に無い見出し・2回目の見出し、仕様の節の読めない行（字下げの無い欄・知らない欄・番号の前の欄など。行番号で示す）、仕様の行の欄の欠け・2回目の欄、空の要求文 | 全体 |
| `requirement-reference` | 票 | RDRA 欄の要素が読めない、種類が語彙に無い、名前が表に無い | 全体 |
| `example-syntax` | 例 | Gherkin として読めない | 全体 |
| `example-feature` | 例 | 機能が無い、機能名が UC の表に無い、同じ UC の機能が複数ある | 全体 |
| `example-rule-mismatch` | 例 | ルール名が票のどの要求文とも一致しない、ルールの外のシナリオ | 全体 |
| `example-duplicate` | 例 | 同じ機能の中で手順の文の並びが同じ例 | 全体 |
| `requirement-missing` | 票 | 仮説でない UC に要求票が無い | `--doc-missing` |
| `requirement-coverage` | 票 | UC の条件・UC が遷移先にする状態が、票の RDRA 欄に挙がっていない | `--doc-missing` |
| `example-missing` | 例 | 票の要求文に同名のルールが無い（例を求めない行を除く。「例」） | `--doc-missing` |

終了コード: 0 違反なし、1 違反あり、2 次のいずれか。ただし `check --open` の 0・1 は「未決の一覧（`check --open`）」が定める。

- 引数の誤り
- 起点が見つからない
- 正本が見つからない
- 根の探索を続けられない（読めないファイルがある、検査中に根の目印が見つからなくなった）
- 設定の誤り（`.living-spec.json` を読めない・根に属さない置き場）
- 根に表の置き場が無い

`render --base` と `diff` は、基準の版を読めないときも終了コード 2 で終わる（どの場合かは「基準の版との描き分け」）。

中継（`scripts/run.mjs`）を通して呼ぶときは、検査器がこのプラグインの前提より古いときも終了コード 2 で終わる。標準エラーの1行目は「living-spec の検査器が、このプラグインの前提より古い」で始まる。続く出力は古い検査器のもので、根の行・違反の有無・書き出した場所・一覧として扱わない。直し方は `README.md` の「検査器の導入」である。`check`・`render`・`diff` に当たる。

## 未決の一覧（`check --open`）

`living-spec check --open [起点]` は、根の表の未決の印を1項目1行で標準出力へ出す。1行目は `check` と同じ `根: <絶対パス>` である。続く各行の形は次のとおりである。

```text
[未決] <ファイル>:<行> <対象> <欄>: <未決の内容>
```

- `<ファイル>` は根からの相対パス、`<行>` はその項目が表のファイルで始まる行（1から）である。
- `<対象>` は違反の行と同じ要素の表し方である（`条件:<名前>`、状態は `状態:<状態モデル>／<状態>`）。
- `<未決の内容>` は前後の空白を除き、改行をまたぐ空白を1つの空白にしたものである。
- 並びは、「RDRA の表」の表の順、表の中のレコードの順、項目の順である。
- 最後の行は `未決の一覧: <N> 件` で、印が無ければ `未決の一覧: なし` である。

終了コードは、一覧を出せたら印の件数によらず 0 である。表に `invalid-shape` の違反があれば、一覧を出さない。読めない表・レコード・項目の未決が一覧から欠けうるためである。このときは違反の行と `未決の一覧: 表の形の違反 <N> 件のため出せない` を出し、終了コード 1 で終わる。2 の場合は `check` と同じである。一覧を出すときも、`invalid-shape` 以外の違反は見ない。違反は `check` で確かめる。

設計の可視化（`render`）は、未決の印を持つ要素の欄の後ろに、「未決（<欄>）: <未決の内容>」の印を実線の枠で付ける。仮説の印（破線の遷移・「仮説」のバッジ）と見分けるためである。どの UC の縦串にも現れない要素がある。アーキテクチャ特性、どの UC からも指されない条件などである。それらも含め、全ての印は「未決の一覧」の節に、この一覧と同じ並びと所在で出る。表に `invalid-shape` の違反があれば、節の先頭に、違反の件数と一覧が欠けうることを示す。このときは印が0件でも節を残す。節が消えると、未決が無いと読まれるためである。印が1つも無く、違反も無ければ、その節を出さない。

## 機械検査が見ないもの

検査器が見るのは「検査の規則」節に挙げた欠陥だけで、意味は見ない。次は規則間の矛盾の突き合わせ（`crosscheck`）と人の確認に残る。

- 要求文と RDRA 欄の対応（欄に挙げた要素に要求文が触れていない、欄の名前は文にあるが指すものが違う、欄の要素を別の語へ言い換えて指している）。名前の文字列が一致するかでは、活用・略称で正しく書いた文を止め、指すものの違いを見逃す。
- 規則どうしの論理の矛盾（同じ状態・同じ操作に、両立しない2つの要求文がある等）
- 条件の説明と、それを指す要求文・例の食い違い
- 規則の束（1ルールの例が、「例」の節の判定で束に当たる）。判定は「前提」を `条件の説明` に当てて読む、意味の判定である。
- 判定に入らないルールの例の件数。`値` の違いの無いルールが目安の3件を超えても、検査器も突き合わせも見ない。書き手が「例」の節の目安に照らして見直す。
- 状態遷移の抜け（到達できない状態、出口の無い状態の意図の確認）
- どの層にも基準の無い空白（規則の結果を分ける基準が、表・票・例のどこにも書かれていない）。決める人の答えを待つ箇所は、表に未決の印として残す（「未決の印」）。
- 要求文が業務として正しいか

## 基準の版との描き分け（`render --base`）

`living-spec render --base <版> [起点]` は、基準の版と作業ツリーを要素の同一性で突き合わせ、足された・変わった・外された要素を描き分ける。基準の版は、git が1つのコミットに解く参照（ブランチ・タグ・コミット等）で指定する。比べる相手は作業ツリーの今の中身で、コミットしていない変更を含む。`--base <版>` は空白で区切る形だけを受け、起点の前後どちらに置いてもよい。

git が要るのは `--base` を付けたときだけである。描き分けは検査に混ぜない。`check` とフックは基準の版を読まない。

### 根と置き場

作業ツリーの根は、基準の版を付けないときと同じ規則で決まり、同じ注記を出す。基準の版の根は、同じ起点から基準の版の木を上へ辿り、同じ目印の規則（「根の決め方」）で決める。辿るのは git の作業ツリーの根までである。基準の版で決まる根が作業ツリーの根と違う位置なら、描かずに止まる。

基準の版の置き場は、基準の版の根の `.living-spec.json`（無ければ既定）で決まる。置き場の設定が版で違っても止まらず、要素を名前で比べる。

### 書き出し先とフック

描き分けは、`output` の語幹に `-diff` を付けたファイルへ書く。拡張子は保つ（既定は `.cache/living-spec/index-diff.html`）。`output` の HTML には触れない。標準出力は書き出した場所だけで、止まるときは標準出力に何も出さず、ファイルも書かない。

フックは描き分けの HTML を描き直さない。表・要求票・例を編集した後に描き分けを見るときは、`render --base` を実行し直す。

### 同一性と比べる中身

要素は、種類ごとに下の表の同一性で2つの版を突き合わせ、次の区分に分ける。

- 外された: 基準の版にだけある。
- 足された: 作業ツリーにだけある。
- 変わった: 両方にあり、比べる中身が違う。変わった欄の名前を添える。
- 変わっていない: それ以外。印を付けない。

| 種類 | 同一性 | 比べる中身（欄名） |
|---|---|---|
| アクター・外部システム・情報・条件・バリエーション・UC | 表の名前 | 名前キー以外のキーと、表に許されないキー。 |
| 状態 | 状態モデル・状態 | なし（足された・外されただけ）。 |
| 遷移 | 状態モデル・遷移元・遷移先・遷移UC | `状態モデル・状態の説明`・`仮説`・`未決`・表に許されないキー。 |
| 要求票 | 表題の UC 名 | `理由`（理由の節）・`要求文`（各行の文・理由・RDRA 欄の組の集合）。 |
| 要求文 | UC 名・文 | `理由`・`RDRA`（欄の要素の文字列の集合）。 |
| 例 | 機能名（UC 名）・ルール名・シナリオ名 | `手順`（展開した1件ごとの手順の文の並び）。 |

- 状態は、その状態モデルの記録の遷移元か遷移先に現れれば在る。
- 遷移の元・先・遷移 UC の無い記録（初期遷移の元、終端の先、`遷移UC` の無い記録）は、「無い」を1つの値として同一性に持つ。
- ルールの外のシナリオは、ルール名を「なし」として同一性に持つ。
- 表の値の比べ方: 並びの型のキーと「、」区切りのキーは、集合として比べる。文字列は前後の空白を除いて比べ、無い・空・`null` を同じとみなす。`仮説` だけはキーの有無も比べ、無いと空の並びを区別する。`未決` は、読めた項目の欄と内容の組を集合として比べ、キーが無ければ空の集合とする。内容は一覧と同じく正規化して比べるので、空白と改行だけの変更は「変わった」にならない。表に許されないキーは値をそのまま比べ、欄名はキーの名前とする。
- 要求文の `RDRA` は、欄が無い・空・「なし」のとき空の集合とする。
- 「変わった」に添える欄名は、上の表の欄の順に並べる。表の記録の欄は「RDRA の表」の表のキーの順で、`仮説`・`未決` の順にその後ろに置く。表に許されないキーは最後に、キーの名前の UTF-16 の符号単位の順で並べる。
- 並び順は比べない。表の記録の順、並びの値の順、票の行の順、ルールの中の例の順、シナリオアウトラインの例の表の行の順がこれに当たる。
- 例の手順の並びは例の中身である。手順の文が同じで並びだけを入れ替えた例も「変わった（手順）」になる。展開した件どうしの順は比べない。
- 改名は追わない。名前を変えた要素は、旧い名前の「外された」と新しい名前の「足された」になる。遷移 UC の差し替えも同じである。要求文を言い換えると、例のルール名を追随させても、旧い文の行と例は「外された」、新しい文の行と例は「足された」になる。
- 同じ版に同じ同一性の記録が複数あれば、1つの要素にまとめる（遷移では `duplicate-name` に当たる形）。記録ごとに比べる欄の値の組を作り、組の集合として順を問わず比べる。組の集合が違えば「変わった」で、欄ごとの値の集合が違う欄を添える。どの欄の値の集合も同じで組の対応だけが違うときは、どちらかの版の記録の間で2つ以上の値を持つ欄を添える。

### 印の付け方

- 印の文言は `足された`・`変わった（<欄名>・<欄名>）`・`外された` である。HTML では `<span class="diff" data-diff="<区分>">` に入れ、区分は `added`・`changed`・`removed` とする。
- 印は、要素自身の名前を持つセルか項に1つ付ける。遷移の表の行の元の状態の欄、UC の一覧の UC 名、縦串の見出し、縦串のアクター・外部システムの各項がこれに当たる。情報・条件の表の名前の欄、条件のバリエーションの各項、要求票のファイル名の行、要求文の各行の先頭も当たる。行の直下に畳む中身（条件・バリエーション・情報と、条件の中のバリエーション）の各項と、例の各項も当たる。
- 入れ子で中に並ぶ子の項は、子自身の位置として印を持ち、親の位置の印に数えない。
- UC の一覧のアクター名、RDRA 欄の文字列、ツールチップ、情報の項に添える集約の子の名前には印を付けない。
- 外された要素も残して描く。外された UC は作業ツリーの UC の後ろに並べ、UC の一覧から縦串へ辿れる。外された要求文の行は同じ UC の最初の票の行の後ろに、外された例は同じルール（ルールの外を含む）の例の後ろに並べる。作業ツリーのその UC に無い結び付かないルールは、外された例を持つときだけ、その例ごと加える。例の無いルールは、外された子を持たないので加えない。
- UC・条件から外れただけで表に残る要素（UC のアクター・外部システム・情報・条件、条件のバリエーション）は、その UC・条件の下に載らず、印も持たない。外れたことは、その UC・条件の「変わった」と欄名が示す。外された UC・条件・要求票・要求文の行の下に並ぶ要素には、その要素自身の区分を付ける。
- 作業ツリーに残る UC・要求文の行と、UC の縦串の「要求票の行に結び付かない例」の枠では、欠けの示し方を作業ツリーにある子だけで決める。作業ツリーにある子は、作業ツリーの表・票・例から読んだ子であり、区分によらない。基準の版から加えた子（外された子）は印を付けて並べる。欠けの示し方は、UC の一覧の要求票の行数と例の件数、「要求票が無い」「この行に結び付く例が無い」の注記、その枠の警告の枠線である。その枠は、作業ツリーにある結び付かないルールかルールの外の例があるときだけ警告の枠線で囲む。そのルールには、例の無いルールと、例を全て外したルールを含む。基準の版から加えた外された例だけが残るときは、警告でない枠線で囲む。UC・要求票・要求文の行のどれかが外されていれば、その下では全ての子（基準の版の中身）で決める。
- UC の一覧のアクター名は印を付けない位置なので、同じ判定で絞る。作業ツリーに残る UC の行には作業ツリーの UC が挙げるアクターだけを並べ、外された UC の行には全てを並べる。表から外したアクターを作業ツリーの UC がまだ挙げていれば、区分は「外された」でも作業ツリーにある子なので、基準の版を付けないときと同じく表に無い名前として並べる。
- 状態遷移図では、区分のある状態の節点と遷移の辺の名札の先頭に印を付け、色でも示す。節点の印は `［足された］`・`［外された］`、辺の印はそれに `［変わった］` を加えた3つである。辺の区分の色は全体図にだけ付ける。UC の縦串の図では辺の色が UC の強調を示し、辺の区分は名札の印だけで示す。破線は、基準の版を付けないときと同じく仮説の遷移だけを示す。
- 辺は遷移の記録ごとに1本で、区分はその記録の同一性の要素から決まる。同じ遷移元・遷移先の辺が並んでも、印は足された・変わった・外された記録の辺にだけ付く。
- 冒頭の根のパスの後ろに基準の版とそのコミット（先頭12字）を出し、状態遷移図の凡例の後ろに区分の説明を足す。

### 止まる場合

次のときは描かずに標準エラーへ理由を出し、終了コード 2 で終わる。作業ツリーの側の誤りでは、基準の版を付けないときと同じく、基準の版を読む前に止まる。

- `--base` の値が無い・空・`-` で始まる・2回ある、または知らない `--` の引数がある（使い方を出す）。
- git を実行できない。
- 根が git の作業ツリーの中に無い。
- 基準の版が無い、またはコミットに解けない。
- 基準の版の木で、起点から上へ辿っても目印が無い（基準の版に正本の根が無い）。
- 基準の版で決まる根の位置が、作業ツリーの根と違う。
- 基準の版の `.living-spec.json` を読めない。JSON の誤り・未知のキー・型の誤りと、通常のファイルでない項を含む。
- 基準の版の表の置き場が、ディレクトリとして無い。git の作業ツリーの根の外へ出る値と、置き場かその祖先がディレクトリでない項を含む。
- 基準の版の正本を読めない。読む位置かその祖先に読めない種類の項があるときと、git の読み出しが失敗したときに当たる。表・票・例のファイルの位置では通常のファイルでない項、票と例の置き場ではディレクトリでない項、祖先ではディレクトリでない項（シンボリックリンク・submodule の参照・ファイル）である。票と例の置き場が git の作業ツリーの根の外へ出る値のときも当たる。

票と例の置き場が git の作業ツリーの根の中を指し、その位置に基準の版の項が無ければ、止まらずに空として読む。

### 保証の範囲

次は描き分けの対象にしないか、描き分けで見分けられない。

- 全体像の「どの UC にも結び付かない要求票・例」（表題か機能名の UC が UC の表に無い票と例）には、印を付けない。表題から UC 名を読めない票と、Gherkin として読めない例・機能の無い例は、同一性を取れないので比べない。
- アーキテクチャ特性は縦串に載らないので、比べない。
- 基準の版の木のシンボリックリンクと submodule の参照は、リンク先を辿らない。根の目印の判定ではファイルとして扱い、読む位置かその祖先にあれば止まる（「止まる場合」）。作業ツリーの側は、ファイルシステムから読むのでリンク先も読む。
- 基準の版の置き場の値は検証しない（「置き場は根に属する」を掛けない）。git の作業ツリーの根の中を指す値なら、正本の根の外や別の根の中でも、その場所から読んで比べる。git の作業ツリーの根の外を指す値は、木を読めないので止まる（「止まる場合」）。
- 基準の版の木では submodule の中身が無い。起点が submodule の中なら、目印の無いディレクトリとして上へ辿る。
- 差分を求めても HTML に出ない要素がある。どの UC からも指されないアクター・外部システムと、UC からも要求文の RDRA 欄からも指されない情報・条件である。どの UC の条件からも RDRA 欄からも（欄の条件を介しても）指されないバリエーションも出ない。これらは区分によらず、HTML から見分けられない。UC からも RDRA 欄からも指されない集約の子は、親の項に名前だけが添えられ、区分は見分けられない。
- 例は、展開した手順の文だけを比べる。手順に付く表（DataTable）・文書（DocString）、タグ、シナリオの説明の変化は「変わった」にしない。
- 同じ（状態モデル・遷移元・遷移先・遷移UC）の記録が複数ある遷移（`duplicate-name` に当たる）は、1つの要素として比べる。その記録の辺と行の全てに同じ区分を付け、どの記録が変わったかは見分けない。
- 外された要求文の行（外された要求票の行を含む）と同じ名前のルールが、作業ツリーの例に結び付かないルールとして残ることがある。このとき、そのルールの例は、外された行の下と結び付かないルールの下の2か所に出うる。これは `check` が `example-rule-mismatch` を出す状態でだけ起きる。
- どちらかの版で、YAML の構文の誤りかトップが並びでない表は空の表として読み、マップでない記録と名前キーの値が無い・空・文字列でない記録は読まない。読まなかった表や記録の要素は比べられず、もう一方の版にある同じ名前の要素が足された、または外されたになる。

## 基準の版から変わった要素の一覧（`diff`）

`living-spec diff --base <版> [起点]` は、基準の版から変わった要素を1件1行で標準出力へ出す。`--base` は必須で、既定の版を持たない。基準の版の指定、比べる相手、`--base <版>` の置き方は、「基準の版との描き分け」の節の冒頭の段落に従う。作業ツリーの根と注記、基準の版の根と置き場は同じ節の「根と置き場」に、要素と区分は同じ節の「同一性と比べる中身」に従う。

### 行の形

行は `<種類>`・`<区分>`・同一性の値をタブで区切った形である。

- 種類は「同一性と比べる中身」の表の「種類」の列の語で、区分は同じ節の区分の名前（`足された`・`変わった`・`外された`）である。変わっていない要素は出ない。
- 同一性の値は、同じ表の「同一性」の列の順に並べる。
- 無い値（遷移の元・先・遷移 UC の無い記録）は `なし` と書く。変わった欄の名前は出さない。
- 例（`\t` はタブ）: `遷移\t足された\t申請の状態\tなし\t作成中\t申請を作成する`

差分が無ければ何も出さない。

### 並びと出力の範囲

行は、種類ごとに状態・遷移・UC・アクター・外部システム・情報・条件・バリエーション・要求票・要求文・例の順に並ぶ。同じ種類の中では、作業ツリーにある要素を作業ツリーでの出現順に並べ、外された要素をその後ろに基準の版での出現順に並べる。

標準出力は一覧の行だけである。根の行は出さず、ファイルも書かない。

### 終了コード

差分の有無によらず 0 で終わる。次のときは一覧を出さずに標準エラーへ理由を出し、終了コード 2 で終わる。

- 引数の誤り（`--base` が無いときを含む）
- 作業ツリーの側の誤り（「検査の規則」の終了コード 2 の場合）
- 基準の版を読めない（「基準の版との描き分け」の「止まる場合」）
- 中継が検査器を前提より古いと判定した（「検査の規則」の終了コード）。このときは古い検査器の一覧が出ることがあるが、一覧として扱わない

上のどれにも当たらない想定外の例外は捕えず、標準出力を空のまま終了コード 1 で終わる。利用者の誤りに見せないためである。

### 保証の範囲

「基準の版との描き分け」の「保証の範囲」は、一覧にも当たる。ただし、次の部分は描画にだけ当たり、一覧には当たらない。一覧は、これらの部分の要素も行として出す。

- 「どの UC にも結び付かない要求票・例」の項の1文目（印を付けない）。2文目（同一性を取れない票と例は比べない）は一覧にも当たる。
- HTML に出ない要素の項の全体。
- 同じ同一性の記録が複数ある遷移の項のうち、その記録の辺と行の全てに同じ区分を付けるという部分。1つの要素として比べ、どの記録が変わったかを見分けないことは一覧にも当たり、その要素は1行になる。
- 外された要求文の行と同じ名前のルールの項の全体。一覧では、その例は1行である。

一覧に固有の範囲は次の2つである。

- アーキテクチャ特性は比べないので（同じ「保証の範囲」）、特性を足し、変え、外しても、一覧には1行も出ない。
- 名前に含まれるタブ・改行と、`なし` という名前は、そのまま出す。このため、行からは列の区切りや無い値と見分けられない。
