# 書式と検査の正本

RDRA の表・要求票・例の書式と、検査器（`living-spec`。導入は README）が掛ける規則の正本。雛形（`templates/`）とスキルはここを参照し、書式を書き直さない。

## 3層と正本の分担

事実の種類ごとに正本を1つに決める。同じ事実を2層に書かない。

| 層 | 正本が持つ事実 | 置き場（既定） |
|---|---|---|
| RDRA の表 | 全体の構造。アクター・外部システム・情報・状態モデル・UC・条件・バリエーション・アーキテクチャ特性と、その間の参照。条件の中身・名詞の定義 | `docs/rdra/*.yaml` |
| 要求票 | UC ごとの要求文（EARS の型）・理由・要求文が触れる RDRA の要素 | `docs/requirements/*.md` |
| 例 | 要求文ごとの合否の境界（Gherkin） | `docs/examples/*.feature` |

名前は RDRA の表の語へ揃え、別の語へ言い換えない。要求票の表題と RDRA 欄、例の機能名は表の名前をそのまま書き、例のルール名は要求文をそのまま写す。検査器はこれらの名前の一致で層をつなぐ。要求文は業務の文として書き、表の名前を活用させても略してもよい。

## 置き場の設定（`.living-spec.json`）

根（下の「根の決め方」）に置くと既定を上書きする。置き場の値と `output` は根からの相対パスである。全てのキーは省略できる。未知のキー・型の誤りは終了コード 2。

```json
{
  "tables": "docs/rdra",
  "requirements": "docs/requirements",
  "examples": "docs/examples",
  "output": ".cache/living-spec/index.html",
  "hook": true
}
```

- `output`: 可視化の書き出し先。そのつど生成する派生物で、手で直さない。`.gitignore` へ入れる
- `hook`: `false` にすると、その根の編集で PostToolUse フックが検査も描画もしない（違反で AI の編集を止めたくない場合）。設定の無い領域や別の根の編集には効かないので、止めたい根ごとに置く

### 根の決め方

目印は次の2種である。

- `.living-spec.json` を持つディレクトリ
- `docs/rdra` をディレクトリとして直下に持つディレクトリ。設定が無ければ、中身が `{}` の設定とみなす

両方を持つディレクトリでは、設定が置き場を決める。

ただし `docs` か `docs/rdra` が自身の `.living-spec.json` を持つときは、その `docs/rdra` を親の目印に数えない。設定を持つ側が根になり、誰も設定していない親は根にならない。

起点から親へ1段ずつ辿り、最も近い目印を根にする。目印が入れ子になっていれば、起点に近い方が根になる。起点は次のとおりである。

- フック: 編集したファイル
- `check`・`render`: 引数のパス（ファイルならそのディレクトリ）。引数が無ければ作業ディレクトリ

辿る範囲には境界がある。境界は、起点から上へ辿って最初に見つかる、submodule でない `.git` を持つディレクトリである。`.git` はディレクトリでもファイル（worktree）でもよい。submodule は、上の作業ツリーの `.gitmodules` の `path` に載るディレクトリである。境界のディレクトリ自身は目印になりうるが、その上へは辿らない。境界まで目印が無ければ、正本は無い。

git の外では境界を設けない。このため無関係な祖先の目印を拾いうるので、`check` の1行目で根を確かめる。

起点が同じなら、根はツールを起動した場所によらない。フックも、Claude Code を起動したディレクトリを根にしない。

### パスの比べ方

根の探索・置き場の検証・範囲の判定は、パスを字面のまま比べる。シンボリックリンクは解かない。

同じファイルを別の名前で指せる構成がある。シンボリックリンク、ハードリンク、大文字小文字や Unicode の正規化が違う綴りである。この構成では、置き場の直下のファイルを、置き場の名前どおりのパスで編集する。別の名前で編集すると、フックは検査しない。

根の外を指すシンボリックリンクの置き場は、設定の誤りにならない。

### 複数の根

1つのリポジトリに根を複数置ける。各根は独立した正本である。根をまたぐ参照と、複数の根の一括の検査はしない。`output` は根からの相対なので、根ごとに別の HTML になる。

### 置き場は根に属する

各置き場（`tables`・`requirements`・`examples`）は、その根に属さなければならない。属するとは、置き場から同じ規則で上へ辿って最も近い目印が、その根自身であることをいう。置き場がまだ無くても検証する。無いディレクトリは目印にならない。

外れる形は次の3つである。いずれも設定の誤りで、終了コード 2 になる。

- `..` で根の外へ出る。
- 別の根の中に入る。例: 置き場の値が `<X>/docs/rdra` なら、`<X>` が `docs/rdra` を直下に持つ目印になり、置き場はその中に入る。
- 根と置き場の間に、submodule でない `.git` がある。

避け方は、置き場を根の下に置き、間に別の根や submodule でない `.git` を挟まないことである。別の正本にしたい領域は、その領域を根にする。別の作業ツリーを置き場にしたいときは、submodule として登録する。

置き場の値が先頭以外の位置で `docs/rdra` の並びを含む形（例: `x/docs/rdra`）は、置き場がまだ無くても、別の根の中に入る形の誤りとする。作ると、上のディレクトリ（`x`）が目印になるからである。避け方は、別の名前の置き場にすることである。先頭の位置の並び（例: `docs/rdra/req`）は、この誤りにならない。

外れた置き場の中のファイルを編集しても、フックはその根の誤りを示さない。そのファイルからは、別の根が決まるか、根が決まらないためである。誤りを示すのは、その根に決まる `check`・`render` と、その根の範囲（下の「検査器が読む位置とフックの範囲」）内のファイルの編集である。

### 検査器が読む位置とフックの範囲

検査器が読むのは、置き場の直下のファイルと、根の `.living-spec.json` だけである。置き場の下の深い階層は読まない。

根の範囲は、置き場の直下のファイル、根の `.living-spec.json`、置き場そのものかそれを含むディレクトリである。最後のものは、`check`・`render` の起点にディレクトリを渡すときに当たる。

フックは、根の範囲内のファイルの編集でだけ、その根を全体検査し、可視化を描き直す。次のときフックは何もしない。

- 正本が無い（目印が無い、または根に表の置き場が無い）
- 根が決まる前の探索で、読めないファイルがある（どの根の編集かが分からない）
- その根の `hook` が偽である
- 範囲外のファイルを編集した

根の `.living-spec.json` を読めないときは、範囲を決められない。このときフックは、根が決まる全ての編集で止まる。

次のときフックは編集を止める。

- 違反がある
- 検査器が動かない
- 根が決まった後に、探索を続けられない（読めないファイルがある等）
- `.living-spec.json` を読めない
- 置き場が根に属さない

設定の誤りと読み取りの失敗では、CLI と同じ文面を標準エラーへ出す。可視化を描けなくても、編集は止めない。

## RDRA の表

各表は `<tables>/<id>.yaml`。トップはレコードのシーケンス、各レコードはマップ。値は文字列か文字列のシーケンス（list）。「、」区切りと書いたキーは1つの文字列に「、」で並べる。表のファイルが無ければ空の表として扱う。

| id | 名前キー | ほかのキー |
|---|---|---|
| `actor` | アクター | 役割、社内外 |
| `external-system` | 外部システム | 役割 |
| `information` | 情報 | 属性・関連情報・状態モデル・バリエーション（いずれも「、」区切り）、説明 |
| `state` | 状態モデル | 状態、遷移UC、遷移先状態、状態モデル・状態の説明 |
| `use-case` | UC | アクター・外部システム・情報・条件（いずれも list）、説明 |
| `condition` | 条件 | 条件の説明、バリエーション・状態モデル（「、」区切り） |
| `variation` | バリエーション | 値（「、」区切り）、説明 |
| `architecture-characteristic` | アーキテクチャ特性 | 分類、分類体系、説明、検証方法 |

- アーキテクチャ特性の `分類` は、品質特性の体系（例: 『ソフトウェアアーキテクチャの基礎』、ISO/IEC 25010）の語を目安に付け、1つの体系に固定しない。体系の定義はここへ写さない。写しは古び、体系の改善が届かない。
- `architecture-characteristic` で `分類` に値を書くレコードは、`分類体系` に、分類に用いた体系の名前を書く。分類の流儀は時期で変わるため、体系はレコードごとに記録する。値は自由な文字列で、体系が分からなければ「不明」と書く。空文字・空白だけの文字列は、書いていないものとみなす。`分類`・`分類体系` のキーだけを置いて値を書かない行は、値の型の誤りになる。
- `state` は1レコードが1遷移。同じ状態モデル名のレコードを並べる。初期遷移は `状態` を省略または空にし、終端の状態は `遷移UC`・`遷移先状態` を省略または空にする
- どの表も任意のキー `仮説`（list。例 `[H1]`）を持てる。キーがあれば仮説、無ければ事実。検証されたらキーを外し、棄却されたらレコードを外す。仮説の UC には要求票を求めない
- UC を試みる役割は、条件で通されるかによらずアクターである。拒否の例に使う、条件を満たさない役割もアクターの表に載せ、その例の UC の `アクター` に挙げる。どの役割を通すかは、条件の `条件の説明` が分ける。

## 要求票

UC 1つにつき1件。雛形は `templates/requirement.md`。

- 表題 `# 要求票: <UC 名>`。UC 名が照合のキー（ファイル名は照合しない）
- `## 理由` に UC が要る理由、`## 仕様` に番号つきの要求文を1行ずつ
- 各行の直下に字下げした `- RDRA: <種類>「<名前>」、…`（状態は `状態「<状態モデル>/<状態>」`、参照が無ければ `なし`）と `- 理由: …`
- 種類の語彙: アクター／外部システム／情報／状態モデル／状態／UC／条件／バリエーション／アーキテクチャ特性
- 見出しは `## 理由` と `## 仕様` の2つだけで、1回ずつ。仕様の節には番号つきの要求文と、その直下に字下げした `- RDRA:`・`- 理由:` の欄（各1回、書くことが無ければ `なし`）だけを書く。外れた箇所は `requirement-structure` が出す
- HTML コメントの中は読まない（空行とコメントは自由に置ける）

## 例

UC 1つにつき1ファイル。雛形は `templates/example.feature`。

- `# language: ja`。機能（Feature）の名前が UC 名
- ルール（Rule）の名前は、同じ UC の要求票の要求文と完全に一致させる（前後の空白だけ無視）
- 1ルールあたり例は3件まで（シナリオアウトラインは例の表の行数で数える）

どのルールでも、まず同じ境界の繰り返しを削る。削っても1ルールの例が3件を超え、例のあいだでバリエーションの表の `値` が違うときは、束か組み合わせかを判定する。ここでの `値` は、要求文の行の RDRA 欄から辿れるバリエーション（欄に挙がるものと、欄に挙がる条件・情報の `バリエーション`）の値に限る。例のあいだで `値` が違わないルールと、判定に入らないルールは、3件を超えるなら要求文を分ける。

- 判定: 入力は、要求票の要求文とその行の RDRA 欄、条件の表の `条件の説明`、バリエーションの表の `値`、例の「前提」と「ならば」である。要求文は、分けるかを決める対象である。各例がどの `値` を持つかは「前提」から読み、読めない例は対に入れない。RDRA 欄が条件を挙げるなら、「前提」をその条件の `条件の説明` に当てて各例が条件を満たす側か満たさない側かを決め、同じ側にそろえる。条件が2つ以上なら、側は条件ごとに決め、どの条件でも同じ側にある例どうしをそろえる。「前提」が触れない条件は、満たす側とする。条件を挙げないなら、全ての例を同じ側とする。そろえた側の中で、`値` の違う例どうしの「ならば」を比べる。どの側にも `値` の違う例の対が無ければ、判定に入らない。結果の種類は、受け付けるか拒否するかと、「ならば」が触れる RDRA の要素（遷移先の状態・外部システム・情報）で読み、どちらかが違えば別の種類とする。値の語の違いは数えない。いずれかの対で結果の種類が変わるなら束、どの対でも変わらないなら組み合わせとする。
- 束: 結果の種類ごとに要求文を分ける。
- 組み合わせ: 要求文は分けない。各軸の境界の両側から代表の値を選び、例を3件以内に絞る。値の一覧の正本はバリエーションの表の `値` で、例に全ての値を並べない。

## 検査の規則

`living-spec check [起点]` が全体検査である。`living-spec check --doc-missing [起点]` は、書き漏らしの向き（上の層が先に進み下の層が追い付いていない状態）だけの検査である。違反は `[規則] ファイル 対象: 内容` の1行で出る。

根は、「置き場の設定」の規則で起点から決まる。根が決まると、標準出力の1行目に `根: <絶対パス>` を出す。

起点を引数で渡し、それが根の範囲（「検査器が読む位置とフックの範囲」）の外なら、その根を検査し、標準エラーへ注記を出す。引数が無ければ、注記は出さない。注記は扱いを2つ示す。1つは起点を根の置き場へ移すこと、もう1つは起点の領域を独立した正本にすることである。後者には、根にするディレクトリの候補を添えるか、候補を決められないことを示す。候補は作業ディレクトリである。作業ディレクトリが根より下にあり、起点を含み、根の置き場をどれも中に持たず、どの置き場の中にも無いときに候補として示す。注記は終了コードを変えない。

`living-spec render [起点]` も同じ規則で根を決め、同じ注記を出す。`render` の標準出力は、書き出した場所だけである。止まるときは標準出力に何も出さない。

検査器が正本（表・要求票・例）に見るのは、下の規則表の規則が検出する欠陥だけで、その種類は書式の欠け・参照の切れ・層間の追跡の切れである。

- 書式の欠け: 規則表の規則が1つのファイルの中だけで判定する書き方の定めを、そのファイルが満たさないこと。
- 参照の切れ: 表のキーや要求票の RDRA 欄が名前で指す要素が読めないか表に無いこと、または UC の表のキーが指しうる要素がどの UC からも指されないこと。
- 層間の追跡の切れ: 仮説でない UC・要求文と、それを受ける票・例の機能・ルールが名前で1対1に対応しないこと、または UC の条件・遷移先の状態をその票の RDRA 欄が名前で挙げていないこと。

| 規則 | 層 | 検出するもの | 実行 |
|---|---|---|---|
| `unknown-key` | 表 | 表ごとに許すキー以外のキー | 全体 |
| `invalid-shape` | 表 | YAML の構文誤り、トップがシーケンスでない、レコードがマップでない、名前キーの欠落・空、値の型の誤り、`分類` に値のある特性の `分類体系` の欠け・空 | 全体 |
| `undefined-reference` | 表 | 参照先が表に無い（UC→アクター・外部システム・情報・条件、情報→関連情報・状態モデル・バリエーション、状態→遷移UC・遷移先状態、条件→バリエーション・状態モデル） | 全体 |
| `unconnected` | 表 | どの UC からも参照されないアクター・外部システム・情報・条件 | 全体 |
| `duplicate-name` | 表 | 名前の重複（state は（状態モデル, 状態, 遷移UC）の組） | 全体 |
| `requirement-uc` | 票 | 表題から UC 名を読めない、UC が表に無い、同じ UC の票が複数ある | 全体 |
| `requirement-structure` | 票 | 見出しの欠け・雛形に無い見出し・2回目の見出し、仕様の節の読めない行（字下げの無い欄・知らない欄・番号の前の欄など。行番号で示す）、仕様の行の欄の欠け・2回目の欄、空の要求文 | 全体 |
| `requirement-reference` | 票 | RDRA 欄の要素が読めない、種類が語彙に無い、名前が表に無い | 全体 |
| `example-syntax` | 例 | Gherkin として読めない | 全体 |
| `example-feature` | 例 | 機能が無い、機能名が UC の表に無い、同じ UC の機能が複数ある | 全体 |
| `example-rule-mismatch` | 例 | ルール名が票のどの要求文とも一致しない、ルールの外のシナリオ | 全体 |
| `example-limit` | 例 | 1ルールの例が3件を超える | 全体 |
| `example-duplicate` | 例 | 同じ機能の中で手順の文の並びが同じ例 | 全体 |
| `requirement-missing` | 票 | 仮説でない UC に要求票が無い | `--doc-missing` |
| `requirement-coverage` | 票 | UC の条件・UC が遷移先にする状態が、票の RDRA 欄に挙がっていない | `--doc-missing` |
| `example-missing` | 例 | 票の要求文に同名のルールが無い | `--doc-missing` |

終了コード: 0 違反なし、1 違反あり、2 次のいずれか。

- 引数の誤り
- 起点が見つからない
- 正本が見つからない
- 根の探索を続けられない（読めないファイルがある、検査中に根の目印が見つからなくなった）
- 設定の誤り（`.living-spec.json` を読めない・根に属さない置き場）
- 根に表の置き場が無い

## 機械検査が見ないもの

検査器が見るのは「検査の規則」節に挙げた欠陥だけで、意味は見ない。次は規則間の矛盾の突き合わせ（`crosscheck`）と人の確認に残る。

- 要求文と RDRA 欄の対応（欄に挙げた要素に要求文が触れていない、欄の名前は文にあるが指すものが違う、欄の要素を別の語へ言い換えて指している）。名前の文字列が一致するかでは、活用・略称で正しく書いた文を止め、指すものの違いを見逃す。
- 規則どうしの論理の矛盾（同じ状態・同じ操作に、両立しない2つの要求文がある等）
- 条件の説明と、それを指す要求文・例の食い違い
- 状態遷移の抜け（到達できない状態、出口の無い状態の意図の確認）
- 要求文が業務として正しいか
