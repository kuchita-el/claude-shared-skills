# 書式と検査の正本

RDRA の表・要求票・例の書式と、検査器（`living-spec`。導入は README）が掛ける規則の正本。雛形（`templates/`）とスキルはここを参照し、書式を書き直さない。

## 3層と正本の分担

事実の種類ごとに正本を1つに決める。同じ事実を2層に書かない。

| 層 | 正本が持つ事実 | 置き場（既定） |
|---|---|---|
| RDRA の表 | 全体の構造。アクター・外部システム・情報・状態モデル・UC・条件・バリエーション・アーキテクチャ特性と、その間の参照。条件の中身・名詞の定義 | `docs/rdra/*.yaml` |
| 要求票 | UC ごとの要求文（EARS の型）・理由・要求文が触れる RDRA の要素 | `docs/requirements/*.md` |
| 例 | 要求文ごとの合否の境界（Gherkin） | `docs/examples/*.feature` |

名前は RDRA の表の語へ揃える。要求票・例は表の名前をそのまま（活用させずに）使い、検査器が名前の一致で層をつなぐ。

## 置き場の設定（`.living-spec.json`）

根（リポジトリのルート）に置くと既定を上書きする。全てのキーは省略できる。未知のキー・型の誤りは終了コード 2。

```json
{
  "tables": "docs/rdra",
  "requirements": "docs/requirements",
  "examples": "docs/examples",
  "output": ".cache/living-spec/index.html",
  "hook": true
}
```

- `output`: 可視化の書き出し先。そのつど生成する派生物で、手で直さない。`.gitignore` へ入れる
- `hook`: `false` で PostToolUse フックが検査も描画もしない（違反で AI の編集を止めたくない場合）

## RDRA の表

各表は `<tables>/<id>.yaml`。トップはレコードのシーケンス、各レコードはマップ。値は文字列か文字列のシーケンス（list）。「、」区切りと書いたキーは1つの文字列に「、」で並べる。表のファイルが無ければ空の表として扱う。

| id | 名前キー | ほかのキー |
|---|---|---|
| `actor` | アクター | 役割、社内外 |
| `external-system` | 外部システム | 役割 |
| `information` | 情報 | 属性・関連情報・状態モデル・バリエーション（いずれも「、」区切り）、説明 |
| `state` | 状態モデル | 状態、遷移UC、遷移先状態、状態モデル・状態の説明 |
| `use-case` | UC | アクター・外部システム・情報・条件（いずれも list）、説明 |
| `condition` | 条件 | 条件の説明、バリエーション・状態モデル（「、」区切り） |
| `variation` | バリエーション | 値（「、」区切り）、説明 |
| `architecture-characteristic` | アーキテクチャ特性 | 分類、説明、検証方法 |

- `state` は1レコードが1遷移。同じ状態モデル名のレコードを並べる。初期遷移は `状態` を省略または空にし、終端の状態は `遷移UC`・`遷移先状態` を省略または空にする
- どの表も任意のキー `仮説`（list。例 `[H1]`）を持てる。キーがあれば仮説、無ければ事実。検証されたらキーを外し、棄却されたらレコードを外す。仮説の UC には要求票を求めない

## 要求票

UC 1つにつき1件。雛形は `templates/requirement.md`。

- 表題 `# 要求票: <UC 名>`。UC 名が照合のキー（ファイル名は照合しない）
- `## 理由` に UC が要る理由、`## 仕様` に番号つきの要求文を1行ずつ
- 各行の直下に字下げした `- RDRA: <種類>「<名前>」、…`（状態は `状態「<状態モデル>/<状態>」`、参照が無ければ `なし`）と `- 理由: …`
- 種類の語彙: アクター／外部システム／情報／状態モデル／状態／UC／条件／バリエーション／アーキテクチャ特性
- HTML コメントの中は読まない。見出し・欄の構造の誤りは検査しない（読めない部分は「無い」ものとして扱う）

## 例

UC 1つにつき1ファイル。雛形は `templates/example.feature`。

- `# language: ja`。機能（Feature）の名前が UC 名
- ルール（Rule）の名前は、同じ UC の要求票の要求文と完全に一致させる（前後の空白だけ無視）
- 1ルールあたり例は3件まで（シナリオアウトラインは例の表の行数で数える）

## 検査の規則

`living-spec check [根]` が全体検査、`living-spec check --doc-missing [根]` が書き漏らしの向き（上の層が先に進み下の層が追い付いていない状態）だけの検査。違反は `[規則] ファイル 対象: 内容` の1行で出る。

| 規則 | 層 | 検出するもの | 実行 |
|---|---|---|---|
| `unknown-key` | 表 | 表ごとに許すキー以外のキー | 全体 |
| `invalid-shape` | 表 | YAML の構文誤り、トップがシーケンスでない、レコードがマップでない、名前キーの欠落・空、値の型の誤り | 全体 |
| `undefined-reference` | 表 | 参照先が表に無い（UC→アクター・外部システム・情報・条件、情報→関連情報・状態モデル・バリエーション、状態→遷移UC・遷移先状態、条件→バリエーション・状態モデル） | 全体 |
| `unconnected` | 表 | どの UC からも参照されないアクター・外部システム・情報・条件 | 全体 |
| `duplicate-name` | 表 | 名前の重複（state は（状態モデル, 状態, 遷移UC）の組） | 全体 |
| `requirement-uc` | 票 | 表題から UC 名を読めない、UC が表に無い、同じ UC の票が複数ある | 全体 |
| `requirement-reference` | 票 | RDRA 欄の要素が読めない、種類が語彙に無い、名前が表に無い | 全体 |
| `requirement-name-absent` | 票 | RDRA 欄の名前が同じ行の要求文に現れない（読めない要素・語彙に無い種類は `requirement-reference` だけが拾う） | 全体 |
| `example-syntax` | 例 | Gherkin として読めない | 全体 |
| `example-feature` | 例 | 機能が無い、機能名が UC の表に無い、同じ UC の機能が複数ある | 全体 |
| `example-rule-mismatch` | 例 | ルール名が票のどの要求文とも一致しない、ルールの外のシナリオ | 全体 |
| `example-limit` | 例 | 1ルールの例が3件を超える | 全体 |
| `example-duplicate` | 例 | 同じ機能の中で手順の文の並びが同じ例 | 全体 |
| `requirement-missing` | 票 | 仮説でない UC に要求票が無い | `--doc-missing` |
| `requirement-coverage` | 票 | UC の条件・UC が遷移先にする状態が、票の RDRA 欄に挙がっていない | `--doc-missing` |
| `example-missing` | 例 | 票の要求文に同名のルールが無い | `--doc-missing` |

終了コード: 0 違反なし、1 違反あり、2 引数・`.living-spec.json` の誤り、または根に表の置き場が無い。

## 機械検査が見ないもの

検査器が見るのは名前・参照・層間の追跡だけで、意味は見ない。次は規則間の矛盾の突き合わせ（`crosscheck`）と人の確認に残る。

- 規則どうしの論理の矛盾（同じ状態・同じ操作に、両立しない2つの要求文がある等）
- 条件の説明と、それを指す要求文・例の食い違い
- 状態遷移の抜け（到達できない状態、出口の無い状態の意図の確認）
- 要求文が業務として正しいか
