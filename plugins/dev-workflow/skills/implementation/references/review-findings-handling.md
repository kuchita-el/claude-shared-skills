implementation がレビュー指摘を深刻度で確定し、修正・返信へ帰着させるまでの正本。SKILL.md 本体は骨格＋制御フロー＋本ファイルへのポインタに留め、詳細は本ファイルに置く。

**射程宣言**: 本ファイルは Phase 中立である。

- **§1 深刻度**: Phase 2（セルフレビュー）と Phase 5（レビュー指摘への対応サイクル）の双方が読む。指摘の出どころ（自分のセルフレビューが生成した指摘か、PR に投稿された外部指摘か）で適用の有無を分岐させず、一律に適用する。
- **§2 Phase 5 手順**: Phase 5 のみが読む。Phase 2 は §2 を自らの責務としない。
- §1 が規定するのは格下げの帰結までであり、返信の要否と返信先の別（スレッドか PR 本体か）がその射程に入る。**返信の投稿手段**と、**格下げに当たらない改善提案の応答先**は §2 が規定する。§1 はこの2点を節番号で指すだけで、内容を書かない。

## 1. 深刻度

レビュー結果および外部から受け取った指摘を周辺コード文脈で再評価し、誤検知（差分の周辺で既に対処済みの指摘）の深刻度を調整するためのルール定義。

差分中心のレビューは、指摘箇所の上流・周辺で既に対処済みの問題まで指摘する（誤検知）ことがある。本ルールは指摘をフィルタリング（除外）せず、深刻度を格下げして補足情報を付加することで、Phase 3 の判定精度と人間レビュアーの判断を助ける。

### 1.1 値域と Phase 3 での扱い

implementation が Phase 3 の判定に用いる深刻度は2段（ブロッカー／改善提案）とする。**値域の定義（各ラベルの意味・該当条件・タイブレーク規則）は `${CLAUDE_PLUGIN_ROOT}/agents/code-reviewer.md`「4. 重大度の分類」が正本**であり、本ファイルへ複製しない。

| 深刻度 | Phase 3 での扱い | 根拠 |
|---|---|---|
| ブロッカー | 修正ループに戻す | マージ判断に影響する指摘であり、放置すると欠陥が残る |
| 改善提案 | PR 本文に記載し人間に委ねる | マージ判断に影響しない指摘であり、対応要否の判断は human review に委ねてよい |

**本表が Phase 3 の帰結規定（分岐先の指定とその根拠）の正本である。** `SKILL.md` の Phase 3 節・Phase 4 節、および `pr-body-template.md` は本表の存在と行き先の骨格（どの Phase・どのセクションへ向かうか）のみを言及し、根拠を含む帰結の本文は複製しない。

### 1.2 レビュー実行経路のラベル → 2段の初期マッピング

指摘は経路により深刻度軸が異なる（Phase 2 のレビュー実行経路と、Phase 5 で受理する外部レビューの経路の双方を含む）。調整の起点として、各経路の出力を以下で2段の初期値に変換する。この初期値は調整前の参考値であり、最終深刻度は後述の格下げ判定で確定する。

| レビュー実行経路 | 出力ラベル | 2段初期値 |
|---|---|---|
| メインループ自身のセルフレビュー（superpowers 非導入時） | ブロッカー | ブロッカー |
| 同上 | 改善提案 | 改善提案 |
| `superpowers:requesting-code-review`（導入時） | Critical | ブロッカー |
| `superpowers:requesting-code-review`（導入時） | Important | ブロッカー |
| `superpowers:requesting-code-review`（導入時） | Minor | 改善提案 |
| 外部レビュー（PR に投稿された指摘。Phase 5 で受理する） | 投稿者が付けた任意の表記、またはラベルなし | 下記フォールバックで2段化する |

経路がここに無い深刻度ラベルを出力した場合、「マージを止めるべき指摘か否か」で判断し、止めるべきならブロッカー、そうでなければ改善提案に割り当てる（委譲先の出力スキーマは固定ではないため、未知ラベルでも本フォールバックで2段化される）。外部レビューの任意の表記・ラベルなしの指摘も、経路ごとの判定規則を新設せずこの同一のフォールバックで2段化する。

### 1.3 格下げ判定

2段初期値が **ブロッカー** の指摘について、指摘箇所の周辺コードを調査し、既に対処済みの証拠があれば **改善提案** へ格下げする。

#### 対処済みの証拠の例

指摘が問題視するリスクを、指摘箇所より上流または同一パスで無効化している実装。

- 入力バリデーション・サニタイズ（指摘が「未検証入力」を問題視する場合）
- 認証・認可チェック（指摘が「認可漏れ」を問題視する場合）
- null/境界ガード・早期 return（指摘が「null 参照・境界値」を問題視する場合）
- 例外ハンドリング・リソース解放（指摘が「未処理例外・リーク」を問題視する場合）

#### 判定の原則

- 証拠は指摘が問題視するリスクを**実際に無効化している**こと。表層的な名前の一致では格下げしない（実際のコードパスを追跡して確認する）。
- 周辺コードに証拠が**見つからない指摘は維持**する（調整なし）。推測で格下げしない。
- 格上げ（改善提案 → ブロッカー）は本ルールの対象外とする。本ルールの主眼は誤検知（過剰なブロッカー指摘）の軽減にある。

### 1.4 格下げの帰結の非対称（帰結規定の正本）

格下げは無視を意味しない。格下げした指摘の帰結は、その指摘が外部から受け取ったものか自分のセルフレビューが生成したものかで異なる。

| 指摘の出どころ | 格下げしたときの帰結 |
|---|---|
| 外部から受け取った指摘（PR に投稿された指摘。Phase 5 で受理する） | 格下げの理由を当該指摘のスレッド（スレッドを持たない指摘は PR 本体）へ返信する。理由には根拠とした周辺コードの位置を含める |
| 自分のセルフレビューが生成した指摘（Phase 2） | 返信は要求されない。調整結果は出力フォーマットに記録し、要約を PR 本文へ載せる |

**外部から受け取った指摘へ返信するとき、分類（受理して対応した／改善提案／反論する）によらず、解決とみなすかどうかの判断は投稿者に残し、自分の側でスレッドを解決済み（resolve）にしない。**

この非対称は「指摘の出どころによる**判定**の分岐」ではなく「**応答すべき相手の有無**」に由来する。外部指摘は投稿者が応答を待っているが、自分のセルフレビューが生成した指摘には返す相手がいない。返信先がスレッドか PR 本体かは投稿場所の別に過ぎず、応答の要否を分けない。格下げするかどうかの判定規則（§1.3）は出どころによらず同一であり、出どころを判定材料にしない。返信の投稿手段は §2.2 の手順5が、格下げに当たらない改善提案（2段初期値が初めから改善提案の指摘）の応答先は §2.2 の手順3が規定する。

### 1.5 出力フォーマットと Phase 別の帰着先

本フォーマットは Phase 2・Phase 5 いずれの調整作業の出力（ワーキング出力）でも用い、元の指摘を保持する（§1.6）。ただし調整結果の帰着先は Phase により異なる。

- **Phase 2 の調整出力**: 人間レビュアー向けの PR 本文への記載は、これを要約したテーブルとして別途行う（implementation SKILL.md Phase 4「深刻度調整（誤検知格下げ）」を参照。役割分担: 本フォーマット=作業出力／PR 本文=要約）。
- **Phase 5 の格下げ出力**: 帰着先は当該指摘のスレッドへの返信であり、PR 本文の要約テーブルは Phase 2 由来のものに留まる。Phase 5 は PR 作成後に走るため PR 本文は既に書かれており、外部指摘への応答は投稿者が読む場所（スレッド）へ返す。

各指摘について、調整方向と根拠を以下の形式で出力する。

```
**[{調整前} → {調整後}] {指摘タイトル}**
{元のレビュー指摘の内容（そのまま。除外・改変しない）}
**補足**: {格下げ時は根拠とした周辺コードのファイルパス:行を1つ以上含む。維持時は調整なしの旨}
```

格下げの例:

```
**[ブロッカー → 改善提案] 未バリデーションの入力使用**
src/handler.ts:30 で `userId` を直接クエリに使用しています。
**補足**: src/middleware/auth.ts:45 の認証ミドルウェアで既にバリデーション済みのため格下げ。実際のリスクは低いと考えられます。
```

維持の例:

```
**[ブロッカー → ブロッカー（維持）] SQL インジェクション**
src/repo.ts:80 で入力を文字列連結でクエリに埋め込んでいます。
**補足**: 周辺コードに対処の証拠が見つからないため維持。
```

### 1.6 不変条件

- 元のレビュー指摘の内容は常にそのまま出力に含める（除外・改変しない）。
- 調整するのは深刻度（2段）のみ。指摘の存在自体は消さない。
- 格下げ時は必ず根拠（周辺コードのファイルパス:行）を伴う。根拠を示せない場合は格下げせず維持する。

## 2. Phase 5: レビュー指摘への対応サイクル（詳細手順）

Phase 5（S8）でレビュー指摘を受理し、修正を反映してスレッドへ返信するまでの手順の正本。

### 2.1 再入構造（Phase 5 の位置）

レビュー指摘は全件を列挙し、`resolved|unresolved|blocked|unknown` のいずれかを付与する。blockerが1件でも残る場合はPhase 1へ戻し、完了扱いにしない。

Phase 5 は Phase 4 の線形な後続ではない。Phase 0 でインプット種別が「PRレビュー指摘」と判定されたときに分岐して**前半**が走り、Phase 1〜3 を挟んで**後半**が走る再入構造である。

```
Phase 0（インプット種別判定: PRレビュー指摘）
  → Phase 5 前半: 1. 指摘の取得 → 2. 受理判定（S8） → 3. 深刻度調整 → 作業リスト化
      ブロッカー 1 件以上 → Phase 1 へ
      ブロッカー 0 件     → Phase 5 後半へ直行（Phase 1〜3 を経由しない）
  → Phase 1〜3: 修正・検証・セルフレビュー・判定
      Phase 3「ブロッカーなし」→ Phase 4 ではなく Phase 5 後半へ復帰
  → Phase 5 後半: 4. 修正の反映（コミット & push → CI ゲート再走行） → 5. スレッド返信
```

PR は既に存在するため、後半で `superpowers:finishing-a-development-branch` 委譲（S6・PR 作成）へは再入しない。

### 2.2 手順

#### 1. 指摘の取得

指摘は GitHub 上の**3経路**で投稿されうる。3経路すべてを取得し、会話コンテキストで与えられた指摘と合わせて1つの指摘リストへ束ねる。

```bash
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments --paginate  # (a) インラインコメント（差分行に紐づく）
gh pr view <PR番号> --json reviews                              # (b) レビューのサマリ本文
gh pr view <PR番号> --json comments                             # (c) PR 会話欄の通常コメント
```

**(c) を落とさない**: レビュー指摘が (c) の形だけで投稿される PR は現に存在する（本リポジトリの PR #697 は実測で (a) 0 件・(b) 0 件・(c) 1 件）。(a)(b) だけを取ると指摘リストが空になり、ブロッカー0件と判定して何も修正せず何も返信せずに終わる。実在するレビュー本文が一度も読まれない。取得段階での取りこぼしは「指摘が無検証のまま流れる」状態そのものであり、Phase 5 が防ごうとしているものである。`--paginate` を落とした場合の (a) の取りこぼしも同じ理由で許さない。

**(d) 会話コンテキストも取得元に含める**: Phase 0 のインプット種別表は「PRレビュー指摘」の読み込み方法に会話コンテキストを含めており、種別判定は「現在のブランチに PR が存在」だけで成立する。会話で与えられた指摘を同じ指摘リストへ合流させないと、PR のあるブランチで会話越しに受けた指摘が受理判定を迂回し、ブロッカー0件と判定されて実行されないまま終わる。合流させた指摘は返信先を持たない指摘として扱う。

**再入フィルタ（2周目以降）**: (a) は自分の返信を `in_reply_to_id` 付きの通常要素として返し、(b)(c) は全周回分を返す。素朴に再取得すると、対応済みの指摘と自分が投稿した返信そのものが指摘として S8 へ渡り、解消済みの指摘へ再度返信が飛ぶ。次の2段で除外する。

1. **自分の投稿を除外する**: Phase 5 が投稿する返信には `<!-- implementation:phase5-reply -->`、エスカレーションには `<!-- implementation:escalation -->` のマーカーを**本文の先頭行**へ置く（5.・6. で規定）。除外の判定も**先頭行がマーカーと一致するか**で行う。**本文中のどこかにマーカーを含むか、では判定しない**——マーカーに言及しただけの指摘（「エスカレーションのマーカーが探索されない」旨のレビュー指摘等）を自分の投稿と誤判定し、その指摘が丸ごと落ちる。本 PR のドッグフードで実際に起きた誤判定である。**投稿者アカウントでも判別しない**——単独利用者のリポジトリではレビュー指摘の投稿者と PR の作成者が同一になるため、アカウントは判別材料にならない。
2. **対応済みの指摘を除外する**: 基準に使うのは `<!-- implementation:phase5-reply -->` **のみ**で、`escalation` マーカーは使わない。エスカレーションは応答の完了ではなく**全体を止めた印**であり（2. の規定により修正も返信もせずに終わる）、基準に含めると回答を受けて再開したときに、未応答のブロッカーと改善提案がまとめて「対応済み」として落ちる。判定は指摘の種類で分ける。
   - **スレッドを持つ指摘（(a) インラインコメント）**: そのスレッドに `phase5-reply` マーカー付きの返信があるかで判定する。**時刻では判定しない**。周回の途中で中断しても、返信済みの指摘だけが正しく落ちる。
   - **スレッドを持たない指摘（(b)(c)(d)）**: これらへの応答は**1つの PR コメントへまとめて投稿する**（5. で規定）。まとめることで「一部だけ応答済み」の状態が生じず、投稿が完了したかどうかだけで対応済みが決まる。基準時刻は **PR 本体へ投稿した `phase5-reply` コメントのうち最新のものの作成時刻**とし、それより古いものを外す。**スレッドへの返信は基準時刻に数えない**——数えると、スレッド返信を投稿した後・PR コメントを投稿する前に中断したときに、未応答の非スレッド指摘が落ちる。基準時刻が無い（初回起動）ときは絞らない。

**取得を時刻で絞らない**: (a) の対応済み判定はスレッド単位で行うため、取得側で `since` を掛けない。掛けると、まだ返信していない古い指摘が取得の段階で落ちる。取得量より取りこぼしの無さを優先する（`--paginate` で全件取る）。

スレッドの解決状態は判別材料に使わない。根拠は §1.4 の帰結規定。加えて REST のレビューコメントは解決状態のフィールドを持たない。

**プレースホルダ記法の別**: `gh` がカレントリポジトリから自動補完するのは `{owner}` / `{repo}` / `{branch}` の3つのみである（`gh api --help`）。それ以外の `<PR番号>` `<コメントID>` は呼び出す側が値へ置換する。`{}` 記法で書くと自動補完されるものと誤読され、字面のまま発行して 404 になるため `<>` 記法で書き分ける。

**`--paginate` を落とさない**: 付けないと1ページ目のインラインコメントしか取得できず、指摘が黙って落ちる。取得段階での取りこぼしは「指摘が無検証のまま流れる」状態そのものであり、Phase 5 が防ごうとしているものである。

**エンドポイントは引用符で囲まない**: `{` `}` を含む語をシェルが展開しないことは zsh・bash とも実測済みで引用は不要であり、付けると字面が `gh api "repos/...` となり `allowed-tools` の前方一致パターンから外れうる。取得のみのためメソッド指定は不要（既定 GET）。

束ねた各指摘には**返信先**（インラインコメントのスレッド識別子＝コメント ID の有無）を保持する。理由は、後段 5. で受理・反論・格下げの結果を元のスレッドへ返すためである。返信先を持たない指摘（サマリレベルのレビュー）は 5. で別経路へ回す。

#### 2. 受理判定（S8）

`superpowers:receiving-code-review` へ委譲する（参照機構②: メインループから `Skill` ツールで呼ぶ）。

委譲先が担うのは、指摘の技術的検証（コード本体で妥当性を確認する）・不明点があれば全体を止める規律・技術的根拠に基づく反論・YAGNI チェック・修正順序（ブロッキング→簡単→複雑）である。

implementation が接続契約として保持するのは次の2つ。

- Phase 0 で導出した作業リスト／レビュー契約への受理結果の受け渡し
- 3. の深刻度調整への引き渡し

**接続契約: 投稿者によらず外部レビュー経路を通す**。委譲先は指摘の出どころで扱いを分け、`From your human partner` は「信頼して、理解したうえで実装する」、`From External Reviewers` は「実装の前に5点を検証する」と規定している。PR へ投稿された指摘は投稿者が誰であっても後者の経路を通す。レビュアーが人間か AI かは判別できず（AI のレビュー結果が開発者のアカウントで投稿されうる）投稿者を判定材料にできないためであり、前者へ落とすと外部指摘が無検証で作業リストへ入る状態が委譲先の内側で復活する。

出力は指摘を3つに分ける: **受理した指摘** ／ **反論する指摘** ／ **確認が要る指摘**。確認が要る指摘は 6. のエスカレーションへ回す。

**確認が要る指摘が1件でも残る場合は、同時にブロッカーが確定していても Phase 1 へ渡さず、修正を行わずにエスカレーションへ進む**。部分的に実装して残りを後で聞く形を採らない。委譲先は「項目 1,2,3,6 は理解した。4 と 5 の確認が要る」と述べて全体を止めることを正しい振る舞いとして明示している。先に修正だけ push すると、投稿者は説明の無い push を見ることになる。superpowers 非導入時の縮退挙動は SKILL.md「フォールバック分岐」節を参照。

#### 3. 深刻度調整との接続

適用順序は **2. 受理判定 → 3. 深刻度調整 → 6. 曖昧指摘のエスカレーション判定** とする。

受理した指摘を深刻度調整のルール（§1。SKILL.md Phase 5 節からも直接指される）でブロッカー／改善提案の2段へ確定し、**ブロッカーのみ**を作業リストへ載せる。

改善提案は修正ループへ戻さないが、**Phase 5 起点では Phase 4（PR 本文の作成）へ到達しないため、PR 本文ではなく 5. の返信で投稿者へ返す**。これは格下げされたものだけでなく、2段初期値が初めから改善提案だった指摘（外部レビュアーの nit 等）も含む。格下げ判定はブロッカーを対象とするルールであり、初めから改善提案の指摘は格下げに当たらないため、格下げの帰結の規定だけでは応答先が決まらない。

深刻度調整は指摘の出どころで適用の有無を分岐させない。ただし格下げした外部指摘には 5. のスレッド返信が伴う（§1.4 の帰結の非対称）。

#### 4. 修正の反映

前半で確定したブロッカーの修正を Phase 5 は自前で回さない。規定する遷移は次の4本である。

1. 前半で確定したブロッカーを作業リストとして Phase 1 へ渡す。
2. 修正・検証・セルフレビューは Phase 1〜3 の既存ループが担う。Phase 5 は自前の修正ループ・周回統治を持たない（implementation が自前の周回統治を持たないという既存の設計と揃える）。
3. Phase 3 の「ブロッカーなし」判定からの復帰先は、Phase 5 起点の場合に限り Phase 4（PR 作成）ではなく **Phase 5 後半**である。PR は既に存在するため `finishing-a-development-branch` 委譲（S6）による PR 作成へは再入しない。
4. 前半でブロッカーが 0 件だった場合は Phase 1 を経由せず、前半から直接後半へ進む。条件は「ブロッカーが 0 件」であって内訳の列挙ではない。0 件になる経路は複数ある（全件に反論した／受理した指摘が格下げされた／受理した指摘の2段初期値が初めから改善提案だった）。

修正コミットを push した後、**5. のスレッド返信へ進む前に CI ゲートを再走行する**。**修正コミットが1件も無い場合（遷移4 で前半から直接後半へ来た場合）は再走行しない**。差分が変わっておらず結審は前回と同じで、待つだけ Phase 5 が長引く。既に赤い PR に対して全件を格下げ・反論した場合も同じで、赤のまま返信へ進み、CI が赤である旨を返信に含める（作業を伴わない再走行の周回に入らないため）。

再走行する範囲は `phase4-ci-gate.md` の **2.（猶予付き再ポーリングによる check run 有無の判定）から 4.（終端 exit code による分岐）まで**とする。**5.（Ready 化・レビュー依頼）へは進まず、S6（PR 作成）へも再入しない**。分岐表・猶予窓・exit code の意味は同ファイルが正本であり、本ファイルへ複製しない。

- **2. を射程から外さない**: 外すと exit 1 が「CI 赤」なのか「CI 未設定（no checks reported）」なのかを区別できず、CI を持たないリポジトリで空振りの差し戻しが起きる。push 直後の run 登録ラグでも同じ誤判定が起きる。同ファイル 2. はまさにこの区別のために置かれている。
- **Phase 4 と行き先が変わるのは緑のときだけ**: 緑 → Phase 4 では Ready 化＋レビュー依頼だが、Phase 5 では 5. のスレッド返信へ抜ける。赤（修正ループへ差し戻し）・判定不能（再試行または判断依頼）・pending（待機を再実行）・収束不能（6. のエスカレーション）の行き先は Phase 4 と同一である。

再走行する理由は、赤のまま「対応した」と返信すると投稿者に誤った完了を伝えるためである。Phase 4 が確立した「Draft ＝ CI 未検証／Ready ＝ CI 緑」というコンテンツ状態の規律を、修正 push にも同じく適用する。

#### 5. スレッド返信

指摘の分類ごとに、返信へ含める内容を規定する。

| 指摘の分類 | 返信に含める内容 |
|---|---|
| 受理して対応した | 対応した旨と、修正コミットの参照（コミット SHA） |
| 受理したが本 PR では修正しない（改善提案） | 妥当と認めたうえで本 PR の射程では修正しない理由。格下げした場合は格下げの理由と、根拠とした周辺コードの位置（ファイルパス:行）を含める |
| 反論する | 反論の技術的根拠と、根拠としたコードの位置（ファイルパス:行） |

**外部から受け取った指摘には分類によらず必ず応答する**。受理して修正した指摘にだけ返信し、改善提案となった指摘を黙って落とさない。投稿者から見ると、応答の無い指摘は無視されたものと区別が付かない。「確認が要る指摘」だけは返信ではなく 6. のエスカレーション（質問の投稿）で応答する。

いずれの分類でも解決の判断の扱いは §1.4 の帰結規定に従う。返信先スレッドを持たない指摘（サマリレベルのレビュー・PR 会話欄の通常コメント・会話コンテキスト由来）にも応答する。返す先が PR 本体になるだけで、応答の要否は変わらない。

**返信本文の先頭行に `<!-- implementation:phase5-reply -->` を置く**（先頭行であること。1. の判定が先頭行の一致で行われる）。落とすと次回起動時に自分の返信が指摘として受理判定へ渡り、その指摘は対応済みと判定されず再び返信が飛ぶ。

**投稿手段**: 返信本文は複数行の散文になるため、Write で一時ファイル（`/tmp/pr-reply-<timestamp>.md`）へ書き出してからファイル経由で渡す（HEREDOC は使わない）。

```bash
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<コメントID>/replies -F body=@/tmp/pr-reply-<timestamp>.md
```

- `gh api` に `--body-file` は**存在しない**。ファイル経由の受け渡しは `-F/--field` の `@{ファイル名}` 形を使う（`gh api --help`「if the value starts with `@`, the rest of the value is interpreted as a filename to read the value from」）。
- `-F` でパラメータを付けた時点でメソッドは POST へ自動切替されるため `--method POST` は書かない（同 help「The default HTTP request method is `GET` normally and `POST` if any parameters were added」）。書くと語順が `gh api --method POST repos/...` となり `allowed-tools` の前方一致パターンから外れる。
- エンドポイントは引用符で囲まない（理由は 1. と同じ）。この語順によりエンドポイントが第1引数に来るため、`allowed-tools` の前方一致パターンと両立する。

返信先スレッドを持たない指摘（(b) レビューサマリ・(c) PR 会話欄の通常コメント・(d) 会話コンテキスト由来）への応答は、**1件ずつ分けず1つの PR コメントへまとめて** `gh pr comment` で PR 本体へ投稿する。分けて投稿すると「一部だけ応答済み」の状態が生じ、途中で中断したときに未応答の指摘が 1. の再入フィルタで対応済みと判定されて落ちる。まとめて投稿すれば、投稿が完了したかどうかだけで対応済みが決まる。投稿に失敗した場合は SKILL.md 注意事項「pushの失敗」と同型に扱い、状況を報告して手動対応を依頼する。

#### 6. エスカレーション

次のいずれかに当たる場合は、SKILL.md の既存エスカレーション機構へ接続する（インプット種別「PRレビュー指摘起点」→ `gh pr comment`）。Phase 5 固有のエスカレーション経路は新設しない。

- 2. の受理判定で不明点が残る（委譲先が規定する「不明点があれば全体を止める」規律による）
- 仕様の曖昧さで受理／反論を判断できない指摘がある
- 4. の CI ゲート再走行で同一失敗が反復し、収束しない
- 1. の指摘の取得に失敗する（権限不足・PR 不在）

エスカレーションの投稿先は PR コメント（`gh pr comment`）であり、**回答も同じ欄に返る**。したがって 1. の取得は (c) PR 会話欄の通常コメントを必ず含める必要がある（含めないと回答が読まれず同じ質問を再投稿する）。Phase 0 のエスカレーション履歴確認も同じ理由で PRレビュー指摘起点を対象に含める（SKILL.md Phase 0）。投稿本文の**先頭行**に既存の `<!-- implementation:escalation -->` マーカーを置き、1. の再入フィルタと Phase 0 の履歴確認の双方が同じ位置で判別できるようにする。このマーカーは 1. の第1段（自分の投稿の除外）にのみ使い、**第2段の基準時刻には使わない**。エスカレーションは応答の完了ではなく全体を止めた印だからである。

### 2.3 入出力の例

指摘1件が受理判定 → 深刻度調整 → 返信内容へ変換される流れを、代表的な1ケースで示す。

```
指摘: 「この関数は null チェックが無い」（インラインコメント、src/foo.ts:42、コメント ID 12345）
2. 受理判定の出力: 受理（技術的に妥当。上流に null ガードは無い）
3. 深刻度調整の出力: ブロッカー（維持。周辺コードに対処の証拠なし）
   → 作業リストへ載せ Phase 1 へ渡す
5. 返信内容: 対応した旨と修正コミットの参照（コメント ID 12345 のスレッドへ返信）
```
