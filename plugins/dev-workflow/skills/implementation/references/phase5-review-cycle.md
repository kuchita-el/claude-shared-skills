# Phase 5: レビュー指摘への対応サイクル（詳細手順）

Phase 5（S8）でレビュー指摘を受理し、修正を反映してスレッドへ返信するまでの手順の正本。SKILL.md 本体は骨格＋制御フロー＋本ファイルへのポインタに留め、詳細手順は本ファイルに置く。

## 再入構造（Phase 5 の位置）

Phase 5 は Phase 4 の線形な後続ではない。Phase 0 でインプット種別が「PRレビュー指摘」と判定されたときに分岐して**前半**が走り、Phase 1〜3 を挟んで**後半**が走る再入構造である。

```
Phase 0（インプット種別判定: PRレビュー指摘）
  → Phase 5 前半: 1. 指摘の取得 → 2. 受理判定（S8） → 3. 深刻度調整 → 作業リスト化
      ブロッカー 1 件以上 → Phase 1 へ
      ブロッカー 0 件     → Phase 5 後半へ直行（Phase 1〜3 を経由しない）
  → Phase 1〜3: 修正・検証・セルフレビュー・判定
      Phase 3「ブロッカーなし」→ Phase 4 ではなく Phase 5 後半へ復帰
  → Phase 5 後半: 4. 修正の反映（コミット & push → CI ゲート再走行） → 5. スレッド返信
```

PR は既に存在するため、後半で `superpowers:finishing-a-development-branch` 委譲（S6・PR 作成）へは再入しない。

## 手順

### 1. 指摘の取得

インラインコメントとサマリレベルのレビュー本文を**分けて**取得し、両者を1つの指摘リストへ束ねる。

```bash
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments --paginate   # インラインコメント（差分行に紐づく）
gh pr view <pr> --json reviews                                   # サマリレベルのレビュー本文
```

**プレースホルダ記法の別**: `gh` がカレントリポジトリから自動補完するのは `{owner}` / `{repo}` / `{branch}` の3つのみである（`gh api --help`）。それ以外の `<PR番号>` `<コメントID>` は呼び出す側が値へ置換する。`{}` 記法で書くと自動補完されるものと誤読され、字面のまま発行して 404 になるため `<>` 記法で書き分ける。

**`--paginate` を落とさない**: 付けないと1ページ目のインラインコメントしか取得できず、指摘が黙って落ちる。取得段階での取りこぼしは「指摘が無検証のまま流れる」状態そのものであり、Phase 5 が防ごうとしているものである。

**エンドポイントは引用符で囲まない**: `{` `}` を含む語をシェルが展開しないことは zsh・bash とも実測済みで引用は不要であり、付けると字面が `gh api "repos/...` となり `allowed-tools` の前方一致パターンから外れうる。取得のみのためメソッド指定は不要（既定 GET）。

束ねた各指摘には**返信先**（インラインコメントのスレッド識別子＝コメント ID の有無）を保持する。理由は、後段 5. で受理・反論・格下げの結果を元のスレッドへ返すためである。返信先を持たない指摘（サマリレベルのレビュー）は 5. で別経路へ回す。

### 2. 受理判定（S8）

`superpowers:receiving-code-review` へ委譲する（参照機構②: メインループから `Skill` ツールで呼ぶ）。

委譲先が担うのは、指摘の技術的検証（コード本体で妥当性を確認する）・不明点があれば全体を止める規律・技術的根拠に基づく反論・YAGNI チェック・修正順序（ブロッキング→簡単→複雑）である。

implementation が接続契約として保持するのは次の2つ。

- Phase 0 で導出した作業リスト／レビュー契約への受理結果の受け渡し
- 3. の深刻度調整への引き渡し

**接続契約: 投稿者によらず外部レビュー経路を通す**。委譲先は指摘の出どころで扱いを分け、`From your human partner` は「信頼して、理解したうえで実装する」、`From External Reviewers` は「実装の前に5点を検証する」と規定している。PR へ投稿された指摘は投稿者が誰であっても後者の経路を通す。レビュアーが人間か AI かは判別できず（AI のレビュー結果が開発者のアカウントで投稿されうる）投稿者を判定材料にできないためであり、前者へ落とすと外部指摘が無検証で作業リストへ入る状態が委譲先の内側で復活する。

出力は指摘を3つに分ける: **受理した指摘** ／ **反論する指摘** ／ **確認が要る指摘**。確認が要る指摘は 6. のエスカレーションへ回す。**確認が要る指摘が1件でも残る場合はエスカレーションが優先し、後半（修正の反映・スレッド返信）へ進まない**（委譲先の「不明点があれば全体を止める」規律に従う）。superpowers 非導入時の縮退挙動は SKILL.md「フォールバック分岐」節を参照。

### 3. 深刻度調整との接続

適用順序は **2. 受理判定 → 3. 深刻度調整 → 6. 曖昧指摘のエスカレーション判定** とする。

受理した指摘を深刻度調整のルール（同ディレクトリの `review-severity-adjustment.md`。SKILL.md Phase 5 節からも直接指される）でブロッカー／改善提案の2段へ確定し、**ブロッカーのみ**を作業リストへ載せる。改善提案は Phase 4 の PR 本文と同じ扱いで人間の判断へ委ね、修正ループへ戻さない。

深刻度調整は指摘の出どころで適用の有無を分岐させない。ただし格下げした外部指摘には 5. のスレッド返信が伴う（帰結の非対称）。

### 4. 修正の反映

前半で確定したブロッカーの修正を Phase 5 は自前で回さない。規定する遷移は次の4本である。

1. 前半で確定したブロッカーを作業リストとして Phase 1 へ渡す。
2. 修正・検証・セルフレビューは Phase 1〜3 の既存ループが担う。Phase 5 は自前の修正ループ・周回統治を持たない（implementation が自前の周回統治を持たないという既存の設計と揃える）。
3. Phase 3 の「ブロッカーなし」判定からの復帰先は、Phase 5 起点の場合に限り Phase 4（PR 作成）ではなく **Phase 5 後半**である。PR は既に存在するため `finishing-a-development-branch` 委譲（S6）による PR 作成へは再入しない。
4. 前半でブロッカーが 0 件だった場合（全件が改善提案へ格下げされた／全件に反論する場合）は Phase 1 を経由せず、前半から直接後半へ進む。

修正コミットを push した後、**5. のスレッド返信へ進む前に CI ゲートを再走行する**。**修正コミットが1件も無い場合（遷移4 で前半から直接後半へ来た場合）は再走行しない**。差分が変わっておらず結審は前回と同じで、待つだけ Phase 5 が長引く。既に赤い PR に対して全件を格下げ・反論した場合も同じで、赤のまま返信へ進み、CI が赤である旨を返信に含める（作業を伴わない再走行の周回に入らないため）。再走行するのは CI ゲートの待機・分岐部分（`gh pr checks <pr> --watch --required` の待機と終端 exit code による分岐）のみで、S6（PR 作成）へは再入しない。分岐先は Phase 4 と同じである:

| CI ゲートの結審 | アクション |
|---|---|
| 緑 | 5. のスレッド返信へ進む |
| 赤（exit 1） | Phase 1〜3 の修正ループへ差し戻す |
| その他の非0（2=cancel / 4=auth / ネットワーク断等） | CI 判定不能。修正ループへ流さず、再試行または判断依頼へ回す |
| 収束不能（同一失敗が反復して解消しない） | 6. のエスカレーションへ接続する |

待機・分岐の手順そのものは Phase 4 の CI ゲート手順（`phase4-ci-gate.md`）が正本であり、本ファイルへ複製しない。再走行する理由は、赤のまま「対応した」と返信すると投稿者に誤った完了を伝えるためである。Phase 4 が確立した「Draft ＝ CI 未検証／Ready ＝ CI 緑」というコンテンツ状態の規律を、修正 push にも同じく適用する。

### 5. スレッド返信

指摘の分類ごとに、返信へ含める内容を規定する。

| 指摘の分類 | 返信に含める内容 |
|---|---|
| 受理して対応した | 対応した旨と、修正コミットの参照（コミット SHA） |
| 反論する | 反論の技術的根拠と、根拠としたコードの位置（ファイルパス:行） |
| 格下げした | 格下げの理由と、根拠とした周辺コードの位置（ファイルパス:行） |

いずれの分類でも**解決の判断は投稿者に残す**。自分の側でスレッドを解決済み（resolve）にしない。返信先スレッドを持たない指摘（サマリレベルのレビュー）にも応答する。返す先が PR 本体になるだけで、応答の要否は変わらない。

**投稿手段**: 返信本文は複数行の散文になるため、Write で一時ファイル（`/tmp/pr-reply-<timestamp>.md`）へ書き出してからファイル経由で渡す（HEREDOC は使わない）。

```bash
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments/<コメントID>/replies -F body=@/tmp/pr-reply-<timestamp>.md
```

- `gh api` に `--body-file` は**存在しない**。ファイル経由の受け渡しは `-F/--field` の `@{ファイル名}` 形を使う（`gh api --help`「if the value starts with `@`, the rest of the value is interpreted as a filename to read the value from」）。
- `-F` でパラメータを付けた時点でメソッドは POST へ自動切替されるため `--method POST` は書かない（同 help「The default HTTP request method is `GET` normally and `POST` if any parameters were added」）。書くと語順が `gh api --method POST repos/...` となり `allowed-tools` の前方一致パターンから外れる。
- エンドポイントは引用符で囲まない（理由は 1. と同じ）。この語順によりエンドポイントが第1引数に来るため、`allowed-tools` の前方一致パターンと両立する。

返信先スレッドを持たない指摘（サマリレベルのレビューへの応答）は、`gh pr comment` で PR 本体へ投稿する。投稿に失敗した場合は SKILL.md 注意事項「pushの失敗」と同型に扱い、状況を報告して手動対応を依頼する。

### 6. エスカレーション

次のいずれかに当たる場合は、SKILL.md の既存エスカレーション機構へ接続する（インプット種別「PRレビュー指摘起点」→ `gh pr comment`）。Phase 5 固有のエスカレーション経路は新設しない。

- 2. の受理判定で不明点が残る（委譲先が規定する「不明点があれば全体を止める」規律による）
- 仕様の曖昧さで受理／反論を判断できない指摘がある
- 4. の CI ゲート再走行で同一失敗が反復し、収束しない
- 1. の指摘の取得に失敗する（権限不足・PR 不在）

## 入出力の例

指摘1件が受理判定 → 深刻度調整 → 返信内容へ変換される流れを、代表的な1ケースで示す。

```
指摘: 「この関数は null チェックが無い」（インラインコメント、src/foo.ts:42、コメント ID 12345）
2. 受理判定の出力: 受理（技術的に妥当。上流に null ガードは無い）
3. 深刻度調整の出力: ブロッカー（維持。周辺コードに対処の証拠なし）
   → 作業リストへ載せ Phase 1 へ渡す
5. 返信内容: 対応した旨と修正コミットの参照（コメント ID 12345 のスレッドへ返信）
```
