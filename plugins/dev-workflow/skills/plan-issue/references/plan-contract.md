# プラン成果物の規範（plan-issue）

本ファイルはプラン成果物の**値域・値域の閉性・構造・多重度・節間の整合要求・既定文言**の正本である。ここに定義された値域を他のファイルへ複製せず、必要な箇所は本規範を参照する。ここでいう**構造**は要素の種類・必須性・列構成を指し、それらを紙面へどう並べて書くか（レイアウト）は含まない。

射程の境界は次のとおり:

- **何を選び何を書くか**（ピックアップ基準・フィルタ基準・分類基準・抽象度ルール）は生成手順 `plan-prompt.md` が持つ。
- **何を不合格とするか**（レビュー観点とブロッカー条件）は検査観点 `review-guide-default.md` が持つ。
- **どの節を置きどの節を省略できるか**（節見出しと省略可否）と、**各節をどう書き並べるか**（レイアウト＝エントリの行の並び・表の見出し行・プレースホルダの雛形）はテンプレート `plan-output-format.md` が持つ。

## 1. 判断依頼エントリの構造

各エントリは分類ラベル1つ・1行概要1つと、4つの必須フィールド・1つの任意フィールドで構成する。このうち**分類ラベル・1行概要・4つの必須フィールド**の計6つを本規範の**必須要素**と呼び、1つでも欠けたエントリは構造を満たさない。任意フィールドは必須要素に含まない。エントリの充足を検査する側は、必須フィールドではなくこの必須要素を単位とする。

**1行概要**: 必須。確認事項を1行で述べる自由記述。`説明` とは別要素であり、`説明` が判断対象の内容を述べるのに対し、1行概要はエントリの見出しとして一覧性を担う。

**分類ラベルの値域と多重度**: `判断待ち` / `前提確認` の2値からなる閉じたリスト。各項目に以下いずれかを付与する（いずれか1つを必ず付与する）。どちらへ入れるかの分類基準は生成手順が持つ。

**フィールドの値域**:

| フィールド | 必須 | 値域 |
|---|---|---|
| `観点ID` | 必須 | `J{n}` 形式。プラン内で一意 |
| `説明` | 必須 | 自由記述。レビュアーが判断対象として認識できる粒度 |
| `検出フェーズ` | 必須 | `plan` 固定（plan-issue が生成するため） |
| `判断者ロール` | 必須 | 下記の4値からなる**閉じたリスト**。値域外の値を用いず、いずれか1つを必ず付与する |
| `関連AC番号` | 任意 | `AC{番号}`。複数は `AC1, AC2` のようにカンマ区切り |

`判断者ロール` の値域:

- `アーキテクト`: 技術設計判断・既存アーキテクチャ整合判断
- `プロダクトオーナー`: 仕様判断・ビジネス価値判断
- `ドメイン専門家`: ドメイン知識に基づく判断
- `レビュアー（汎用）`: 上記いずれにも該当しない、または複数を兼ねる

## 2. 決定論点テーブルの構造

列は `項目` / `選択肢` / `推奨` / `振り分け` / `理由` の5列で、全列必須。

**`振り分け` 列の値域**: `plan段階` / `実装段階` の2値からなる閉じたリスト。いずれか1つを必ず付与する。どちらへ振り分けるかの基準は生成手順が持つ。

## 3. テストケース対応表の構造

列は `AC#` / `テストケース概要` / `観点` / `採用技法` / `テストレベル` の5列で、全列必須。

3つのリストは**閉性と多重度の組み合わせが互いに異なる**。まとめて1つの規定に畳まず、リストごとに次のとおり扱う。

**観点** — 値域は下記の5値からなる**閉じたリスト**。いずれか1つを必ず付与する。

- `典型ケース`: 主要なハッピーパス
- `境界値`: 仕様で定義された境界の前後
- `異常系`: バリデーション失敗・例外・エラー
- `状態遷移`: 状態を持つ機能の遷移パターン
- `組み合わせ`: 複数条件の組み合わせ

**採用技法** — 値域は次の5値で、**開いた例示列挙（テスト分析技法の代表例。値域外の技法を追加してよい）**。いずれかを**1つ以上**付与する。

- `同値分割`: 等価な入力をグループ化して代表値で検証する
- `境界値分析`: 境界の前後・直上の値で検証する
- `ディシジョンテーブル`: 条件の組み合わせと結果のマトリクスで検証する
- `状態遷移テスト`: 状態遷移図・遷移表に基づいて検証する
- `ユースケーステスト`: シナリオ全体を通した振る舞いを検証する（技法と紐付けにくいケースでも漏れなく付与できる既定の例示）

**テストレベル** — 値域は次の4値で、**開いた例示列挙（一般的なテストレベルの代表例。プロジェクトのテストレベル体系に応じて値域外のレベルを用いてよい）**。いずれか1つを必ず付与し、かつ「## 検証方針 > テストレベル」の方針と整合させる。値域外のレベルを用いる場合は、そのレベルが同節の方針に現れていることを整合の条件とする。

- `unit`: 単体
- `integration`: 統合
- `e2e`: エンドツーエンド
- `目視確認`: 自動テストフレームワークがないプロジェクトで使用する

## 4. タスク分解の粒度基準と必須記載

- **1タスク ≒ 1コミット**: 数十分〜数時間で完了できる粒度に分解する。
- **依存関係・完了条件の明示**: タスク間の実行順序制約と、各タスクの検証可能な完了条件（何が達成されていればよいか＋どう確認するか）を記載する。
- **入出力の例示**: 成果物に入出力がある場合、具体例を最低1つ含める。検証タスクではテスト入力と期待結果のペアとして記載する。代表的な1ケースで構造と意図が伝わる量に留める。
- **読み方区分の付与**: 同一ファイルへ複数箇所の編集を含むタスクには、そのファイルをどう読むかの区分を付与する。値域は `全文読み` / `局所読み` の2値からなる**閉じたリスト**で、いずれか1つを付与する。単一箇所の編集だけからなるタスクには付与しない。どちらへ振り分けるかの判定条件は生成手順が持つ。この区分は `file:line`・変更前後の期待値・照合に用いる needle の記載を**置き換えるものではなく併記する**。区分を付けたことを理由にこれらの記載を省略しない。

## 5. 既定文言

- **AC未定義時のテストケース対応表**: 「該当なし。AC定義後に再生成すること」と出力する。
