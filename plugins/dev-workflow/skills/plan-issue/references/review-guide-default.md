# プランレビュー基準（デフォルト）

実装プランの品質をレビューするための基準。12の観点でプランを評価する。

本基準が「規範」と呼ぶのは `plan-contract.md`（プラン成果物の値域・値域の閉性・構造・多重度・節間の整合要求・既定文言の正本）であり、その全文はレビュー基準と共に渡される。本基準は値域を再掲せず、何を見るか（観点）と何を不合格とするかを定める。

## レビュー観点

| # | 観点 | チェック項目 |
|---|---|---|
| 1 | 実現可能性 | 各ステップで変更対象のファイル/モジュールが実在するか。存在しないAPIや未導入ライブラリを前提にしていないか |
| 2 | スコープ適切性 | Issueの要件に対して過不足がないか。Issue外の改善を混ぜていないか |
| 3 | 依存関係 | ステップ間の順序制約が明示されているか。外部サービスやCI/CDへの影響が考慮されているか |
| 4 | ステップ粒度 | 各ステップが規範の定める粒度基準に沿うか。「〜を適切に実装する」のような曖昧な記述がないか |
| 5 | 検証方法 | 完了を確認する手段（テスト、動作確認コマンド等）が各ステップに対して明示されているか |
| 6 | リスク | 破壊的変更、マイグレーション、後方互換性への影響が識別されているか |
| 7 | 検証方針の妥当性 | 検証方針のピックアップ基準（ACから自明でないもの・修正コストが高い振る舞い）が妥当か。重要な振る舞いの見落としや、自明なケースの過剰な列挙がないか |
| 8 | タスクの自己完結性 | 各タスクがサブエージェント1セッションで完結できるか。参照コンテキストが広すぎる場合、事前調査ステップが計画に含まれているか |
| 9 | アーキテクチャ準拠 | DBスキーマ変更・API変更・新規依存ライブラリが既存のアーキテクチャ方針と整合しているか。実装設計セクションが必要十分に記載されているか |
| 10 | テストケース対応表 | 「テストケース対応表」セクションが存在するか。AC全項目との対応・観点・採用技法・テストレベルが付与されているか。各テストケースが AC の意図と合致しているか（誤読検出）。抽象度がコード非依存か |
| 11 | 判断明示セクションの存在 | `## 判断依頼` と `## 決定論点` の両セクションが存在するか。各セクションに内容または「該当なし」が明示されているか。「判断依頼」の各エントリが規範の定める必須要素を備えているか |
| 12 | 出力テンプレート定義外の節の不在 | プランの見出しが、出力テンプレートが定義する節の集合（正規化後）に含まれるか。含まれない見出しが1件でもあればブロッカー |

## 各観点の詳細

### 1. 実現可能性

- 変更対象ファイルがGrep/Globで実在確認されているか
- 前提としている機能・ツール・仕組みが既に利用可能か
- 新たに必要なものがある場合、そのステップが計画に含まれているか

### 2. スコープ適切性

- Issueの受け入れ条件と計画の成果物が1:1で対応しているか
- 「ついでに」的な改善・リファクタリングが混入していないか
- 必要な変更が漏れていないか（受け入れ条件の各項目がカバーされているか）

### 3. 依存関係

- タスク間の実行順序に矛盾がないか（依存先のタスクが先に実行される構成か）
- 外部サービス・CI/CDパイプラインへの影響が識別されているか
- 並行作業可能なタスクが明示されているか

### 4. ステップ粒度

- 各タスクが規範の定める粒度基準に沿う規模か
- 実装内容が具体的に記述されているか（「適切に」「必要に応じて」等の曖昧表現がないか）
- 変更するファイルが明示されているか

### 5. 検証方法

- 各タスクに完了条件が明示されているか
- テスト実行、コマンド実行、目視確認等の具体的な検証手段が記載されているか
- 検証手段が再現可能か（誰が実行しても同じ結果を得られるか）

### 6. リスク

- 既存機能への影響が識別されているか
- 破壊的変更がある場合、影響範囲と対処方針が記載されているか
- 後方互換性を損なう変更がある場合、移行手順が考慮されているか

### 7. 検証方針の妥当性

- ピックアップ基準が妥当か（ACから自明でないもの・修正コストが高い振る舞いが選ばれているか）
- 重要な振る舞いの見落としがないか（リスクの高い境界条件・異常系が含まれているか）
- 自明なケース（単純なCRUD、設定値の反映等）が過剰に列挙されていないか

### 8. タスクの自己完結性

- 各タスクの説明だけで、実装に必要な情報が揃っているか
- 広範囲のコードベース理解を前提としていないか
- コンテキストが大きい場合、事前調査ステップ（Grep/Globで対象を特定する等）が含まれているか

### 9. アーキテクチャ準拠

- DBスキーマ変更がある場合、既存のテーブル設計・命名規則と整合しているか
- マイグレーション方針（破壊的変更の有無、ロールバック手順）が明記されているか
- API変更がある場合、既存のエンドポイント設計・命名規則・レスポンス形式と整合しているか
- 新規依存ライブラリがある場合、選定理由と代替案との比較が記載されているか
- 既存の技術スタックや方針に反する選択をしていないか（している場合はその根拠が示されているか）

### 10. テストケース対応表

- 「テストケース対応表」セクションが存在するか（欠落時はブロッカー）
- AC全項目に最低1テストケースが対応付けられているか（未対応AC1件以上でブロッカー）
- 各テストケースの概要が対応する AC の意図と合致しているか。AC の振る舞いと食い違うテストケース（誤読）がある場合はブロッカー
- 各テストケースに「観点」「採用技法」「テストレベル」が付与されているか（欠落1件でブロッカー）
- 観点が規範の定める値域内の値か（規範は観点を閉じたリストとしており、範囲外はブロッカー）
- テストケースの抽象度がコード非依存か（関数名・テスト名・モック設定が混入していないか）
- AC未定義のIssueの場合、規範が定める既定文言が明記されているか

### 11. 判断明示セクションの存在

- `## 判断依頼` セクションが存在するか（欠落時はブロッカー）
- `## 決定論点` セクションが存在するか（欠落時はブロッカー）
- 各セクションに内容または「該当なし」が明示されているか（空のままはブロッカー）
- 「判断依頼」の各エントリが規範の定める必須要素を備えているか（1件でも欠落時はブロッカー）
- 各必須要素の値が規範の定める値域に収まっているか。とりわけ `分類ラベル` と `判断者ロール` は規範が閉じたリストとして定めており、値域外の値はブロッカー
- 「該当なし」が明示されている場合は指摘としない（セクション欠落と区別すること）

判定基準（ディシジョンテーブル）:

| セクション状態 | 深刻度の分類 |
|---|---|
| セクション自体が存在しない | ブロッカー |
| セクション存在 + 「該当なし」明示 | 指摘なし |
| セクション存在 + エントリあり + 必須要素が全て揃っている | 指摘なし |
| セクション存在 + エントリあり + 必須要素に欠落あり | ブロッカー |
| セクション存在 + エントリあり + 必須要素は揃うが記述の改善余地がある | 改善提案 |

### 12. 出力テンプレート定義外の節の不在

- 射程はテンプレートが定義する見出し集合に含まれない `##` 以下のすべての見出しとする。対象の見出しレベルを列挙して射程を閉じない（`##` のみ、あるいは `##` と `###` のみ、といった限定を置かない）。テンプレートはより深いレベルの見出しを定義していないため、レベルを列挙して閉じると、列挙した最下位レベルの1段下へ記録を落とすだけで検出を免れる無検査の書き込み先が残る
- テンプレートが定義する見出し集合との照合は、次の正規化を施したうえで行う:
  1. テンプレート側の見出し末尾の `（該当する場合）` を除去してから比較する
  2. `{...}` を含むテンプレート見出しは可変部として扱い、`{...}` より前の固定部分で比較する
  3. テンプレートが `...` で反復を示す箇所は、同じ固定部を持つ見出しが任意個現れてよいことの表明として読む
- 正規化後の集合に含まれない見出しが1件でもあればブロッカー（改善提案に留めない）
- テンプレートが省略可と注記する節が省略されている場合は指摘としない
- レビュー経緯の記録がプラン本体の節として置かれている場合はブロッカー（出力テンプレートが定める経緯付録へ分離されているべきもの）
- 判定にはレビュアーへ渡される出力テンプレート本文を用いる。本基準はテンプレートの節見出しを列挙しない（列挙すると正本が二重化してドリフトする）

## 深刻度の分類と総合判定

各指摘は**ブロッカー**と**改善提案**の2段へ分類する。両ラベルの意味とタイブレーク規則の正本は `code-reviewer.md`「4. 重大度の分類」であり、その全文は本基準と共にレビュアーへ渡される。本基準はラベルの意味を再掲せず、どの指摘がどちらへ落ちるかだけを定める。すなわち上記12観点のうち「〜はブロッカー」と明記した条件に該当する指摘がブロッカーであり、それ以外の指摘は改善提案とする。

総合判定は次のとおり: **ブロッカーが1件以上あればFAIL、ブロッカーが無ければPASS**（改善提案のみの場合もPASS）。

## レビュー手順

1. プランの各セクション（実装設計、タスク分解等）を上記12観点で確認する
2. 問題がある場合、具体的な指摘と修正案を、ブロッカー／改善提案の別を付けて記録する
