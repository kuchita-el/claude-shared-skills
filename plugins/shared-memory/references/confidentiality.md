# 機密の確認

記録が、元のリポジトリの外へ出るときの確認を定める。プロジェクトで得た学びを Global Memory へ書くときが、これに当たる。

## いつ行うか

記録を、元のリポジトリの外へ書く前に行う。最初に境界を越えるのは、別のリポジトリの作業ツリーへ記録を書く時点である。push と PR の作成は、その後に在る。

- 確認が済むまで、下書きは、別のリポジトリの作業ツリーの外に置く。
- 別のリポジトリへ書くのは、確認を通った内容だけである。書いた後に内容を変えるときは、確認を通し直してから書き直す。
- 確認を通らなかった下書きは、別のリポジトリへ書かず、外へ出す変更にも含めない。下書きがどこに残っているかを、利用者へ報告する。

## 外せないこと

記憶の利用規則は、確認の対象を足せる。確認そのものと、下の下限の対象は、利用規則で外せない。記録がリポジトリの境界を越え、元のプロジェクトを知らない読み手へ届くためである。

## 下限の対象

| 対象 | 含むものの例 | 判定の入力 | 段 |
|---|---|---|---|
| 認証情報 | トークン、API キー、パスワード、秘密鍵、認証情報を含む接続文字列、セッションの識別子、署名つきの URL | 記録と PR の本文の文字列 | 読み |
| 個人を特定できる情報 | 氏名、メールアドレス、アカウント名、電話番号、住所 | 記録と PR の本文の文字列 | 読み |
| 公開していないプロジェクト・組織の固有名。リポジトリの名前と、内部の URL を含む | 所有者の名前、顧客・組織の名前、製品や機能の内部の呼び名、内部のホスト名・IP アドレス、内部のチケットの番号と URL、プロジェクトに固有のパスとモジュールの名前 | 照合する語と、記録と PR の本文の文字列 | 語の照合と読み |

段は、下の「語の照合」と「読み」のどちらで確かめるかを表す。例は、対象を狭めない。

## 語の照合

固有名のうち、語として挙げられるものは、機械で照合する。

照合する語は、次の3つから集める。

- 元のプロジェクトのリポジトリで `git remote get-url origin` が返す URL の、所有者の名前とリポジトリの名前。remote が無ければ、リポジトリの最上位のディレクトリの名前。
- 利用規則が、機密の語として挙げるもの。
- 利用者が、この起動で挙げたもの。

照合は、全ての語と全ての対象のファイルを、次の形の1回の呼び出しで行う。大文字と小文字を区別しない、固定の文字列の照合である。出力は、一致した行の、ファイルの名前と行番号と中身である。

```bash
grep -i -F -n -e <語1> -e <語2> <ファイル1> <ファイル2>
```

- 語ごとに `-e` を1つ付け、対象のファイルを全て後ろへ並べる。語やファイルごとに呼び出しを分けない。`&&`・`;`・パイプでつながない。
- 対象は、外へ出す記録の下書きのファイルと、PR の本文のファイルである。
- PR の本文には、外へ出す記録の全てのパス（置く先の根からの相対）を載せる。記録のファイル名は、このパスとして照合に掛かる。
- 一致は、全て挙げる。語を単語の境界で区切らない。過検出は、安全な側である。
- 一致した箇所は、一般の言い方へ書き換える。書き換えたら、照合し直す。
- 語が、別の語の一部として当たっただけの一致は、書き換えずに残せる。固有名としての出現かどうかは、下の「読み」の段が判断する。残した件数を、結果に書く。
- それ以外の一致は、0件になるまで書き換える。
- 一致が無いとき、`grep` は何も出力せず、終了コード 1 で終わる。誤りではない。

## 語を残してよい場合

固有名として出現した語を残してよいのは、次の2つの場合だけである。

- 利用者が、この会話で、公開の名前だと明示した。
- 利用規則が、その名前を公開のものとして書いている。

AI の知識で「公開のはず」と判断して残さない。どちらにも当たらなければ、書き換える。書き換えられなければ、その記録を外へ出さない。

出典に書く、層の名前・記録の識別子・版の並び（`Project MEM-202611210300-01@1a2b3c4`）は、固有名に数えない。記録を指す決まった形であり、`format.md` が定める。

## 記録と本文のほか

ブランチの名前、コミットのメッセージ、PR の題にも、元のプロジェクトの固有名を書かない。

## 読み

語に載らないものは、読んで確かめる。認証情報、個人の情報、語に挙がっていない固有名が、これに当たる。読むのは、外へ出す記録と、PR の本文である。記録は、front-matter（とくに `title`・`applies-when`・`sources`）と本文の両方を読む。

語の照合で残した一致が、固有名としての出現でないことも、ここで判断する。迷えば、固有名として扱い、書き換える。

読みは、記録を書いた文脈とは別の文脈に委ねる。書いた文脈は、プロジェクトの名前を普通の語として読むので、混入に気づきにくい。別の文脈を作れないときは、確認は終わっていない。同じ文脈の読みで代えない。読みを行った文脈を、結果に書く。

## 結果の書き方

PR の本文に、照合した語の数・一致の件数・残した一致が在ればその件数と根拠・読みの指摘の件数・読みを行った文脈を書く。照合した語と、指摘された文字列は書かない。書くと、確認そのものが混入の経路になる。

下限の対象を含む記述は、一般の言い方へ置き換える。出典は、「いつ、どの環境で実測したか」の形で書けば、プロジェクトの名前を含めずに済む。
