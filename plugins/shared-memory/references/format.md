# 記録の形式

共有の記憶（Shared Memory）の記録・送り出しの下書き・候補・索引・採用の台帳の形と、Task Memory の置き場を定める。検査器（`scripts/memory.mjs`）は、ここに書いた規則を検査する。

## 記憶の根

記憶の根は、次を直下に持つディレクトリである。

| 場所 | 中身 |
|---|---|
| `records/` | 記録。1記録1ファイル。下の階層は読まない |
| `outbox/` | 送り出しの下書き。1件1ファイル。Project Memory の根に置く。無くてもよい。下の階層は読まない。送り出しの報告を `reports/` に置く |
| `candidates/` | 選別の前の候補。1件1ファイル。Global Memory の根に置く。無くてもよい。下の階層は読まない |
| `index.md` | 索引。検査器が生成する |
| `adopted/` | 採用の台帳。1つの記録につき1ファイル。無くてもよい。下の階層は読まない |
| `tasks/` | Task Memory。作業中のブランチにだけ置く。形式は検査しない。無くてもよい |
| `policies/memory-policy.md` | その根の利用規則。無くてもよい。検査器は読まない |

ここに無い名前のものを、根の直下に置いてもよい。検査器は読まない。

根がどこに在るかは、利用先が決める。検査器は、根を引数で受け取る。`records/` を持たないディレクトリは、記憶の根として扱わない。記録がまだ無い根は、空の `records/` を持つ。

記憶は、置き場で層に分かれる。プロジェクトのリポジトリの中に置く根が Project Memory であり、全プロジェクトで共有するリポジトリに置く根が Global Memory である。記録の形式は、どちらの層でも同じである。識別子は層を表さない。

プロジェクトのリポジトリに置くときの既定は、`docs/memory/` である。変えるときは、プロジェクトの指示ファイル（`AGENTS.md`。無ければ `CLAUDE.md`）に置き場を書く。CI が検査器へ渡す引数も、同じ置き場へ合わせる。

根への書き方を定める規則（利用規則）の在りかは、次の順で決める。

1. 根の直下の `policies/memory-policy.md` が在れば、それである。
2. 無ければ、指示ファイルが、その根の規則として述べるか、指すものである。Project Memory では、プロジェクトの指示ファイルの記述が、これに当たる。
3. どちらも無ければ、その根に利用規則は無いものとして扱う。ほかの場所を探さない。

Git は空のディレクトリを追跡しない。空の `records/` を残すには、`.md` で終わらない名前のファイル（`.gitkeep` など）を置く。検査器は、`.md` で終わるファイルだけを読む。

## 記録

記録は Markdown のファイルである。先頭の front-matter に項目を持ち、本文に内容を書く。

```markdown
---
id: MEM-202611141215-01
type: experience
title: 記録の主張を1文で
author: ai
verification: verified
confidence: high
applies-when: この記録が当てはまる条件
sources:
  - 出典
created: 2026-11-14
updated: 2026-11-14
---

本文。何を観測したか、何が言えるか、当てはまらない場合を書く。
```

### 必ず書く項目

| 項目 | 値 |
|---|---|
| `id` | `MEM-<年月日時分の12桁>-<連番2桁>`。時刻は UTC で取る |
| `type` | `knowledge`（知識・事実）、`experience`（作業や検証から得た経験）、`belief`（判断基準）、`decision`（意思決定と理由）、`evolution`（何からなぜ変わったか） |
| `title` | 記録の主張を1文で |
| `author` | `human`、`ai`、`joint`。`belief` では `human` か `ai` に限る。`human` は本人が明示したもの、`ai` は AI が推測したものを表す。人間と AI が話し合って本人が認めた判断基準は、`human` とする |
| `verification` | `verified`、`unverified` |
| `confidence` | `high`、`medium`、`low` |
| `applies-when` | この記録が当てはまる条件 |
| `sources` | 出典を1件以上。作業の記録、文書の URL、別の記録の識別子。同じ根の記録は、識別子だけを書く。別の層の記録は、層の名前（`Project` か `Global`）を識別子の前に置く。別のリポジトリに在る記録は、リポジトリの名前を書かず、層の名前・識別子・版で指す（`Project MEM-202611210300-01@1a2b3c4`） |
| `created` / `updated` | `YYYY-MM-DD` |

### 場合によって書く項目

| 項目 | 書く場合 | 値 |
|---|---|---|
| `sent-as` | この記録を元に、送り出しの下書きを書いたとき | 送り出した下書きの識別子を1件以上 |
| `superseded-by` | 別の記録で置き換えたとき | 置き換えた先の記録の識別子 |
| `moved-to` | 記憶の外へ移したとき | 移した先。lint の規則名、指示ファイルのパスなど |
| `from` | `type` が `evolution` のとき | 置き換えられた記録の識別子を1件以上 |
| `to` | `type` が `evolution` のとき | 置き換えた記録の識別子を1件以上 |

`superseded-by` か `moved-to` を持つ記録を、置き換え済みの記録と呼ぶ。両方を同時には書かない。

`sent-as` は、下書きと同じ変更で書く。主張は変えないので、置き換えにはしない。下書きを取り下げたら、消す変更と同じ変更で、その識別子を外す。指す下書きが `outbox/` に在るかは、検査器は見ない。運んだ後に消してよいためである。

ここに無い項目を足してもよい。検査器は読み飛ばす。項目の名前には、日本語や空白を使ってよい。コロンは使えない。

### ファイル名

`<id>-<名前>.md` とする。名前は、英小文字と数字をハイフンでつないだものにする。

### front-matter の書き方

- 値は1行で書く。`sources`・`sent-as`・`from`・`to` は、項目の次の行から「`- 値`」を並べる。
- 値に「`: `」や「` #`」を含むときは、引用符で囲む。
- 値が次の記号で始まるときも、引用符で囲む。``[ ] { } , # & * ! | > ' " % @ ` ``と、後ろに空白が続く `-`・`?`・`:` である。YAML が別の意味に読むためである。
- 改行は LF でも CRLF でもよい。

## 送り出しの下書きと候補

送り出しの下書きは、Project Memory の記録を一般化し、Global Memory へ送るために書く文書である。Project Memory の根の `outbox/` に置く。候補は、運んだ下書きであり、選別の前のものである。Global Memory の根の `candidates/` に置く。下書きは、手を加えずに候補になる。

形は、記録と同じである。ファイル名も、記録と同じ形にする。ただし、次を持たない。

- `Project` の出典。`sources` の値を、層の名前 `Project` で始めない。Global Memory の記録は、識別子だけで指す。置かれる先の根の記録になるためである
- `superseded-by`・`moved-to`
- `type: evolution`・`from`・`to`

下書きと候補の改行は LF だけにする（記録は CRLF でもよい）。運び済みかを blob の識別子で判定するため、Global 側が改行を正規化すると、CRLF の下書きは運び済みと判定されなくなる。検査器の `draft` の規則が、`\r` を含む下書きと候補を落とす。

識別子は、新しく発番する。元の記録の写しではないためである。識別子の重複は、`records/`・`outbox/`・`candidates/` を合わせて見る。

- 送り出しの報告は、`outbox/reports/<下書きの識別子>.md` に置く。1件の下書きにつき1ファイルである。中身の形は、`outbox-report.md` が定める。検査器は読まず、運ぶコマンドも写さない。
- プロジェクトの既定のブランチの `outbox/` に在ることが、送り出しの承認を表す。承認の後に、下書きを書き換えない。運び済みかを、内容の一致で判定するためである。
- 運ぶ前に誤りが分かったら、下書きを `outbox/` から消して取り下げる。直すときは、新しい識別子の下書きを足す。消す変更が既定のブランチへ入る前に運ばれた下書きは、取り下げられない。
- 運んだ下書きを `outbox/` に残すか消すかは、利用先が決める。
- 候補を `records/` へ移すことが、受け入れである。候補を除くこと・まとめることも、選別で行う。

## 置き換え

記録を別の記録で置き換えるときは、次の3つを同じ変更で行う。

1. 新しい記録を足す。
2. 旧い記録に `superseded-by` を書く。旧い記録は消さない。
3. `evolution` の記録を足す。`from` に旧い記録を、`to` に新しい記録を書く。本文に、何がなぜ変わったかを書く。

記憶の外へ移すときは、旧い記録に `moved-to` を書く。`evolution` は足さない。

## 索引

索引は、記録の front-matter から検査器が生成する。手で編集しない。

- 記録1件につき1行を、識別子の順に並べる。
- 置き換え済みの記録は載せない。
- 1行は、識別子・種類・主張（`title`）・当てはまる条件（`applies-when`）・検証（`verification`）を持つ。
- 候補は、記録の表の後ろの、見出し `## 候補` の表に載せる。列と並べ方は、記録の表と同じである。候補が無い根では、見出しごと出さない。
- 送り出しの下書きは載せない。

## 記録の版

記録の版は、起点の ref でその記録を最後に変えたコミットである。記録の識別子と合わせて、`<識別子>@<コミットの省略形>` と書く。候補の版も、同じく数える。

```
MEM-202611141215-01@a1c5dc1
```

`version` は、起点の `records/` と `candidates/` の直下から、その識別子のファイルを探す。候補で見つけたときは、空白の後に `candidate` を足して出す。

```
MEM-202611141215-01@a1c5dc1 candidate
```

`records/` と `candidates/` を合わせて1件に決まらないときは、版を返さない。両方に在るときも、これに当たる。

版は、検査器の `version` で得る。得る前に、記録が在るリポジトリで、既定のブランチを取り直す。次の `origin` と `main` は、そのリポジトリの remote と既定のブランチの名前に置き換える。名前は、その根の利用規則か、プロジェクトの指示ファイルが名指す。`scripts/memory.mjs` は、このプラグインの根からの相対パスである。

```bash
git fetch --deepen=1000 origin main
node scripts/memory.mjs version <記憶の根> <識別子> --ref FETCH_HEAD
```

- 省略形は7桁である。7桁で一意にならないときは、git が伸ばす。
- 取り直しには `--deepen` を使う。全履歴の clone でも、浅い clone でも通る。`--unshallow` は、全履歴の clone では失敗する。使うなら、先に `git rev-parse --is-shallow-repository` が `true` を返すことを確かめ、`origin main` を付ける。
- 取り直しが失敗したら、版を得ない。検査器が版を返しても、確定した版として扱わない。前に取り直した結果が残っていると、検査器は古い起点から版を返すためである。
- 起点の ref は、`--ref` で指す。取り直した直後の `FETCH_HEAD` か、取り直した枝の remote 追跡の ref（`refs/remotes/origin/main` など）を指す。
- 取り直した枝が `remote.<remote>.fetch` の refspec に含まれていれば、取り直した後は、どちらも同じコミットを指す。含まれていなければ、remote 追跡の ref は作られないか、進まない（`--single-branch` の clone など）。そのときは `FETCH_HEAD` を指す。
- `--ref` を省くと、`refs/remotes/origin/HEAD` を使う。clone のときに git が記録する、remote の既定のブランチである。clone の仕方によっては無い。無いときは、`--ref` で起点を指す。remote 追跡の ref が在れば、`git remote set-head origin main` で作ってもよい。この形は、ネットワークへ出ない。
- 検査器は、起点を最後に取り直した結果（その worktree の `FETCH_HEAD`）と照合する。食い違えば、版を返さずに終了コード 2 で止まり、取り直し方を示す。
  - remote 追跡の ref は、省いたときの既定も含めて、照合する。`FETCH_HEAD` に、同じ枝をその remote の URL から取り直した行が在り、その行のコミットが起点と一致するときだけ通す。行が無いときも止まる。clone しただけで取り直していない checkout と、別の remote から同じ名前の枝を取り直しただけの checkout が、これに当たる。
  - URL は、`git ls-remote --get-url <remote>` が返す URL（insteadOf を解いたもの）と比べる。比べる前に、両方から認証情報と末尾の `/`・`.git` を除く。git は、`FETCH_HEAD` へ書く URL を、この形に整えるためである。
  - 枝が refspec の外なら、`FETCH_HEAD` を起点にするよう案内する。`FETCH_HEAD` が、その remote のその枝を取り直した1行だけを持つときは、「そのまま `--ref FETCH_HEAD` で実行し直せる」と述べる。
  - `refs/remotes/origin/HEAD` が、枝を指すシンボリックな ref でないときは止まり、`git remote set-head` を案内する。
  - `FETCH_HEAD` を起点に渡したときは、枝を取り直した行がちょうど1つのときだけ通す。引数なしの `git fetch` は全ての枝の行を書き、`FETCH_HEAD` がどの枝を指すかが設定に左右されるためである。
  - ローカルのブランチ・タグ・コミットを起点に渡したときは、照合しない。それが既定のブランチを指すことは、渡す側が責任を持つ。`carry` の Project Memory の起点は、これらを受けない（「下書きを運ぶ」）。
- 照合で分かるのは、起点が最後に取り直した結果と食い違わないことまでである。取り直した後に上流が進み、ref と `FETCH_HEAD` が揃って古くなった状態は、ネットワークへ出ずには見分けられない。版を求める直前に取り直すのは、そのためである。
- 起点を解決できなければ、版を返さずに止まる。作業中の HEAD は使わない。マージの前のブランチのコミットを、版にしないためである。
- 履歴が浅い checkout では、版を返さずに止まり、`git fetch --deepen=1000 <remote> <枝>` の形の取り直し方を示す。浅いまま数えると、エラーにならずに誤ったコミットが出るためである。取り直してもまだ浅ければ、深さを増やす。
- 履歴を取り直すのは、呼び出す側である。検査器は、fetch のようにネットワークへ出る git のコマンドを呼ばない。
- 対象の一部を持たない clone（部分 clone）は、この約束の外である。欠けた対象を、git が自分で取りに行くことがある。取得に失敗したときは、終了コード 2 で止まる。
- 名前だけを変えたコミットも、版になる。
- 作業ツリーの記録がその版と内容が違うときは、版を返したうえで、標準エラーへ知らせる。知らせが出たら、その版の記録を読み直す。

提案に引用するときは、層の名前を前に添える。書き方は `Project MEM-202611210300-01@1a2b3c4`、`Global MEM-202611141215-01@a1c5dc1` である。層の名前は、`Project` と `Global` の2語に限る。まだ既定のブランチに無い記録は、版の代わりに「未マージ」と書く。候補は、版の後ろに「（候補）」と添える（`Global MEM-202611141215-01@a1c5dc1（候補）`）。候補は、確かめていない仮説として扱う。事実として引用せず、採用しない。

## 下書きを運ぶ

検査器の `carry` は、Project Memory の起点の `outbox/` の下書きを、Global Memory の作業ツリーの `candidates/` へ写す。

```bash
node scripts/memory.mjs carry <Project Memory の根> <Global Memory の根> [--project-ref <ref>] [--global-ref <ref>]
```

- 起点の決め方は、2つのリポジトリのそれぞれについて、「記録の版」と同じである。`--project-ref` と `--global-ref` を省いたときの既定、取り直した結果との照合、履歴が浅いときの扱い、ネットワークの扱いも同じである。
- ただし、Project Memory の起点は、origin の既定のブランチに限る。この側の remote は、「記録の版」の「置き換える」の対象外で、名前が `origin` でなければならない。別の名前のときは、`git remote rename <名前> origin` で改める（`origin` を同じ URL で足してもよい）。既定のブランチは、`refs/remotes/origin/HEAD` が指す枝である。`--project-ref` に通すのは、次の2つである。その枝の remote 追跡の ref（`refs/remotes/origin/HEAD` を含む）と、その枝を origin から取り直した1行だけを持つ `FETCH_HEAD` である。ほかの起点は、読まずに終了コード 2 で止める。ローカルのブランチ・HEAD・タグ・コミット・ほかの枝の remote 追跡の ref と、ほかの枝か別の URL から取り直した `FETCH_HEAD` が、これに当たる。承認されていない下書きを運ばないためである。
- `refs/remotes/origin/HEAD` が無いか、origin の枝を指すシンボリックな ref でないときは、既定のブランチを決められず、終了コード 2 で止まる。まず `git remote set-head origin -a` を使う。remote に問い合わせて、既定のブランチを設定する。名前が remote か指示ファイルで分かっているときだけ、`git remote set-head origin <既定のブランチ>` で作る。後者は、ネットワークへ出ない。
- この判定は、起点の渡し間違いを防ぐためのものである。ローカルの `refs/remotes/origin/HEAD` を意図して付け替える者は防げない。承認の保証は、プロジェクトのレビューに在る。
- 下書きは、Project Memory の起点のコミットの木の、`outbox/` の直下の `.md` から読む。リンクは読まない。作業ツリーと、作業中のブランチは読まない。承認されていないものを運ばないためである。
- `outbox/` の下の階層は写さない。送り出しの報告は、運ばない。
- 下書きの形式は検査しない。形式は、Project Memory の `check` が既定のブランチで見ており、Global Memory の取り込みの前にも見るためである。

写す前に、下書きごとに、運び済みかを判定する。見るのは、Global Memory の起点から辿れる全てのコミットの、`candidates/` と `records/` の直下の `.md` である。今のツリーだけでは見ない。次を上から当て、最初に当たったものにする。

| 順 | 条件 | 結果 |
|---|---|---|
| 1 | 下書きと同じ内容のファイルが、一度でも在った | `carried` |
| 2 | 名前が `<下書きの識別子>-` で始まり、内容の違うファイルが、一度でも在った | `stopped` |
| 3 | 上のどちらにも当たらない | `copied` か `stopped` |

- 同じ内容かは、git の blob の識別子で比べる。リポジトリをまたいでも、内容が同じなら blob の識別子は同じである。
- 1 は、選別で捨てた候補を、運び直さないためにある。運んだ後に `outbox/` に残っている下書きと、選別で言い回しを直して採った候補の下書きも、これで飛ばす。
- 2 は、別のプロジェクトの記録と識別子が重なったか、承認の後に下書きを書き換えたかである。どちらも、人間が決める。
- 3 では、Global Memory の作業ツリーの `candidates/<下書きのファイル名>` へ、バイトの単位で同じに書く。`candidates/` が無ければ作る。同じパスに同じバイトのファイルが既に在れば、書き直さずに `copied` とする。違うバイトのファイルか、ファイルでないものが在れば、書かずに `stopped` とする。
- 下書きのファイル名から識別子を読めないときも、`stopped` とする。

出力は、下書き1件につき1行である。ファイル名の順に、「`outbox/<ファイル名>:<結果>: 説明`」の形で標準出力へ出す。

```
outbox/MEM-202611221000-01-bom-breaks-header-match.md:copied: candidates/MEM-202611221000-01-bom-breaks-header-match.md へ写した
outbox/MEM-202611221000-02-csv-shift-jis.md:carried: 同じ内容のファイルが Global Memory の履歴に在る: candidates/MEM-202611221000-02-csv-shift-jis.md
outbox/MEM-202611221000-03-cron-in-utc.md:stopped: 同じ識別子で内容の違うファイルが Global Memory の履歴に在る: records/MEM-202611221000-03-cron-evaluated-in-utc.md。別のプロジェクトの記録と識別子が重なったか、承認の後に下書きを書き換えた。人間が決める
```

- 写したファイルを commit し、Global Memory へ入れるのは、呼び出す側である。`carry` は、commit も push もしない。
- `outbox/` が起点に無いか、下書きが0件のときは、何も出さない。

## 採用の台帳

プロジェクトが、別のリポジトリに在る記憶（Global Memory）の記録を設計判断の根拠にしたとき、採用した版を台帳へ残す。台帳は、プロジェクト側の記憶の根の `adopted/` に置く。1つの記録につき、1ファイルである。

```markdown
---
record: MEM-202611141215-01
version: a1c5dc1
decisions:
  - ADR-202611200000-01
adopted: 2026-11-21
---

採用の理由。この記録を、何の判断の根拠にしたかを書く。
```

| 項目 | 値 |
|---|---|
| `record` | 採用した記録の識別子 |
| `version` | 採用した版。`version` の出力の `@` より後ろ。16進の小文字で7桁から64桁 |
| `decisions` | 採用先の決定を1件以上。ADR の識別子、決定を書いた文書のパスなど。「`- 値`」を並べる |
| `adopted` | この版を採用した日。`YYYY-MM-DD` |
| 本文 | 採用の理由。空にしない |

- 上の項目は、すべて必ず書く。ここに無い項目を足してもよい。front-matter の書き方は、記録と同じである。
- ファイル名は `<record>.md` とする。同じ記録の台帳は、1件だけである。採用先の決定が増えたら、`decisions` へ足す。
- 台帳が指せるのは、`records/` の記録だけである。候補は採用しない。`adopted` は、`candidates/` を見ない。
- 記録の本文と表題は写さない。記憶のリポジトリの名前も書かない。
- 記憶の側の変化に追随するときは、`version` と `adopted` を書き換える。前の版は、台帳のファイルの履歴に残る。
- 追随しないと決めたときは、理由を本文へ足す。採用をやめたときは、ファイルを消す。

## 採用した記録の変化

検査器の `adopted` は、台帳の1件ごとに、採用した版と、記憶のリポジトリの起点の ref とを比べる。起点の決め方、取り直した結果との照合、履歴が浅いときの扱い、ネットワークの扱いは、「記録の版」と同じである。結果は、次のどれか1つである。上から順に当て、最初に当たったものにする。

| 順 | 条件 | 結果 |
|---|---|---|
| 1 | 台帳の版を、コミットの識別子の省略形として解決できない | `missing` |
| 2 | 版のコミットが、起点の祖先でない | `missing` |
| 3 | 版のコミットで、その識別子の記録が1件に決まらない | `missing` |
| 4 | 起点で、その識別子の記録が1件に決まらない | `missing` |
| 5 | 起点の記録が `superseded-by` を持つ | `superseded` |
| 6 | 起点の記録が `moved-to` を持つ | `moved` |
| 7 | 版での記録と起点での記録で、ファイルの内容が違う | `changed` |
| 8 | 上のどれにも当たらない | `unchanged` |

- 台帳の版は、コミットの識別子の先頭の桁として読む。同じ綴りの名前のブランチやタグが在っても、それを版にしない。
- あるコミットでの「その識別子の記録」は、`records/` の直下で、名前が `<識別子>-` で始まり `.md` で終わるファイルである。
- 内容は、front-matter を含むファイルの全体で比べる。ファイル名だけが変わった記録は、`unchanged` である。
- 採用した時点で置き換え済みだった記録は、内容が同じでも `superseded` か `moved` になる。
- 起点の記録の front-matter を読めないときは、5 と 6 を飛ばし、説明にその旨を添える。

出力は、台帳の1件につき1行である。ファイル名の順に、「パス:結果: 説明」の形で標準出力へ出す。`unchanged` も出す。

```
adopted/MEM-202611141215-01.md:unchanged: MEM-202611141215-01@a1c5dc1
adopted/MEM-202611151518-01.md:changed: MEM-202611151518-01@a1c5dc1 -> MEM-202611151518-01@9f8e7d6
adopted/MEM-202611160455-01.md:superseded: MEM-202611160455-01@a1c5dc1 -> MEM-202611160455-01@9f8e7d6 superseded-by MEM-202611200000-01
adopted/MEM-202611160455-02.md:moved: MEM-202611160455-02@a1c5dc1 -> MEM-202611160455-02@9f8e7d6 moved-to lint の規則 no-foo
adopted/MEM-202611170000-01.md:missing: MEM-202611170000-01@a1c5dc1 起点に記録が無い
```

- `->` の左は台帳の版、右は起点での版である。`superseded` は置き換えた先を、`moved` は移した先を続ける。置き換えの連鎖は辿らない。
- `changed`・`superseded`・`moved` は、違反ではない。追随するかは、利用先が決める。
- 違反は、`missing` と、台帳の形式の違反である。形式の違反が在る台帳のファイルは、比べずに、違反の行を出す。
- `missing` の説明は、当たった条件を言う。記録が1件に決まらないときは、無いのか、複数在るのかを分ける。
- `missing` は、台帳の誤記か、渡した根の誤りで起きる。記憶のリポジトリの履歴が古く、版のコミットをまだ持たないときにも起きる。
- 台帳は、作業ツリーから読む。記憶のリポジトリは、起点のコミットから読む。作業ツリーは読まない。
- 台帳は、どのリポジトリの記録かを持たない。違うリポジトリを渡すと、全件が `missing` になる。

## Task Memory

Task Memory は、1つのタスクの間だけ持つ覚え書きである。記録ではない。

- 置き場は、根の直下の `tasks/` である。タスクごとに1ファイルを置く。
- ファイル名の既定は、ブランチの名前の `/` を `-` に置き換え、`.md` を付けたものとする。ブランチの名前が取れないときは、タスクを見分けられる名前を付ける。
- 形式は検査しない。確かめていない仮説を書いてよい。索引には載らない。
- 作業中のブランチにだけ置く。既定のブランチへは持ち込まない。レビューへ出す前に、残す価値のあるものを記録などへ取り出し、ファイルを消す。
- ほかのタスクのファイルには書かない。
- 別の文脈や別のセッションが読むものとして書く。追跡していない文書でしか解けない記号や略語に頼らない。
- 既定のブランチへ入るツリーに残っていないことは、`check` に `--no-task-memory` を付けて確かめる。いつ確かめるかは、呼び出す側が決める。
- 残留の検出は、種類を問わず、`tasks/` の直下の全てを見る。別のリポジトリへ送るものは、`tasks/` に置かず、送り出しの下書きとして `outbox/` に置く。

## 検査器が違反とするもの

| 規則 | 違反の内容 |
|---|---|
| `front-matter` | front-matter が無い、閉じていない、項目を読めない、同じ項目を2回書いている |
| `required` | 必ず書く項目が無い。台帳では、`decisions` が0件である、本文が空である、も含む |
| `value` | 値が上の表の範囲に無い。`superseded-by` と `moved-to` を同時に書いている。`belief` の `author` が `joint` である。`sent-as` が0件である、識別子の形でない値を持つ。台帳では、`record`・`version`・`adopted` が形に合わない |
| `filename` | ファイル名が形に合わない。ファイル名の識別子が `id` と一致しない。台帳では、ファイル名が `<record>.md` でない |
| `duplicate-id` | 同じ `id` が、`records/`・`outbox/`・`candidates/` を合わせて2件以上ある |
| `draft` | 下書きか候補が、`Project` の出典・`superseded-by`・`moved-to`・`type: evolution`・`from`・`to` のどれかを持つ |
| `dangling` | `superseded-by`・`from`・`to` が指す記録が無い |
| `evolution` | `evolution` が `from` か `to` を持たない。`evolution` でない記録が `from` か `to` を持つ |
| `replacement` | `superseded-by` を持つ記録に、その置き換えを説明する `evolution` が無い。`evolution` の `from` の記録が、`to` の記録を `superseded-by` で指していない。`superseded-by` を辿ると元の記録へ戻る |
| `index` | 索引が無い。索引が記録と一致しない |
| `task-memory` | `tasks/` の直下に何かが在る。`tasks` がディレクトリでない。`tasks` がリンクのときは、辿らずに、ディレクトリでないものとして扱う。`check` に `--no-task-memory` を付けたときだけ見る |

`front-matter`・`required`・`value`・`filename` は、記録・下書き・候補・台帳に掛かる。`duplicate-id` は、記録・下書き・候補に掛かる。`draft` は、下書きと候補だけに掛かる。`task-memory` は、`tasks` だけに掛かる。ほかの規則は、記録だけに掛かる。下書きと候補の `sources` が Global Memory の記録の識別子を指しても、`dangling` にしない。違反の行のパスは、置き場の名前で始まる。記録は `records/`、下書きは `outbox/`、候補は `candidates/`、台帳は `adopted/`、Task Memory の残留は `tasks` である。

`check` は、根の中のファイルだけから機械で決まる違反を扱う。記録どうしの意味の矛盾や、主張の正しさは扱わない。台帳の版のコミットが在るかも、`check` は見ない。それは `adopted` が見る。

## 検査器の使い方

```bash
node scripts/memory.mjs check <記憶の根>          # 記録・下書き・候補・台帳の形式を検査する
node scripts/memory.mjs check <記憶の根> --no-task-memory  # Task Memory が残っていないことも検査する
node scripts/memory.mjs index <記憶の根>          # 索引を標準出力へ出す
node scripts/memory.mjs index <記憶の根> --write  # 索引を index.md へ書く
node scripts/memory.mjs version <記憶の根> <識別子> [--ref <ref>]                             # 記録の版を出す
node scripts/memory.mjs adopted <プロジェクト側の記憶の根> <Global Memory の根> [--ref <ref>]  # 採用した記録の変化を出す
node scripts/memory.mjs carry <Project Memory の根> <Global Memory の根> [--project-ref <ref>] [--global-ref <ref>]  # 下書きを候補へ写す
```

`--ref` と値は、別々の引数として最後に置く。`carry` の `--project-ref` と `--global-ref` も、それぞれ値と別々の引数とし、根の後ろに置く。どちらを先に置いてもよい。

| コマンド | 0 | 1 | 2 |
|---|---|---|---|
| `check`・`index` | 違反なし | 違反あり | 引数の誤りか、検査できない入力 |
| `version` | 版を返した | 起点で、その識別子の記録と候補が合わせて1件に決まらない | 引数の誤りか、版を決められない状態 |
| `adopted` | `missing` も台帳の違反も無い | `missing` か台帳の違反が在る | 引数の誤りか、検査できない状態 |
| `carry` | `stopped` が無い | `stopped` が在る | 引数の誤りか、判定できない状態 |

`version` が終了コード 1 で終わるとき、標準エラーは、起点にその記録が無いのか、複数在るのかを分けて述べる。

次は、終了コード 2 に当たる。

- 記憶の根でないディレクトリを渡した。
- `check` と `adopted` で、台帳を読む根に `adopted` という名前のものが在り、ディレクトリでない。
- `check` と `index` で、`outbox` か `candidates` という名前のものが在り、ディレクトリでない。
- `version`・`adopted`・`carry` で、git が無い、根が git の作業ツリーの中に無い、履歴が浅い、起点の ref を解決できない。
- `carry` で、Global Memory の作業ツリーの `candidates` がディレクトリでない。

終了コード 2 のときは、標準出力へ何も出さず、理由を標準エラーへ出す。

Node 22 以上で動く。`version`・`adopted`・`carry` は git を要する。`check` と `index` は git を要さない。
