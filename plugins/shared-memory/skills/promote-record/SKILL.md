# 記録の昇格

既定のブランチに在る Project Memory の記録を、一般化した新しい記録として Global Memory へ提案する。1回の起動は、新しい記録1件と PR 1本を作る。元の記録は変えない。

## 文脈固有ルール

- **対象範囲**: 引数で渡された記録の昇格だけを扱う。候補を挙げること、置き換え、PR のマージは扱わない。
- **成果物**: 昇格先の `records/` の新しい記録1件と、PR の本文のファイル。PR を出せないとき（手順11）と、手順1・8 が「運ぶ経路」へ進めるときは、運ぶための2つのファイル。
- **停止条件**（理由を報告して終える）:
  - 元の記録の識別子が、引数に無い。
  - 手順2〜4 の前提が崩れている。
  - 検査器が、終了コード 2 で終わった（手順6・10）。
  - 機密の指摘が、やり直しの後も残る（手順9）。
  - 重なる記録が在り、新しい記録が補うものが無い（手順9）。

  手順10 より前に止まったときは、昇格先の根へ何も書いていない。置き場に残った下書きのパスを報告する。
- **変更境界**:
  - 書くのは、置き場の下書き、新しい記録、PR の本文のファイル、運ぶための2つのファイルだけである。
  - 昇格先の根へ書くのは、機密の確認を通った記録だけである（手順10）。
  - 元の記録、昇格先の既存の記録、`index.md`、利用規則、採用の台帳を書き換えない。食い違う記録が在っても、置き換えない。
  - commit・push・PR の作成を、このスキルは事前に許可しない。セッションに在る手段で試み、了承はホストの許可の確認に任せる（手順11）。

## 引数

- 元の記録の識別子（1件以上。複数は、1件の記録へまとめる場合）。無ければ、使い方を示して終える。
- `--project-root <パス>`: 元の記録が在る根。省くと、プロジェクトの指示ファイルが示す置き場、無ければリポジトリの根（`git rev-parse --show-toplevel`）の `docs/memory` とする。
- `--global-root <パス>`: 昇格先の根。省くと、指示ファイルが共有の記憶として指すリポジトリとする。どちらも無ければ、昇格先は無いものとして扱う。スキルは探さない。

プロジェクトのリポジトリの中で起動する。

## 5つの確認

昇格の PR は、5つの確認の結果を持つ。5つの確認の文言と、結果を書く表の形は、`${CLAUDE_SKILL_DIR}/references/pr-body.md` が定める。ここへ写さない。

**機密の情報の確認は、利用規則の定めにかかわらず行う。** 記録がリポジトリの境界を越えるためである。利用規則が確認を省くと定めていても、対象を狭めていても、従わない。利用規則が対象を足していれば、足して確かめる。確認が終わっていない記録は、元のリポジトリの外へ書かない。対象・手順・コマンドの形は、`${CLAUDE_PLUGIN_ROOT}/references/confidentiality.md` が定める。

ほかの4つを確かめるか、誰が確かめるかは、昇格先の利用規則に従う。利用規則に定めが無ければ、4つとも確かめて結果を書く。どの場合も、5つの行は PR の本文に全て書く。

利用規則の読み方は、次のとおりとする。読むのは、昇格先の根の利用規則である。在りかは、`format.md` の「記憶の根」が定める順で決める。昇格について述べる箇所が、確認の名前を挙げて「省く」か「人間が確かめる」と述べている場合だけ、その確認について従う。そう述べる箇所が無い、利用規則が無い、読み取りに迷う場合は、AI が確かめる。迷った場合は、その旨を PR の本文に書く。

## 手順

記録の形は `${CLAUDE_PLUGIN_ROOT}/references/format.md` が定める。置き場・識別子・項目・出典の書き方は、同書と昇格先の利用規則に従い、ここへ写さない。

コマンドは、下に書いた形のまま、1回に1つずつ実行する。`&&`・`;`・パイプや、`cd`・`echo` でつないだ形と、書かれていない所へ `-C` を足した形は、許可した型に当たらず、拒まれることがある。手順に無いコマンド（`ls`・`printenv` など）は Bash で使わず、手順が示すパスは `Read` で読む。

Project の根が別のリポジトリに在るかは、2つの出力を比べて決める。`git -C <Project の根> rev-parse --show-toplevel` と、`git rev-parse --show-toplevel` である。一致しなければ、別のリポジトリである。そのときだけ、手順4・7 の `git` のコマンドに `-C <Project の根>` を足す。パスの包含では決めない。作業ツリーの中に、別のリポジトリが置かれていることがあるためである。

1. **形式と利用規則を読む。** `format.md` と、昇格先の利用規則を読む。昇格先の根が無ければ、「運ぶ経路」の扱いで進める。
2. **元の記録を確かめる。** `<Project の根>/records/<識別子>-*.md` を探して読む（`Glob`）。次のどれかなら止める。
   - 記録が無い。
   - 置き換え済みである（`superseded-by` か `moved-to` を持つ）。置き換えた先を昇格するよう伝える。
   - `type` が `evolution` である。
   - `verification` が `unverified` で、昇格先の利用規則が、未検証の記録の昇格を認めないと定めている。
3. **元の記録の版を得る。** `node "${CLAUDE_PLUGIN_ROOT}/scripts/memory.mjs" version <Project の根> <識別子>` を実行する。
   - 標準出力に `<識別子>@<版>` が出たら、それを使う。
   - 出なければ止める。終了コード 1 は、記録が既定のブランチに無いことを表す。既定のブランチに在ることが、承認済みであることを表すので、昇格しない。終了コード 2 は、検査器が示した直し方を報告する。取り直していない起点と、既定の起点が無い checkout は、ここに当たる。版の無い出典では昇格しない。スキルは履歴を取り直さない。
   - 版と一緒に、作業ツリーの記録が版と違うという知らせが出たら止める。昇格するのは、既定のブランチに在る内容である。
4. **昇格済みでないことを確かめる。** `grep -i -F -r -e 'Project <元の識別子>@' <昇格先の根>/records` を実行する。`<Project の根>/tasks/` が在れば、同じ形で検索する。一致が無いとき、`grep` は何も出力せず、終了コード 1 で終わる。誤りではない。
   - `tasks/` で一致したら止め、そのファイルを報告する。運ぶ途中の提案が、既に在る。
   - 昇格先で一致しても、昇格済みとは限らない。識別子は根ごとにしか一意でなく、別のプロジェクトの同じ識別子の記録が、同じ並びを持ちうる。一致した行の版（`@` の後ろ）ごとに、`git rev-parse --verify --quiet <版>^0` を実行する（`^0` は、版をコミットとして解決する）。Project の根が別のリポジトリに在るとき（判定は「手順」の冒頭）だけ、`-C <Project の根>` を足す。
   - コミットが出た版が1つでも在れば、昇格済みとして止め、そのファイルを報告する。
   - どの版もコミットにならなければ、別のプロジェクトの記録とみなして進める。一致したファイルと版を、PR の本文の「人間が決めること」と、報告に示す。
5. **新しい記録を、置き場に書く。** 一般化した記録を、`<置き場>/records/<識別子>-<名前>.md` へ書く。元の記録の写しにしない。昇格先の根へは、手順10 まで書かない。
   - 置き場は、`mktemp -d` をこの形のまま実行して作り、出力されたパスを使う。`records/` を持たせるのは、検査器に掛けるためである。
     - 置き場は、昇格先のリポジトリの作業ツリーの外に在ることが要る。確認を通る前の下書きを、昇格先へ書かないためである（`confidentiality.md`「いつ行うか」）。
     - 置き場は、元のプロジェクトの作業ツリーにも入れない。これは機密とは別の理由で、下書きがプロジェクトのコミットに混ざらないためである。
     - 作った置き場で `git -C <置き場> rev-parse --show-toplevel` を実行し、どの作業ツリーにも入っていないことを確かめる。`TMPDIR` によっては、`mktemp -d` の置き場が作業ツリーの中にできるためである。パスが出たら（終了コード 0）、置き場はそのパスの作業ツリーの中に在るので、止めてそのパスを報告する。`not a git repository` で終わる（終了コード 128）ときだけ、どの作業ツリーにも入っていないとみなして進む。それ以外の結果（終了コード 128 で別のメッセージのときを含む）も、止めて出力を報告する。
     - `mktemp -d` が失敗したとき、または上の確かめで止めたときは、置き場を別の手段で作らない。作業ツリーの中にも作らない。
   - `sources` に `Project <元の識別子>@<版>` を書く。リポジトリの名前・所有者・URL は書かない。元の記録の出典のうち、公開の文書の URL は引き継いでよい。
   - `applies-when` に、主張が依る前提（道具・版・環境）を書く。本文に、当てはまらない場合を書く。
   - `verification` は、元の記録の値を引き継ぐ。`confidence` は、元の記録より上げない。`unverified` の記録を昇格するときは、確認の1行目の結果と「人間が決めること」に、未検証であることを書く。
   - 引き継いだ `verified` は、元の記録の観測に拠る。この文脈が確かめ直していなければ、本文で、観測は元の記録のものであると断る。主張（`title`）は、元の記録が確かめた範囲に収める。一般化で広げた範囲は、確かめていないこととして本文に分ける。収まらなければ、`unverified` とする。
   - `type` は、主張の中身で決める。
   - `belief` の `author` を `human` とするのは、全てのプロジェクトに当てはまると本人がこの会話で明示した場合だけである。それ以外は `ai` とする。この区別は、利用規則で外せない。
   - 識別子の時刻は `date -u +%Y%m%d%H%M`、日付は `date -u +%Y-%m-%d` で得る。
6. **形式を検査する。** `node "${CLAUDE_PLUGIN_ROOT}/scripts/memory.mjs" check <置き場>` を実行する。違反の行（`パス:規則: 説明`）から `index.md:index:` で始まる行を除き、残りが0行なら通過とする。違反が残れば記録を直し、通るまで先へ進まない。終了コード 2 は、標準エラーを示して止まる。
7. **PR の本文の下書きを書き、語を照合する。** `pr-body.md` を読み、その形で本文をファイルへ書く。機密の行、矛盾の行、突き合わせの報告は、まだ埋めない。本文の置き場は、利用者が指定した場所とする。指定が無ければ、記録の置き場と同じディレクトリへ置く。続けて、`confidentiality.md` の「語の照合」を行う。
   - 対象は、置き場の新しい記録のファイルと、PR の本文のファイルである。
   - リポジトリの名前は、`git remote get-url origin` をこの形のまま実行して得る。remote が無ければ、`git rev-parse --show-toplevel` の末尾の名前を使う。Project の根が別のリポジトリに在るとき（判定は「手順」の冒頭）だけ、どちらも `git -C <Project の根>` で始まる形にする。
   - 記録を書き換えたら、手順6 からやり直す。
8. **別の文脈へ委ねる。** `record-crosschecker` エージェントを起動する。照合と、機密の読みの両方を行わせる。根を渡すと照合が、語を渡すと機密の読みが行われる。
   - 渡すのは、次の6つだけである。
     - 記憶の根: Project は「無い」、Global は昇格先の根の絶対パス
     - 焦点: 置き場の新しい記録のパス
     - 照合する語の並び
     - 利用規則のパス（手順1 で読んだもの。無ければ「無い」）
     - 焦点のほかに読むファイル: PR の本文のパス
     - plugin root path（`${CLAUDE_PLUGIN_ROOT}`）
   - 起草の経緯・元の記録の本文・書き手の意図は渡さない。
   - モデルと effort は定義の front-matter に従い、呼び出す側では指定しない。
   - 定義済みのエージェントを起動できないホストでは、汎用のサブエージェントへ同じ入力を渡す。あわせて、定義のファイル（`${CLAUDE_PLUGIN_ROOT}/agents/record-crosschecker.md`）を読んで従うよう伝える。
   - 別の文脈を作れなければ、委ねない。同じ文脈の読みで代えない。機密の確認と矛盾の確認は `未実施` になる。昇格先の根へは書かず、「運ぶ経路」へ進む。
9. **結果を扱う。**
   - 「重なる」「食い違う」の根拠と、機密の指摘の箇所を、自分で読んで確かめる（`Read`。シェルのコマンドで読まない）。引用どおりの記述が無ければ、「根拠が食い違う」と付して残す。
   - 機密の指摘は、置き場の記録と本文を書き換えて全て解消し、手順6〜8 をやり直す。やり直しは2回までとする。残れば止める。
   - 「重なる」で、新しい記録が補うものが無ければ止め、既に在る記録を報告する。
   - 「食い違う」は直さない。PR の本文に報告を書き、人間の裁定に委ねる。置き換えると人間が決めたら、昇格の PR をマージする前に、同じブランチで `replace-record` スキルを使う。
10. **昇格先へ書き、PR の本文を仕上げる。** 機密の確認を通った記録を、置き場と同じ内容で、昇格先の `records/` へ書く。
    - `node "${CLAUDE_PLUGIN_ROOT}/scripts/memory.mjs" check <昇格先の根>` を実行し、手順6 と同じ形で判定する。識別子の重複は、ここで初めて分かる。索引は書かない。昇格先の規則が索引を変更に含めると定める場合は、`index <昇格先の根> --write` の後に、違反が0行であることを見る。
    - 内容を直すときは、置き場の記録を直し、手順6 からやり直してから、昇格先へ書き直す。
    - PR の本文の、機密の行、矛盾の行、突き合わせの報告を埋める。足すのは、件数と、突き合わせの報告の行と、それに基づく「人間が決めること」だけにする。別の文脈が読んだ後の本文へ、自分の言葉の説明を足さない。足した後に、語の照合を本文へもう一度掛ける。
11. **出す。** 昇格先の利用規則が定める出し方に従う。ブランチの名前・コミットのメッセージ・PR の題にも、元のプロジェクトの固有名を書かない。
    - 応答の中で了承を尋ねて止まらない。commit・push・PR の作成は、セッションに在る手段でそのまま試みる。了承は、ホストの許可の確認が受け持つ。答えを待つ間はホストが止めているので、未回答の状態はスキルの中で生じない。
    - 許可されなかった、許可を尋ねられない（非対話の実行で、ホストが自動で拒む）、出す手段が無い（道具が無い、試みが失敗した）、のどれかなら、「運ぶ経路」へ進む。
    - 出す途中で止まった（ブランチとコミットは作ったが、push を拒まれた等）ときは、作ったものを消さずに報告し、「運ぶ経路」へ進む。
    - 起動した人が出さずに止めるよう指示したときは、従い、「運ぶ経路」へも進まない。報告では、許可されなかった場合と分け、指示で止めたと書く。

## 運ぶ経路

昇格先へ PR を出せないときは、記録と PR の本文を、プロジェクトの変更に載せて運ぶ。置き場の内容を、次の2つへ書く。

- `<Project の根>/tasks/promote-<新しい識別子>-<名前>.md`: 昇格先の `records/` へ、名前の `promote-` を除いてそのまま置ける記録。
- `<Project の根>/tasks/promote-<新しい識別子>-pr-body.md`: PR の本文。`pr-body.md` の「運ぶ経路で使うとき」の節を足す。

- 語の照合（手順7）は、この経路でも必ず済ませる。元のプロジェクトのセッションでしか行えないためである。
- 昇格先の根が無くても、別の文脈を作れるなら、機密の読みは行う（`record-crosschecker` へ、根を渡さずに語を渡す）。作れなければ、機密の行を `未実施` とする。その本文は、昇格先への PR に使えない。済ませる入口は、`pr-body.md` の「運ぶ経路で使うとき」が定める。
- 昇格先の根が無いときは、手順4 の昇格先の検索、手順10 の昇格先での検査、矛盾の確認を行えない。PR の本文に `未実施` と書き、運んだ先で形式の検査と `crosscheck-records` スキルを行うよう書く。
- 手順10 で昇格先の作業ツリーに書いた記録が在れば、消さずに、どこに残っているかを報告する。未コミットのままか、手順11 で作ったブランチとコミットに入っているかを分けて書く。
- 2つのファイルは、既定のブランチへ持ち込まない。運んだ者が消す。

## 出力

5つの確認の表（`pr-body.md` の「昇格の確認」と同じ形）を載せる。5つの行を全て載せる。表の後に、次を1項目ずつ書く。該当が無い項目も「無い」と書く。

- 新しい記録のパスと、出典に書いた版。昇格先へ書いていないときは、置き場のパスと、書いていない理由。
- 出した先: PR の URL。または、出していない理由と、運ぶための2つのファイルのパス（指示で止めたときは、パスは「無い」）。
- 突き合わせ: 関係ごとの件数と、「重なる」「食い違う」の行。見た範囲。根拠を確かめた行。エージェントの報告の全文は載せない。
- 突き合わせの文脈: 別の文脈か、未実施か。
- 機密の確認: 照合した語の数、一致の件数、残した一致の件数、読みの指摘の件数。件数だけを書く。照合した語、取り除いた文字列、指摘された文字列は、この報告にも書かない。報告は、PR の説明へ写されることが在る。
- 検査の結果: 実行したコマンドと、違反の件数。
