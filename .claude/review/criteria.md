# PR レビューの観点（本リポジトリ固有）

本書は、本リポジトリの差分・PR をレビューするときに AI レビュワーと人間が共通に使う観点を定める。実行時エラー・境界値・セキュリティといった一般的な正しさは各レビュワーの既定の観点に委ね、本書は本リポジトリで欠陥が繰り返し出た型と、機械検査が届かない規範に絞る。規範の本文は各出典が持ち、本書は問いと出典だけを置く。

## 適用の仕方

- 差分が触れた面に当たる節を適用する。どの節にも当たらない差分には、既定の観点だけを使う。
- CI（`scripts/run-tests.sh`）が実資産に掛ける検査の対象は指摘しない。対象はマニフェストの整合と、SKILL.md からの参照切れ・配布元への逆参照である。
- ADR の front-matter・相互参照と日本語の一文長は、CI では実資産を検査しない。前者は Claude Code 経由の commit でだけ走り、後者は手動実行だけなので、指摘の対象に含める。
- 指摘は欠陥そのものを主語に書く。計量（何字一致・何件）を主語にすると、計量だけを潰す表層の修正が返る。
- 振る舞いの断定には `file:line` の根拠を添える。命名からの推測で断定しない。

## 重大度

重大度の名前は各レビュワーの既定（ブロッカー／改善提案、Important／Nit 等）をそのまま使い、本リポジトリでは次の振り分けを既定の較正より優先する。

- 次はマージを妨げる側に置く。正本の写し、変更に追随せず事実と食い違う記述、配布境界の違反、文書の恒久性の違反、新しい規律の自己違反である。
- 判定の入力が特定されていない判定規則と、退行しても赤くならない検査も、マージを妨げる側に置く。
- 理由は、これらが後続の変更で欠陥を連鎖的に生んできたことにある。製品コード向けの既定の較正では、規約違反として軽く扱われやすい。
- 表現の好みと、意味の変わらない語の選び方は、マージを妨げない側に置く。

## 1. 正本と追随

- 同じ規範を2か所以上に書いていないか。写しが要るなら正本への参照に置き換えたか。出典は `docs/development/coding-agent-plugin-design-principles.md` の正本の一意性。
- 件数・列挙・節名・節番号・層の数を書いた文が、変更後も真か。「次の N 件」と列挙の件数が合っているか。
- 概念を改名・廃止・移設したとき、その概念を表す語でリポジトリを全文検索し、取り残しを拾ったか。検査器名・変数名だけで探すと、地の文に埋まった現在形の指示が落ちる。
- 文書・設定を削除するとき、それを唯一の根拠にしていた文書・設定が孤立しないか。
- コメント・検査器の説明文が、変更後の挙動と合っているか。

## 2. 配布境界とホスト

- 配布物（`plugins/` 配下）から、配布元にしかないもの（`docs/`・ADR・`scripts/tests/`・他のプラグイン）を参照していないか。出典は `docs/distribution-boundary.md`。
- `${CLAUDE_PLUGIN_ROOT}`・`${CLAUDE_SKILL_DIR}` を、その変数が展開される面で使っているか。agents/・README・references 同士の参照は機械検査の外にある。
- Claude Code と Codex の片方でしか成り立たない記述・検査になっていないか。出典は `docs/references/cross-host-plugin-conformance.md`。

## 3. スキルとサブエージェントの定義

- description・本文の行数・`references/` への分離が、CLAUDE.md「スキル設計の token 規律」に収まるか。write-doc 以外のスキルは機械検査の外にある。
- `allowed-tools` が最小か。Bash がコマンドの型で絞られているか。`AskUserQuestion` は対話の経路があるときだけ許可しているか。
- サブエージェント定義が `model` と `effort` を明示しているか。出典は `docs/references/subagent-execution-parameters.md`。
- 「自分が書いたものを読み直せ」型の手順を足していないか。逆に、独立検証・コマンド実行による検証ゲート・完了判定での全項目の列挙を、単純化の名目で削っていないか。出典は CLAUDE.md「成果物の分量と作業範囲」。
- 手順が、大きな文書の全文読みや生の検索結果をメインのコンテキストへ載せることを強いていないか。出典は `docs/references/context-budget.md`。
- 探索の手順が、特定の探索ツールが常にある前提に立っていないか。ツールセットごと欠ける実行条件がある。

## 4. 条文と判定規則

- 新しい規律が、それを書いた文書自身に違反していないか。
- 集合の境界（「X のみ」「X を除く」「全て」）を変えるとき、隣接する条文からその集合へ入る経路を全て列挙したか。局所的な修正のたびに隣の節で新しい指摘が出るなら、この型を疑う。
- 判定規則は、判定者や試行が変わっても同じ結論になるか。判定の入力（どのファイルの、どの版の、どの範囲か）が特定されているか。
- 「不変条件」「冪等」のように既定の意味を持つ語を使うとき、仕組みがその語の射程を覆っているか。
- 新しい軸・新語を足す前に、既存の分類で説明し切れないか。既存の図・表と重複する図表を足していないか。
- 存在・件数・因果の断定（「過去に起きた」「N 件ある」）が一次情報と一致するか。

## 5. 検査器とテスト

- 対象を退行させたとき、検査が実際に赤くなるか。負例があるか。
- 変異で検査を確かめるとき、検出の側だけでなく、免除・除外の側（正例が赤へ転じる変異）も対で置いているか。検査が観測する量（集合・下限・行数）を保ったまま中身を変える変異も置いているか。
- 失敗すべき経路（収集の欠落・前提の欠如）が合格として返らないか。環境変数や CI の有無に依存して緑になっていないか。
- 変異検査のような重い検査を CI の門に置いていないか。

## 6. 文書の置き場と恒久性

- `docs/` に工程の記録・一時的な数値・Issue や PR の番号を置いていないか。出典は `docs/references/document-permanence.md`。
- 追跡下の文書が、追跡外（gitignore 対象の `docs/plans/` 等）の内容を根拠にしていないか。
- mermaid の subgraph のタイトルに全角の等号（U+FF1D）を直書きしていないか。図全体が描画されなくなる。

## 7. 転換期間

- PR が、直接コミットで回してよい変更（統治機構の縮小・新方式プラグインの立ち上げ）と、レビュー契約を通す変更（存続配布物の機能変更）のどちらか。両者が1本に混在していないか。縮小の名目で存続配布物の挙動を変えていないか。出典は CLAUDE.md「転換期間中の開発方式」。
- CI が緑であることを、レビュー契約の代わりにしていないか。
- 退役予定の `dev-workflow` へ、新しいスキル・参照・依存を足していないか。廃止済みの ADR を現行の根拠に引いていないか。
- README・marketplace の変更が利用者の手順を変えるとき、影響範囲を列挙しているか。
